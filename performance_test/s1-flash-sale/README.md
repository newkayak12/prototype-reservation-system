# S1 — Flash Sale (오픈런 순간 버스트)

> 정해진 시각에 전원이 동시에 도착한다. 얼마나 빨리 매진되고, 마지막 사람은 언제 답을 받는가.

**상태**: ✅ 측정 완료 (before 70회 / after 70회). 단, [사전 정지 작업](../ENVIRONMENT.md) 이전
데이터라 절대값은 P6Spy 오버헤드를 포함한다. 상대 비교는 유효.

---

## 질문

티켓팅 오픈 순간의 가장 단순한 형태. **좌석 30석, N명이 동시에 1번씩.**

이건 B2C 스톰의 가장 순한 버전이다 — 부하가 한 번에 들어오고 끝난다. 지속되지 않으므로
"무너짐"은 관측되지 않는다. **이 시나리오의 역할은 두 설계의 기저 성능을 재는 것**이고,
나머지 시나리오가 그 위에서 "그런데 지속되면?"을 묻는다.

## 부하 모형

```
executor: per-vu-iterations   (폐쇄형 — 이 시나리오만)
vus: N, iterations: 1
VU 레벨: 100 / 300 / 600 / 1000 / 1500 / 2000 / 3000
레벨마다 좌석 30석 리셋 + 새 restaurantId, 10회 반복 → 중앙값
```

**레벨마다 좌석을 리셋하는 게 핵심.** 좌석을 한 번만 시딩하고 VU를 램프업하면 첫 구간에서
30석이 소진돼 이후 전 구간이 "이미 매진된 좌석에 대한 거절 응답" 측정이 된다. (초기 설계의 결함)

**폐쇄형인 이유**: 오픈런은 실제로 "각자 1번 누르고 결과를 기다리는" 모양이다. 여기서는
폐쇄형이 현실을 더 잘 반영한다. 단 이 모형으로는 붕괴를 볼 수 없고, 그건 S2가 맡는다.

## 지표

| 지표 | 정의 |
|---|---|
| 매진(s) | 버스트 발사 → 마지막 좌석 판매 |
| TPS | 팔린 좌석 / 매진 시간 = **실제 예약 성공 처리율** |
| 해소(s) | 마지막 요청이 성공이든 거절이든 응답을 받기까지 |
| 처리율(req/s) | 전체 요청 / 해소 시간 = 시스템이 소화한 req/s |
| 정착(s) | HTTP 응답 이후 DB 점유 건수가 안정될 때까지 (after의 비동기 지연) |

## 결과

| VU | 처리율 B→A (req/s) | p95(ms) B→A | 해소(s) B→A |
|---:|:--|:--|:--|
| 100 | 150 → 169 | 652 → 50 | 0.67 → 0.59 |
| 600 | **486** → 171 | 1104 → 56 | 1.23 → 3.53 |
| 1500 | **568** → 163 | 2052 → 54 | 2.64 → 9.19 |
| 2000 | **608** → 171 | 2543 → 미측정 | 3.29 → — |
| 3000 | 529 → 170 | 3943 → 38 | 5.68 → 17.69 |

**정합성: 140회 전부 30/30 판매, 오버부킹 0, 중복 0, 5xx 0, timeout 0.**

## 해석

### before가 이긴다 — 그리고 그 이유가 정확히 계산된다

```
해소 5.68s / 3000건 = 임계구간 1.9ms  →  직렬 처리 상한 1/0.0019 = 526 req/s
                                        실측 최대 608 req/s
이 가정으로 예측한 p50 2.85s          →  실측 p50 2.71s
```

**직렬화는 실제로 일어나고 있다. 다만 임계구간이 짧아서 빠를 뿐이다.**
락 키가 하나(`restaurantId:date:startTime`)라 완전 직렬인데도 526 req/s가 나온다.

### 이건 before 아키텍처의 최선의 경우다

단일 슬롯 = 락 키 1개 = 동시에 열린 트랜잭션이 항상 1개. **after의 원자 연산과 파티션 병렬성이
발휘될 여지가 전혀 없는 조건**이다. before가 유리한 판에서 잰 값이라는 걸 명시해야 한다.

### after의 평탄함은 포화가 아니라 설정이다

VU 100→3000에서 169·139·171·166·163·171·170. 상한
`admission-capacity(100) / admission-interval-millis(500)` = 200 req/s.
대기열이 **의도대로 뒷단 부하를 상수로 만든 결과**이고, 동시에 처리량에서 지는 이유다.

### 그래서 이 시나리오가 증명하지 못한 것

- 무너지는가 (부하가 지속되지 않으므로 관측 불가) → **S2**
- 무관한 트래픽은 어떻게 되는가 (배경 트래픽이 없으므로 관측 불가) → **S3**
- 재시도가 붙으면 어떻게 되는가 → **S4**
- 정합성 우위 (양쪽 다 완벽 → 재설계 명분 아님) → **S7**에서 극한 확인

## 재실행 필요성

현재 데이터는 P6Spy 로깅이 켜진 채, Hikari pool 10 기본값으로 측정됐다. 임계구간 1.9ms의
상당 부분이 SQL 로깅일 수 있다. [ENVIRONMENT.md](../ENVIRONMENT.md)의 고정 조건으로 재측정하면
**절대값은 개선되고 상대 관계는 유지될 것**으로 예상 — 예상이 맞는지도 확인 대상이다.

우선순위는 낮다. S2/S3이 먼저다.
