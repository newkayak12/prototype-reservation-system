# S5 — Hotspot Skew

> 총 트래픽을 고정한 채 경합점 수만 바꾸면 처리량이 어떻게 변하는가?

## 왜 이 시나리오가 포폴의 축인가

이게 **B2B와 B2C를 가르는 축**이다.

| 경합점 K | 뜻 | 대응 |
|---:|---|---|
| 100개 | 예약이 여러 지점에 골고루 퍼진다. 락은 서로 독립 | **B2B** |
| 1개 | 굿즈 하나, 콘서트 회차 하나에 전원이 몰린다 | **B2C** |

같은 시스템이 어느 쪽 트래픽을 받느냐에 따라 얼마나 다르게 동작하는지를
하나의 표로 보여준다. "B2B 경험만 있다"는 약점을 정면으로 다루는 실험이다.

## 부하 모형

**총 도착률을 K와 무관하게 고정한다.** 그래야 "부하는 같은데 분산도만 다르다"가 된다.
각 요청은 K개 경합점 중 하나를 균등하게 고른다.

| 항목 | 값 |
|---|---|
| 실행기 | `constant-arrival-rate` (개방형) |
| 총 도착률 | **1,500 req/s 고정** |
| 경합점 레벨 | K = 1 → 5 → 20 → 100 |
| 경합점당 좌석 | **1,000석 고정** (S2/S3와 동일) |
| 지속 | 30초 |
| 반복 | 워밍업 1 + 본 3회 |

경합점당 좌석을 고정하는 게 중요하다. `before`의 임계구간 비용은 잔여 재고에 비례하므로,
락 **하나가 보는** 재고가 레벨마다 같아야 K의 순효과만 남는다.
총 좌석은 K에 비례해 늘어난다(K=100이면 10만 행).

## 설계 판단

### 균등 분배를 쓴다

실제 트래픽은 지프 분포에 가깝다. 하지만 여기서 편향을 주면 "경합점이 K개"라는
전제 자체가 깨지고, K의 효과와 편향의 효과를 분리할 수 없다.
편향의 영향은 별도 실험의 몫이다.

### 비교해야 하는 값은 goodput이 아니라 할당 처리량이다

K 레벨마다 매진 시점이 다르다. 전체 경과 시간으로 나눈 goodput은
매진 후 빠른 실패 구간이 긴 쪽을 부당하게 깎는다.

실제로 첫 구현에서 K=1은 22 req/s, K=20은 53 req/s가 나왔는데,
매진 전 구간만 보면 **62 req/s와 61 req/s로 사실상 같았다.**
goodput만 봤다면 "분산이 2.4배 효과"라는 정반대 결론을 냈을 것이다.

### 발생기 한계를 반드시 함께 낸다

서버 지연이 20초까지 커지면 1,500 req/s를 유지하는 데 30,000 VU가 필요하다.
상한(20,000)에 걸리면 k6가 발사를 포기하고 `dropped_iterations`로 센다.
이때 **실제 제공 부하는 목표보다 낮다.** 이걸 모르고 낮은 처리량을 보면
"서버가 못 버텼다"로 오독한다. 그래서 `제공 req/s` 열을 항상 같이 낸다.
드롭이 완료 요청의 10%를 넘으면 summary.md에 경고 블록이 붙는다.

## 지표

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| **할당 req/s** | 매진 전 구간의 성공/초 | **K끼리 비교할 값** |
| **점당 할당** | 할당 / K | K가 늘어도 유지 → 락이 병목 / 반비례로 하락 → 공유자원이 천장 |
| 제공 req/s | (완료 + 드롭) / 경과 | 목표에 못 미치면 그 레벨은 부하 미달 |
| p50 / p95 | 지연 분포 | |
| timeout / 5xx | 실패 | |
| 오버부킹 | DB 직접 조회 | |

## 가설과 반증 조건

> **H5.** `before`의 락은 `restaurantId` 단위라 경합점이 늘면 병렬로 처리된다.
> 따라서 처리량 ≈ min(K × 단일키상한, 공유자원상한) 이고,
> K에 비례해 오르다가 어느 지점에서 평평해진다.

| | 관측되면 |
|---|---|
| **지지** | 할당 처리량이 K에 거의 비례해 증가 |
| **반증** | K를 늘려도 할당 처리량이 그대로 → 병목이 락이 아니다 |

평평해지는 K가 **이 아키텍처가 요구하는 최소 분산도**다.

## 검증 실측 (probe, 1회, 총 600 req/s, 15초)

하네스 검증용 짧은 런이다. 본 측정 아님.

| K | 할당 req/s | 점당 할당 | 매진 | 제공 req/s | 달성 req/s | p95 | dropped |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | **62** | 62.5 | 16s | 415 | 253 | 14,089ms | 3,518 |
| 20 | **61** | 3.0 | 31s | 296 | 180 | 16,595ms | 3,538 |

### 읽은 것 (잠정)

**락 키를 20개로 흩어도 할당 처리량이 62 → 61 req/s로 그대로다.**
가설 H5의 반증 방향이다. 병목이 `restaurantId` 단위 락 경합이 아니라
**전역 공유 자원**이라는 뜻이 된다.

이 62 req/s는 S2(도착률 200과 800에서 동일하게 62)와 S8(N=1,000에서 17.6ms → 57)이
독립적으로 낸 값과 일치한다. 세 시나리오가 같은 천장을 가리킨다.

> 다만 **양쪽 레벨 모두 드롭이 컸다**(제공 부하가 목표 미달). K=100까지 포함한
> 본 측정에서 확인해야 확정할 수 있다. 지금은 신호이지 결론이 아니다.

## 실행

```bash
cd performance_test/s5-hotspot-skew
./run.sh before
./run.sh after

# 짧은 확인
POINT_LEVELS="1 20" REPEATS=1 WARMUP=0 RATE=600 DURATION=15 ./run.sh probe
```

| 환경변수 | 기본값 | 뜻 |
|---|---:|---|
| `POINT_LEVELS` | `1 5 20 100` | 경합점 레벨 |
| `RATE` | `1500` | 총 도착률 (전 레벨 고정) |
| `DURATION` | `30` | 지속(초) |
| `SEATS_PER_POINT` | `1000` | 경합점당 재고 |

> K=100은 100,000행을 시딩한다. 레벨당 시딩에 시간이 걸린다.

출력: `<label>/summary.md`, `<label>/summary.json`, `<label>/raw/`
