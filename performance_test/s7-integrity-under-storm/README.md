# S7 — Integrity Under Storm (폭풍 속에서 데이터가 깨지는가)

> 이 실험의 목적은 **재설계의 명분이 정합성이 아니라는 걸 확정하는 것**이다.

**우선순위 6.** 싸고(기존 하네스 + 파라미터만 변경) 빠르지만, 결론의 정직성을 위해 반드시 한다.

---

## 질문

극한 경합에서 오버부킹이 발생하는가. **양쪽 다 발생하지 않는다면, "동시성 제어를 위해
재설계했다"는 서사는 성립하지 않는다.**

## 가설 H5 — 정합성은 양쪽 다 문제 없다

S1의 140회(before 70 + after 70) 전부 30/30 판매, 오버부킹 0, 중복 점유 0.
하지만 S1은 좌석이 30석이라 **경합 강도가 100:1(3000 VU / 30석)** 수준이었다.

여기서는 **좌석 1석에 3000 VU = 3000:1**로 경합 강도를 극한까지 올린다.
정합성이 깨진다면 여기서 깨진다.

### 왜 이걸 명시적으로 실험하는가

재설계 프로젝트에서 흔한 함정: "동시성 문제를 해결했다"고 쓰는데 **원래 문제가 없었던** 경우.
그러면 전체 주장이 무너진다.

**자기 가설이 부정되는 지점을 먼저, 스스로 밝히는 게 전체 논증의 신뢰도를 올린다.**
결론은 이렇게 써야 한다:

> before는 정합성을 지킨다. 분산락 + 트랜잭션 조합은 **정확하다.**
> 재설계의 명분은 정합성이 아니라 **부하 하에서의 거동**이다.

### 반증 조건

**어느 한쪽이라도 오버부킹이 1건이라도 나오면 H5는 반증**이고, 그 경우 정합성이 재설계의
명분에 포함된다. (그리고 그건 훨씬 강한 논거가 된다.)

## 부하 모형

### Part A — 극한 경합 (좌석 1석)

```
executor: per-vu-iterations
vus: 3000, iterations: 1
좌석: 1석          ← 3000:1 경합
반복: 30회 (양쪽 각각)
```

**판정: 성공 수 == 1.** 단 1회라도 2 이상이면 오버부킹.

### Part B — 스톰 중 정합성 (개방형)

```
executor: constant-arrival-rate
rate: 1500/s, duration: 60s
좌석: 100석         ← 60초간 지속 경합 + 매진
반복: 10회
```

Part A는 순간 경합, Part B는 **지속 부하 + 자원 포화 상태**에서의 정합성을 본다.
스레드 고갈·커넥션 타임아웃·GC 정지 같은 이상 상태에서 락이 풀리거나 트랜잭션이 잘리는지가
관심사다. Part A보다 이쪽이 현실적으로 더 위험하다.

### 설계 판단

**after는 판정 기준이 다르다.** 점유가 `PENDING` 상태로 생성되므로
`occupied_status = 'OCCUPIED'`로 세면 **판매 좌석이 전부 0으로 집계된다.**
판정 기준은 **`released_at IS NULL`**.

**슬롯 단위로 센다.** 총합만 보면 한 슬롯의 오버부킹이 다른 슬롯의 미판매에 가려진다.

```sql
-- 슬롯 단위 초과: 한 timetable에 유효 점유가 2건 이상인 경우
SELECT COUNT(*) FROM (
  SELECT o.timetable_id
  FROM timetable_occupancy o
  JOIN timetable t ON t.id = o.timetable_id
  WHERE t.restaurant_id = ? AND o.released_at IS NULL
  GROUP BY o.timetable_id HAVING COUNT(*) > 1
) dup;
```

**정착(settle) 대기 후에 검사한다.** after는 비동기라 HTTP 응답 시점에 DB가 아직 최종
상태가 아니다. 응답 직후에 세면 after가 부당하게 유리해 보인다.

## 지표

| 지표 | 판정 |
|---|---|
| **판매 좌석 수 vs 시드 좌석 수** | 초과하면 오버부킹 |
| **슬롯 단위 중복 점유 수** | > 0 이면 오버부킹 |
| 미판매 좌석 수 | > 0 이면 **과소 판매** (기회 손실 — 이것도 결함이다) |
| 성공 응답 수 vs 실제 DB 점유 수 | 불일치하면 응답과 상태가 어긋난 것 |
| 정착 시간 | after의 비동기 지연 — 언제 최종 상태가 되나 |

**"성공 응답 수 vs 실제 DB 점유 수"가 after에서 중요하다.** 사용자에게 성공을 알렸는데 DB에
없으면 그건 오버부킹보다 나쁘다. before는 동기라 구조적으로 불일치가 없다 — **이건 before의
장점으로 기록해야 한다.**

## 판정 기준

| 판정 | 조건 |
|---|---|
| **H5 지지 (예상)** | 양쪽 모두 전 회차 오버부킹 0, 중복 0 |
| **H5 반증** | 어느 한쪽이라도 오버부킹 1건 이상 |
| **과소 판매 결함** | 매진돼야 하는데 미판매 좌석 잔존 |
| **응답/상태 불일치** | 성공 응답 수 ≠ 정착 후 DB 점유 수 |
