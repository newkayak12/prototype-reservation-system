# S2 — 다건 오픈런 (한 사람이 여러 슬롯을 잡는다)

> 정각에 N명이 동시에 **슬롯 3개씩** 예약을 시도한다. 슬롯당 30석, 총 90석.
> **3건을 원했는데 몇 건을 받았는가.**

## S1과 무엇이 다른가

부하 모형은 [S1](../s1-single-booking/README.md)과 **완전히 같다** — 유한 인구,
시각 배리어(CountDownLatch), 커넥션 예열, 동일한 인원 사다리. 두 시나리오를 나란히
읽으려면 인원 축이 같아야 하기 때문이다.

다른 건 하나뿐이다. **한 사람이 3건을 한꺼번에 요구한다.**

그런데 이 하나가 단건에서는 **원리적으로 나타날 수 없는** 실패 모드를 만든다.

## 이 시나리오가 존재하는 이유: 부분 성공

3건 중 2건만 성공하면 시스템은 무엇을 하는가?

사용자에게 이건 예약이 된 것도 아니고 안 된 것도 아니다 —
**"18시 19시는 됐고 20시는 실패"** 다. 저녁 자리를 3개 잡으려던 사람에게
이건 쓸모없는 예약이지만, 재고는 이미 붙잡혀 있다.

그리고 **현재 코드에는 이걸 되돌리는 경로가 없다.**

```kotlin
@DistributedLock(key = "DISTRIBUTED_LOCK:{restaurantId}:{date}:{startTime}", ...)
@Transactional
override fun execute(command: CreateTimeTableOccupancyCommand): Boolean
```

락 키와 트랜잭션 경계가 **슬롯 단위**다. 여러 슬롯에 걸친 경계가 애초에 존재하지 않으므로,
1·2번이 커밋된 뒤 3번이 실패해도 앞의 둘은 그대로 남는다. 보상 트랜잭션도, 홀드-확정
2단계도 없다.

→ **부분 성공자 수와 그들이 점유한 좌석 수가 이 시나리오의 결론이다.**

### 락 획득 순서

부차적으로, 같은 사람이 서로 다른 락 3개를 동시에 요구한다. 단건은 슬롯 하나에 완전
직렬이라 이 상황 자체가 없다. 획득 순서가 고정되어 있지 않으면 교착이 가능한 구조인지
드러난다(현재 코드는 요청마다 독립적으로 락을 잡으므로 한 요청이 락 2개를 동시에 쥐지는
않는다 — 그래서 교착은 예상되지 않지만, 확인하지 않고 넘어갈 항목은 아니다).

## 왜 순차가 아니라 동시(`http.batch`)인가

순차로 쏘면 2번째 요청은 1번째 **응답을 받은 뒤에야** 나간다.
S1에서 그 응답이 최대 27초 걸렸으므로, 슬롯 2·3은 일제 도착이 아니라 27초에 걸쳐
흩어진 완전히 다른 부하가 된다. **그러면 "동시에 몰렸을 때"를 재는 게 아니게 된다.**

`http.batch`로 3건을 한 번에 내보내면 세 슬롯 모두 일제 도착이 유지되고,
같은 사용자가 세 락을 동시에 요구하는 상황도 그대로 재현된다.

## 시딩

`SLOTS=3` — 18:00 / 19:00 / 20:00, 각 30석. 총 90석.
(`_lib/seed.sh`가 슬롯 수를 받도록 확장되어 있다. 단건은 `SLOTS=1`.)

인원 사다리는 S1과 동일: **200 / 1,000 / 3,000 / 8,000 / 10,000**, 각 5회.
근거는 [S1 README](../s1-single-booking/README.md#동시-인원을-이렇게-고른-이유) 참조.

## 재는 것

### 사람 단위 (핵심)

| 지표 | 의미 |
|---|---|
| 3건 전부 | 원하는 걸 온전히 받은 사람 |
| **부분 성공** | 1~2건만 받은 사람 — **되돌릴 수 없는 반쪽 예약** |
| 전부 실패 | 0건. 깨끗한 실패라 오히려 낫다 |
| 부분성공자 점유 좌석 | 반쪽 예약에 묶인 재고 |

### 요청 단위

요청 수 = 인원 × 3. 분류는 S1과 같다.
`접속 불가`(`dial` 실패)와 `무응답`(응답 타임아웃)을 **합치면 안 된다** —
합치면 `max-connections` 벽이 "서버가 느리다"로 둔갑한다.

## 유효성

S1과 동일하게 `fire_skew_ms` / `late_vus`를 k6 threshold로 걸어 자동 판정하고,
제외된 회차 수를 `summary.md`에 남긴다.

## after의 대기열 — 줄이 3개가 된다

after는 예약 앞에 대기열이 있고, 그 키가 **슬롯 단위**다
(`WaitingQueueSlot = restaurantId + date + startTime`). 3슬롯을 잡으려면 줄을 3개 서야 한다.
**이 시나리오가 지적하는 것 — 다건에 걸친 경계가 없다 — 이 대기열에서도 그대로 반복된다.**

진입도 폴링도 `http.batch`로 묶는다. 순차로 돌면 슬롯 1의 대기가 슬롯 2·3의 진입을
늦추면서, 재려는 대상(같은 사람이 세 줄에 동시에 선다)이 사라진다.

단, **입장한 슬롯은 그 자리에서 즉시 예약한다.** 셋을 다 받고 모아 쏘면 안 된다 —
permit은 "지금 예약 중인 사람 수"라는 계약이고 예약을 마쳐야 반납되므로, 다른 줄을
기다리며 쥐고 있으면 회전이 멈춘다. 1차 측정(2026-08-30)이 정확히 그렇게 죽었다:
capacity 150 × 3슬롯이 전부 "기다리는 중인 사람"으로 채워져 1,000명부터 뒷줄 전원이
예산을 소진했다(전부 포기 399~4,930명). 모아 쏘기로 지키려던 "세 락 동시 요구"도
대기열 뒤에서는 성립하지 않는다 — 세 줄의 입장 시각이 이미 다르기 때문이다.
before는 대기열이 없으니 지금도 3건을 batch로 동시에 쏜다.

예산 안에 **일부만 입장하면 입장한 것만 예약한다.** 전부 포기시키면 부분 성공이 과소
집계되고, 안 된 슬롯까지 쏘면 입장 자격 없음 거절이 매진 거절에 섞인다. 대신 못 들어간
슬롯 수를 따로 세서 요청 수가 조용히 줄어드는 일이 없게 한다 — `요청 수` 열은
`인원 × 3 − 미입장`이다.

`전부 포기`와 `일부만 입장`은 **0이어야 정상이다.** 특히 `일부만 입장`은 부분 성공 수치를
직접 흔들기 때문에, 0이 아닌 회차는 원인을 찾기 전까지 결과로 읽으면 안 된다.

시나리오 파일은 before와 after가 같고, `SKIP_QUEUE` 하나로만 갈린다(`run.sh`가 라벨에서 결정).

## 실행

```bash
./run.sh before
./run.sh after                                # 대기열 단계가 자동으로 켜진다
CROWDS="1000" REPEATS=1 WARMUP=0 ./run.sh probe
```

## 잠정 관측 (probe 1회, 1,000명)

정식 결과가 아니다. 하네스 검증용 단발 실행이다.

```
3건 전부 받은 사람 :   1명
부분 성공          :  73명  (좌석 87개 점유)
전부 실패          : 926명
정합성             : 90/90 판매, 오버부킹 0
```

**90석 중 87석(97%)이 반쪽 예약에 묶였다.** 원하는 걸 온전히 받은 사람은 1명뿐이다.
오버부킹 0에 미판매 0이라 정합성 지표는 완벽한데, **아무도 만족하지 못한 상태로 재고가
소진됐다.** 정합성만 보면 놓치는 종류의 실패다.
