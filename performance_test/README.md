# B2C 트래픽 모사 실험

**질문 하나를 위한 실험이다.**

> B2B 저트래픽을 전제로 만들어진 예약 시스템에 **B2C 트래픽**이 들이닥치면
> 사용자는 무엇을 겪는가.

## 부하테스트가 아니라 트래픽 테스트다

이 구분이 설계 전체를 결정한다.

| | 부하테스트 | 이 실험 |
|---|---|---|
| 독립변수 | 부하 레벨을 램프업 | **이벤트 규모** (오픈런에 몇 명 왔나) |
| 묻는 것 | 몇 req/s에서 무너지나 | **그날 그 사람들이 뭘 겪었나** |
| 결과물 | 처리량 천장 | 좌석 획득 / 대기 시간 / 실패 사유 / 정합성 |

평균 처리량은 재지 않는다. B2C 스톰은 평균이 아니라 **모양**이 문제다.

## 왜 예약 도메인에서 일제 도착이 기본값인가

예약은 **오픈 시각이 공표되어 있다.** 다들 그 시각을 알고, 그 시각에 온다.
그래서 일제 도착이 스트레스 테스트가 아니라 **평상시 트래픽 모양**이다.

이게 왜 중요하냐면, 흔히 쓰는 도착률 모델(`constant-arrival-rate`)은
"서로 독립적인 무작위 도착"을 가정하기 때문이다. 정각이 박혀 있는 도메인에는 안 맞는다.
`rate=8000, timeUnit=1s`는 8,000건을 1초에 **균등 배분**한다(125µs 간격) —
일제 도착이 아니라 촘촘한 줄서기다.

그래서 이 실험은 **유한 인구 + 1인 1요청 + 시각 배리어(CountDownLatch)** 로 간다.
자세한 구현은 [`s1-single-booking/README.md`](s1-single-booking/README.md).

## B2B와 B2C가 갈리는 축

| | B2B (설계 전제) | B2C (실제로 올 것) | 재는 시나리오 |
|---|---|---|---|
| 도착 | 하루에 흩어져서 | **공표된 정각에 전원 동시** | **S1** |
| 예약 단위 | 건별 | 한 번에 여러 슬롯 | **S2** |
| 재시도 | 정책적 백오프 | 새로고침 연타 | (미구현) |
| 실패 | SLA 협의 대상 | 그대로 이탈 | — |

## 시나리오

| 폴더 | 질문 | 상태 |
|---|---|---|
| [`s1-single-booking/`](s1-single-booking/) | 정각에 N명이 몰리면 무슨 일이 벌어지나 | ✅ before 측정 완료 |
| [`s2-multi-booking/`](s2-multi-booking/) | 한 사람이 3슬롯을 잡으려 하면 — 2개만 성공하면 어떻게 되나 | ✅ before 측정 완료 |

두 시나리오는 **부하 모형과 인원 사다리가 동일**하다. 다른 건 한 사람이 요구하는
건수뿐이라, 표를 나란히 놓고 읽을 수 있다.

S2가 보려는 건 처리량이 아니라 **부분 성공**이다. 3건 중 2건만 되면 시스템이 뭘 하는가
(롤백? 방치?). 현재 코드는 락과 트랜잭션 경계가 슬롯 단위라 **되돌리는 경로가 없다.**
단건에서는 원리적으로 나타날 수 없는 실패 모드다.

## before에서 확인된 것

**S1 — 대기는 인원에 선형, 정합성은 완벽**

| 동시 | 매진까지 | 마지막 응답 | 접속 불가 | 오버부킹 |
|---:|---:|---:|---:|---:|
| 200 | 0.5s | 0.9s | 0 | 0 |
| 3,000 | 0.5s | 8.4s | 0 | 0 |
| 10,000 | 0.7s | 27.3s | 408 | 0 |

매진 시각은 인원과 **무관하다**(0.5~0.7초). 좌석 30석은 순식간에 나가고,
나머지 9,970명은 "품절입니다"를 듣기 위해 27초를 줄 선다. 임계구간이 약 2.8ms로
수렴하므로 **직렬 처리 상한 ≈ 357 req/s**이고, 이게 락 키 하나당 하드 상한이다.

MySQL CPU 최대 13%. **하드웨어가 놀고 있는데 느리다** — 직렬화가 병목이라
확장으로 해결되지 않는다는 뜻이다.

**S2 — 정합성이 완벽해도 아무도 만족하지 못할 수 있다**

정합성 지표(오버부킹 0, 미판매 0)는 S1과 똑같이 깨끗한데, 재고 대부분이
**되돌릴 수 없는 반쪽 예약**에 묶인다. 정합성만 보면 놓치는 종류의 실패다.

→ **재설계의 명분은 정합성이 아니라 대기 시간과 예약 단위다.**
이걸 먼저 밝히고 들어가는 게 주장의 신뢰도를 올린다.

## 두 층위만 관측한다

| 층위 | 지표 | 출처 |
|---|---|---|
| 클라이언트 | 좌석 획득, 대기 분포, 실패 사유별 분류, 발사 스큐 | k6 |
| 데이터 | 오버부킹, 미판매, 정착 시간 | MySQL 직접 조회 |

**서버 내부 지표(Actuator의 Tomcat 스레드·힙·커넥션 풀)는 관측하지 않는다.**
이 실험이 답하려는 건 "사용자가 뭘 겪는가"이고, 내부 지표는 그 답이 아니라 원인 해설이라
결론을 바꾸지 못한다. 다만 **인프라가 병목이 아니었다는 증거**는 필요하므로,
`_lib/infra-sample.sh`가 부하 중 컨테이너 CPU·DB 스레드·호스트 부하·TIME_WAIT을
1초 간격으로 기록한다.

## 유효성 판정이 결과보다 먼저다

동시 도착이 이 실험의 **전제**다. 발사가 번진 회차는 결과가 아니라 폐기 대상이다.
`fire_skew_ms`를 k6 threshold로 걸어 자동 판정하고, 제외된 회차 수를 `summary.md`에
반드시 남긴다. 조용히 버리면 "5회 측정"이라 써놓고 실제로는 2회인 상황이 된다.

## 폴더 구조

```
performance_test/
├── README.md          ← 이 문서
├── ENVIRONMENT.md     ← 측정 환경 + 고정 기동 인자 + 사전 점검
├── _lib/              ← 공용 시딩 / 유저풀 / 정합성 / 인프라샘플링 / preflight
└── s*-*/
    ├── README.md      ← 시나리오 설계 (질문·부하모형·인원 근거·판정 기준)
    ├── scenario.js    ← k6
    ├── run.sh         ← 러너
    ├── aggregate.py   ← 집계 → summary.md / summary.json
    └── before/        ← summary.md, summary.json, raw/
```

## 실행

```bash
# 0. 사전 점검 (컨테이너 생존, 8081의 앱이 before 빌드인지, 동시 실행 중인 k6 없는지)
./performance_test/_lib/preflight.sh before

# 1. 측정
./performance_test/s1-single-booking/run.sh before

# 빠른 확인
CROWDS="1000" REPEATS=1 WARMUP=0 ./performance_test/s1-single-booking/run.sh probe
```

> ⚠️ **두 측정을 동시에 돌리지 않는다.** 같은 MySQL 픽스처·Redis·8081 포트를 공유하므로
> 조용히 결과가 오염된다. `preflight.sh`가 다른 k6 프로세스를 검사해 막는다.
