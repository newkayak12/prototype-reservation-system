# S6 — Sustained Storm (폭풍이 끝나면 회복하는가)

> 스파이크를 한 번 견디는 것과, 스파이크가 반복되는 하루를 버티는 것은 다른 문제다.

**우선순위 5.** S2가 "언제 무너지나"라면 이건 "무너진 다음 어떻게 되나"다.

---

## 질문

두 가지를 본다.

1. **지속(sustained)**: 용량 근처 부하를 10분간 유지하면 성능이 유지되는가, 서서히 나빠지는가.
2. **웨이브(waves)**: 스파이크가 반복되면 웨이브마다 같은 성능이 나오는가, 갈수록 나빠지는가.

B2C 서비스는 판매 회차마다, 신상품마다 스파이크를 반복해서 맞는다.
**첫 웨이브를 견뎌도 세 번째 웨이브에서 죽으면 그건 견딘 게 아니다.**

## 가설 H2 (연장) — 잔여 부하 누적

### 메커니즘

before는 부하 차단이 없고 태스크 큐가 무제한이다(F3). 웨이브가 끝나도 **큐에 남은 요청이
계속 처리 중**이다. 휴지 기간이 잔여 큐를 비우기에 충분하지 않으면 다음 웨이브는
**이미 밀린 상태에서 시작**한다.

```
웨이브 1 끝 → 잔여 큐 Q1 → 휴지 60s 동안 일부 소진 → 웨이브 2는 Q1' 위에서 시작
                                                     → 잔여 Q2 > Q1 → 단조 증가
```

after는 웨이브마다 대기열이 정원까지만 차고 초과분은 즉시 거절되므로 **잔여가 웨이브 간에
이월되지 않는다.**

지속 부하에서는 추가로 확인할 것: 커넥션 누수, heap 증가 추세, GC pause 증가.
**"10분 후에도 1분째와 같은가"** 가 질문이다.

### 예측

**Part A — 지속 부하 (10분)**

| | before | after |
|---|---|---|
| 처리량 추세 | 초반 유지 후 하락? | 평탄 |
| p99 추세 | **우상향(누적)** | 평탄 |
| heap / GC pause | 상승? | 안정 |

**Part B — 반복 웨이브 (5회)**

| 웨이브 | before p95 | after p95 |
|---:|---|---|
| 1 | 기준 | 기준 |
| 3 | 기준의 1.5~2배? | 기준 |
| 5 | **기준의 3배 이상?** | 기준 |

### 반증 조건

**웨이브 5의 성능이 웨이브 1과 같고, 10분 지속에서 p99가 평탄하면 H2 연장은 반증이다.**
그 경우 before는 회복력이 있는 것이며, "누적되어 무너진다"를 쓸 수 없다.

## 부하 모형

### Part A — 지속

```
executor: constant-arrival-rate
rate: 각 아키텍처 knee의 80% (S2 결과에서 결정)
duration: 600s (10분)
좌석: 넉넉히 (500,000석 — 10분간 매진되지 않아야 함)
```

**knee의 80%로 잡는 이유**: 100%면 이미 불안정해서 "지속 가능성"이 아니라 "붕괴 속도"를 재게
된다. 80%는 "정상 운영 범위의 상단"이고, 여기서 나빠진다면 그게 진짜 문제다.

**아키텍처마다 다른 도착률을 쓰는 게 공정한가**: 이 실험의 질문은 "누가 빠른가"가 아니라
"자기 용량의 80%를 오래 버티는가"이므로 각자의 knee 기준이 맞다. 절대 처리량 비교는 S2가 한다.

### Part B — 웨이브

```
스파이크 1500 req/s × 30초  →  휴지 60초   ×5회   (총 450초)
좌석: 웨이브마다 리셋하지 않음 (잔여 누적을 보는 게 목적)
```

**웨이브 사이에 좌석을 리셋하지 않는 게 중요하다.** 리셋하면 시스템 상태가 초기화돼서
"누적"을 볼 수 없다. 대신 좌석을 넉넉히 두어 매진으로 인한 왜곡을 막는다.

## 지표

### Part A

| 지표 | 판정 |
|---|---|
| 처리량 60초 버킷 시계열 | 하락 추세 있나 |
| **p99 60초 버킷 시계열** | 우상향이면 누적 확정 |

### Part B

| 지표 | 판정 |
|---|---|
| **웨이브별 p50/p95/p99** | 웨이브 번호에 따라 악화되나 |
| 웨이브별 완료율 | 갈수록 떨어지나 |
| **휴지 구간 잔여 처리량** | 휴지 중에도 서버가 일하고 있으면 = 잔여 큐 존재 |

**"휴지 구간 잔여 처리량"이 이 실험의 결정적 증거다.** 부하를 껐는데 서버가 계속 응답을
내보내고 있다면, 그건 큐에 밀린 요청이 있다는 직접 증거다.

## 판정 기준

| 판정 | 조건 |
|---|---|
| **누적 확정** | 웨이브 5 p95 ≥ 웨이브 1 p95 × 2, 또는 휴지 구간 잔여 처리량 > 0 |
| **반증** | 웨이브 5 ≈ 웨이브 1, 휴지 구간 잔여 0 |
| **지속 열화** | 10분 p99가 1분 p99의 2배 이상 |
| **자원 누수** | heap 또는 hikari active가 단조 증가 |

## 선행 조건

**S2 완료 필수** — Part A 도착률(knee의 80%)을 S2 결과에서 가져온다.

## 실행

```bash
../_lib/preflight.sh before
PART=sustained RATE=<S2 knee × 0.8> ./run.sh before
PART=waves ./run.sh before
```

Part A 반복 2회 (런당 10분), Part B 반복 3회 (런당 7.5분).
