# S2 — Arrival Storm

> 도착률을 올릴수록 처리량은 어디까지 따라오고, 어디서부터 무너지는가?

## 왜 이 시나리오가 필요한가

S1(flash sale)은 **폐쇄형** 부하였다. VU 3,000명이 각자 한 번씩 요청하고 끝난다.
폐쇄형에는 치명적인 맹점이 있다 — **서버가 느려지면 부하도 같이 줄어든다.**
VU는 응답을 받아야 다음 요청을 보내므로, 서버가 버벅이면 발생기가 알아서 속도를 늦춰준다.

실제 B2C 트래픽은 서버 사정을 봐주지 않는다. 굿즈 드롭 시각이 되면 사람들은
서버가 느리든 말든 계속 누른다. 그래서 **개방형**(constant-arrival-rate)으로
"초당 R건을 서버 상태와 무관하게 밀어넣는" 부하를 만든다.
개방형에서만 큐가 쌓이는 모습과 붕괴가 관측된다.

## 부하 모형

한 번의 실행 = 사다리 한 칸(고정 도착률 R로 30초). 칸마다 재시딩하므로 각 칸은 독립이다.

| 항목 | 값 |
|---|---|
| 실행기 | `constant-arrival-rate` (개방형) |
| 도착률 사다리 | 100 → 200 → 400 → 800 → 1600 → 3200 req/s |
| 칸당 지속 | 30초 |
| 경합점 | **1개** (단일 분산락 키) |
| 좌석(재고) | **1,000석 고정** |
| 클라이언트 타임아웃 | 30초 |
| 반복 | 워밍업 1 + 본 3회, 중앙값 |

램프 하나로 이어붙이지 않는 이유: 앞 칸에서 소진된 재고와 쌓인 대기열이 뒤 칸으로 새기 때문이다.

## 설계 판단

### 좌석 1,000석 — 왜 이 숫자인가

`before`의 `findBookableTimeTable` 쿼리에는 **`LIMIT`이 없다.** 좌석 하나를 잡으려고
남은 좌석을 **전부** 엔티티로 로딩하고, 그게 분산락 임계구간 **안에서** 일어난다.
즉 임계구간 비용이 잔여 재고 N에 비례한다.

좌석 수만 바꿔 실측했다 (목표 200 req/s, 10초):

| 좌석 | 달성 req/s | 할당 req/s | p95 | 결과 |
|---:|---:|---:|---:|---|
| 100 | 200 (100%) | 10 | 723ms | 즉시 매진 |
| 1,000 | 91 (46%) | 61 | 9,393ms | 매진 |
| 3,000 | 31 (16%) | 26 | 28,797ms | 미매진 |

- **100석**은 즉시 매진돼 사다리 전체가 "빠른 실패 경로 처리량"만 재게 된다.
- **3,000석 이상**은 재고 비용이 지배해서, 아키텍처가 아니라 **그 쿼리 하나**를 재게 된다.
- **1,000석**은 그 사이 지점이라 락 전략의 차이가 드러난다.

1,000석에서의 임계구간은 서로 다른 세 시나리오가 독립적으로 같은 값을 냈다.

| 출처 | 방법 | 임계구간 |
|---|---|---:|
| S2 | 개방형, 할당 처리량 62 req/s의 역수 | 16.1ms |
| S5 | 개방형 K=1, 할당 62 req/s의 역수 | 16.1ms |
| S8 | 폐쇄형 버스트, 매진시간 / 판매수 | 17.6ms |

재고 민감도의 정확한 기울기는 S8의 전체 스윕이 잰다.
S2는 재고를 **고정**해 도착률의 순효과만 본다.

### 매진은 회피하지 않는다 — 대신 국면을 나눈다

굿즈 드롭은 원래 매진된다. 문제는 매진 전후가 **완전히 다른 코드 경로**라는 것이다.

| 국면 | 동작 | 비용 |
|---|---|---|
| 매진 전 | 락 획득 → 잔여 좌석 전부 읽기 → 쓰기 | 비싸다 |
| 매진 후 | 락 획득 → 읽을 게 없음 → 즉시 실패 | 싸다 |

이 둘을 하나의 "처리량"으로 뭉치면 **거짓말이 된다.**
실측에서 좌석 100석·목표 200 req/s일 때 달성은 200 req/s(도달률 100%)였지만,
실제로 좌석을 받은 사람은 **초당 10명**뿐이었다. 나머지는 전부 "품절"을 빠르게 받은 것이다.

그래서 1초 버킷 태그를 달아 두 처리량을 분리해 낸다.

## 지표

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| **할당 req/s** | 매진 전 구간의 성공/초 | **진짜 처리량.** 사용자에게 의미 있는 유일한 값 |
| **거절 req/s** | 매진 후 구간의 요청/초 | 재고 없을 때 부하를 털어내는 속도. 높다고 좋은 게 아니다 |
| 달성 req/s | 전체 응답/초 | 위 둘이 섞인 값. 매진이 빠를수록 부풀려진다 |
| 도달률 | 달성 / 목표 | 90% 아래로 떨어지는 칸이 **무릎**(포화 시작) |
| dropped | k6가 VU를 못 구해 발사 못한 수 | 0이 아니면 실제 제공 부하가 목표보다 낮다 |
| p95 (매진 전/후) | 국면별 지연 | 매진 전 p95가 진짜 사용자 경험 |
| timeout / 5xx | 실패 | 실패율 5% 초과 = **붕괴점** |
| 오버부킹 | DB 직접 조회 | 느려지는 것과 틀리는 것은 다른 문제다 |

**초 단위 시계열**이 이 시나리오의 핵심 산출물이다. 성공이 끊기는 순간이 매진이고,
그 뒤로 요청 수가 뛰면 빠른 실패 경로로 전환된 것이다.

## 가설과 반증 조건

> **H2.** 도착률을 올려도 할당 처리량은 오르지 않는다. 분산락이 완전 직렬이므로
> 처리량 천장은 임계구간의 역수로 고정되어 있고, 초과 부하는 처리량이 아니라
> **지연**으로만 나타난다.

| | 관측되면 |
|---|---|
| **지지** | 할당 req/s가 사다리 전 칸에서 평평하고, p95만 도착률에 따라 증가 |
| **반증** | 할당 req/s가 도착률에 따라 증가 → 락이 병목이 아니다 |

> **H2b.** 붕괴는 실패가 아니라 지연의 형태로 온다. 요청은 큐에 쌓일 뿐 거절되지 않으므로,
> 클라이언트 타임아웃이 걸리기 전까지 5xx는 나오지 않는다.

| | 관측되면 |
|---|---|
| **지지** | timeout/5xx가 0인 채로 p95만 클라이언트 타임아웃까지 상승 |
| **반증** | 5xx가 발생 → 서버가 능동적으로 부하를 거절하고 있다 |

## 검증 실측 (probe, 10초 × 1회, 좌석 1,000)

하네스 검증용 짧은 런이다. 본 측정 아님.

| 목표 req/s | 할당 req/s | 매진 | 거절 req/s | 달성 req/s | 도달률 | p95 매진전 | timeout | 5xx | 오버부킹 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 200 | 62 | 미매진 | — | 96 | 48% | 8,855ms | 0 | 0 | 0 |
| 800 | 62 | 16s | 660 | 237 | 30% | 14,637ms | 0 | 0 | 0 |

목표 200 req/s 시계열 (요청 / 성공 / p95):

```
t=0   59 / 59 /   660ms
t=4   62 / 62 / 3,421ms
t=8   67 / 67 / 6,133ms
t=14  76 / 76 / 8,855ms
t=15 521 /  2 / 8,739ms   ← 매진, 빠른 실패 경로로 전환
```

**목표를 200 → 800 req/s로 4배 올렸는데 할당 처리량은 62 req/s로 동일하다.**
늘어난 건 지연뿐이다 (8.9초 → 14.7초). timeout과 5xx는 양쪽 다 0 —
**이 시스템은 죽지 않는다. 큐에 쌓일 뿐이다.** 그리고 오버부킹은 없다.
느려지는 것과 틀리는 것은 다른 문제이고, `before`는 전자만 겪는다.

## 실행

```bash
cd performance_test/s2-arrival-storm
./run.sh before          # 전체 사다리
./run.sh after

# 짧은 확인
RATES="200 800" REPEATS=1 WARMUP=0 DURATION=10 ./run.sh probe
```

| 환경변수 | 기본값 | 뜻 |
|---|---:|---|
| `RATES` | `100 200 400 800 1600 3200` | 도착률 사다리 |
| `DURATION` | `30` | 칸당 지속(초) |
