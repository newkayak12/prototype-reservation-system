# S8 — Inventory Scale (재고가 많을수록 느려지는가)

> B2B: 식당 좌석 30개. B2C: 한정판 굿즈 10만 개.
> **재고 규모가 커지면 요청 하나의 비용이 어떻게 변하는가.**

**우선순위 2 (S3과 공동).** 코드 리뷰에서 발견한 구조적 결함을 정량화하는 실험.
다른 모든 시나리오의 좌석 수 설계를 좌우하므로 **먼저 돌려야 한다.**

---

## 발견

```kotlin
// TimeTableJpaRepository.kt:11-24 — LIMIT이 없다
SELECT timetable FROM TimeTableEntity timetable
WHERE timetable.restaurantId = :restaurantId
  AND timetable.date = :date
  AND timetable.startTime = :startTime
  AND timetable.tableStatus = 'EMPTY'
  AND timetable.timeTableConfirmStatus = 'NOT_CONFIRMED'
  AND NOT EXISTS (... occupiedStatus = 'OCCUPIED')
```

```kotlin
// CreateTimeTableOccupancyService.kt
val list = loadBookableTimeTables(command)      // ← 남은 좌석 전부를 엔티티로 로딩
acquireSemaphore(key, list.size)
val domainEvent = saveOccupancy(command.userId, list)
  // saveOccupancy: timeTables.sortedBy { it.id } 후 첫 성공 건만 사용
```

**좌석 하나를 잡으려고 남은 좌석 전부를 로딩하고 정렬한다.**
게다가 이 전부가 **분산락 임계구간 안에서** 일어난다 — 직렬 처리되는 구간이 재고에 비례해 길어진다.

## 질문

잔여 재고 N이 커질 때 **임계구간 길이와 직렬 처리 상한이 어떻게 변하는가.**

S1에서 계산된 값(임계구간 1.9ms, 상한 526 req/s)은 **좌석 30석 조건의 값**이다.
재고가 10배, 100배가 되면 이 숫자가 어떻게 되는가.

## 가설 H6 — 처리 상한이 재고에 반비례한다

```
임계구간 T(N) ≈ 고정비용 + 행당비용 × N
직렬 처리 상한 = 1 / T(N)              ← N이 커지면 감소
```

### 예측

| 좌석 N | 임계구간 예측 | 직렬 상한 예측 |
|---:|---:|---:|
| 10 | ~1.8 ms | ~550 req/s |
| 100 | ~2.5 ms | ~400 req/s |
| 1,000 | ~8 ms | ~125 req/s |
| 10,000 | ~60 ms | **~17 req/s** |

숫자는 행당 하이드레이션 비용을 6μs로 가정한 러프 추정. **관심사는 절대값이 아니라 기울기**다.

**after는 영향을 받지 않아야 한다.** 요청 경로에서 이 쿼리를 돌지 않고, 원자 연산으로 재고를
차감하기 때문. 재고가 커질수록 **after가 유리해지는 교차점**이 존재해야 한다.

### 반증 조건

**임계구간이 N에 무관하게 일정하면 H6은 반증**이다 (JPA 캐시나 DB 최적화가 흡수하는 경우).
그 경우 재고 규모는 설계 변수에서 제외한다.

## 부하 모형

```
executor: per-vu-iterations   (폐쇄형 — 임계구간 측정이 목적이라 단순하게)
vus: 1000, iterations: 1
좌석 N: 10 / 100 / 1,000 / 10,000 / 50,000
경합점: 1개 (직렬 상한을 직접 재기 위해)
반복: 5회
```

**폐쇄형을 쓰는 이유**: 이 실험은 "무너지는가"가 아니라 **"임계구간이 얼마인가"** 를 잰다.
`해소 시간 / 처리 건수`로 임계구간을 역산하는 게 목적이므로 폐쇄형이 더 깨끗하다.

**VU 1000 고정**: N을 유일한 변수로 두기 위해. VU가 N보다 작으면 매진이 안 나서 전원이
성공 경로를 타고, 이게 임계구간 측정에 딱 맞다. (N ≥ 1000 구간에서는 전원 성공)

**주의**: N < VU 인 구간(N=10, 100)은 매진이 발생해 일부가 sold-out 경로를 탄다.
이 구간은 **성공 경로 요청만** 골라 임계구간을 계산한다.

## 지표

| 지표 | 계산 |
|---|---|
| **임계구간 T(N)** | 해소 시간 / 성공 처리 건수 |
| **직렬 처리 상한** | 1 / T(N) |
| p50 / p95 / p99 | N에 따른 지연 분포 변화 |

**heap과 GC를 보는 게 중요하다.** 동시 요청 200개 × 각 10,000 엔티티 = 200만 엔티티가
동시에 heap에 뜬다. OOM 또는 GC 정지가 관측되면 그건 처리량 문제를 넘어선 **가용성 문제**다.

## 판정 기준

| 판정 | 조건 |
|---|---|
| **H6 지지** | T(N)이 N에 대해 단조 증가, N=10 대비 N=10,000에서 5배 이상 |
| **H6 반증** | T(N)이 N에 무관하게 일정 (±20% 이내) |
| **가용성 결함** | N=10,000 이상에서 OOM, GC 정지 > 1s, 또는 5xx 발생 |
| **교차점** | before 직렬 상한이 after 상한(200 req/s) 아래로 내려가는 최소 N |

## 이 실험이 다른 시나리오에 미치는 영향

**S2·S3·S5·S6의 좌석 수 설계가 이 결과에 의존한다.**

원래 계획은 "매진되지 않도록 10만 석 시딩"이었으나, H6이 맞다면 그 조건에서는 **락 경합이
아니라 재고 하이드레이션을 측정하게 된다.** 두 효과가 분리되지 않는다.

→ S8 결과를 보고 **"임계구간이 실용적으로 일정한 N의 상한"** 을 정하고, 다른 시나리오는
그 이하의 좌석 수로 고정한다. 재고가 부족해 매진되는 문제는 **경합점 수를 늘려** 해결한다.

## 포폴에서의 의미

이건 아키텍처 비교와 독립적인, **설계 가정의 문제**다.

> 좌석 30개짜리 식당을 전제로 짜인 쿼리다. 그 전제에서는 완벽히 합리적이다 —
> 30행 로딩은 공짜고, 도메인 서비스에 엔티티 리스트를 넘기는 게 코드도 깔끔하다.
> **B2B 도메인에서는 옳은 코드였다.**
>
> 같은 코드가 재고 10만 개짜리 굿즈 판매에 놓이면 요청 하나가 10만 행을 로딩한다.
> 아키텍처를 바꾸기 전에, **어떤 가정이 깨졌는지**를 먼저 짚어야 한다.
