# S3 — Blast Radius

> 식당 하나에 트래픽이 몰릴 때, 그 식당과 아무 상관 없는 조회 트래픽까지 같이 죽는가?

## 왜 이 시나리오가 가장 중요한가

S2는 "그 상품이 늦게 팔린다"로 끝난다. 나쁘지만 국지적이다.
폭발 반경이 넓으면 이야기가 달라진다 — **굿즈 하나 때문에 사이트 전체가 죽는다.**

B2B에서는 이 차이가 잘 안 드러난다. 트래픽이 여러 고객사에 분산돼 있어
한 곳이 몰려도 다른 곳을 밀어낼 만큼은 아니다.
B2C에서는 정확히 반대다. 트래픽이 한 점에 몰리는 게 정상이고,
그때 나머지 서비스가 버티느냐가 아키텍처의 값어치다.

## 메커니즘 가설

`before`의 예약은 분산락 대기(최대 2분)를 **Tomcat 워커 스레드를 점유한 채로** 한다.
워커는 200개고 큐는 전 엔드포인트 공용이다.

```
핫슬롯 요청 1,500/s ──┐
                      ├─→ [Tomcat 워커 풀 200] ─→ 요청이 워커를 물고 락을 기다림
배경 조회      50/s ──┘         ↑
                          워커가 없어서 큐에서 대기 (head-of-line blocking)
```

락과 아무 상관 없는 GET조차 큐에서 순서를 기다리게 된다.

## 부하 모형

두 시나리오가 **동시에** 돈다.

| | 대상 | 도착률 | 구간 | 역할 |
|---|---|---:|---|---|
| `background` | `K6_BG` 식당 **GET** | 50 req/s | 0~120초 내내 | 피해자. 락을 전혀 안 탄다 |
| `hotspot` | `K6_HOT_0001` 예약 **POST** | 사다리 | 30초부터 60초간 | 가해자 |

| 항목 | 값 |
|---|---|
| 핫스팟 사다리 | **0**(대조군) → 400 → 1500 → 3000 req/s |
| 핫슬롯 좌석 | 1,000석 (S2/S5와 동일) |
| 배경 조회 타임아웃 | 10초 (조회는 원래 빨라야 한다) |
| 버킷 | 10초 |
| 반복 | 워밍업 1 + 본 3회 |

**대조군(핫스팟 0)이 필수다.** 배경 조회만 돌렸을 때의 p95를 알아야,
다른 런의 "평상 구간" p95가 믿을 만한지 검증된다.

## 설계 판단

### 국면을 셋으로 나눈다

처음에는 "스파이크 구간"과 "스파이크가 아닌 구간"으로 나눴는데, **결론이 정반대로 나왔다.**

스파이크가 끝나도 시스템은 바로 회복되지 않는다. 그래서 아직 망가져 있는
스파이크 **이후** 구간이 기준선에 섞이면서, 기준선이 12ms가 아니라 4,921ms로 부풀었다.
증폭 배수는 0.9배가 되었고 판정은 "격리됨"이었다. 실제로는 798배였다.

| 국면 | 정의 | 쓰임 |
|---|---|---|
| `평상` | 스파이크 **이전** | **진짜 기준선** |
| `스파이크` | 스파이크 구간 | 피해 측정 |
| `회복` | 스파이크 **이후** | 피해가 얼마나 오래 가는지 |

### 성공 0건 구간의 지연은 0ms가 아니라 "표본없음"

성공한 요청이 하나도 없으면 지연 분포에 표본이 없다. 이걸 0ms로 두면
평균이 **좋아진다** — "빨랐다"로 읽히는데 실제로는 **아무도 응답을 못 받았다**는 뜻이다.
정반대다. 그 구간은 지연이 아니라 **성공률**로 읽어야 한다.

판정 로직도 지연 배수와 성공률 하락 중 **더 나쁜 쪽**을 택한다.
성공률이 0이 되면 지연 배수는 아예 계산되지 않으므로, 지연만 보면 최악 구간을 통째로 놓친다.

### 매진을 회피하지 않는 이유

핫슬롯 1,000석은 스파이크 도중 매진된다. 매진 후 요청은 빠른 실패 경로로 빠져
워커를 오래 붙잡지 않으므로, 폭발 반경도 같이 줄어들 것으로 예상된다.

이걸 피하지 않고 그대로 관측한다. **"폭발 반경은 재고가 남아 있는 동안만 크다"**가
참이라면 시계열의 봉우리가 매진 시점에 맞춰 꺼져야 하고,
그건 회피할 결함이 아니라 이 시나리오가 내놓을 **결론**이다.

## 지표

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| **증폭** | 스파이크 p95 / 평상 p95 | **이 배수 하나가 결론이다.** 1이면 격리 |
| **성공률 하락** | 평상 성공률 − 스파이크 성공률 | 지연 배수가 못 잡는 최악의 경우를 잡는다 |
| 회복 배수 | 회복 p95 / 평상 p95 | 1로 안 돌아오면 피해가 스파이크보다 오래 간다 |
| 배경 timeout | 10초 안에 응답 못 받은 조회 | 사용자가 실제로 포기한 요청 |
| 오버부킹 | DB 직접 조회 | 느려지는 것과 틀리는 것은 다른 문제다 |

**10초 버킷 시계열**이 핵심 산출물이다. 봉우리가 스파이크 구간에 정확히 겹치는지가 인과의 근거다.

## 가설과 반증 조건

> **H3.** 락을 쓰는 엔드포인트의 폭주는 락을 쓰지 않는 엔드포인트까지 마비시킨다.
> 분산락 대기가 Tomcat 워커를 점유하기 때문이다.

| | 관측되면 |
|---|---|
| **지지** | 배경 GET의 p95 봉우리가 스파이크 구간에 겹치고, 대조군은 평탄 |
| **반증** | 배경 GET이 스파이크 중에도 평탄 → 두 경로가 격리되어 있다 |

## 검증 실측 (probe, 1회, 핫슬롯 1,000석, 스파이크 20초)

하네스 검증용 짧은 런이다. 본 측정 아님.

| 핫스팟 | p95 평상 | p95 스파이크 | 증폭 | p95 회복 | 성공률 평상→스파이크→회복 | 배경 timeout |
|---:|---:|---:|---:|---:|:--|---:|
| 0 (대조군) | 12ms | 13ms | — | 12ms | 100% → 100% → 100% | 0 |
| 1,500 | 11ms | 8,977ms | **798배** | 9,823ms | 100% → **3.8%** → 42.0% | 1,045 |

배경 조회 시계열:

```
 0–10s  평상       요청 500 / 성공 500 / 100.0% /    11ms
10–20s  스파이크   요청 364 / 성공  28 /   7.7% / 8,977ms
20–30s  스파이크   요청 454 / 성공   0 /   0.0% / 표본없음  ← 전멸
30–40s  회복       요청 440 / 성공 185 /  42.0% / 9,823ms  ← 아직도 망가져 있음
```

### 읽은 것

- **폭발 반경은 넓다.** 전혀 무관한 식당의 조회가 100% → 3.8%로 죽었다.
  대조군이 12ms로 평탄했으므로 원인은 핫스팟이 맞다.
- **피해는 스파이크보다 오래 간다.** 폭격이 끝난 뒤 10초가 지나도 성공률은 42%,
  p95는 평상의 873배다. 트래픽이 빠졌다고 서비스가 돌아오지 않는다.
- **20–30초 구간은 성공률 0%다.** 이 구간의 지연을 0ms로 집계했다면
  "빨라졌다"로 읽혔을 것이다. 실제로는 전멸이다.
- **오버부킹은 0.** 1,000석에 정확히 1,000건 팔렸다.
  `before`는 느려지고 죽을 뿐, 틀리지는 않는다.

## 실행

```bash
cd performance_test/s3-blast-radius
./run.sh before
./run.sh after

# 짧은 확인
HOT_RATES="0 1500" REPEATS=1 WARMUP=0 TOTAL_SEC=40 SPIKE_AT=10 SPIKE_SEC=20 ./run.sh probe
```

| 환경변수 | 기본값 | 뜻 |
|---|---:|---|
| `HOT_RATES` | `0 400 1500 3000` | 핫스팟 사다리 (0 = 대조군) |
| `BG_RATE` | `50` | 배경 조회 도착률 |
| `TOTAL_SEC` / `SPIKE_AT` / `SPIKE_SEC` | `120` / `30` / `60` | 관측 창 / 스파이크 시작 / 지속 |
| `SEATS` | `1000` | 핫슬롯 재고 |

출력: `<label>/summary.md`, `<label>/summary.json`, `<label>/raw/`
