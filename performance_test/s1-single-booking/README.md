# S1 — 단건 오픈런 (B2C 일제 도착)

> 정각에 N명이 동시에 예약 버튼을 누른다. 좌석은 30석뿐이다.
> **몇 명이 좌석을 받고, 나머지는 무엇을 겪는가.**

## 이건 부하테스트가 아니다

"몇 req/s에서 무너지나"를 묻지 않는다. 그건 용량 계획의 질문이고, 이 실험의 질문이 아니다.

이 시스템은 **B2B 저트래픽 전제** 위에 지어졌다 — 요청 하나하나를 분산락으로 붙잡고
순서대로 처리한다. 동시성이 낮으면 그게 실제로 가장 빠르다. 여기서 묻는 건 하나다.

> 그 전제 위에 **B2C 트래픽**이 들이닥치면 사용자가 무엇을 겪는가.

예약 도메인이 B2C가 되면 트래픽의 모양 자체가 달라진다.

| | B2B (설계 전제) | B2C (실제로 올 것) |
|---|---|---|
| 도착 | 하루에 흩어져서 | **공표된 정각에 전원 동시** |
| 인구 | 소수 클라이언트 | 재고 대비 압도적 |
| 재시도 | 정책적 백오프 | 새로고침 연타 |
| 실패 | SLA 협의 대상 | 그대로 이탈 |

첫 줄이 이 시나리오다. **일제 도착은 B2C의 정의적 특징**이고, 그게 재현되지 않으면
B2C를 모사한 게 아니라 그냥 부하를 준 것이다.

## 부하 모형: 유한 인구, 1인 1요청, 동시 발사

```
executor: per-vu-iterations
vus: N, iterations: 1
```

**개방형(`constant-arrival-rate`)은 쓸 수 없다.** `rate=8000 timeUnit=1s`는 8,000건을
1초에 균등 배분한다(125µs 간격) — 일제 도착이 아니라 촘촘한 줄서기다. 도착률 모델은
"서로 독립적인 무작위 도착"을 가정하는데, 오픈 시각이 공표된 도메인에는 맞지 않는다.

**루프 도는 VU도 쓸 수 없다.** 서버가 느려지면 다음 발사도 느려져서 부하가 자기제한된다.
`iterations: 1`이면 각 VU가 한 번만 쏘므로 그 문제가 사라지고, 부하가 오직 인구수로 결정된다.

### CountDownLatch를 시각으로 구현한다

k6에는 VU 간 공유 가변 상태가 없다(`SharedArray`는 읽기 전용). 배리어로 쓸 수 있는 건
시각뿐이다. `setup()`의 반환값은 전 VU에 배포되고 전부 같은 프로세스라 시계 스큐가 0이므로,
공통 벽시계 시각이 `countDown()` 역할을 한다.

```js
export function setup() {
  return { fireAt: Date.now() + SPREAD_MS + SETTLE_MS, ... };
}

export default function (data) {
  /* 1 */ sleep(warmupAt - Date.now());   // 흩뿌려서 커넥션 선점
  /* 2 */ http.get(배경식당);              //   ← keep-alive 소켓 확보
  /* 3 */ sleep(data.fireAt - Date.now()); // 배리어 = await()
  /* 4 */ http.post(예약);                 // 일제 발사
}
```

### 커넥션 예열 — 의도와 실제가 다르다 (측정으로 밝혀짐)

**의도**: 배리어 직후 TCP 핸드셰이크 N개가 동시에 몰리면 재는 게 예약 API가 아니라
**커널 accept 큐**가 된다. 그래서 배리어 전에 락 없는 GET을 보내 소켓을 열어둔다.
실제 티켓팅에서도 사람들은 오픈 전에 페이지를 열어두고 시계를 보므로, 트릭이 아니라
더 정확한 모사이기도 하다. 예열이 두 번째 스톰이 되지 않도록 인원에 비례해 흩뿌린다
(`spread = max(30s, N/100)`).

**실제**: 예열된 커넥션은 **발사 시점까지 살아있지 않다.** Spring Boot의 Tomcat
keep-alive 타임아웃이 기본 20초인데, 예열 창이 최대 100초 + `SETTLE_SEC` 20초라
먼저 예열한 VU의 소켓은 서버가 이미 닫아버린다. 그래서 발사 순간 상당수가 **다시
dial 한다.**

이걸 측정 결과에서 발견했다 — 10,000명 회차의 실패 사유가 전부 `dial: i/o timeout`
이었다. 응답을 기다리다 만료된 게 아니라 **연결 자체를 못 맺은 것**이다.

**그래서 이 시나리오는 "완벽하게 예열된 일제 발사"가 아니라 "정각에 전원이 동시에
연결을 시도하는" 상황을 잰다.** 후자가 오히려 오픈런의 실제 모습에 가깝고,
`max-connections=8192` 벽이 여기서 정면으로 드러난다. 다만 **의도한 격리는 실패했다는
점을 명시**해야 한다 — accept 큐 비용이 측정에 섞여 있다.

실패는 네 갈래로 나뉜다.

| 시점 | k6 에러 | 분류 | 사용자에게는 |
|---|---|---|---|
| 배리어 이전 | 예열 GET 실패 | 페이지 못 엶 | "페이지가 안 열려요" |
| 발사 | `dial: ...` | **접속 불가** | "누르자마자 에러" |
| 발사 | `EOF` / `reset` | **튕김** | "누르자마자 튕김" |
| 발사 | `deadline exceeded` | **무응답** | "눌렀는데 답이 없어요" |

`dial` 실패를 응답 타임아웃과 합치면 **`max-connections` 벽이 "서버가 느리다"로
둔갑한다.** 1·2차 측정에서 연속으로 이 함정에 빠졌다 — 문자열에 `timeout`이
들어있다는 이유만으로 같은 버킷에 넣었기 때문이다.

## 동시 인원을 이렇게 고른 이유

임의값이 아니다. 이 시스템에서 **사용자 경험이 질적으로 바뀌는 경계**에 맞췄다.

| 경계 | 값 | 넘어가면 |
|---|---:|---|
| `tomcat.threads.max` | 200 | 접속은 되지만 워커 큐에서 대기 시작 |
| `tomcat.max-connections` | 8,192 | 서버가 커넥션을 끊기 시작 |
| macOS 임시 포트 | 16,383 | 서버가 아니라 발생기를 재게 됨 |

→ **200 / 1,000 / 3,000 / 8,000 / 10,000**, 각 5회.

10,000이 상한이다. 그 위는 발생기 한계와 구분이 안 되므로 재지 않는다.

**좌석은 30석 고정.** 오픈런은 재고가 희소한 게 정상이고, 군중만 변수로 둔다.
경합비는 6.7:1 → 333:1로 간다.

## 유효성 판정이 결과보다 먼저다

동시 도착이 이 실험의 **전제**이므로, 발사가 번진 회차는 결과가 아니라 폐기 대상이다.
"동시 10,000명에서 이랬다"고 쓰려면 정말 동시였다는 증거가 있어야 한다.

`fire_skew_ms`(각 VU의 실제 발사 시각 − `fireAt`)를 k6 threshold로 걸어 자동 판정한다.
위반하면 k6가 exit 99로 끝나고, `aggregate.py`가 그 회차를 중앙값에서 제외하며,
**몇 개를 왜 뺐는지 `summary.md`에 남긴다.** 조용히 버리면 "5회 측정"이라 써놓고
실제로는 2회인 상황이 된다.

`late_vus`(배리어를 이미 지나쳐 도착한 VU)도 같이 본다. 0이 아니면 `SPREAD_SEC`/
`SETTLE_SEC`가 부족하다는 뜻이다.

## 재는 것

용량이 아니라 **그날 그 사람들이 겪은 것**.

| 지표 | 정의 |
|---|---|
| 페이지 못 엶 | 오픈 전 커넥션 실패 |
| 좌석 획득 | 성공 응답 수 (30이어야 정상) |
| 매진까지 | 발사 → 마지막 좌석 판매 |
| 마지막 응답 | 발사 → 답을 받은 마지막 사람 |
| 무응답 / 튕김 / 접속불가 | 답을 못 받은 사람 (사유별) |
| 오버부킹 | `_lib/integrity.sh`, 슬롯 단위 |
| 정착 | HTTP 응답 이후 DB가 안정될 때까지 |

`무응답`과 `튕김`을 반드시 분리한다. 합치면 `max-connections` 벽이 통계에서 사라진다
— 1차 측정에서 실제로 그렇게 놓쳤다.

## after의 대기열 — 왜 같은 파일로 재는가

after는 예약 앞에 대기열이 있고 서버가 강제한다. 그래서 발사 이후 흐름이 세 단계다:
`진입 → 폴링 → 예약`.

**시나리오 파일은 before와 after가 같다.** 갈라지는 건 `SKIP_QUEUE` 하나뿐이고 `run.sh`가
라벨에서 정한다. 배리어·예열·인원 사다리·좌석 수·스큐 판정·에러 분류·시간 기준점이
전부 같아야 비교가 성립하므로, 파일을 나누는 대신 단계 하나를 켜고 끈다.

`마지막 응답`과 `대기 p50/p95`에는 **줄 서는 시간이 포함된다.** 그게 before와 같은 잣대다
— 사용자에게 중요한 건 버튼을 누르고 답을 받기까지지 예약 API 하나의 지연이 아니다.
after 쪽에 불리하게 잡히는 게 정확하다. 예약 호출만 따로 보려면 `timing.bookingMs`.

| 지표 | 정의 |
|---|---|
| 입장 / 진입 실패 | 줄을 통과한 사람 / 줄에 서지도 못한 사람 |
| 포기 | 대기 예산 안에 입장 못 함. **0이어야 정상** — 0이 아니면 승격이 막힌 것이다 |
| 폴링 | 폴링 요청 수. **before에 없는 부하다.** 안 세면 after 실부하가 통계에서 사라진다 |
| 앱이 받은 요청 | 진입 + 폴링 + 예약. 실제 배포에서는 폴링 몫이 CDN(=폴링 간격 TTL)으로 넘어간다 |

## 실행

```bash
./run.sh before                               # 본 측정 (5레벨 × 5회)
./run.sh after                                # 대기열 단계가 자동으로 켜진다
CROWDS="10000" REPEATS=1 WARMUP=0 ./run.sh probe   # 빠른 확인
```

회차별 원본은 `<label>/raw/`.
