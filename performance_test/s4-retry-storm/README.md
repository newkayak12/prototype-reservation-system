# S4 — Retry Storm (새로고침이 장애를 증폭시키는가)

> B2B 클라이언트는 실패하면 백오프한다. **B2C 사용자는 F5를 연타한다.**

**우선순위 3.** 이 실험만이 B2C 고유의 장애 모드를 다룬다. 면접에서 가장 자주 묻히는 지점.

---

## 질문

요청이 느리거나 실패했을 때 사용자가 재시도하면, 그 재시도가 **부하를 증폭시켜 더 많은 실패를
만드는 양성 피드백(죽음의 나선)** 이 발생하는가.

지금까지의 모든 시나리오는 "사용자가 한 번 쏘고 결과를 받아들인다"고 가정했다.
**현실의 B2C 사용자는 그러지 않는다.**

## 가설 H3 — 재시도 증폭에 의한 죽음의 나선

### 메커니즘

```
요청 지연 ↑ → 사용자 인내 한계 초과 → 새로고침 → 유효 도착률 ↑
     ↑                                                    │
     └────────────────────────────────────────────────────┘
```

**before가 이 나선에 특히 취약한 이유**: 요청을 거절하지 않고 **붙잡아 둔다.** 사용자는 응답을
못 받은 채 기다리다 새로고침하는데, **원래 요청은 여전히 워커 스레드를 점유한 채 살아 있다.**
버려진 요청이 자원을 계속 먹으므로 실효 부하가 재시도 횟수만큼 곱해진다.

**after가 덜 취약한 이유**: 정원 초과분을 **즉시** 거절한다. 사용자는 빨리 실패를 알고,
버려진 요청이 자원을 물고 있지 않다. 재시도가 늘어도 각 시도의 비용이 상수다.

### 예측

| 재시도 정책 | before 유효 처리량 | before 실패율 | after |
|---|---|---|---|
| 없음 (기준선) | 기준 | 기준 | 기준 |
| 3초 후 1회 재시도 | 소폭 하락 | 상승 | 거의 불변 |
| **3초 간격 무한 재시도** | **급락** | **급증** | **거의 불변** |

**핵심 관측값**: 재시도를 켰을 때 **before의 유효 처리량(고유 사용자 기준 성공 수)이
오히려 감소**하면 나선이 확인된다. 부하를 더 넣었는데 처리량이 줄어드는 것 —
이게 congestion collapse다.

### 반증 조건

**재시도를 켜도 before의 유효 처리량이 유지되거나 증가하면 H3은 반증이다.**
그 경우 before는 재시도에 강건한 것이며, B2C 장애 모드 논거를 쓸 수 없다.

## 부하 모형

```
executor: constant-arrival-rate
rate: knee의 150% (S2 결과에서 결정), duration: 120s
좌석: 넉넉히 (100,000석)

재시도 정책 3종을 각각 별도 런으로:
  A. NO_RETRY        — 기준선
  B. RETRY_ONCE      — 3초 내 응답 없으면 포기하고 1회 재시도
  C. RETRY_FOREVER   — 3초 간격으로 성공할 때까지 (사용자 인내 한계 = 3초)
```

### 설계 판단

**"사용자 인내 한계"를 클라이언트 타임아웃으로 모델링한다.**
k6 요청 `timeout: '3s'` → 3초 내 응답이 없으면 요청을 버리고 재시도. 이게 F5 연타의 정확한
모사다: 브라우저는 원래 요청을 취소하지만 **서버는 그걸 모르고 계속 처리한다.**

> ⚠️ 이 "서버가 모른다"가 실험의 핵심이다. k6가 커넥션을 끊어도 Tomcat 워커는 이미 락 대기에
> 들어가 있으면 2분 타임아웃까지 그 스레드를 놓지 않는다. 버려진 요청이 자원을 먹는다.

**도착률을 knee의 150%로 잡는 이유**: 나선은 용량 초과 상태에서만 발생한다. 여유가 있으면
재시도가 그냥 흡수된다. **S2를 먼저 돌려야 이 값을 정할 수 있다** → S2 이후에 실행.

**유효 처리량을 별도로 센다**: 총 요청 수가 아니라 **고유 사용자 중 성공한 수**. 재시도가
늘면 총 요청은 당연히 늘지만, 그게 실제 성과인지는 별개다.

## 지표

| 지표 | 정의 / 판정 |
|---|---|
| **유효 처리량** | 고유 사용자 기준 성공 수 / 시간. **이게 줄면 나선 확정** |
| 증폭 계수 | 총 발사 요청 수 / 고유 사용자 수 |
| 사용자 관점 성공률 | 성공한 고유 사용자 / 전체 고유 사용자 |
| 사용자 관점 완료 시간 | **첫 시도 시작 → 최종 성공** (재시도 포함한 체감 시간) |
| 포기(abandon) 수 | 3초 타임아웃으로 버려진 요청 수 |

**"사용자 관점 완료 시간"이 중요하다.** 서버 p95는 좋아 보여도 사용자가 5번 재시도했다면
체감은 15초 이상이다. 서버 지표와 사용자 체감의 괴리를 드러내는 지표.

## 판정 기준

| 판정 | 조건 |
|---|---|
| **H3 지지** | before의 유효 처리량이 A → C로 갈수록 **감소**, 동시에 abandon 수 급증 |
| **H3 반증** | before 유효 처리량이 A ≈ C |
| **after 우위** | after 유효 처리량이 A ≈ C 이고 사용자 관점 완료 시간이 안정 |

## 선행 조건

**S2 완료 필수** — 도착률(knee의 150%)을 S2 결과에서 가져온다.

## 실행

```bash
../_lib/preflight.sh before
RATE=<S2 knee × 1.5> ./run.sh before
```

정책 3종 × 반복 3회.
