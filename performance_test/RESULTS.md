# before vs after — 측정 결과 (2026-08-30)

분산락 직렬 처리(before) → Redis 대기열 + permit 세마포어 + Lua 원자획득/조건부
UPDATE + Kafka(after) 재설계가 **B2C 일제 도착에서 사용자 경험을 바꿨는가.**

- before: `~/Downloads/port/prototype-reservation-system` (`chore/performance-test`)
- after: 이 워크트리 (`newkayak12/chore-performance-test-after`)
- 같은 머신(M4 Pro/48GB), 같은 시나리오 파일, 같은 인원 사다리(200/1,000/3,000/8,000/10,000 × 5회).
  환경 드리프트 통제를 위해 before 10,000 구간은 같은 날 재측정했다(`before-rerun`) —
  마지막 응답 27.3→28.2s, 접속불가 408→189로 옛 측정과 대차 없다.
- 측정 조건: [ENVIRONMENT.md](ENVIRONMENT.md). before 단독 분석(직렬 상한 357 req/s,
  임계구간 2.8ms 등)은 before 저장소의 `performance_test/RESULTS.md` 참조.

세 축으로 쟀다. **축마다 결론이 다르며, 셋을 합쳐야 정직한 그림이 된다.**

## ① S1 정면 승부 — 예약 경로 자체가 빨라졌는가

대기열이 결과를 걸러주면 예약 경로의 성적을 알 수 없다. 그래서 after를
`admission-capacity=20000`으로 열고(전원 즉시 입장, 폴링 0), 발번은 예열 창에서
끝낸 뒤 **발사는 예약 요청만** 하게 했다(`QUEUE_PREPASS=1`).
양쪽 모두 N명이 예약 API에 일제 도착하는 완전히 같은 조건이다.

집계: `s1-single-booking/after-capacity20000/`. 25회 전부 채택.

| 인원 | before 마지막 응답 | **after** | before 대기 p95 | **after** | before 접속불가 | **after 실패** |
|---:|---:|---:|---:|---:|---:|---:|
| 200 | 0.9s | **0.1s** | 909ms | **80ms** | 0 | 0 |
| 1,000 | 3.0s | **0.3s** | 2,872ms | **272ms** | 0 | 0 |
| 3,000 | 8.4s | **0.7s** | 8,065ms | **658ms** | 0 | 0 |
| 8,000 | 22.5s | **1.7s** | 21,515ms | **1,659ms** | 0 | 튕김 14 |
| 10,000 | 27.3s (재측정 28.2s) | **4.0s** | 26,087ms | **2,020ms** | 408 (재측정 189) | 튕김 47 |

- **p95 기준 13배** (8,000명: 21.5s → 1.7s). before는 인원 선형, after는 준선형이되 기울기가 낮다.
- **매진까지 0.1~0.2초.** before도 매진 자체는 빨랐다(0.5~0.8s) — 차이는 나머지 전원이
  "품절"을 듣기까지 걸리는 시간이다.
- **커넥션 벽이 밀려났다.** before는 10,000에서 189~408명이 접속조차 못 했는데, after는
  같은 10,000 동시에서 접속불가 0이다. 처리가 1~2초에 끝나 커넥션이 빨리 비워지므로
  8192 자리가 회전한다 — 빠른 경로가 벽의 실효 위치를 밀어낸 것이다.
- 처리량: 10,000명 응답 완료 4.0s → **약 2,500 req/s.** 단, 이건 운영 TPS가 아니다 —
  실배포에선 대기열이 동시성을 capacity로 자르므로 사용자가 겪는 처리량 상한은
  `capacity ÷ (폴링/2 + 예약지연)` ≈ 500 req/s대다. 이 수치의 의미는 셋이다:
  경로 자체의 개선이라는 귀속(대기열 필터 효과가 아님), 예약지연 단축이 위 식의
  분모를 줄여 같은 capacity에서 실통과량을 올린다는 것, 그리고 튜닝 여유 —
  capacity·폴링 간격은 짝으로 움직이는 손잡이인데, 경로가 1만 동시를 버틴다는
  실측이 있어야 그 손잡이를 어디까지 올려도 되는지 근거를 갖고 정할 수 있다.
  (정상 동작에서 예약 임계구간 동시성은 세마포어가 capacity로 보장하므로,
  1만 동시 도달 자체는 오설정·게이트 우회가 아니면 일어나지 않는다.)

원인은 코드 차이 그대로다: 분산락 + 잔여재고 전체 로딩(임계구간 2.8ms 직렬)이
Lua 원자획득 + 조건부 UPDATE(락 없음)로 바뀌었다.

> 유의: 10,000 회차에서 MySQL CPU 피크 78.9%·포트 압박 플래그가 섰다. 판정(13배, 벽
> 없음)은 8,000까지로도 성립하므로 바뀌지 않지만, 10,000의 절대값은 보수적으로 읽을 것.

## ② S1 실사용 조건 — 대기열을 낀 체감은 어떤가

after의 실제 배포 형태(capacity 150, 폴링 0.5s). 사용자 체감 = 진입 + 줄 + 예약.
집계: `s1-single-booking/after/`.

| 인원 | before 마지막 응답 | after | after 예약만 p95 | 폴링 비중 | after 접속불가+튕김 |
|---:|---:|---:|---:|---:|---:|
| 200 | 0.9s | **0.7s** | 51ms | 14% | 0 |
| 1,000 | 3.0s | **2.4s** | 255ms | 46% | 0 |
| 3,000 | 8.4s | **6.6s** | 179ms | 73% | 0 |
| 8,000 | 22.5s | 31.5s | 696ms | 92% | 9 |
| 10,000 | 27.3s | 44.8s | 955ms | 92% | 1,303 |

3,000까지는 대기열을 끼고도 before보다 빠르고 실패 0이다. 8,000부터 역전되는데,
**원인은 예약 경로가 아니라 앞단이다** — 예약만 보면 696ms다.

- 폴링이 앱 요청의 92%(8,000명 회차 18만 건)를 차지한다. 실제 배포에서는 폴링
  간격(0.5s)=CDN TTL로 엣지가 흡수할 몫인데, **로컬에는 그 계층이 없어** 원 서버와
  발생기 CPU를 직접 때린다.
- 진입+폴링 때문에 동시 요청 수가 부풀어 `max-connections=8192` 벽을 before보다
  3배 세게 맞는다(10,000: 1,223 vs 408).

→ ①이 증명한 이점 위에, 로컬에서 재현 불가능한 비용(CDN 부재)이 얹힌 수치다.
8,000+ 구간의 역전은 "이 아키텍처가 느리다"가 아니라 **"이 아키텍처는 엣지 캐시를
전제한다"**로 읽어야 한다. 참고로 순번 조회 URL에 `ticketId`가 박혀 있어 지금 API
형태로는 CDN 캐시 키가 사용자마다 갈린다 — 엣지 흡수가 실제로 성립하려면 공유 커서
방식(`admittedThrough` 단일 값) 같은 캐시 가능한 엔드포인트가 필요하다.

## ③ S2 다건 오픈런 — 반쪽 예약이 줄었는가

한 사람이 3슬롯(18/19/20시, 각 30석)을 동시에 원한다. before의 핵심 결함:
슬롯 경계 트랜잭션이라 "2건 성공 1건 실패"를 되돌릴 수 없고, 1,000명이면 90석
전부가 반쪽 예약에 묶였다. 집계: `s2-multi-booking/after/`.

| 인원 | 3건 전부 (b→a) | 부분 성공 (b→a) | 묶인 좌석/90 (b→a) | 마지막 응답 (b→a) |
|---:|---:|---:|---:|---:|
| 200 | 9 → **21** | 43 → **17** | 63 → **27** | 1.2s → 0.9s |
| 1,000 | 0 → **6** | 63 → **50** | 90 → **72** | 6.6s → 3.0s |
| 3,000 | 4 → **13** | 54 → **38** | 78 → **51** | 19.5s → 15.6s |
| 8,000 | 0 → **9** | 73 → **41** | 90 → **63** | 36.8s → 67.2s |
| 10,000 | (판정 제외 — 아래) | | | |

- **전 레벨에서 반쪽 예약이 줄고(최대 -57%), 3건 완수자가 늘었다.** before는 3개 락
  난투라 아무나 한두 개씩 걸치지만, after는 대기열이 슬롯마다 순서를 만들어 앞사람이
  원하는 걸 다 가져간다. 정합성 지표(90/90, 오버부킹 0)에는 안 보이는 개선이다.
- 다만 **구조적 결함 자체는 남아 있다.** 다건에 걸친 트랜잭션 경계는 after에도 없고,
  대기열 키도 슬롯 단위라 줄을 3개 선다. 부분 성공이 줄었을 뿐 0이 되지는 않는다.
  0으로 만들려면 다건 홀드-확정 같은 예약 단위의 경계가 필요하다.
- 8,000의 체감 역전(36.8→67.2s)은 ②와 같은 원인(진입 3배 + 폴링, CDN 부재)이다.
- **10,000은 판정 제외**: 요청 30,000건이 발생기 포트 한계(16,383)를 넘어 양쪽 다
  접속불가가 65%+이고, before-rerun은 스큐 폐기 2회, after는 승격 막힘 플래그(전부
  포기 8, 일부만 입장 54)가 섰다. 어느 쪽 숫자도 시스템의 성적이 아니다.

## 측정 사고 기록 — 1차 S2 after는 하네스가 병목을 만들었다

첫 S2 after 측정(무효 데이터: `s2-multi-booking/after-permit-hold-bug/`)은 시나리오가
"3슬롯 전부 입장할 때까지 기다렸다가 모아서 예약"하도록 짜여 있었다. permit은 예약을
마쳐야 반납되는데(`ReleaseAdmissionRedisAdapter`) 입장해 놓고 예약을 안 하니
capacity 150×3이 전부 대기 상태로 잠겨 회전이 멈췄고, 1,000명부터 뒷줄 전원이 예산을
소진했다. **시스템이 아니라 부하 생성기가 만든 병목**이라 폐기하고, 입장 즉시 예약하도록
고쳐 재측정했다(상세: `s2-multi-booking/README.md`).

부산물로 실제 결함 하나가 드러났다: **입장 후 예약하지 않는 이탈자는 permit을
lease(300s) 만료까지 점유하며, 이를 조기 회수하는 장치가 없다.** 이탈률이 높은 날은
유효 capacity가 그만큼 깎인다. 별도 시나리오로 크기를 재기 전까지는 정성적 결함이다.

## 이 측정이 답하지 못한 것

- **엣지 캐시를 얹은 실제 배포 형태의 앞단 성적** — 폴링을 CDN이 흡수할 때 ②의 역전이
  사라지는지. 공유 커서 엔드포인트 + nginx `proxy_cache`로 로컬 재현 가능하나 미실시.
- 발생기·서버 동거로 인한 CPU 경합의 정확한 기여도 (8,000+ 절대값의 오차 범위).
- 이탈자 permit 점유의 실제 크기 (이탈률 X%를 주입하는 시나리오 필요).
- before 문서의 미해결 질문들(재고 스케일, 폭발 반경, 재시도 폭풍, 지속 부하)은
  양쪽 다 여전히 미측정.
