# before 측정 결과 (2026-08-29 재측정)

B2B 저트래픽 전제로 만든 예약 시스템에 B2C 트래픽이 들이닥쳤을 때
**사용자가 무엇을 겪는가.**

측정 조건은 [ENVIRONMENT.md](ENVIRONMENT.md), 설계 근거는 각 시나리오 README 참조.
원시 집계는 `s*/before/summary.md`.

## 요약

| | S1 단건 오픈런 | S2 다건 오픈런 |
|---|---|---|
| 상황 | N명이 정각에 좌석 1건씩 | N명이 정각에 **3슬롯씩** |
| 재고 | 30석 | 3슬롯 × 30석 = 90석 |
| 결론 | **매진은 0.5초, 대기는 27초** | **원하는 걸 온전히 받은 사람 ≈ 0명** |
| 정합성 | 오버부킹 0 / 미판매 0 | 오버부킹 0 / 미판매 0 |

**두 시나리오 모두 정합성은 완벽하다.** 재설계의 명분은 정합성이 아니다.
S1은 **대기 시간**을, S2는 **예약 단위**를 문제로 지목한다.

## S1 — 단건 오픈런

동시 인원 200 / 1,000 / 3,000 / 8,000 / 10,000, 각 5회. **25회 전부 채택, 폐기 0.**

| 동시 | 매진까지 | 마지막 응답 | 대기 p50 | p95 | p99 | 접속 불가 | 오버부킹 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 200 | 0.5s | 0.9s | 685ms | 909ms | 925ms | 0 | 0 |
| 1,000 | 0.5s | 3.0s | 1,764ms | 2,872ms | 2,961ms | 0 | 0 |
| 3,000 | 0.5s | 8.4s | 4,522ms | 8,065ms | 8,331ms | 0 | 0 |
| 8,000 | 0.6s | 22.5s | 11,830ms | 21,515ms | 22,321ms | 0 | 0 |
| 10,000 | 0.7s | 27.3s | 14,323ms | 26,087ms | 27,067ms | 408 | 0 |

### 1. 매진 시각이 인원과 무관하다

**0.5초 → 0.7초.** 인원이 50배 늘어도 거의 안 변한다.
좌석 30석은 어차피 순식간에 나간다.

### 2. 그런데 마지막 사람의 대기는 29배가 된다

0.9초 → 27.3초. **이 시스템은 몰린다고 느려지는 게 아니다.**
좌석은 0.5초에 소진되고, **나머지 9,970명은 "품절입니다"를 듣기 위해 26.8초를 줄 선다.**

분산락이 전원을 한 줄로 세우기 때문이고, **팔 게 없어진 뒤에도 줄은 그대로 유지된다.**

### 3. 직렬 처리 상한 ≈ 357 req/s

마지막 응답 시각을 인원으로 나누면 요청당 임계구간이 나온다.

| 동시 | 마지막 응답 ÷ 인원 |
|---:|---:|
| 200 | 4.50ms |
| 1,000 | 3.00ms |
| 3,000 | 2.80ms |
| 8,000 | 2.81ms |
| 10,000 | 2.73ms |

**약 2.8ms로 수렴한다 → 1/0.0028 ≈ 357 req/s.**
락 키 하나당 이게 하드 상한이고, 인원을 늘려도 변하지 않는다.
대기 시간이 인원에 선형 비례하는 이유가 이 하나로 설명된다.

### 4. 실패는 "느림"이 아니라 "접속 불가"였다

| 동시 | 무응답 | 튕김 | **접속 불가** |
|---:|---:|---:|---:|
| ~8,000 | 0 | 0 | 0 |
| 10,000 | **0** | 15 | **408** |

**무응답이 전 레벨 0이다.** 연결만 잡으면 27초 안에 반드시 답을 받았다.
유일한 실패는 **연결 자체를 못 맺은 408명(4%)** 이고, 8,000명까지는 0이다가
10,000명에서만 나타난다 — `tomcat.max-connections=8192` 벽이다.

> 이 구분은 처음에 놓쳤다. `dial: i/o timeout`을 문자열에 `timeout`이 있다는 이유로
> 응답 타임아웃과 합쳤더니 **찾으려던 벽이 "서버가 느리다"로 둔갑했다.**
> `dial`은 TCP 연결 수립 단계이므로 "기다렸는데 답이 없다"가 아니라
> **"줄에 서지도 못했다"** 이다. 자세한 경위는 [S1 README](s1-single-booking/README.md).

### 5. 인프라는 놀고 있었다

| 동시 | MySQL CPU | DB 실행 중 쿼리 | DB 커넥션 | TIME_WAIT |
|---:|---:|---:|---:|---:|
| 200 | 6.7% | 3 | 12 | 372 |
| 10,000 | 13.7% | 3 | 11 | 9,598 |

**10,000명이 몰려도 앱이 DB에 준 동시 작업은 3~4개뿐이다.**
DB가 굶어서 느린 게 아니라 앱이 DB를 그만큼밖에 안 쓴다.
TIME_WAIT도 임계값 12,000 미만이라 발생기 포트도 마르지 않았다.

→ **관측된 한계는 전부 애플리케이션 안이다.** "장비가 약해서"라는 반론이 막힌다.
→ **수직·수평 확장으로 해결되지 않는다.** 하드웨어가 놀고 있는데 느리기 때문이다.

## S2 — 다건 오픈런 (한 사람이 3슬롯)

같은 인원 사다리, 각 5회. 슬롯 3개(18/19/20시) × 30석 = 90석.
**24회 채택, 1회 폐기** (10,000명 레벨에서 일제 발사 재현 실패 1회).

### 1. 원하는 걸 온전히 받은 사람이 사실상 없다

| 동시 | 3건 전부 | **부분 성공** | 전부 실패 | 부분성공자가 점유한 좌석 |
|---:|---:|---:|---:|---:|
| 200 | 9 | **43** | 148 | 63 / 90 |
| 1,000 | **0** | **63** | 936 | **90 / 90** |
| 3,000 | 4 | **54** | 2,942 | 78 / 90 |
| 8,000 | **0** | **73** | 7,927 | **90 / 90** |
| 10,000 | 2.5 | **62** | 9,936 | 82.5 / 90 |

**1,000명부터 3건을 온전히 받은 사람이 0명이고, 90석 전부가 반쪽 예약에 묶인다.**

"18시 19시는 됐고 20시는 실패"는 저녁 자리를 3개 잡으려던 사람에게 쓸모없는 예약이다.
그런데 재고는 이미 붙잡혀 있고, **되돌릴 방법이 없다.**

`@DistributedLock` 키와 `@Transactional` 경계가 **둘 다 슬롯 단위**라,
여러 슬롯에 걸친 트랜잭션 경계가 코드에 존재하지 않는다. 1·2번이 커밋된 뒤 3번이
실패해도 앞의 둘은 남는다. 보상 트랜잭션도, 홀드-확정 2단계도 없다.

> **정합성 지표는 완벽하다** — 전 레벨 90/90 판매, 오버부킹 0, 미판매 0.
> **정합성만 보면 이 실패가 보이지 않는다.**

### 2. 요청이 3배가 되자 커넥션 벽에 정면으로 부딪힌다

| 동시 | 요청 수 | 성공 | 매진 거절 | **접속 불가** | 비율 |
|---:|---:|---:|---:|---:|---:|
| 200 | 600 | 90 | 510 | 0 | 0% |
| 1,000 | 3,000 | 90 | 2,910 | 0 | 0% |
| 3,000 | 9,000 | 90 | 8,910 | 0 | 0% |
| 8,000 | 24,000 | 90 | 7,960 | **15,688** | **65%** |
| 10,000 | 30,000 | 90 | 9,422 | **20,033** | **67%** |

S1에서는 10,000명에서 408명(4%)만 접속을 못 했다. S2는 **8,000명에서 이미 65%가
접속조차 못 한다.** 사람 수는 적은데 **요청 수가 3배**(24,000)라
`max-connections=8192`의 약 3배를 동시에 요구하기 때문이다.

→ **커넥션 벽은 "동시 접속자 수"가 아니라 "동시 요청 수"에 걸린다.**
1인당 요청이 늘면 훨씬 적은 사용자에서 터진다.

### 3. 인원이 늘었는데 오히려 빨라지는 역전

| 동시 | 마지막 응답 |
|---:|---:|
| 3,000 | 19.5s |
| 8,000 | **36.8s** |
| 10,000 | **29.3s** |

10,000명이 8,000명보다 빠르다. **부하가 줄어서가 아니라 67%가 서버에 도달조차
못 해서** 실제로 처리된 일이 적었기 때문이다.

**과부하가 심해지면 지표가 좋아 보이는 구간이 생긴다.** 응답 시간만 보고 있으면
"개선됐다"고 읽게 되는 지점이라, 도달률과 함께 보지 않으면 안 된다.

## 이전 측정과의 차이 — latch가 만든 것

같은 실험을 예전에도 했다(백업 `s1-flash-sale/before/`, VU 7레벨 × 10회).
설계가 거의 같아 겹치는 인원에서 직접 비교가 된다.

| 동시 | 이전 (해소) | 오늘 (마지막 응답) | 배수 |
|---:|---:|---:|---:|
| 1,000 | 1.77s | **3.0s** | 1.69× |
| 3,000 | 5.68s | **8.4s** | 1.48× |

| 동시 | 이전 p95 | 오늘 p95 | 배수 |
|---:|---:|---:|---:|
| 1,000 | 1,544ms | **2,872ms** | 1.86× |
| 3,000 | 3,943ms | **8,065ms** | 2.05× |

**오늘이 1.5~2배 느리다.** 그런데 조건은 오늘이 유리했다.

| | 이전 | 오늘 |
|---|---|---|
| P6Spy SQL 프록시 | **켜짐** (프로파일러 켠 채 측정) | 꺼짐 |
| Docker VM | 2 vCPU / 3.83GB *(문서 기재, 미검증)* | 6 vCPU / 15.6GB |
| 발사 방식 | VU가 뜨는 순서대로 자연 발사 | **시각 배리어(latch) 일제 발사** |

**두 조건 모두 오늘이 더 빨라야 하는 방향인데 오늘이 느리다.**
남는 차이는 latch뿐이다.

→ **진짜 일제 도착은 자연 발사보다 측정 가능하게 더 가혹하다.**
이전 측정은 B2C 오픈런을 과소평가하고 있었고, latch를 넣은 게 정당했다는 근거가 된다.

> `after` 수치가 이전 문서 본문에 적혀 있었지만(170 req/s, p95 38ms 등),
> **그 수치를 뒷받침하는 원시 데이터는 백업 어디에도 없다.** 문서에 옮겨 적힌 것만 남아 있다.
> 계획됐던 `before-2` 재측정도 라벨과 preflight 코드까지 만들어졌을 뿐 **실행되지 않았다.**
> 오늘 측정이 현재 스펙에서의 새 기준선이다.

## 현재 설계의 한계

측정값과 코드를 함께 놓고 정리한다.

### 측정으로 확인된 것

| 한계 | 근거 |
|---|---|
| 직렬 상한 **≈357 req/s** | 임계구간 2.8ms 수렴. 인원 무관 (S1) |
| 대기가 인원에 **선형** | 10,000명 → 27.3초 (S1) |
| **매진 후에도 줄이 유지** | 좌석은 0.5초에 소진, 남은 26.8초는 "품절" 응답 직렬 발급 (S1) |
| 커넥션 벽은 **요청 수**에 걸린다 | S1 10,000명 → 4% 불가 / S2 8,000명 → **65%** 불가 |
| **다건 예약을 원자적으로 못 한다** | 1,000명부터 3건 완수 0명, 90석 전부 반쪽 예약 (S2) |
| **확장이 안 먹힌다** | MySQL CPU 13%, DB 동시 쿼리 3~4개 |
| 과부하 시 **지표가 좋아 보인다** | 10,000명이 8,000명보다 빠름 — 67%가 도달 못 해서 (S2) |

### 코드에서 나오는 원인

```kotlin
@DistributedLock(key = "DISTRIBUTED_LOCK:{restaurantId}:{date}:{startTime}",
                 FAIR_LOCK, waitTime = 2분)
@Transactional
override fun execute(command): Boolean {
    val list = loadBookableTimeTables(command)    // 잔여 좌석 '전부' 로딩
    acquireSemaphore(key, list.size)              // Redis 세마포어
    val domainEvent = saveOccupancy(userId, list) // sortedBy{id} 후 첫 건만 저장
    return saveToOutBoxAndPublish(domainEvent)
}
```

1. **락 키가 슬롯 단위** — 같은 슬롯의 모든 요청이 완전 직렬. 락 대기 최대 2분.
2. **잔여 재고를 전부 로딩한다.** `list.size`를 세마포어 크기로 쓰는 게 LIMIT이 없다는 증거다.
   `sortedBy { it.id }`로 정렬한 뒤 **첫 건만 쓰고 버린다.**
   → **요청 하나의 비용이 잔여 재고에 비례한다.** 30석에선 2.8ms라 안 보이지만
   굿즈 10만 개면 치명적이다.
3. **이 전부가 임계구간 안에서** 일어난다. DB 왕복 + Redis 세마포어 + 정렬이 직렬화된다.
4. 락은 트랜잭션 **바깥**에서 잡히므로 DB 커넥션은 안 물지만,
   **락 대기가 Tomcat 워커 스레드를 점유한다** (워커 200개).
   인기 슬롯 하나가 워커를 다 물면 무관한 요청까지 대기한다.

### 이번 측정이 답하지 못한 것

좌석 30석 고정 · 배경 트래픽 없음 · 1인 1요청 · 1회성 버스트라,
아래는 이 데이터로 말할 수 없다.

- 재고가 커지면 어떻게 되나 (위 2번의 실제 크기)
- 무관한 트래픽이 같이 죽는가 (워커 점유의 폭발 반경)
- 재시도가 붙으면 (F5 연타 = B2C 고유 실패 모드)
- 부하가 지속되면 (회복 가능한가)
