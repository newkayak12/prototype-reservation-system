# 개선 전/후 비교 (Phase 0 baseline vs Phase 1~4 재설계)

`docs/perf/baseline-report.md`(개선 전)와 동일한 시나리오·시드·검증으로 재설계본을 10회 측정한 결과.
원본 산출물은 `perf/k6/result-after/`.

> **Phase 1~4가 모두 반영된 앱을 측정했다.**
> 점유는 `PENDING`으로 생성되고 사용자가 확정하면 `CONFIRMED`가 되며, 확정되지 않은 홀드는
> 스케줄러가 회수한다. 그래서 "팔린 좌석"의 집계 기준이 `occupied_status = 'OCCUPIED'`에서
> **`released_at IS NULL`**(= 아직 살아 있는 점유)로 바뀌었고, `verify-overbooking.sql`과
> `wait-settle.sh`도 같은 기준으로 맞췄다. baseline 쪽 수치는 원래 전부 `OCCUPIED`였으므로
> 두 기준이 같은 집합을 세며, 비교는 그대로 성립한다.

## 무엇이 달라졌나 (요청 경로)

```
Phase 0:  @RateLimiter → @DistributedLock(FAIR_LOCK, 최대 2분 대기) → 세마포어
          → timetable 조회 → INSERT ×2 → 응답
재설계:    (대기열 진입 → 입장 허용까지 폴링)
          @RateLimiter → 대기열 게이트 → Lua 원자 차감 → Kafka 발행 → 응답
          → 컨슈머가 슬롯 키 순서대로 좌석 행을 조건부 갱신으로 가져가고 PENDING 점유 저장
          → (사용자 확정 시 CONFIRMED / 미확정이면 스케줄러가 회수)
```

> 좌석 행을 가져가는 방식은 `SELECT ... FOR UPDATE`에서 조건부 `UPDATE`로 한 번 더 바뀌었다.
> 아래 "재설계(after)" 수치는 **현재 구현(조건부 `UPDATE`, `claim-update-*`)** 의 10회 측정이다.
> 두 잠금 방식 사이에는 유의미한 성능 차이가 없었다 — 대조 측정은
> `docs/perf/row-lock-select-vs-update.md`에 따로 정리했다.

## 측정 환경

두 측정 모두 동일:
- 앱: `temporary` 프로파일, 로컬 docker-compose MySQL/Redis/Kafka(3-broker), 포트 8081
- 시드: 좌석 30개, 유저 300명(실제 회원가입 API), 매회 재시딩
- 부하: `ramping-vus` 100→300→600→1000→1500→2000 (각 15s 램프업 + 20s 유지), 총 3m40s
- k6 기본 요청 타임아웃 60s

**차이는 시나리오의 단계 수뿐이다.** 재설계본은 예약 앞에 대기열 진입과 폴링이 붙어 이터레이션당
요청이 1개에서 3개 이상으로 늘었다. 그래서 태그 없는 `http_req_duration`은 비교 대상이 아니고,
**`http_req_duration{name:booking}` 하나만 직접 비교된다.**

> **측정 환경을 완전히 초기화한 뒤 잰 값이다.** Docker의 이미지·컨테이너·볼륨을 전부 지우고
> (로컬 k3d 클러스터 포함, 약 11 GB 회수) 새 볼륨 위에 스택을 다시 세웠다. DB도 비어 있는
> 상태에서 Flyway가 V1_0~V1_21 마이그레이션 22개를 처음부터 적용했다. 이전 측정에 섞여 있던
> 자원 경합 요인을 제거하기 위한 조치이며, 아래 "환경에서 드러난 결함"에 그 경위를 적었다.
> baseline 측정 당시에도 같은 제약이 있었는지는 확인할 수 없다 — 아래 "재현성" 항목의 baseline 쪽
> 불안정성에 이 요인이 섞여 있을 가능성을 배제하지 못한다.

## 관찰

### 1. 처리량 상한은 여전히 좌석 수다 — 그리고 그게 맞다

성공 건수는 양쪽 모두 30건이다. 좌석이 30개니 당연하고, 이 숫자가 늘어나면 그건 개선이 아니라
오버부킹이다. 달라진 것은 **나머지 요청이 어떻게 끝나는가**다. baseline에서는 분산락 뒤에 줄 서
있다가 60초 타임아웃으로 버려졌고, 재설계본에서는 즉시 "품절" 응답을 받는다.

### 2. baseline의 과소예약이 사라졌다

baseline은 8회차에 10건, 10회차에 2건만 팔고 나머지 좌석을 비운 채 끝냈다. 원인은
`DistributedLockAspect`가 Redis 커넥션 풀 고갈 시 상호 배제되지 않는 MySQL Named Lock으로
폴백하는 락 이중화 결함이었다(baseline 리포트 관찰 4). 재설계에서 락과 세마포어를 통째로 걷어내면서
그 결함의 근거 자체가 없어졌고, **10회 전부 정확히 30건**이 나왔다.

### 3. 재현성이 근본적으로 달라졌다

baseline은 회차를 거듭할수록 무너졌다 — 총 요청수가 6천에서 22만으로 36배 튀고, 중앙값은 50초에서
1초 미만으로, 최댓값은 16분까지 벌어졌다. "앱이 회차 사이에 회복되지 않는다"는 신호였다.
재설계본은 10회 내내 요청수 편차 2%, 중앙값 81~174ms, 정착시간 2.27~2.35초 안에 들어온다.
**측정할 때마다 같은 답이 나온다는 것 자체가 결과다.**

### 4. 정착 시간이 짧아졌다 — 예상과 반대 방향

DB 쓰기를 컨슈머로 넘겼으니 정착 시간이 **늘어날** 것으로 예상했는데(비동기니까), 오히려 줄었다
(2.46~11.43s → 2.27~2.35s). 응답을 보낸 뒤에 저장하지만, 저장 자체가 락 대기 없이 진행되기 때문에
전체가 끝나는 시점은 오히려 빨라진 것으로 보인다. baseline의 정착 시간이 최대 11초까지 늘어난 것도
동기 구조라서가 아니라 락 경합으로 마지막 요청들이 늦게 처리됐기 때문일 가능성이 높다.

### 5. p95는 해결되지 않았다 — 원인은 예약이 아니라 폴링

p95가 여전히 60초 타임아웃에 붙어 있다. 단계별로 나눠 보면 원인이 드러난다 (7회차):

```
queue_poll  VU 600  : p50 = 29,724ms   VU 1000 : p50 = 59,268ms
queue_enter VU 1500 : p95 = 59,629ms
booking     VU 1000 : p50 =    175ms
```

**예약 자체는 빠른데 대기열 폴링이 앱을 포화시킨다.** VU 2000이 0.5초 간격으로 폴링하면 초당 4천
요청이고, 이 앱은 그 근처에서 이미 포화한다(전체 처리량 약 115 req/s). 즉 p95의 꼬리는 재설계가
남긴 병목이 아니라 **폴링 방식이 만든 새 비용**이다.

- 폴링 간격을 늘리면 즉시 완화되지만 입장 체감 지연이 그만큼 늘어난다.
- 근본적으로는 폴링 대신 SSE/WebSocket으로 밀어 주는 편이 맞다.
- VU 2000 구간에 `booking` 데이터가 아예 없는 것도 같은 이유다 — 그 구간의 VU는 폴링 대기에서
  예산을 소진하고 예약까지 도달하지 못한다.

**이 항목은 미해결로 남긴다.** 다음에 손볼 곳이 어디인지가 이번 측정의 결론 중 하나다.

### 6. 부하의 상당량을 대기열이 흘려보낸다

매 회차 약 2,420건이 `queue_timeout`으로 끝났다 — 입장 정원(`admission-capacity` 100)에 막혀
예약 단계까지 가지 못한 요청들이다. 예약 지연이 좋아 보이는 데에는 **대기열이 부하를 막아 준 몫이
섞여 있다.** "예약이 200배 빨라졌다"가 아니라 "대기열이 부하를 흡수하고, 통과한 요청은 기다리지
않는다"로 읽어야 정확하다.

Phase 4에서 입장 permit을 명시적으로 반납하도록 바꿨는데도 이 수치는 회차당 2,400건대로 거의 그대로다
(Phase 3 측정: 2,401~2,492건 / 현재: 2,392~2,459건). 반납이 회전을 늘려 주긴 하지만, 예약까지 도달하는 사용자가 애초에
좌석 수(30) 근처로 묶여 있어 전체 통과량을 바꾸지는 못한다는 뜻이다. 병목은 permit 회전이 아니라
아래 5번의 폴링 포화다.

### 7. Phase 4의 마지막 방어선은 실제로 발동했다

좌석 행 조건부 갱신과 `UNIQUE(timetable_id, active_marker)`는 "앞단이 전부 틀렸을 때"를 위한
장치라 부하테스트만으로는 작동 여부를 알 수 없다 — 오버부킹이 0이어도 그게 Redis 카운터 덕인지
DB 제약 덕인지 구분되지 않는다. 그래서 실제 MySQL 위에서 따로 검증했다
(`TimeTableOccupancyConcurrencyTest`, 좌석 10개에 80스레드 동시 진입).

```
Duplicate entry '01a043ef-6289-7b31-ae74-5452ccc96a87-1'
  for key 'timetable_occupancy.unique_active_occupancy'
```

끝의 `-1`이 `active_marker` 값이다. 잠금을 일부러 우회한 경로뿐 아니라 **동시성 테스트에서 행 잠금을
빠져나간 경합도 이 제약에 걸려 거절됐다.** 두 겹이 각자 다른 일을 하고 있다는 증거다.

> 이후 1번 겹을 조건부 `UPDATE`로 바꿨다. 바꾼 뒤에는 이 로그가 "일부러 우회한 경로" 하나에서만
> 찍힌다 — `docs/perf/row-lock-select-vs-update.md` 참고.

스키마는 테스트에 DDL을 베껴 쓰지 않고 `db/migration`의 실제 파일을 읽어서 세운다 — 베껴 쓰면
마이그레이션이 틀려도 테스트는 통과하기 때문이다.

## 환경에서 드러난 결함 (측정 자체와 별개)

측정을 반복하는 과정에서 인프라 설정 결함 두 개가 드러났다. 둘 다 이번에 고쳤다.

**1. MySQL 데이터가 바인드 마운트였다.** `compose.yaml`에 `mysql-data` 네임드 볼륨이 **선언은 돼
있는데 실제로는 연결되지 않고** 호스트 디렉터리(`./mysql_data`)를 쓰고 있었다. 측정 도중 그
디렉터리가 사라지자 InnoDB가 리두 로그를 만들지 못해(`error 1504`) FATAL로 자폭했고, 5회차가
통째로 날아갔다. 네임드 볼륨으로 연결해 호스트 쪽 사정과 분리했다.

**2. Kafka 헬스체크가 항상 실패하고 있었다.** 명령어 이름에 `.sh`가 빠져 있었고, 고친 뒤에도
`/opt/kafka/bin`이 헬스체크 셸의 PATH에 없어 계속 127로 죽었다. 절대경로로 바꾸니 **브로커 3대가
처음으로 healthy가 됐고 kafka-ui도 처음 기동했다.** 그동안 `unhealthy` 표시는 전부 거짓 경보였고,
그래서 진짜 브로커 장애와 구분되지 않는 상태였다.

## 남은 결함 (측정 중 발견)

- **하류 `reservation` 테이블이 여전히 0건.** Phase 3에서 토픽명 불일치를 고쳐 컨슈머가 이벤트를
  실제로 받게 됐지만, 내부 API 호출에 토큰을 싣지 않아 401로 실패한다. 토픽명 결함에 가려져 있던
  별개 결함이고 서비스 간 인증 설계가 필요해 이번 스코프에서 제외했다. 좌석 정합성과 예약 지연
  측정에는 관여하지 않는다.
- **`AcquireTimeTableSemaphore` / `ReleaseSemaphore`가 참조 0인 채로 남아 있다.**
