# 배치 스케줄링 실전 선택기: @Scheduled vs Quartz vs Jenkins, 어떤 것을 선택해야 할까?

## 들어가며

"매월 시간표를 미리 생성하는 배치 작업이 필요해"라는 요구사항을 받았을 때, 가장 먼저 든 생각은 **"어떻게 실행시킬 것인가"**였다. Spring의 `@Scheduled` 어노테이션으로 간단하게? Quartz로 안정적으로? 아니면 Jenkins 같은 외부 인프라를 활용해서?

언뜻 보면 세 방식 모두 같은 결과를 낼 수 있을 것 같지만, 실제 운영 환경에서는 **성능**, **안정성**, **운영 편의성** 면에서 큰 차이가 있었다.

이번 글에서는 **예약 시스템 프로젝트**에서 월간 시간표 생성 배치의 스케줄링 방식을 선택하면서 마주한 현실적인 고민들과 최종적으로 **Jenkins**를 선택한 이유를 솔직하게 공유하려고 한다.

## 1. 배치 스케줄링, 무엇을 선택해야 할까?

월간 시간표 생성 배치가 필요했다. 문제는 **"어떻게 실행시킬 것인가"**였다.

## 2. 3가지 실행 방식 비교

### @Scheduled: 간단하지만 위험한 선택

```kotlin
@Scheduled(cron = "0 0 0 1 * *")
fun generateMonthlyTimeTable() {
    // 배치 로직
}
```

- **장점**: 코드 몇 줄로 완성
- **문제**: 웹 서비스와 같은 JVM에서 실행 → 메모리 경합 위험

### Quartz: 안정적이지만 복잡함

- **장점**: 클러스터링 지원, 상태 관리
- **문제**: 여전히 웹 애플리케이션과 리소스 경합

### Jenkins: 완전 분리의 선택

```bash
java -jar reservation-batch.jar --job.name=timeTableJob
```

- **장점**: 웹 서비스와 완전 분리
- **단점**: 추가 인프라 관리 부담

## 3. Jenkins를 선택한 이유

**결정적 한마디**: *"배치가 터져도 예약은 받을 수 있어야 한다"*

### 핵심 이유

1. **완전한 분리**: 웹 서비스와 독립적 실행
2. **운영팀 친화**: 기존 Jenkins 인프라 활용
3. **장애 격리**: 배치 실패가 웹 서비스에 영향 없음

## 4. 실무의 현실

### @Scheduled 방식의 실제 문제
- 대량 데이터 처리 시 웹 애플리케이션 메모리 경합
- 배치 실행 중 API 응답 지연
- 다중 인스턴스에서 중복 실행 위험

### Jenkins 분리 방식의 실제 이점
- 웹 서비스와 완전 독립적 실행
- 배치 장애 시에도 예약 시스템 정상 동작
- 운영팀 기존 프로세스 활용

## 마치며

배치 스케줄링 선택의 핵심은 **"어떻게 실행시킬 것인가"**다.

- **@Scheduled**: 간단하지만 리소스 경합 위험
- **Quartz**: 안정적이지만 여전히 같은 JVM
- **Jenkins**: 추가 인프라 부담이지만 완전한 분리

우리의 선택: **Jenkins**
이유: 배치가 터져도 예약은 받을 수 있어야 하니까.
