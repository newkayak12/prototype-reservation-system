# RFC-011 — 프로젝션 재구축·catch-up 운영

- **상태**: Open · 논의 중 · 2026-06-15
- **선행**: [[RFC-001-v2-cqrs-and-event-sourcing]] · 인덱스 [[RFC-INDEX]]
- **닫으면**: [[03-read-model]] 보강 + 신규 ADR(프로젝션 운영 전략) 가능

## 맥락

[[RFC-002-read-model-consistency]]가 *무엇을* 읽기 모델에 두느냐의 문서라면, 이 RFC는 *그것을 어떻게 운영하느냐*의 문서다. 읽기 모델은 이벤트로부터 파생된 2차 구조물이다. 이벤트 스토어와 토픽이라는 진실 원천이 있고, 프로젝터가 그것을 소비해 read model 테이블을 채운다. 그렇다면 그 read model은 언제든 버려도 되고, 다시 만들 수 있어야 한다 — 스키마가 바뀌었을 때, 프로젝터에 버그가 있어 잘못 채워졌을 때, 새 read model을 운영 중에 투입할 때. 이 "다시 만든다"가 재구축(rebuild)이고, 다시 만드는 동안 흘러 들어온 신규 이벤트를 따라잡는 것이 catch-up이며, 그 사이 읽기 트래픽을 끊지 않는 것이 무중단 교체다. 이것은 ES/EDA를 택한 순간 따라오는 핵심 운영 주제인데, 정작 어느 design_doc에도 절차로 적혀 있지 않다(T-09 백로그). 이 RFC가 그 절차의 방향을 prose로 정리한다.

이하는 추론과 입장이지, 확정된 표가 아니다. 이의가 있으면 그 지점에서 갈라치면 된다.

## 논의

### 재구축의 진실 원천을 무엇으로 둘 것인가

read model을 처음부터 다시 채우려면 과거 이벤트 전체를 어딘가에서 다시 읽어야 한다. 후보는 둘이다. Kafka 토픽을 from-beginning으로 재소비하거나, 이벤트 스토어를 직접 리플레이하거나. 또는 둘을 혼합할 수도 있다.

토픽 재소비는 매력적으로 들리지만 함정이 있다. [[RFC-003-messaging-delivery]]에서 토픽 보존기간을 짧게 가져가기로 한 이상, 토픽은 "최근 이벤트의 전달 통로"일 뿐 "전체 이력의 보관소"가 아니다. retention이 7일이라면 8일 전 이벤트는 토픽에 없고, from-beginning이라 해봐야 보존 경계까지밖에 못 거슬러 올라간다. 그 위에서 read model을 재구축하면 경계 이전 상태가 통째로 비어버린다.

그래서 내 입장은 **재구축의 기본 원천을 이벤트 스토어 리플레이로** 둔다. 이벤트 스토어는 정의상 전체 이력을 무한 보관하는 진실 원천이고, ES 컨텍스트(`reservation`·`timetable`·`restaurant`)는 거기서 애그리거트별·전역 스트림을 처음부터 다시 읽어 프로젝션을 재구축한다. 토픽은 재구축 원천이 아니라 실시간 catch-up 구간에서만 쓴다 — 즉 "스토어로 과거를 채우고, 토픽 구독으로 현재를 따라잡는다"는 2단 구조다. 비-ES 컨텍스트처럼 이벤트 스토어가 없는 쪽은 사실 재구축할 진실 원천이 약하므로, 이 경우엔 원본 테이블에서 read model을 다시 빌드하는 별도 경로를 쓴다 — 여기에 토픽 from-beginning을 끼우는 건 retention 때문에 신뢰할 수 없다고 본다. (이의 여지: 비-ES 쪽 재구축 경로가 ES 쪽과 절차가 갈리면 운영이 복잡해진다는 반론이 가능하다. 다만 애초에 진실 원천이 다른 두 세계라 절차가 같을 수 없다고 본다.)

### 재구축 중에 읽기를 끊지 않으려면

스키마가 바뀌거나 대량 재구축이 필요할 때, read model 테이블을 그 자리에서(in-place) 비우고 다시 채우면 채우는 동안 읽기 결과가 불완전하다. 컷오버 전에 섀도로 빌드해 비교 후 전환하는 방법도 있지만, 그건 검증 정밀도가 높을 뿐 가용성 문제 자체는 blue-green과 같은 방식으로 푼다.

내 입장은 **blue-green 프로젝션 스왑**이다. 현재 트래픽이 보는 테이블(blue)은 그대로 두고, 새 테이블(green)을 이벤트 스토어 리플레이로 처음부터 빌드한다. green이 catch-up까지 끝나 blue와 동등해지면, 읽기 경로가 가리키는 대상을 green으로 원자적으로 스왑한다(뷰/별칭 교체 또는 라우팅 스위치). blue는 롤백 안전망으로 잠시 남겼다가 폐기한다. in-place는 절차가 단순하지만 재구축 중 읽기 가용성을 희생하므로 기본값으로 두지 않는다. (이의 여지: 테이블 두 벌을 동시에 유지하는 스토리지·운영 비용, 그리고 스왑의 원자성을 무엇으로 보장하느냐 — 별칭인지 애플리케이션 레벨 스위치인지 — 는 Design에서 검증한다.)

### catch-up이 끝났는지를 무엇으로 판단하고, 그게 readiness와 어떻게 묶이나

green을 스왑하거나 새로 띄운 프로젝터에 트래픽을 보내려면, 그것이 "충분히 따라잡았다"는 판정이 필요하다. 판정 없이 라우팅하면 lag이 큰 read model로 트래픽이 흘러 신선도가 깨진다([[RFC-002-read-model-consistency]]).

내 입장은 **catch-up 완료를 readiness 신호로 승격**하는 것이다. 단순히 프로세스가 떠 있다고 ready가 아니라, "Kafka(또는 스토어) 연결 + 목표 오프셋 도달(lag 0 또는 임계 이하) = ready"를 규약으로 잡는다. [[09-deployment-runtime]]의 readiness 프로브와 [[RFC-007-deployment-infra-ops]]의 catch-up 완료 규약이 여기에 직접 연결된다 — readiness가 거짓인 동안 라우팅을 보류하면, 미완성 프로젝션으로 가는 트래픽이 자연히 차단된다. 다만 "lag이 어느 수준 이하면 따라잡았다고 볼 것인가"의 구체적 임계는 지금 못 박지 않는다. 그건 실제 이벤트량·재구축 시간을 측정해야 정할 수 있는 운영 수치이므로 **측정 트리거로 남기고**, 규약(읽기 트래픽은 readiness=true에만)만 지금 확정한다.

### 프로젝터가 같은 이벤트를 두 번 봐도 안전한가

재구축이든 catch-up이든 장애 복구든, 프로젝터는 같은 이벤트를 다시 적용하게 된다. 토픽 전달이 at-least-once인 한([[RFC-003-messaging-delivery]]) 중복은 예외가 아니라 정상이다. 그러니 "두 번 적용해도 결과가 같다"가 전제되지 않으면 재구축 자체가 read model을 오염시킨다.

내 입장은 **프로젝터를 멱등하게 강제**하는 것이다. 구체적으로는 (1) 단순 삽입이 아니라 키 기반 upsert로 쓰고, (2) 이벤트에 실린 버전/시퀀스를 가드로 두어 이미 반영된(또는 더 최신인) 상태에 과거 이벤트를 덮어쓰지 않으며, (3) 프로젝션별 처리 오프셋을 추적해 어디까지 봤는지 안다. 자연 멱등(예: 절대값 상태 치환)이 성립하는 프로젝션은 버전 가드를 생략할 수 있지만, 누적·증분 갱신이 들어가는 프로젝션은 반드시 가드가 필요하다 — 증분은 두 번 더하면 틀리기 때문이다. 이는 [[RFC-003-messaging-delivery]]의 inbox 논의와 같은 멱등성 문제의 read-side 표현이다. (이의 여지: 멱등을 프로젝터 코드에 둘지, inbox 같은 공통 인프라로 한 번에 풀지 — 책임 배치는 Design에서 검증.)

### 읽기 모델 스키마가 바뀌면 재구축을 어떻게 트리거하나

read model 스키마는 진실 원천이 아니라 파생 구조라, 바꾸는 비용이 원칙적으로 싸다 — 버리고 다시 만들면 되니까. 문제는 "언제, 어떻게 다시 만드느냐"의 절차다.

내 입장은 **프로젝션에 버전을 태깅하고, 버전이 바뀌면 새 버전 테이블을 blue-green으로 재구축**하는 것이다. 스키마 변경을 곧 새 프로젝션 버전의 등장으로 취급하면, 위에서 정한 blue-green 스왑 절차가 그대로 재사용된다 — 별도의 "스키마 마이그레이션" 메커니즘을 따로 만들 필요가 없다. 자동 재구축을 어디까지 자동화할지(배포 시 버전 불일치 감지 → 자동 빌드 트리거)는 매력적이지만, 대량 재구축을 무인으로 도는 건 위험이 있어 **트리거 조건만 규약화하고 실행은 운영 승인 단계를 두는** 쪽으로 기운다. (이의 여지: 점진 전환 — 구버전 읽기 + 신버전 백필 동시 운영 — 이 blue-green보다 나은 경우가 있는지는 Design에서 검증.)

### 운영 중 신규 프로젝션을 어떻게 끼워 넣나

새 read model을 무중단 운영에 투입하는 건 재구축의 특수 케이스다. 핵심 위험은 이음매다 — 과거 이벤트를 백필하는 동안 흘러 들어온 신규 이벤트를 놓치면 gap이 생기고, 백필과 실시간 구독이 겹치면 중복이 생긴다.

내 입장은 **"구독 먼저, 백필 나중, 멱등으로 봉합"** 순서다. 먼저 실시간 구독을 켜서 현재 시점 이후 이벤트를 받기 시작하고(버퍼/적용), 그 다음 이벤트 스토어에서 과거를 백필한 뒤, 두 구간이 겹치는 부분은 위에서 정한 멱등 프로젝터(upsert + 버전 가드)로 흡수한다. 이 순서면 백필과 실시간 사이에 빈틈(gap)이 생기지 않고, 겹침은 멱등이 자동으로 처리한다. 반대로 "백필 먼저, 구독 나중"은 백필이 끝나는 시점과 구독 시작 시점 사이의 이벤트를 놓칠 수 있어 택하지 않는다. catch-up이 끝나기 전엔 위의 readiness 규약대로 트래픽을 보내지 않는다.

## Design으로 넘기는 것

방향은 위에서 정했고, 다음은 검증·수치·구체 메커니즘이라 Design에서 다룬다.

- blue-green 스왑의 **원자성 보장 수단** — DB 뷰/별칭 교체 vs 애플리케이션 라우팅 스위치, 롤백 윈도.
- catch-up 완료 판정의 **lag 임계값** — 측정 기반(실제 이벤트량·재구축 소요시간) 운영 수치.
- 멱등 책임의 **배치** — 프로젝터 코드 내부 vs 공통 inbox 인프라.
- 이벤트 스토어 리플레이의 **성능·부하** — 대량 리플레이가 운영 스토어에 주는 영향, 병렬 리플레이 필요 여부. 스냅샷 자체는 [[RFC-004-event-store-schema-evolution]]에서 두기로 이미 확정했으므로(존재 여부는 미정이 아니다), 여기서 다룰 것은 *그 애그리거트 스냅샷을 투영 재구축 리플레이 가속에 활용할 수 있는가* — 현재 상태만 반영하는 read model이면 최신 스냅샷+이후 이벤트로 단축 가능하지만, 전체 이력을 펼쳐야 하는 투영은 풀 리플레이가 불가피하다 — 의 판단이다.
- 비-ES 컨텍스트의 **재구축 경로** — 원본 테이블 기반 빌드 절차 구체화.
- 스키마 변경 시 **자동 재구축 트리거 자동화 범위** — 무인 자동 vs 운영 승인 게이트.
