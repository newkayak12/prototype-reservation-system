# RFC-004 — 이벤트 스토어·스키마 진화

- **상태**: 🏷 합의 (2026-06-21) · design [[08-event-store-lifecycle]] 반영 · ADR [[05.event-store-mysql-table]] 비준 대기 · 스키마 진화는 [[RFC-023-event-schema-evolution]]로 분리
- **선행**: [[RFC-001-v2-cqrs-and-event-sourcing]] · 인덱스 [[RFC-INDEX]]
- **닫으면**: [[08-event-store-lifecycle]] · [[05.event-store-mysql-table]] 보강·비준 (스키마 진화·업캐스터·[[10.event-schema-evolution]]은 [[RFC-023-event-schema-evolution]]가 닫음)

## 맥락

[[RFC-001-v2-cqrs-and-event-sourcing]]에서 쓰기 모델의 진실 원천을 append-only 이벤트 스토어로 잡았다. 메커니즘 자체 — MySQL에 이벤트를 추가만 하고, N마다 스냅샷을 찍고, 읽을 때 업캐스팅하고, 페이로드는 JSON으로, 디스크리미네이터는 논리 타입명(eventType)으로 — 는 그 논의에서 이미 합의됐다. 여기서 다루는 건 그 메커니즘이 운영에 닿았을 때 드러나는 긴장들이다.

append-only는 깔끔한 개념이지만, "절대 지우지 않는다"는 약속은 곧장 네 갈래의 압력을 만든다. 첫째, 스트림이 길어지면 재구성이 느려진다 — 그래서 스냅샷을 둔다. 그런데 스냅샷을 두는 순간 "얼마나 자주, 몇 개나, 이벤트와 정말 일치하는가"라는 질문이 따라온다. 둘째, 절대 지우지 않으면 테이블은 무한히 자란다 — 그래서 보존·아카이빙·콜드 이관이 필요하고, "언제 식은 것으로 볼 것인가"를 정해야 한다. 셋째, append-only는 시간 축을 공짜로 주는 것처럼 보인다 — 그래서 "과거 시점 재구성(temporal)을 어디까지 열 것인가"가 떠오른다. 넷째, 이벤트는 영원히 남는데 코드는 계속 바뀐다 — 그래서 옛 이벤트를 새 코드로 읽는 스키마 진화 장치가 필요하다.

아래는 이 네 압력을 따라가며 내 입장과 근거를 적은 것이다. 결정처럼 보이는 문장이라도 반박을 환영하며, 수치가 걸린 것은 운영·k6 측정으로 검증할 자리를 명시한다. 다만 넷째 압력(스키마 진화 — 업캐스터·eventType 매핑·Avro/Protobuf 스키마 레지스트리)은 저장 라이프사이클과 결이 달라 **[[RFC-023-event-schema-evolution]]로 분리**했다. 이 문서는 스토어 라이프사이클(스냅샷·파티셔닝·콜드·시점 질의·직렬화 규약)에 집중한다.

## 논의

### 스냅샷을 얼마나 자주 찍을 것인가

스냅샷 주기 N의 초안은 50~100이었다([[05.event-store-mysql-table]] · [[02-write-model]] · [[08-event-store-lifecycle]] · [[11-environments-and-testing]]). 여기서 가르고 싶은 건 정책과 수치다. "스냅샷 주기를 둔다, 트리거는 이벤트 카운트다"는 지금 정해도 되지만, 절대 N은 책상에서 정할 값이 아니다. 재구성 지연과 스냅샷 쓰기 비용은 트레이드오프 곡선이고, 그 곡선은 [[11-environments-and-testing]] §5.4의 k6 스윕으로 그려야 보인다.

그래서 `N=100`을 기본값으로 두되 `aggregate_type`별로 설정 가능하게 열어둔다. 재검토 트리거는 명시해 둔다 — 재구성 p99가 50ms를 넘으면 k6 스윕으로 N을 조정한다. 예약 도메인은 한 애그리거트의 스트림이 짧아서, 100이면 스냅샷이 사실상 거의 찍히지 않는다. 이건 단점이 아니라 의도다. 짧은 스트림에 공격적으로 스냅샷을 찍는 건 과최적화다. (이의 여지: 장수 애그리거트가 섞여 있다면 타입별 N의 기본값을 더 잘게 나눠야 할 수 있다 — 비중은 측정으로 확인한다.)

### 스냅샷을 몇 개나 보관할 것인가

선택지는 최신 1개만 덮어쓰며 유지하느냐, 디버깅·롤백용으로 최근 N개를 보존하느냐다([[08-event-store-lifecycle]]). 보존하면 과거 시점 재구성이나 디버깅이 편하지만, 보관량이 늘고 GC 기준을 또 만들어야 한다.

나는 핫(DB)에는 최신 1개만 유지하는 쪽이다 — 스냅샷은 언제든 버릴 수 있는 최적화일 뿐 진실 원천은 이벤트이므로, 활성 경로가 여러 개를 들고 있을 이유가 없다(과거 시점이 필요하면 그 시점까지 이벤트를 리플레이, 아래 temporal 갈래). 다만 덮어쓸 때 직전 스냅샷을 *버리지 않고* S3 Glacier로 이관한다. 핫은 1개로 가볍게 유지하되, 밀려난 과거 스냅샷은 콜드(Glacier)에 거의 공짜로 쌓아 디버깅·롤백·감사에 쓴다 — 콜드를 S3로 두는 흐름(아래 콜드 갈래)과 같은 결이고, DB 용량·백업 부담은 지지 않는다. 안전 교체는 현재+직전 2-슬롯 토글로 원자적으로 갈아끼우고, 교체가 확정되면 밀려난 슬롯을 Glacier로 export한다. 이건 "핫에 최근 N개 보존"이 아니라 **1핫 + 콜드(Glacier) 아카이브** 구조다. (정합성 의존이 아니라 편의 — 진실은 여전히 이벤트다.)

### 스냅샷이 이벤트와 정말 일치하는가

스냅샷을 최적화로 신뢰하려면 "스냅샷 = 0..version 이벤트를 재생한 결과"라는 등식이 깨지지 않아야 한다([[08-event-store-lifecycle]]). 여기서도 정책과 수치를 가른다 — 검증을 돌린다는 건 지금 정하고, 얼마나 자주·어느 표본률로 돌릴지는 운영 부하를 보고 튜닝한다.

내 입장은 2겹 검증이다. 하나는 스냅샷을 만든 직후 인라인으로 한 번 검증하는 것 — 저비용이고 항상 돈다. 다른 하나는 배경에서 주기적으로 표본을 떠서 검증하는 것 — 시간이 지나며 누적되는 드리프트를 조기에 잡는다. 불일치가 잡히면 그 스냅샷은 폐기하고 이벤트 리플레이로 재생성하며(아래 스냅샷 진화 갈래와 같은 처방), 알람을 띄운다. 표본률과 주기의 구체 값은 운영 측정에 맡긴다.

### 무엇을 단위로 보존·파티셔닝할 것인가

선택지는 시간(생성월 등) 파티셔닝이냐 `aggregate_type` 파티셔닝이냐다([[05.event-store-mysql-table]] · [[08-event-store-lifecycle]]). 긴장은 분명하다 — 보존·아카이빙은 시간이 자연스러운 축이지만, 핫패스 조회는 aggregate 단위(특정 스트림 재생)다. 두 축이 어긋나면 핫패스가 여러 파티션을 가로지르며 느려진다.

나는 시간(생성월) 파티셔닝을 택한다. 핵심 근거는 예약 애그리거트의 수명이 짧다는 것이다. 수명이 짧으면 한 스트림이 한두 파티션에 모이고, 따라서 핫패스 리플레이가 파티션 경계를 거의 넘지 않는다. 시간 축의 이득(옛 파티션을 통째로 drop하거나 이관해 보존·콜드 이관을 처리)은 그대로 가져가면서 핫패스 손해는 거의 없다. 스트림 조회는 `aggregate_id` 인덱스로 커버한다. (이의 여지: 장수 애그리거트의 비중이 생각보다 크면 이 전제가 흔들린다 — 측정으로 확인한다.)

### 언제 식은 스트림으로 볼 것인가

콜드로 이관해도 되는 "종료된 스트림"의 정의는 기술이 줄 수 없다. 예약이 끝났다는 건 도메인이 말하는 것이다([[08-event-store-lifecycle]]). 그래서 핫/콜드 경계 판정은 도메인 종결 상태 + 유예 기간으로 잡는다 — 미종결이거나 유예 안에 있으면 핫, 종결됐고 유예가 지났으면 콜드. 유예는 감사·분쟁 윈도우다(예: 종결 +90일). 컨텍스트마다 어떤 상태가 "종결"인지는 목록으로 모아야 하는데, 그건 각 도메인 작업에서 채운다. RFC 단계에서 도메인 이벤트 카탈로그를 먼저 확정할 필요는 없다 — 경계 기준의 형태(상태+유예)만 합의하면 된다.

### 콜드 스토리지를 어디에 둘 것인가

같은 DB의 아카이브 테이블이냐, S3 같은 오브젝트 스토리지냐다([[08-event-store-lifecycle]] · [[11-environments-and-testing]]). 콜드 데이터는 재구성 빈도가 낮으니, 판단 기준은 복원 경로와 운영 단순성이다.

나는 오브젝트 스토리지(S3)를 택한다. 흐름은 이렇다 — 식은 시간 파티션(위 파티셔닝 갈래)을 S3로 export한 뒤 drop하고, 드물게 복원이 필요하면 로드해서 리플레이한다. DB 안에 아카이브 테이블을 두면 결국 같은 인스턴스의 용량·백업 부담을 계속 지는데, 콜드는 그럴 가치가 없다. 셰딩(crypto-shredding 등)이 콜드까지 닿는 경로는 여기서 풀지 않고 [[RFC-005-pii-security]]에 맡긴다. 검증은 localstack S3로 한다([[RFC-009-testing-quality-gates]]).

### 시점 질의를 어디까지 열 것인가

append-only는 "as-of 재구성"을 거의 공짜로 주는 듯 보인다. 그래서 이걸 운영·디버깅에만 쓸 것인가, 일반 API로도 열 것인가가 문제다([[08-event-store-lifecycle]]). 제품 기능으로 열면 인덱스·성능·권한 부담이 따라붙는다.

나는 운영·디버깅 한정을 기본으로 둔다. temporal 질의는 사고 조사나 데이터 복구에는 값지지만, 제품 화면이 정말 그걸 요구한다는 증거가 나오기 전에 일반 API로 노출하면 비용만 미리 진다. 화면 요구가 증명되면 그때 다시 본다.

### 스키마 진화(업캐스터·eventType 매핑·스키마 레지스트리)는 별도 RFC로 분리

옛 이벤트를 새 코드로 읽는 **업캐스터**(명시 등록 vs 어노테이션 스캔), 논리 타입명(**eventType**)↔클래스 매핑(`@JsonTypeName` 스캔 vs 명시 빈), JSON+업캐스팅을 **Avro/Protobuf 스키마 레지스트리**로 갈아탈지 — 이 세 갈래는 *저장소를 시간 축에서 운영하는* 이 RFC의 라이프사이클 관심사와 결이 다르다. 직렬화 계약이 시간에 따라 진화하는 문제라 한 묶음으로 **[[RFC-023-event-schema-evolution]]**에서 다룬다(원래 여기 있던 입장 — 명시 등록 레지스트리 빈, `@JsonTypeName` 스캔 배제, Avro/Protobuf YAGNI 보류 — 도 그쪽으로 옮겼다).

### 스냅샷 포맷이 바뀌면 어떻게 할 것인가

이벤트는 업캐스팅으로 진화시킨다 치고, 스냅샷 포맷 자체가 바뀌면? 선택지는 옛 스냅샷을 폐기하고 이벤트 재생으로 재생성하느냐, 스냅샷도 이벤트처럼 업캐스팅하느냐다([[10.event-schema-evolution]] · [[08-event-store-lifecycle]]).

나는 폐기 후 이벤트 리플레이로 재생성하는 쪽이다. 이건 위에서 스냅샷을 "버릴 수 있는 최적화"로 본 입장과 일관된다 — 스냅샷이 최적화일 뿐이라면, 포맷이 바뀌었을 때 굳이 그것까지 업캐스팅 코드를 둘 이유가 없다. 배경에서 이벤트를 다시 재생해 새 포맷으로 찍으면 된다. 스냅샷은 업캐스팅하지 않는다 — 업캐스팅은 이벤트에만 둔다.

### JSON 페이로드를 어떻게 직렬화할 것인가

JSON 방향은 이미 합의됐고, 남은 건 직렬화 규약의 세부다([[05.event-store-mysql-table]]) — null·기본값 처리, enum 표현, 시간·금액 타입, 모르는 필드 처리, 컬럼 타입. 세부지만 한번 저장된 이벤트는 영원히 남으니, 규약을 흔들면 옛 데이터가 깨진다. 그래서 여기서 못박아 둔다.

저장은 MySQL JSON 컬럼으로 한다. 역직렬화 시 모르는 필드는 무시한다(forward-compat — 새 필드가 추가된 이벤트를 옛 코드가 만나도 깨지지 않게). enum은 이름(문자열)으로, 시간은 ISO-8601 UTC로, 금액은 정수 최소단위(분 단위 등)로 적고, null은 생략하지 않고 명시적으로 직렬화한다. (이의 여지: TEXT 대비 JSON 컬럼의 인덱싱·검증 이득이 핫패스에서 실제로 값을 하는지는 측정으로 확인할 수 있다.)

## Design으로 넘기는 것

방향은 위에서 잡았고, 다음은 검증과 세부다.

- **스냅샷 주기 N과 검증 표본률** — `N=100` 기본·타입별 설정. 재구성 p99 > 50ms 트리거에서 k6 스윕으로 조정, 인라인+배경 검증의 표본률·주기는 운영 측정으로. → [[08-event-store-lifecycle]] · [[11-environments-and-testing]] §5.4
- **스냅샷 보관·Glacier 이관 경로** — 핫 1개 + 밀려난 직전본 S3 Glacier export(2-슬롯 토글 교체 확정 후). 콜드 S3 흐름과 단일화. → [[08-event-store-lifecycle]]
- **파티셔닝·콜드 이관** — 시간(월) 파티셔닝, 핫/콜드 경계(종결 상태+유예), S3 export/복원 경로 확정. 장수 애그리거트 비중 측정. → [[08-event-store-lifecycle]] · [[05.event-store-mysql-table]]
- **컨텍스트별 종결 상태 목록** — "종료"의 정의를 도메인 작업에서 채움.
- **직렬화 규약** — JSON 컬럼·필드 무시·enum·시간·금액·null 규약 확정. → [[05.event-store-mysql-table]]
- (업캐스터·eventType 레지스트리·Avro/Protobuf 스키마 레지스트리 도입 기준은 **[[RFC-023-event-schema-evolution]]**로 분리.)
