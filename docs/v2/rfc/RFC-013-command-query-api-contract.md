# RFC-013 — command/query API 계약·비동기 command

- **상태**: Open · 논의 중 · 2026-06-15
- **선행**: [[RFC-001-v2-cqrs-and-event-sourcing]] · 인덱스 [[RFC-002-decision-queue]]
- **닫으면**: 신규 design_doc(API 계약) + ADR 가능

## 맥락

[[RFC-001-v2-cqrs-and-event-sourcing]]에서 쓰기와 읽기를 갈라놓기로 방향을 잡았지만, 그 결정의 *외부 인터페이스*는 어느 design_doc에도 적혀 있지 않다. 내부적으로 command 핸들러와 read model을 나눈다는 것과, 그것을 HTTP API로 어떻게 노출하느냐는 별개의 문제다. 클라이언트가 보는 것은 결국 엔드포인트와 응답 바디뿐이고, 그 표면이 CQRS의 성질을 정직하게 드러내지 못하면 내부를 아무리 잘 나눠도 클라이언트는 V1과 똑같은 가정을 하고 깨진다.

가장 정직해야 할 지점은 비동기다. ES 위에서 쓰기를 받으면 이벤트는 즉시 커밋되지만 그 이벤트로 read model 프로젝션이 갱신되는 것은 비동기다. 즉 "쓰고 바로 그 결과를 읽을 수 없다"가 V2의 기본값이다. V1의 동기 CRUD에 익숙한 클라이언트(그리고 우리 자신)는 `POST` 직후 `GET`이 방금 쓴 것을 돌려주리라 기대하는데, V2에서는 그 기대가 더 이상 보장되지 않는다. API 계약은 이 사실을 숨기지 말고 표면에 새겨야 한다. 그렇지 않으면 클라이언트는 경합에서 산발적으로 실패하고, 그 실패는 재현이 어렵다.

그래서 이 문서는 외부 표면을 한 묶음으로 추론한다. command를 어떤 모양으로 받을지, 비동기 응답을 어떻게 돌려줄지, 중복 제출을 어떻게 막을지, 실패를 어떻게 구분해 알릴지, 경로를 어떻게 가르고 버전을 어떻게 매길지, query는 어떻게 조회하게 할지.

## 논의

### command를 무슨 모양으로 받을까

먼저 command 엔드포인트의 스타일이다. 두 갈래가 있다. 하나는 V1을 이어 자원 CRUD(`PUT /reservations/{id}`)로 받는 것이고, 다른 하나는 행위 단위의 task-based command(`POST /reservations/{id}/cancel`)로 받는 것이다.

나는 task-based로 가야 한다고 본다. 이유는 V2의 안쪽이 이미 그 모양이기 때문이다. [[RFC-001-v2-cqrs-and-event-sourcing]]에서 쓰기를 도메인 이벤트로 적재하기로 했는데, 이벤트는 본질적으로 "무슨 일이 일어났다"는 행위 기록이다. 클라이언트가 `PUT`으로 자원 전체를 덮어쓰는 모양으로 들어오면, 우리는 그 diff를 역산해 어떤 이벤트가 발생했는지 추측해야 한다 — `Cancelled`인지 `Rescheduled`인지를 필드 비교로 복원하는 것은 손실이 크고 깨지기 쉽다. command가 처음부터 의도(`cancel`, `reschedule`)를 들고 들어오면 그 의도가 그대로 이벤트가 되어, API 표면과 이벤트 저장소가 한 줄로 정렬된다. CRUD의 매력은 V1과의 연속성·익숙함뿐인데, 안쪽이 이벤트로 바뀐 마당에 바깥만 CRUD로 두는 것은 임피던스 불일치를 클라이언트가 아니라 우리가 떠안는 거래다. (이의 여지: 모든 command가 깔끔한 행위로 떨어지지는 않는다 — 단순 메타데이터 수정 같은 것은 task-based가 오히려 과해 보일 수 있다. 행위로 명명할 가치가 있는 것과 그렇지 않은 것의 경계는 Design에서 도메인 이벤트 카탈로그와 함께 그어야 한다.)

### 쓰고 바로 못 읽는다면, 응답을 어떻게 돌려줄까

맥락에서 짚은 비동기가 여기서 응답 규약으로 떨어진다. command를 받았을 때 무엇을 언제 돌려줄 것인가. 세 갈래다. (a) 프로젝션이 끝날 때까지 동기로 기다렸다가 200으로 결과를 돌려준다, (b) 이벤트만 커밋하고 즉시 202 Accepted를 돌려준 뒤 결과는 별도 조회로 확인하게 한다, (c) command별로 섞는다.

나는 202를 기본으로 삼아야 한다고 본다. (a)는 표면상 가장 친절하지만, 동기 200을 돌려주려면 쓰기 경로가 프로젝션 완료를 기다려야 하고 이는 [[RFC-001-v2-cqrs-and-event-sourcing]]에서 쓰기·읽기를 가른 이유 자체를 무력화한다. 두 경로의 결합도가 다시 올라가고, 프로젝션이 느리거나 막히면 쓰기까지 같이 멈춘다. 그래서 응답은 "이벤트는 받아 적었다(202), 결과 반영은 곧 따라온다"를 정직하게 말하고, 클라이언트는 결과를 별도 조회로 확인한다. 이 "결과를 어떻게 확인하느냐"가 정확히 [[RFC-003-read-model-consistency]]의 read-your-writes 문제와 맞물린다 — 202를 받은 클라이언트가 자기 쓰기를 확인하려면 그쪽에서 정한 메커니즘(이벤트 위치 토큰을 들고 폴링하든, 그 토큰까지 따라잡은 read를 보장받든)을 그대로 빌려 쓰는 것이 자연스럽다. 따라서 이 둘은 따로 풀 수 없고, 결과 조회 방식의 구체(폴링이냐 SSE냐 웹소켓이냐)는 [[RFC-003-read-model-consistency]]가 read-your-writes를 어떻게 매듭짓느냐에 종속시켜 Design에서 함께 본다. (이의 여지: 모든 command를 비동기로 두면 클라이언트 경험이 일률적으로 무거워진다. 검증 실패처럼 이벤트를 적기도 전에 동기로 거절할 수 있는 것은 202가 아니라 즉시 4xx여야 하고, 그 경계 — 어디까지가 동기 거절이고 어디부터가 202인지 — 는 Design에서 그어야 한다.)

### 같은 command가 두 번 들어오면

비동기 202를 기본으로 두는 순간 중복 제출이 현실 문제가 된다. 클라이언트는 202만 받았을 뿐 결과를 즉시 확인할 수 없으니, 불안하면 다시 누른다 — 더블클릭, 타임아웃 후 재시도. 같은 의도가 두 번 들어와 이벤트가 두 개 쌓이면 예약이 두 번 취소되거나 두 번 생성된다.

나는 클라이언트가 제공하는 Idempotency-Key를 받아 서버가 디듀프하는 방식이 맞다고 본다. command마다 자연 멱등이 되도록 도메인을 설계하는 길(이미 취소된 것을 다시 취소하면 무시)도 있지만, 그것은 command별로 손수 보장해야 하고 "이미 처리한 그 요청과 같은 요청인가"를 도메인 상태만으로는 구분하기 어렵다 — 재시도인지 의도된 두 번째 요청인지는 요청 자체가 말해줘야 한다. 그래서 클라이언트가 키를 붙이고 서버가 같은 키의 재요청을 첫 결과로 되돌려주는 *요청 멱등* 층을 둔다.

여기서 분명히 해둘 것은, 이 멱등이 [[RFC-004-messaging-delivery]]의 멱등과 다른 층이라는 점이다. 그쪽은 메시지가 브로커를 거쳐 컨슈머에게 *전달*되는 과정에서 같은 메시지가 두 번 도착하는 것을 막는 *전달 멱등*이다. 이 문서의 것은 그보다 앞단, 클라이언트의 HTTP *요청*이 두 번 들어오는 것을 막는 *요청 멱등*이다. 둘은 독립적으로 필요하다 — 요청 멱등으로 한 번만 이벤트를 적었어도, 그 이벤트가 컨슈머에게 두 번 전달될 수 있으므로 [[RFC-004-messaging-delivery]]의 전달 멱등이 여전히 따로 필요하다. 두 층을 한 메커니즘으로 합치려 들면 어느 쪽도 제대로 못 막는다. (이의 여지: 키의 보관 기간과 저장 위치, 같은 키에 다른 바디가 온 경우의 처리는 Design 사항이다.)

### 실패를 어떻게 구분해 알릴까

command가 거절될 수 있는 경로는 한 가지가 아니다. 입력 검증 실패(형식이 틀림), 도메인 예외(규칙 위반 — 영업시간 밖 예약 등), 그리고 낙관적 락 충돌(같은 애그리거트에 동시 쓰기가 붙어 기대한 버전과 어긋남)이 모두 "실패"지만 클라이언트의 대응은 제각각이다. 검증 실패는 요청을 고쳐 다시 보내야 하고, 도메인 예외는 보통 고쳐도 안 되며, 락 충돌은 최신 상태를 다시 읽고 재시도하면 풀린다. 이걸 한 덩어리 500이나 막연한 400으로 뭉뚱그리면 클라이언트는 셋을 구분할 수 없다.

나는 셋을 HTTP 상태와 바디로 명시적으로 갈라야 한다고 본다 — 검증 실패는 400, 도메인 규칙 위반은 422(또는 409 계열), 낙관적 락 충돌은 409로 나누고, 바디에는 기계가 분기할 수 있는 에러 코드와 사람이 읽을 메시지를 함께 싣는다. 특히 락 충돌의 409는 "재시도하면 풀릴 수 있다"는 신호이므로 영구 실패와 반드시 구분되어야 한다. V1의 `@ControllerAdvice` 글로벌 예외 처리는 이 분류를 한곳에서 매핑하는 토대로 그대로 계승할 만하다 — 도메인 예외 계층을 HTTP 응답으로 옮기는 일을 컨트롤러마다 흩지 않고 한 곳에 모으는 발상은 V2에서도 유효하다. (이의 여지: 낙관적 락을 409로 노출할지, 아니면 202 비동기 모델 안에서 결과 조회 시점에 충돌을 알릴지는 비동기 응답 모델과 엮여 있어 Design에서 함께 봐야 한다.)

### 경로를 가를까, 버전을 어떻게 매길까

내부에서 command와 query를 나눴으니, 그 분리를 API 표면에도 드러낼지가 다음 갈래다. (a) 단일 게이트웨이 뒤에 통합해 클라이언트에게는 한 표면으로 보이게 할 수도 있고, (b) command 경로와 query 경로를 처음부터 갈라 노출할 수도 있다.

나는 지금 단계에서는 통합 표면 한 호스트 아래 경로 규약으로 command/query 성격을 드러내는 정도가 적당하다고 본다 — 물리적으로 게이트웨이를 쪼개는 것은 운영 복잡도를 지금 떠안을 이유가 없고, 그렇다고 성격 구분을 완전히 감추면 위에서 정한 비동기·멱등 규약이 어느 호출에 적용되는지 클라이언트가 알기 어렵다. command는 행위 POST에 202·Idempotency-Key 규약이 붙고, query는 조회 GET에 페이징 규약이 붙는다는 식으로 규약 차이가 곧 구분이 되게 한다. 버저닝은 깨는 변경을 흡수할 통로가 필요하므로 처음부터 정책을 박아두되(경로 prefix든 헤더든), 구체 방식은 Design에서 정한다. (이의 여지: 모듈을 물리적으로 분리·배포하는 시점이 오면 경로 분리가 다시 테이블에 오른다 — 그건 V2 배포 토폴로지가 결정되어야 답할 수 있다.)

### query는 어떻게 조회하게 할까

마지막은 읽기 쪽 규약이다. 페이지네이션·필터·정렬을 표준화해야 하는데, 핵심 결정은 페이징을 offset으로 하느냐 cursor로 하느냐다.

나는 cursor 페이징을 표준으로 삼아야 한다고 본다. offset 페이징은 직관적이지만 read model이 계속 갱신되는 V2에서는 위험하다 — 페이지를 넘기는 사이 새 프로젝션이 끼어들면 offset 기준이 밀려 항목이 중복되거나 건너뛰어진다. read model은 정의상 비동기로 흘러드는 데이터이므로 "고정된 0번부터 N번"이라는 offset의 전제가 성립하지 않는다. cursor는 위치를 절대 인덱스가 아니라 정렬 키 기준점으로 잡으므로 그 사이에 데이터가 끼어들어도 안정적이다. 다만 cursor가 안정적이려면 정렬 키가 read model 프로젝션에서 안정적으로 채워져 있어야 하므로, 이 규약은 read model을 어떤 형태로 투영하느냐와 맞물린다. (이의 여지: 임의 정렬·복합 필터를 cursor로 일반화하는 것은 까다롭고, 일부 관리용 조회는 offset이 실용적일 수 있다 — 표준은 cursor로 두되 예외 범위를 Design에서 한정한다.)

## Design으로 넘기는 것

- command 엔드포인트 목록과 행위 명명 규약 — task-based로 떨어지는 것과 아닌 것의 경계, 도메인 이벤트 카탈로그와 함께 확정.
- 202 결과 조회 메커니즘의 구체(폴링/SSE/웹소켓)와 동기 거절 vs 202의 경계 — [[RFC-003-read-model-consistency]]의 read-your-writes 결론에 종속.
- Idempotency-Key의 보관 기간·저장 위치·키 충돌(같은 키 다른 바디) 처리.
- 에러 분류의 HTTP 상태·에러 코드 표와 `@ControllerAdvice` 매핑 범위; 낙관적 락 충돌을 409로 노출할지 결과 조회 시점에 알릴지.
- API 버저닝 방식(경로 prefix vs 헤더)과 경로 분리의 재검토 시점(배포 토폴로지 확정 시).
- cursor 페이징의 cursor 인코딩·정렬 키 규약과 offset 예외 허용 범위.
