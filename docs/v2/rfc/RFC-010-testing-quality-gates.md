# RFC-010 — 테스트·품질 게이트

- **상태**: Open · 논의 중 · 2026-06-15
- **선행**: [[RFC-001-v2-cqrs-and-event-sourcing]] · 인덱스 [[RFC-002-decision-queue]]
- **닫으면**: [[11-environments-and-testing]] 보강 + [[14.testing-strategy]] 비준 (Proposed→Accepted)

## 맥락

라운드1에서 *어떤 종류의 테스트를 쌓을지*는 이미 정리됐다. 다섯 범주다. (1) 아키텍처 강제 — query↛command, 도메인↛JPA, command↔query는 이벤트로만 통하게 하는 경계 규칙을 컴파일/테스트 시점에 깨뜨리는 것. 이게 1순위인 이유는 CQRS+ES로 가면서 가장 먼저 무너지는 게 모듈 경계이기 때문이다. 사람이 리뷰로 막을 수 있는 종류의 침범이 아니다. (2) property-based — Fixture Monkey로 도메인 불변식을 무작위 입력에 노출. (3) 소비자 계약 — 이벤트 스키마 생산자와 컨슈머 사이의 합의. (4) 업캐스팅 회귀 — 구버전 이벤트가 신버전 코드로 항상 복원되는지. (5) Chaos Monkey — 장애 주입.

그래서 이 RFC가 남겨 받은 건 *범주를 어떻게 만들지가 아니라*, 각 범주를 어떤 도구로 실현하고 어디까지를 CI 게이트로 묶을지다. 도구 택일 몇 개와 게이트 임계 몇 개. 여기서 그걸 추론한다.

## 논의

### 아키텍처 강제를 무엇으로 거나

경계 규칙을 강제하는 도구는 사실상 둘이다. ArchUnit과 Konsist. ArchUnit은 JVM 진영의 표준에 가깝고 성숙도와 레퍼런스가 압도적이다. 안전한 선택이라는 뜻이다. 다만 ArchUnit은 바이트코드/리플렉션 기반이라 본질적으로 Java의 타입 세계를 본다. 우리가 강제하려는 규칙은 "query 모듈은 command 모듈을 import하지 않는다", "도메인은 JPA 애너테이션을 모른다" 같은, Kotlin 소스 구조에 붙는 규칙이다.

여기서 Konsist가 유력하다고 본다. Konsist는 Kotlin 네이티브로, 코틀린 심볼·소스 구조를 직접 DSL로 질의한다 — 패키지·클래스·함수·import를 코틀린 코드로 순회하며 단언한다. 우리 규칙이 "Kotlin 모듈 경계"라는 점, [[01.cqrs-command-query-module-split]]에서 정한 분리와 [[01-module-structure]]의 모듈 레이아웃이 코틀린 패키지 단위로 그어져 있다는 점을 보면, 검증 대상과 검증 도구의 언어가 일치하는 쪽이 규칙을 더 자연스럽게 표현한다. [[14.testing-strategy]]가 이 경계를 1순위로 둔 만큼, 규칙 표현력이 성숙도보다 우선한다고 판단한다.

(이의 여지) ArchUnit의 생태계 두께를 포기하는 비용이 정말 작은가. Konsist는 비교적 신생이고, 복잡한 의존성 사이클 탐지 같은 ArchUnit의 검증된 기능군에서 약할 수 있다. 경계 규칙이 단순한 import 금지를 넘어 "사이클 없음" 류로 커진다면 재검토 여지가 있다.

### 계약을 Pact로 하나 Spring Cloud Contract로 하나

소비자 계약은 이벤트 스키마(생산자)와 컨슈머 사이의 합의를 코드로 고정하는 일이다. 후보는 Pact와 Spring Cloud Contract. Pact는 consumer-driven 계약의 사실상 표준이고 Pact Broker라는 별도 생태계를 끼고 돈다. Spring Cloud Contract는 우리 스택(Spring Boot)에 그대로 얹히고, 계약을 producer 쪽에 두는 모델이라 빌드 파이프라인에 녹이기 쉽다.

나는 우리 맥락에서 어느 쪽도 아직 못 박지 않는 게 맞다고 본다 — 다만 기울기는 있다. 우리는 외부 다자간 컨슈머를 가진 공개 API 계약이 아니라, 같은 시스템 안의 이벤트 생산자/컨슈머 계약을 다룬다. 이 경우 별도 브로커 인프라(Pact Broker)를 세우고 운영하는 비용이 이득보다 크기 쉽고, producer-side 계약이 ES의 "이벤트는 생산자가 정의한다"는 방향과도 맞는다. 그래서 Spring 생태계 친화성과 인프라 단순성으로 Spring Cloud Contract 쪽으로 기운다.

(이의 여지) 이 판단은 "컨슈머가 내부에 머문다"는 전제에 매달려 있다. 추후 외부 파트너가 이벤트 스트림을 구독하는 그림이 생기면 consumer-driven인 Pact의 장점이 살아난다. 컨슈머 경계가 시스템 밖으로 나가는 순간 재논의 대상이다.

### 카오스는 어느 레벨까지 자동화하나

앱 레벨 장애 주입은 **Chaos Monkey for Spring Boot로 확정**한다 — 라운드1에서 이미 굳은 부분이고, 스프링 빈 레벨에서 지연·예외·메모리 압박을 주입하는 데 더 나은 대안이 없다. 쟁점은 그 위, 인프라(파드 kill·네트워크 분단) 레벨이다. 후보는 수동 kill, Chaos Mesh, Litmus.

여기서 내 입장은 "지금 도입하지 않는다, 단 트리거를 명시한다"이다. 인프라 카오스는 쿠버네티스 위에서 의미가 큰데, 우리가 그 레벨의 회복탄력성을 *시험할 대상*(다중 파드·네트워크 토폴로지)을 아직 갖고 있지 않다. 도구를 미리 들이는 건 검증할 게 없는 검증이다. 트리거는 [[11-environments-and-testing]]의 T-05 확장 — 즉 인프라 레벨 회복탄력성이 실제 운영 리스크로 올라오는 시점 — 으로 잡고, 그때 Chaos Mesh(쿠버네티스 네이티브·CRD 기반)를 1순위 후보로 둔다.

(이의 여지) "필요해지면 그때"는 카오스 엔지니어링의 정신과 어긋난다 — 장애는 준비됐을 때 오지 않는다. 다만 도구 부재가 곧 무방비는 아니고, 앱 레벨 Chaos Monkey가 당장의 표면을 덮는다는 점에서 인프라 레벨 연기는 감당 가능한 빚이라고 본다.

### 커버리지 목표와 게이트 임계 — 정책은 지금, 숫자는 측정 후

다섯 범주의 커버리지 목표와 그중 무엇을 CI 필수 게이트로 묶을지는 성격이 둘로 갈린다. *어느 범주를 게이트로 둘 것인가*라는 정책은 지금 추론으로 정할 수 있다 — 아키텍처 강제는 무조건 필수 게이트(통과 못 하면 머지 불가), property-based·계약·업캐스팅 회귀도 게이트, Chaos Monkey는 게이트가 아니라 비-차단 관측으로 두는 게 합리적이다(장애 주입은 본질적으로 비결정적이라 머지를 막는 기준으로 부적합).

반면 "라인 커버리지 X%" 같은 절대 숫자는 지금 정하면 근거 없는 숫자다. 베이스라인을 측정하기 전에 임계를 박으면 늘 너무 느슨하거나 너무 빡빡하다. 그래서 임계 숫자는 **측정에서 검증**한다 — 현 커버리지를 측정하고, 후퇴 금지(ratchet) 방식으로 점진 상향하는 게 임의의 절대치보다 낫다고 본다.

(이의 여지) 비-차단으로 둔 관측 게이트는 시간이 지나면 아무도 안 본다. Chaos Monkey 결과를 게이트 밖에 두는 대신 별도 리포팅 경로로 가시화하지 않으면 죽은 테스트가 된다.

### k6 SLO와 부하 게이트 — 같은 패턴

부하 테스트(k6)도 위와 같은 모양이다. *부하 테스트를 CI 게이트로 둘 것인가*라는 정책은 지금 입장을 낼 수 있다 — 매 PR마다 부하 테스트를 돌려 머지를 막는 건 비용·시간상 비현실적이므로, k6는 CI 차단 게이트가 아니라 정기/릴리스 전 게이트로 두는 게 맞다. 다만 절대 SLO(p99 응답시간, 처리량 하한)는 지금 숫자로 박을 근거가 없다. 베이스라인 측정 후 정한다.

(이의 여지) 릴리스 전에만 도는 부하 게이트는 회귀를 늦게 잡는다. 성능 회귀가 잦은 영역이 드러나면 그 경로만 경량 부하 스모크로 CI에 올리는 절충이 필요할 수 있다 — 이것도 측정으로 판단한다.

### localstack로 무엇을 검증하나

localstack로 흉내 낼 AWS 서비스 목록은, 우리가 실제로 어떤 AWS 의존을 갖는지가 확정돼야 닫힌다. 컨텍스트 전환 작업이 진행되며 실제 의존(예: 메시징·시크릿·오브젝트 스토리지)이 드러나야 목록이 완결된다는 뜻이다. 그래서 이 목록은 지금 임의로 나열하기보다, 의존이 굳는 대로 채우는 살아있는 목록으로 둔다.

특히 콜드 스토리지 S3 검증을 목록에 넣을지는 우리가 단독으로 못 정한다 — [[RFC-005-event-store-schema-evolution]]가 아카이브 매체를 아카이브 테이블로 갈지 오브젝트 스토리지(S3)로 갈지 결정해야 한다. 테이블이면 localstack S3는 목록에서 빠지고, S3면 들어온다. 따라서 이 갈래는 의존 RFC의 산물로 닫는다.

(이의 여지) 의존 RFC를 기다리는 동안 localstack 검증 자체가 무기한 미뤄질 수 있다. S3 외의 확정된 의존(있다면)은 먼저 목록화해 검증을 시작하는 게 낫다.

## Design으로 넘기는 것

- 아키텍처 강제: Konsist DSL로 표현한 경계 규칙 셋의 구체(규칙 목록·예외 화이트리스트) — Design.
- 커버리지·k6 임계: 베이스라인 측정 후 확정할 절대 숫자와 ratchet 정책 — 측정.
- localstack 서비스 목록: 컨텍스트 전환에서 드러나는 실제 의존에 따라 — 측정. 콜드 S3 항목은 [[RFC-005-event-store-schema-evolution]] 매체 결정에 의존.
- 인프라 카오스 도구: T-05 확장 트리거 도달 시 Chaos Mesh 채택 여부 재검토 — 측정.
