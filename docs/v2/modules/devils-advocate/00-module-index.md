## 1. Position + Steel-man

**핵심 주장**: 모듈 경계는 Gradle 의존성 매트릭스(허용/금지)로 강제되고, 이 컴파일 타임 규칙이 런타임 CQRS/이벤트소싱 경계(특히 "core 이벤트 타입을 아는 유일한 계층은 command-application" 불변식)와 대칭을 이루도록 설계됐다.

**최선의 조건**: 이 구조가 실제로 잘 작동하려면 — Gradle 의존성 금지 규칙 위에 ArchUnit/Detekt 커스텀 룰 같은 자동 검증이 Phase 7-0부터 CI에 걸려 있고, 팀이 그 게이트를 신뢰해 매 PR마다 우회하지 않는다는 전제가 성립해야 한다.

---

## 2. 숨은 가정

1. **"모듈 분리 = 경계 강제"라는 가정**: Gradle 서브모듈 의존성 부재는 컴파일 타임 import만 막을 뿐, `StoredEvent`에 타입 판별자(문자열/enum)가 실려 있으면 command-infrastructure가 그 값으로 `when` 분기하는 것까지는 막지 못한다. 문서는 이 gap을 언급하지 않는다.
2. **query-module이 "하나의 코드 모듈"이면서 두 워크로드로 나뉜다는 서술(27행, 44행)이 실제 배포 아티팩트 분리와 무관하다는 가정**: 07/08 문서가 서로 다른 동시성·스케일·장애격리 특성을 주장하면서도, 이게 프로파일 분기인지 별도 빌드 산출물인지는 [[11-runtime-topology]]로 미뤄져 있다 — 이 허브 문서 시점에서는 미결정인데 이미 "구조"로 확정 서술되어 있다.
3. **12개 문서·상호링크 색인 구조의 유지비용이 프로토타입 학습 목적과 맞는 투자라는 가정**: 트래픽 없는 학습용 v2에서, batch-module 행선지(M-1)조차 미결(63행)인 채로 전환 대응표에 기정사실처럼 한 행을 차지하고 있다.

---

## 3. 반론

### 반론 1 — query-module 단일 모듈·이중 워크로드 서술의 불일치
[type: structural] severity: **high**

44행은 query-module을 "하나의 코드 모듈"이라 명시하면서도 27행은 07(쓰는 projection 서버)과 08(읽는 read model 서버)이 "동시성·스케일·장애 격리 특성이 다르다"고 주장한다. 하나의 Gradle 모듈에서 두 개의 독립적 장애격리 단위가 나온다는 것은, 실제로는 프로파일/엔트리포인트 분기로 두 아티팩트를 만든다는 뜻인데 이 메커니즘이 이 허브 문서에도, 참조된 [[DESIGN-010]] §4.1에도 이 문서 수준에서는 확정되어 있지 않다. 결과가 확정되지 않은 상태에서 색인 표(07/08)와 매트릭스(119행 "query" 단일 행)가 서로 다른 분리 단위를 전제로 작성돼 있어, 실제 구현 시점에 이 문서부터 다시 손봐야 할 가능성이 높다.

선례: no clear precedent — speculative concern (CQRS 문헌에서 "단일 아티팩트, 프로파일로 역할 분기"가 자원 격리를 깨뜨리는 사례는 흔히 언급되지만, 이 프로젝트에 특정된 실패 사례는 없음).

### 반론 2 — "핵심 불변식"이 강제 메커니즘 없이 선언됨
[type: assumption] severity: **critical — 부분 해소됨(2026-07-19 동기화)**

123행의 "core 이벤트 타입을 아는 유일한 계층은 command-application" 불변식은 이 아키텍처의 핵심 전제인데, 그 강제 수단은 Gradle 의존성 매트릭스(113-121행)뿐이었다. §4 기술 스택 표를 Konsist(신규 — [[RFC-009-testing-quality-gates]] 결정 1·[[RFC-031]])로 갱신해, "Detekt에 컨텍스트 경계 규칙 편입"이라는 근거 없는 서술을 제거하고 실제 도구(Konsist, Tier 2)를 명시했다.

**단, 완전히 해소되지는 않았다.** `command-infrastructure`가 `StoredEvent`(직렬화 레코드)의 타입 판별자 필드(문자열/enum)로 `when` 분기하는 코드는 import를 하지 않으므로, Konsist·Gradle 둘 다 정적 import/선언 분석 기반이라 **이 특정 우회를 잡지 못한다** — RFC-031 §논점2·§규칙카탈로그 R6에 이 한계를 명시적으로 기록해 뒀다. 남은 것은 이 gap을 코드 리뷰 컨벤션으로 보완하는 실행 과제다.

선례: no clear precedent — speculative concern.

### 반론 3 — 문서 색인 유지비용과 미결 사항의 기정사실화
[type: execution] severity: **medium**

12개 문서를 위키링크로 엮은 허브 구조는 모듈 경계가 바뀔 때마다(색인 표, 전환 대응표, mermaid 다이어그램, settings.gradle.kts 블록 네 곳을 동시에) 갱신해야 한다. 그런데 batch-module 행선지(M-1, 63행)는 "흡수 or 별도 유지" 미결로 표시돼 있음에도 전환 대응표에서는 다른 확정 행들과 시각적으로 동일한 무게로 나열된다. 실제 트래픽이 없는 학습 목적 프로토타입에서 이 정도의 문서 동기화 비용을 지금 지불하는 것이, 아직 구현되지 않은 Phase 7 전체 순서에 비례해 과도할 수 있다.

## 4. 다중 페르소나 공격

**런타임/운영 담당자**: "query-module이 한 Gradle 모듈이면서 두 워크로드로 뜬다는데, 이게 같은 JAR을 프로파일로 나누는 건지 실제로 다른 배포 아티팩트인지 이 허브 문서에서 답을 안 준다. 근데 내 오토스케일링 정책·서킷브레이커·리소스 리밋 설계는 그 답에 따라 완전히 달라진다. '11번 문서 참조'로 미루기엔 이건 이 문서 0번 색인 항목에서 이미 구조로 확정 서술된 내용이다."

**아키텍처 거버넌스 담당자(나중에 규칙을 강제해야 하는 사람)**: "의존성 매트릭스의 '금지' 화살표들은 Detekt 룰이 실제로 작성되고 Phase 7-0부터 CI에 걸리기 전까지는 그림일 뿐이다. Phase 7-4/7-5까지 가서 우연히 들어간 import 하나 걷어내려면 그때 가서는 다중 파일 고고학이 된다."

**신규 합류자**: "V1 adapter-module 인증 부분이 auth-server-module로 간다는 전환표 행을 보는데, 왜 인증만 독립 서버로 분리해야 하는지 이 문서 안에는 근거가 없다. DESIGN-017·ADR-024를 열어야 이해되는데, 허브 문서라면서 왜 분리하는지 한 줄도 안 써 있다."

---

## 5. 핵심 취약점

**갱신(2026-07-19)**: 강제 메커니즘이 Gradle 단독에서 "Gradle + Konsist(Tier 2)"로 보강돼, import 기반 우회는 이제 잡힌다. 그러나 데이터 값 기반 타입 판별자 우회(§반론 2 갱신분 참조)는 두 도구 모두 정적 import/선언 분석이라 여전히 못 잡는다 — RFC-031이 이 gap을 이제 **명시적으로 인정**하고 있다는 점이 원래의 "검증 불가능한 상태로 조용히 인용되는" 문제보다는 낫지만, gap 자체는 남아 있다. 이것은 숨은 가정 1이 무기화된 형태이며, 남은 대응은 코드 리뷰 컨벤션이다.

---

## 6. 가역성 프레임

모듈 이름·Gradle 서브모듈 재배치 자체는 되돌리기 쉽다(리팩터링 비용만 발생). 그러나 "command-infrastructure는 타입을 몰라야 한다"는 핵심 불변식과 query/command 완전 분리는, 07/08과 06 문서의 실제 코드가 그 전제 위에 쓰이기 시작하면 one-way door에 가깝다 — 나중에 인프라 계층에 타입 인지가 필요하다는 게 드러나면(예: 이벤트 스키마 버저닝), 애초에 타입을 모르도록 설계된 계층에 타입 정보를 다시 꿰매 넣어야 하는 비용이 크다.
