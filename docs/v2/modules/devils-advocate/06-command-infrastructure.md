# Devil's Advocate — 06-command-infrastructure

> 대상: [[06-command-infrastructure]] · 검증 시점: 2026-07-19

## 1. Position + Steel-man

**Position**: 인프라는 도메인을 모르는 배관으로 두고, 순서·원자성·relay 단일성을 전부 DB 원시연산(`SKIP LOCKED`·`UNIQUE`·동일 datasource)과 Redisson 상시 락에 위임한다.

**Steel-man**: 별도 코디네이터·2PC·전용 ES 제품 없이 이미 붙어 있는 MySQL/Redis만으로 원자성과 relay 단일성을 싸게 얻는다 — 무트래픽 프로토타입에서는 코디네이터 운영 비용을 새로 지는 것보다 이미 있는 인프라의 원시연산에 기대는 쪽이 합리적이다.

## 2. 숨은 가정

1. **이 문서(§5.1 코드, §6 체크리스트, §3 라이브러리 표)가 기술하는 relay 메커니즘이 여전히 최신 결정이다** — 그러나 이 전제는 이미 틀렸다(§3 반론 참조).
2. **event_store와 outbox는 영원히 동일 datasource·동일 트랜잭션에 공존한다** — 확장·스케일아웃 이후에도 분리하지 않는다.
3. **모든 ES append에 Redis 왕복(Redisson L1)을 태워도 크리티컬 패스 비용이 수용 가능하다** — 락프리 낙관 append와의 비용 비교 없이 상시 락을 기본 경로로 확정.

## 3. 반론

### 반론 1 — 문서가 이미 폐기된 메커니즘을 구현 항목으로 명문화
`[type: timing]` · **severity: critical**

이 파일은 2026-07-19 22:21(커밋 `2ddc94e`)에 작성됐다. 그런데 같은 날 13:22(커밋 `1756e4f`)에 이미 합의된 [[RFC-025]]는 "SKIP LOCKED 경쟁 소비(D-008 §4.9·RFC-003 논점3)를 supersede"하고 **단일 순차 relay(ShedLock 리더)**를 채택한다고 명시한다(RFC-025 §"네 결정", 라인 91). 즉 이 문서를 쓰는 시점에 이미 SKIP LOCKED 경쟁 소비는 폐기된 설계였다.

그럼에도 §5.1의 코드("여러 relay 인스턴스가 서로 잠기지 않은 행만 경쟁 소비", "leader election 불필요 — 별도 코디네이터 없음이 SKIP LOCKED의 결정적 이점"), §6 체크리스트("Outbox relay (폴링 + `SKIP LOCKED`) + 재시도 스케줄러"), §3 라이브러리 표(ShedLock류 리더선출 라이브러리 부재) 전부가 폐기된 메커니즘 그대로다. §7의 "미결" 표기("relay 병렬성↔순서 계약은 [[RFC-025]]에서 확정")는 마치 RFC-025가 아직 열려 있는 것처럼 읽히지만, 실제로는 이미 닫혀 있고 이 문서와 반대 방향으로 닫혔다.

이대로 §6 체크리스트를 문자 그대로 실행하면 엔지니어는 이미 supersede된 SKIP LOCKED relay를 구현하고, 이후 RFC-025를 교차 확인해야만 ShedLock으로 다시 갈아엎어야 한다는 걸 안다.

선례: 레포 자체 커밋 이력(RFC-025 `1756e4f` 13:22 vs 본 문서 `2ddc94e` 22:21, 2026-07-19) — 추측이 아니라 `git log`로 직접 확인 가능한 사실.

### 반론 2 — event_store+outbox 동일 datasource 전제는 확장의 one-way door
`[type: structural]` · **severity: high**

2PC 회피를 위해 event_store append + outbox insert를 동일 트랜잭션·동일 커넥션에 묶는 순간, event_store는 outbox와 같은 MySQL 인스턴스에서 절대 분리될 수 없다. §5.4는 파티셔닝을 YAGNI로 미루지만, append-only event_store가 성장해 outbox 폴링(핫 경로)과 I/O를 다투기 시작하면 "저장소 분리"라는 정상적 확장 경로가 원자성 상실 없이는 불가능하다. §7은 이 전제를 "명문화 필요"로만 남겨 두는데, 뒤집기 비싼 결정을 미결 상태로 구현 단계까지 끌고 가는 것 자체가 리스크다.

선례: [[DESIGN-003]] 자기리뷰(라인 196)에 "이는 event store를 별도 저장소/제품으로 분리하지 못한다는 제약과 직결"이라고 이미 자인돼 있다 — 문서 스스로 인정한 트레이드오프이며, 이 파일은 그 인정을 반영하지 않고 YAGNI로만 처리한다.

### 반론 3 — RFC 합의가 모듈 문서로 전파되는 경로 자체가 없다
`[type: structural]` · **severity: medium-high**

반론 1이 보여주는 staleness는 우연한 실수가 아니라 구조적이다. RFC-025의 "닫으면" 항목(라인 8)은 "[[DESIGN-020]] 신설 + [[DESIGN-008]] §4.9·§4.10 정합 갱신 + 신규 ADR"만 명시하고, `docs/v2/modules/*` 아래의 모듈 설계 문서는 갱신 대상으로 언급조차 되지 않는다. 즉 RFC → DESIGN → ADR 체인은 있지만 RFC → module 체인은 이 프로젝트의 문서 프로세스에 아예 없다. 이번처럼 module 문서가 design_doc보다 늦게(같은 날이라도) 작성되면, 작성자가 RFC 결론을 수동으로 따라가지 않는 한 module 문서는 구식 상태로 커밋된다. 이 문서 한 건만 고쳐도 다음 RFC 합의 때 같은 drift가 반복된다.

선례: RFC-025 §"닫으면"(라인 8)의 전파 대상 목록에 module 문서 부재 — 문서 자체에서 확인 가능. (module 문서 동기화가 반복적으로 깨질지는 향후 RFC 사이클 관찰이 필요하므로 이 일반화 자체는 다소 추정적이다.)

## 4. 다중 페르소나 공격

**On-call/SRE**: "SKIP LOCKED 경쟁 소비"와 "단일 순차 ShedLock 리더"는 운영 프로파일이 완전히 다르다. 전자는 인스턴스가 죽어도 나머지가 즉시 이어받는 무상태 경쟁 모델이고, 후자는 리더 장애 시 페일오버 지연이 있는 단일 활성 인스턴스 모델이다. 이 문서를 보고 용량 계획·알람 임계치·장애 대응 런북을 짜면, 실제 배포될 ShedLock 리더 모델과 맞지 않는 운영 가정을 세우게 된다.

**Query/Projection 팀 (다운스트림 소비자)**: 07-query-projection-server는 이 인프라가 "발행 순서를 지킨다"는 계약에 기대어 프로젝터를 설계한다. 이 문서가 이미 폐기된 SKIP LOCKED 순서 위반 가능성을 여전히 열어둔 채로 읽히면, 프로젝션 팀은 "우리 쪽에서 순서 역전 방어(LWW 가드)를 얼마나 강하게 넣어야 하는지"를 잘못된 전제로 판단할 위험이 있다.

**아키텍처 거버넌스 (RFC/ADR 규율 담당)**: RFC-025는 "합의"이지 "ADR 비준"은 아직 아니다(라인 3: "ADR 비준 대기"). 그런데 이 module 문서가 미비준 RFC의 결론과도 어긋난 채 구현 체크리스트(§6)를 확정형으로 적어 놓은 것은, "합의됨"과 "구현 확정"의 경계를 흐린다 — ADR 비준 전에 이미 실행 항목이 문서에 박제된 셈이다.

## 5. 핵심 취약점

숨은 가정 1이 무기화된 형태: **이 문서는 스스로 기술하는 메커니즘이 최신이라고 전제하지만, 그 전제는 작성 시점에 이미 거짓이었다.** RFC-025가 같은 날 9시간 먼저 SKIP LOCKED 경쟁 소비를 supersede했는데도, §5.1 코드·§6 체크리스트·§3 라이브러리 표는 여전히 구식 메커니즘을 정상 경로로 서술한다. 게다가 RFC-025 자신의 "닫으면" 전파 목록에 module 문서가 빠져 있어(반론 3), 이 drift를 잡아줄 프로세스가 없다. 그대로 구현하면 이미 결정된 것을 다시 뒤집는 재작업이 발생하고, 그사이 07-query-projection-server가 잘못된 순서 계약을 전제로 설계될 위험이 있다.

## 6. 가역성

**혼합.** SKIP LOCKED→ShedLock 표기 정정(반론 1)과 §3 라이브러리 표 갱신은 문서 수정 한 번으로 되돌릴 수 있는 reversible 결정이다. 그러나 (a) event_store+outbox 동일 datasource 전제(반론 2)는 트랜잭션 경계가 코드로 굳은 뒤에는 저장소 분리가 비싼 one-way door이고, (b) "RFC 합의 → module 문서 전파" 프로세스 부재(반론 3)는 이 문서 하나를 고쳐도 다음 RFC 사이클에서 재발하는 구조적 갭이라 문서 패치만으로는 되돌아가지 않는다.
