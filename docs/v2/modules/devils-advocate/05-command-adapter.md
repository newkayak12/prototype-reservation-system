# Devil's Advocate — 05 · command-adapter

> 대상: [[05-command-adapter]]. 독립 스트레스 테스트 (본문 §8의 자체 검토와 별개, 중복 최소화 목적으로 다른 축을 우선).

## 1. Position + Steel-man

**Position**: command-adapter는 (a) event_store를 Spring Data JPA로 구현하고 UNIQUE 제약을 동시성 백스톱으로 삼으며, (b) REST 인바운드/JPA 아웃바운드를 컨텍스트별 수직 슬라이스 하나의 모듈에 두고, (c) JWT 검증 없이 엣지가 넘긴 클레임 헤더를 그대로 신뢰(pre-authenticated)한다.

**Steel-man**: 프로토타입 단계에서 팀이 이미 아는 Spring/JPA/Testcontainers 스택만으로 정확성(UNIQUE)·인가(엣지 위임)를 확보해 별도 인프라(전용 이벤트스토어, 사이드카 mTLS 등) 도입 비용 없이 빠르게 학습·반복할 수 있다는 조건에서 최선이다.

## 2. 숨은 가정

1. 엣지(API Gateway)가 검증한 `X-User-Id`/`X-User-Role` 헤더가 command-adapter에 도달하기 전, 그 경로 자체가 물리적/네트워크적으로 강제된다 — 즉 엣지를 우회해 이 어댑터에 직접 헤더를 실어 요청할 경로가 없다는 전제. 문서 어디에도 mTLS/공유 시크릿/네트워크 정책 같은 "그 경로 강제" 메커니즘이 명시되지 않는다.
2. `EventStorePort.append`가 던지는 예외의 **타입과 계약**이 포트 경계에서 고정되어 있다 — 5.1 주석은 "위반 시 DataIntegrityViolation → application이 리플레이-재시도 or 409 매핑"이라 쓰지만, 이 `DataIntegrityViolationException`은 Spring Data JPA 타입이지 포트가 선언한 도메인 예외가 아니다. application이 이 타입을 직접 캐치하는지, 아니면 어댑터가 번역해 던지는지가 미명시.
3. Phase 7-4(command-adapter 구현 시점)에 엣지/게이트웨이(JWT 발급·검증, [[ADR-024]])가 이미 존재하고 강제되고 있다 — 로컬/스테이징 환경에서도 이 전제가 항상 성립한다는 가정.

## 3. 반론

1. `[구조]` · **critical — 해소됨(2026-07-20 동기화)** · 선례: no clear precedent — speculative concern, 다만 헥사고날 포트 계약에서 인프라 예외 타입이 애플리케이션 레이어로 새는 것은 일반적으로 알려진 안티패턴. — 이 반론은 예외 타입·번역 계약이 어디에도 정의되지 않았을 때 성립했다. [[04-command-application]] §5가 `AggregateConflictException`을 포트 계약으로 명시하고, 이 문서(05) §5.1이 어댑터에서 `DataIntegrityViolationException`을 캐치해 그 타입으로 번역해 던지도록 구현을 확정했다 — application은 이제 JPA 런타임 타입을 전혀 참조하지 않는다. 다만 이 번역이 실제로 그렇게 구현됐는지는 **Konsist(RFC-031)가 검증하지 못한다** — import 그래프 기반 정적 분석은 "특정 catch 블록이 존재하고 올바르게 번역하는가"를 확인할 수 없으므로, 코드 리뷰로 계속 확인해야 한다(다중 페르소나 "아키텍처 가디언" 참고).
2. `[가정]` · **high** · 선례: 리버스 프록시가 클라이언트가 보낸 신뢰 헤더를 제거/검증하지 못해 발생하는 헤더 위조류 취약점은 일반적으로 알려진 실패 패턴(예: `X-Forwarded-For`/사설 인증 헤더 위조 계열). — pre-authenticated 필터는 `X-User-Id`/`X-User-Role`을 그대로 신뢰한다고 명시하지만(§5.3), 그 헤더가 "엣지를 반드시 거쳐야만" 도달함을 강제하는 메커니즘(mTLS, 공유 시크릿, 네트워크 격리)이 문서에 없다. command-adapter가 어떤 경로로든(내부망 오구성, 서비스 메시 라우팅 실수, 통합 테스트 환경 노출) 직접 도달 가능해지는 순간, 헤더만 조작하면 임의 사용자·임의 역할(ADMIN 포함)로 완전 가장(impersonation)이 가능하다. 인가 게이트([[DESIGN-014]])가 "역할 문자열이 오면 신뢰한다"는 전제 위에 서 있다는 뜻이라 파급력이 크다.
3. `[타이밍]` · **medium** · 선례: no clear precedent — speculative concern. — Phase 7-4 구현 시점은 엣지/게이트웨이가 이미 자리 잡아 pre-auth 신뢰를 뒷받침한다는 전제에 의존한다. 그러나 로컬 개발(`docker-compose up` + `bootRun`, CLAUDE.md 명시 워크플로우)에는 게이트웨이가 없을 가능성이 높고, 이 경우 개발자는 `CommandSecurityConfig`가 헤더를 무조건 신뢰하는 상태로 로컬 실행·통합 테스트를 반복하게 된다. "로컬이니까 괜찮다"는 안이함이 그대로 스테이징 설정에 복사되는 경로가 실제로 흔한 실패 지점이며, 문서는 이 전이 위험에 대한 가드(로컬 전용 프로파일 분리, 헤더 화이트리스트 등)를 언급하지 않는다.

## 4. 다중 페르소나 공격

**AppSec 리뷰어**: "엣지가 검증했으니 여기선 안 한다"는 문장 하나로 인가 전체를 위임하면서, 그 위임의 물리적 보장(누가 이 서비스에 네트워크 레벨로 도달할 수 있는가)은 이 문서의 소관이 아니라고 침묵한다. pre-auth 패턴 자체는 흔하지만, 채택하는 문서라면 최소한 "이 서비스는 엣지 CIDR/서비스 메시 mTLS 외 경로로 도달 불가"를 명시적 불변식으로 못 박아야 하는데 그게 없다 — 인가 계약의 절반이 다른 문서([[DESIGN-010]], [[ADR-024]])에 위임된 채 이 문서는 "신뢰한다"만 반복한다.

**아키텍처 가디언 (Konsist/RFC-031 관점)**: 이 프로젝트는 RFC-031(정정 후 Konsist, ArchUnit 아님)로 의존 방향을 코드로 강제한다. 그런데 Konsist도 ArchUnit과 마찬가지로 "패키지 import 방향"을 검사하지, "런타임에 어떤 예외 타입이 캐치되는가"는 검사하지 못한다. §5.1이 이제 올바른 번역 계약을 코드로 명시했더라도, 이후 다른 컨텍스트(restaurant/, timetable/ …)가 이 패턴을 복제하지 않고 JPA 예외를 직접 캐치하는 실수를 해도 Konsist는 그 위반을 못 잡아낼 개연성이 크다 — "적합성 함수가 있으니 괜찮다"는 안도가 이 특정 결함 클래스에는 안전망이 안 된다.

**온콜/운영 엔지니어**: UNIQUE 위반 → 리플레이-재시도가 프로덕션에서 실제로 발생했을 때, 이걸 감지·경보할 관측 지점(메트릭, 로그 태그, 재시도 횟수 상한)이 문서 어디에도 없다. "L0, 절대 제거 금지"라 부를 만큼 중요한 메커니즘이라면 그게 얼마나 자주 트리거되는지 온콜이 알아야 하는데, 이 문서는 그 가시성을 설계 범위 밖으로 둔 채 "동시성 백스톱"이라는 이름만 부여했다.

## 5. 핵심 취약점

예외 타입·번역 계약 부재(구 반론 1)는 해소됐다. **남은 핵심 취약점은 반론 2** — pre-authenticated 신뢰 경계를 물리적으로 강제하는 메커니즘(mTLS·NetworkPolicy)이 이 문서에도, 인용된 [[ADR-024]]에도 실제 구현 시점까지는 "설정 확인" 수준으로만 존재해, 헤더 위조 시 임의 사용자 가장이 가능한 단일 실패점이 남아 있다는 점이다.

## 6. 가역성

반론 1(예외 번역)은 이미 반영되어 reversible 상태로 안착했다. pre-auth 신뢰 경계(반론 2)는 인프라(게이트웨이/메시) 결정이므로 이 문서 단독으로는 가역/불가역을 판단할 수 없다 — [[DESIGN-010]]·[[ADR-024]]에 종속.
