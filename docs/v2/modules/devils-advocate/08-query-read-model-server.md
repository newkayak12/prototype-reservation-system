# Devil's Advocate — 08-query-read-model-server

> 대상: [[08-query-read-model-server]]. 방법론: position 명료화 → steel-man → 숨은 가정 → 반론 → 페르소나 공격 → 핵심 취약점 → 가역성.

---

## 1. Position + Steel-man

**Position**: 읽기 경로는 "DB→DTO" 단순 변환이므로 layered 구조로 충분하고, 최종 일관성을 기본 사양으로 못 박고, read-your-writes·캐시는 증명된 화면에만 여는 예외로 취급한다.

**Steel-man**: 프로젝션이 이미 조회 모양으로 비정규화된 머티리얼라이즈드 캐시이므로, 그 위에 포트/어댑터·in-memory 캐시·동기 결합을 더 얹지 않고 얇게 서빙하면 조회/투영 장애가 격리되고 운영 표면이 최소가 된다 — 트래픽 패턴이 예측 가능하고 신선도 요구가 실제로 관대한 조회 화면들(가용시간 조회, 식당 목록 등)에서는 이 구조가 정확히 맞는다.

---

## 2. 숨은 가정

1. **read-your-writes를 "예외"로 미뤄도 §5 read path 시그니처(단순 `(userId, page)`)는 나중에 토큰 파라미터를 무리 없이 얹을 수 있는 자리다** — 신선도 토큰이 read path·트랜잭션 경계에 구조적 영향을 주지 않는다고 전제한다.
2. **프로젝션 read model = "머티리얼라이즈드 캐시"이므로 그 앞의 in-memory 캐시는 항상 중복이다** — DB 버퍼풀/디스크 I/O/커넥션 획득 지연이 in-memory 접근과 tail latency 상 동급이라고 본다.
3. **읽기 확장 문제는 HA 레플리카로 풀린다** — 처리량(동시성 분산)과 tail latency(단건 응답 시간)를 같은 축의 문제로 취급한다.
4. **도메인별 스키마를 한 query 인스턴스에 묶어도 프로젝션 쓰기 병목은 이 문서 범위 밖(07)이라 이 문서의 확장 주장에 영향 없다** — 읽기(§9)와 쓰기(07)를 완전히 독립 축으로 본다.

---

## 3. 반론

### 반론 1 — RFC-030이 이미 확정한 신선도 토큰 계약을 이 서버가 자기 구조에 반영하지 않고 R-1로 재차 이월
**[type: structural]** · severity: **critical**

RFC-030(🏷 합의, 2026-07-05 — 오늘 기준 2주 전 확정)은 read-after-write 토큰을 `sequence_no` 재사용으로 결정했고, 논점 4에서 구현 위치를 명시적으로 "읽기 엔드포인트"로 지정했다: "클라가 `(reservationId, sequenceNo)`를 실으면, 읽기 엔드포인트가 `seq ≥ N`까지 반영됐는지 확인 → 못 왔으면 짧게 대기(long-poll)/폴백", "projection row는 적용한 원본 `sequence_no`를 보유". 그런데 이 문서 §5의 `findMyReservations(userId, page)`에는 `sequenceNo` 파라미터, projection row의 원본 seq 컬럼, long-poll/대기 로직이 전혀 없고, §7·§11(R-1)은 이 결정을 "증명된 화면만 예외 → 신규 ADR로 승격"이라며 여전히 미결로 취급한다. 이 서버가 구현해야 할 계약을 서버 설계 문서가 자기 밖으로 재차 밀어낸 것이라 구조적 결함이다. 선례: RFC-030 논점 4·결정 4가 명시적으로 확정 — 추측 아님, 문서 간 실제 불일치.

### 반론 2 — Redis 금지 + "핫 쿼리엔 전용 프로젝션"이 tail latency 문제를 프로젝션 조합 폭발과 캐시 완충 상실로 치환
**[type: assumption]** · severity: **medium**

§45·§9는 캐시 계층 대신 "전용 프로젝션 추가 + HA 레플리카"로 핫 쿼리를 흡수한다. 그러나 파라미터 조합이 많은 조회(식당×날짜×필터)는 미리 만들 프로젝션이 조합 폭발하며, 프로젝션은 특정 조회 모양 하나를 물질화할 뿐 임의 파라미터 질의를 상수시간으로 만들지 못한다. 결국 QueryDSL이 레플리카 MySQL을 직격하고 캐시 완충이 없어 콜드 버퍼풀·offset 페이징·count 분리 쿼리의 p99가 그대로 노출된다 — HA 레플리카는 동시성(처리량)만 나눌 뿐 단건 tail latency는 줄이지 않는다. 선례: 같은 문서군의 DESIGN-004 자기리뷰(§187)가 "프로젝션 N개의 운영·정합성 부담 N배"를 이미 지적 — 문서 내부에서 제기됐으나 이 서버 설계에 반영되지 않은 반론.

### 반론 3 — 도메인별 스키마를 한 인스턴스에 묶는 구조가 프로젝션 쓰기 병목을 읽기 확장(레플리카)으로 못 가리게 만든다
**[type: structural]** · severity: **medium**

§4/§68은 read model을 한 query 인스턴스 안에 도메인별 스키마로 담고, §9는 읽기 확장을 "인스턴스 분할 아님, HA 레플리카"로 못 박는다. 그런데 레플리카는 읽기만 나누고, 프로젝션 쓰기(07의 이벤트 소비→갱신)는 프라이머리 하나에 집중된다. 핫 스트림의 프로젝션 lag이 커지면 §7의 p99 목표를 레플리카 증설로는 지킬 수 없는데, "인스턴스 분할 안 함" 원칙이 이 탈출구를 구조적으로 미리 닫아둔 것이다. 선례: DESIGN-004 자기리뷰(§188)가 "레플리카는 읽기만 나눈다 · 인스턴스 분할 안 함이 탈출구를 미리 닫는다"를 이미 명시적으로 지적 — 추측이 아니라 문서군이 자인한 제약.

## 4. 다중 페르소나 공격

**고객/사용자**: 예약을 확정하면 확인 화면에서 "○○식당 예약 완료"가 보인다(RFC-030 §5 권위 바디 경로). 그런데 앱을 껐다 켜거나 새로고침해서 "내 예약" 목록을 다시 열면 — 콜드 조회다 — 방금 만든 예약이 없다. 예약 시스템에서 "방금 예약한 게 안 보인다"는 부수적 엣지가 아니라 가장 흔한 첫 여정인데, 사용자는 이걸 "예약 실패"로 읽고 최악의 경우 다시 예약을 누른다. RFC-030은 이 콜드 read-your-writes를 `sequence_no` 토큰으로 정확히 닫아뒀지만, 이 읽기 서버의 read path(§5)는 그 토큰을 받지 않으므로 계약이 존재해도 실제 화면에는 도달하지 않는다.

**On-call/SRE**: 새벽에 프로젝션 lag 알람이 뜬다(§7은 p99 골격만 정의, 절대 임계값은 아직 없다). 만약 신선도 토큰의 long-poll이 나중에 얹힌다면, lag이 커진 바로 그 순간에 읽기 요청들이 `seq ≥ N`을 기다리며 readOnly 트랜잭션/커넥션을 붙든 채 쌓여 읽기 서버 스레드가 고갈된다 — 투영이 밀릴 때 조회까지 함께 죽어 §7·§9가 주장하는 "장애 격리"가 정확히 그 순간에 깨진다. 게다가 캐시 완충이 없으므로(§45) 조회 트래픽 폭증은 레플리카를 곧바로 때리고, 즉시 완화 수단이 "프로젝션 추가"(코드·배포 필요)뿐이라 인시던트 중 손잡이가 없다.

---

## 5. 핵심 취약점

읽기 서버가 자기 핵심 책임 — 읽기 엔드포인트의 신선도 토큰 구현 — 을 R-1로 자기 밖에 미뤄, **이미 합의된 RFC-030 계약이 서버의 read path 시그니처·트랜잭션 경계에 전혀 반영되지 않은 채** "최종 일관성 단순 조회"로 설계되었다는 점. 예약 확정 직후 목록 확인이라는 예약 시스템의 핵심 여정에 대해, 계약은 존재하지만 그 계약이 도달할 코드 경로가 없다.

---

## 6. 가역성 프레임

대체로 **reversible**(read path 시그니처·스키마 배치·QueryDSL 구현은 코드 레벨 변경) — 단, 신선도 토큰(long-poll + `seq` 비교)을 뒤늦게 끼워 넣으려면 readOnly 트랜잭션 경계·스레드/커넥션 풀 모델·projection row 스키마(원본 seq 컬럼)를 함께 되짚어야 하므로 **준-one-way door**에 가깝다. 처음부터 read path 시그니처에 토큰 자리를 열어두는 편이 나중에 되짚는 비용보다 싸다.
