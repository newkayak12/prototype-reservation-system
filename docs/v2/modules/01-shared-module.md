# 01 · shared-module [유지]

> 허브: [[00-module-index]] | 근거: [[DESIGN-002]] §4.1

## 1. 책임

전 모듈이 공유하는 **공유 커널(Shared Kernel)**. 도메인 의미를 담지 않는 최하위 공통물만 둔다.

- Enum (상태·역할·코드 등 기술 중립 열거)
- 추상 예외 계층 (도메인 예외가 상속하는 base)
- 유틸리티 (날짜·문자열·암호화 헬퍼 등)

### 1.1 포함 기준 (positive criteria — §7 반론 1·3 대응)

배제 조건("도메인 의미 없음·프레임워크 없음")만으로는 상한이 없다. 새 타입을 shared에 추가하기 전, **세 조건을 모두** 만족해야 한다 — 하나라도 아니면 shared가 아니라 해당 컨텍스트(command-core 서브패키지)나 contract-module로 간다:

1. **프레임워크 의존 0** — Spring·JPA·jakarta import 없음(기존 §3 금지 라이브러리와 동일 기준, R2 순수성 규칙과 동형).
2. **2개 이상의 서로 무관한 모듈이 실제로 사용** — "나중에 재사용될 수도 있다"는 예측이 아니라, 지금 시점에 최소 2개 모듈(예: command-core와 query, 또는 command-*와 auth-server)이 이미 참조하는 타입만 후보. 아직 한 곳에서만 쓰이면 그 모듈 안에 둔다(YAGNI).
3. **특정 바운디드 컨텍스트의 업무 의미를 담지 않음** — `AggregateType`처럼 이벤트 소싱 개념에 결부된 열거형은 "범용"이 아니라 [[02-contract-module]] 소관(§6 M 참조) — contract가 shared를 의존하는 방향 자체가 만드는 인력(gravity)에 저항하는 것이 이 기준의 목적이다.

PR 리뷰에서 새 shared 타입은 이 세 기준을 커밋 메시지/PR 설명에 명시하는 것을 관례로 한다(자동 강제는 기준 2·3의 판단이 정적 분석 범위 밖이라 불가능 — 기준 1만 Konsist로 강제 가능, §3 참조).

## 2. 의존성

| 항목 | 값 |
|------|-----|
| **허용 의존** | 없음 (최하위) |
| **피의존** | 모든 모듈 |
| **금지** | 어떤 상위 모듈도 import 금지. "god module"化 경계 |
| **변경 범위** | 최소 |
| **구현 시점** | Phase 7-0 (사전 정리) |

## 3. 사용 라이브러리

shared는 **프레임워크 비의존**을 지향한다. Spring/JPA를 끌어들이면 이걸 의존하는 `command-core`의 순수성이 깨진다([[03-command-core]]).

| 라이브러리 | 버전 | 용도 |
|-----------|------|------|
| Kotlin stdlib | `2.0.10` | 기본 |
| `kotlin-reflect` | (kotlin 정렬) | 필요 시에만 (enum/reflection 유틸) |
| (테스트) `kotest-*` | `5.9.0` | 유틸 단위 테스트 |

> **금지 라이브러리**: `spring-*`, `jakarta.persistence`, `jakarta.validation`. 검증 어노테이션을 shared에 넣고 싶은 유혹이 있으나([[DESIGN-002]] 자기리뷰 §6.1), 이는 순수성 논쟁을 유발하므로 넣지 않는다. 검증은 각 계층이 순수 Kotlin `require`로 처리.

> **강제**([[RFC-031-architecture-fitness-functions-archunit]] 규칙 카탈로그 R7): `com.reservation.shared..`는 `kotlin..`/`java..`만 접근 — Spring·JPA·jakarta import 시 Konsist 규칙이 빌드를 실패시킨다(R2와 동형, command-core뿐 아니라 shared 자신도 검사). 단 이 규칙은 §1.1 포함 기준의 **기준 1(프레임워크 의존 0)만** 강제한다 — 기준 2(2개 이상 모듈 사용)·기준 3(도메인 의미 없음)은 정적 분석 범위 밖이라 PR 리뷰로만 걸러진다.

## 4. 구조

```
shared-module
└── com.reservation.shared
    ├── enumeration/      # 공통 enum
    ├── exception/        # 추상 예외 base (AbstractDomainException 등)
    └── util/             # 순수 유틸
```

## 6. 미결

- **M**: 이벤트 관련 공유 타입(예: `AggregateType` enum)을 shared에 둘지 contract에 둘지 — contract가 shared를 의존하므로 "이벤트 전용"이면 contract, "범용"이면 shared. 구현 시 판정([[00-module-index]] Phase 7-0).

## 7. 악마의 변호인 (Devil's Advocate)

> 이 문서 설계에 대한 가장 강한 반론 (구현 전 스트레스 테스트용).

**Position**: shared는 도메인 의미·프레임워크를 배제한 최하위 순수 공유 커널로, kotlin stdlib + kotest만 허용하고 얇게 유지한다.
**Steel-man**: 공유 타입이 실제로 소수(enum·추상예외·무상태 유틸)에 그치고, "범용 vs 이벤트 전용" 경계가 구현 시점에 흔들림 없이 판별되며, 검증을 각 계층이 순수 `require`로 자족적으로 처리할 때 — 이때 shared는 최소·안정·프레임워크-프리를 동시에 달성한다.

### 숨은 가정

1. ~~"도메인 의미 없는 범용 공통물"의 집합에 자연스러운 상한이 있다~~ — **부분 해소(2026-07-20)**: §1.1에 positive 기준(프레임워크 의존 0·2개 이상 모듈 사용·도메인 의미 없음) 3개를 명문화했다. 다만 기준 2·3은 정적으로 강제 불가능한 판단 기준이라, PR 리뷰 관례에 의존한다는 한계는 남는다.
2. **"god module化 경계"는 규칙으로 선언하면 지켜진다** — §3에 Konsist R7(프레임워크 순수성)을 추가해 **기준 1만** 이제 강제된다. 기준 2·3("2개 이상 모듈이 실제 사용", "도메인 의미 없음")을 강제하는 메커니즘(의존성 예산, PR 게이트 자동화)은 여전히 없다 — 선언과 강제의 간극이 셋 중 하나만 좁혀졌다.
3. **순수 Kotlin `require` 검증이 검증 로직의 중복·shared 흡입을 유발하지 않는다** — §3이 "검증은 각 계층이 순수 Kotlin require로 처리"한다고 단정하나, 여러 계층·컨텍스트가 같은 불변식(이메일·전화·코드 형식)을 검사할 때 공유 지점이 필요해진다는 반대 압력은 다루지 않는다.

### 반론

1. **[structural] · severity: high** — Steel-man: 최하위 + 전(全)모듈 피의존이라는 위치는 "누구나 재사용하지만 아무도 소유하지 않는" 공유물을 담기에 구조적으로 자연스럽다. 비판(이 문서 한정): shared는 정확히 그 anti-pattern의 좌표에 서 있는데, 이 문서는 "얇게 유지"를 의지(§3 "지향")로만 강제한다. 애매한 cross-cutting 타입(공통 코드 상수, 포맷 헬퍼, ID 래퍼)이 생길 때 **최소저항 종착지가 항상 shared**이고, 이동을 막는 컴파일 신호도 예산도 없다. 선례: 대다수 대형 코드베이스의 `common`/`util`/`core-common` 모듈이 명시적 예산 없이 grab-bag(잡동사니)으로 비대해지는 것은 잘 알려진 재발 패턴.

2. **[assumption] · severity: high** — Steel-man: 프레임워크-프리를 지키면 이걸 의존하는 command-core의 순수성이 보존된다(§3의 핵심 논거)는 것은 타당하다. 비판(이 문서 한정): 그러나 [[DESIGN-002]] 자기리뷰 §6.1은 바로 이 순수성 강제가 "공유 밸리데이션 어노테이션을 shared-module에 재구현하거나 검증을 application으로 올리는 우회"를 낳는다고 **스스로 인정**한다. 즉 이 문서가 §3에서 금지한 "검증 어노테이션의 shared 유입"은, 같은 설계가 만든 순수성 제약 때문에 **압력으로 되돌아온다**. "각 계층이 순수 require로"는 중복 검증 로직을 낳고, 그 중복을 없애려는 순간 shared가 "검증 유틸" 명목으로 다시 부푼다 — 반론 1의 god-module화를 구체적으로 실현하는 경로다. 선례: no clear precedent — speculative concern (이 프로젝트 고유의 순수성-검증 긴장에 국한).

3. **[structural] · severity: medium** — Steel-man: contract가 shared를 의존하므로 "범용은 shared, 이벤트 전용은 contract"라는 방향 규칙은 논리적으로 일관된다. 비판(이 문서 한정): 그 분류 기준("범용 vs 이벤트 전용")은 관찰 가능한 속성이 아니라 **미래 재사용 의도에 대한 추측**이라 판별 불가능에 가깝다. 게다가 의존 방향(contract→shared) 자체가 편향을 만든다 — 애매하면 "더 넓게 재사용 가능하니 아래(shared)에 두자"는 중력이 항상 작동해 contract가 소유해야 할 타입까지 shared로 빨려든다. §6 미결이 `AggregateType`의 소속을 "구현 시 판정"으로 미룬 것은 완화가 아니라, **경계 결정을 가장 결정 압력이 큰 순간으로 연기**하는 것이다.

### 핵심 취약점

**갱신(2026-07-20)**: §1.1이 positive 기준 3개를 명문화하고 §3의 Konsist R7이 그중 하나(프레임워크 순수성)를 빌드 실패로 강제해, "negative로만 정의됨"이라는 원 결함은 부분적으로 닫혔다. **남은 취약점**: 기준 2("2개 이상 모듈이 실제 사용")·기준 3("도메인 의미 없음")은 본질적으로 정적 분석이 판별할 수 없는 의도·재사용 예측의 문제라, 여전히 PR 리뷰어의 판단에 전적으로 의존한다 — 문서화된 기준이 생겼다는 것과 그 기준이 매 PR에서 실제로 적용된다는 것 사이에는 여전히 간극이 있다.

### 가역성

reversible — 타입의 shared↔contract 이동은 패키지 이동 리팩터링이고 컴파일 의존성이 오류를 강제하므로 되돌리기 안전하다. 단 shared는 전(全)모듈 피의존이라, 일단 여러 모듈이 특정 shared 타입에 물린 뒤에는 이동 비용(호출처 전면 수정)이 급격히 커진다 — 되돌릴 수 있으나 늦을수록 비싸다.
