# ADR-015: 결제 연동 경계 = ACL — PG 어휘를 3 이벤트로 번역, 내부는 상태+Outbox

- **상태**: Proposed
- **사이클**: `20260612-v2-cqrs-es-architecture`
- **상위 RFC**: [[RFC-016-payment-integration-boundary]] · **설계**: [[DESIGN-015-payment-integration]]
- **연관 ADR**: [[ADR-008-saga-orchestration-vs-choreography]]

---

## 맥락과 문제 (Context and Problem Statement)

V1에는 결제 흔적이 없다(`payment`·`refund` 코드 0건) — 그린필드 경계 설계다. V2는 코레오그래피([[ADR-008-saga-orchestration-vs-choreography]])로 흐른다. `reservation`이 예약 요청을 받으면 `timetable`이 자리를 잡고(`SeatHeld`), `SeatHeld`를 받은 `payment`가 외부 PG에 결제를 요청하며, PG가 비동기 웹훅/콜백으로 결과를 알리면 `payment`가 검증 후 `PaymentConfirmed`(또는 `PaymentFailed`)를 발행하고, 이를 받은 `reservation`이 예약을 확정한다.

`payment`는 우리 컨텍스트끼리의 관계와 성격이 다르다. PG 호출은 HTTP 한 번이 돈을 움직이는 부수효과라 우리 커밋에 못 묶이고, 결과는 비동기 웹훅(늦음·역순·중복·유실)으로 오며, PG는 우리와 독립적으로 실패한다. PG의 어휘(`transactionId`, `paid`/`failed` 등)를 도메인이 날것으로 받으면 벤더 모델이 코레오그래피 안으로 샌다.

**외부 진실(PG 원장)을 도메인 이벤트로 들이고, 의도를 외부로 내보내고, 어긋나면 맞추되, PG 벤더 모델이 코레오그래피 안으로 새지 않게 경계를 어떻게 봉인하는가.**

## 결정 동인 (Decision Drivers)

- PG 벤더 모델이 코레오그래피 안으로 새면 벤더를 바꿀 때 사가가 깨진다 — 번역 경계가 유일 책임이어야 한다.
- 결제 확정의 진실은 우리가 아니라 PG 원장이다 — 비신뢰 입력(콜백)을 확정 근거로 쓸 수 없다.
- PG 호출(부수효과)은 우리 트랜잭션에 못 묶인다 — dual-write는 이중 청구로 직결된다.
- 모든 방어를 갖춰도 웹훅 유실·verify 타임아웃 같은 잔여 불일치는 남는다 — 안전망이 필요하다.
- 코레오그래피 참여 컨텍스트가 PG의 비동기·실패를 보지 않아야 한다 — 사가 본류로 외부 연동의 불확실성이 새지 않아야 한다.

## 검토한 선택지 (Considered Options)

- **A. `payment` = ACL(부패방지층), 내부 = 상태+Outbox** — PG 어휘를 3 이벤트로 번역하는 것이 유일 책임, 내부는 상태+Outbox(진실 원천은 PG 원장).
- **B. 리다이렉트 콜백을 결제 확정 근거로 사용** — 브라우저 경유 UX 신호로 곧장 확정.
- **C. 웹훅 + verify 역조회를 확정 근거로, 인바운드 입구 3겹(서명검증·멱등 디듀프·verify 수렴)** — 콜백은 verify 트리거용 비신뢰 신호로만 사용.
- **D. PG 호출과 이벤트 기록을 한 트랜잭션으로 묶는 dual-write** — 순진한 원자적 처리.
- **E. 의도 기록(로컬 TX) → 멱등키 릴레이가 PG 호출 → 결과 이벤트** — at-least-once 호출을 effectively-once 청구로 전환. 환불도 동일 경로(새 정방향 호출).
- **F. 양방향 동기화(우리 상태도 PG에 반영)** — 실시간 상호 보정.
- **G. 주기적 단방향 대사(PG가 진실) + 운영 보정 큐** — 자동으로 못 푸는 건은 사람이 처리.

## 결정 (Decision Outcome)

**채택: A(ACL + 상태+Outbox) + C(웹훅+verify, 입구 3겹) + E(의도 기록 → 멱등키 릴레이) + G(단방향 대사).** B는 위조·재전송에 취약해 미결제 예약을 확정시킬 수 있어 기각, D는 PG 호출과 로컬 커밋이 원자 단위가 아니라 이중 청구로 직결되어 기각, F는 우리 상태가 PG 원장의 사본이라는 전제와 어긋나 기각.

| 영역 | 결정 |
|---|---|
| **정체** | `payment` = **ACL**. PG 어휘(`transactionId`, `paid`/`failed` 등)를 `PaymentConfirmed`/`PaymentFailed`/`PaymentRefunded` **3개 이벤트로 번역**하는 것이 유일 책임. 내부 데이터는 **상태+Outbox** — ES가 아니다. 결제 거래의 진실 원천은 PG 원장이고 우리 이력은 그림자일 뿐이라 ES를 도입할 이유가 약하다. |
| **인바운드** | 결제 확정의 진실은 리다이렉트 콜백(브라우저 경유, 비신뢰)이 아니라 **웹훅 + verify 역조회**로 받는다. ACL 인바운드 입구에 3겹을 둔다: (1) **서명 검증** — HMAC/공개키로 PG가 보낸 게 맞는지 확인, (2) **멱등 디듀프** — PG 거래 ID 기준, 이미 처리한 건은 no-op, (3) **verify 역조회 + 순서 무력화** — PG 측 상태를 진실로 받아 수렴, 늦게 온 옛 상태는 무시. |
| **아웃바운드** | PG 호출은 우리 트랜잭션에 못 묶인다. dual-write를 회피한다 — **의도를 먼저 로컬 TX로 기록 → 멱등키 단 릴레이가 PG 호출 → 결과를 이벤트로.** PG의 Idempotency-Key로 at-least-once 호출을 effectively-once 청구로 만든다. **환불도 같은 경로** — 보상은 롤백이 아니라 새 정방향 호출이다. |
| **대사** | 모든 방어를 갖춰도 잔여 불일치는 남는다. 주기적으로 PG 원장과 우리 상태를 대조해 **단방향 보정(PG가 진실)**. 자동으로 못 풀리는 건은 **운영 보정 큐**로 올린다. |
| **이벤트 표면** | `payment`가 코레오그래피에서 다른 컨텍스트에 노출하는 이벤트는 `PaymentConfirmed`/`PaymentFailed`/`PaymentRefunded` **3개로 동결**. PG 벤더가 바뀌어도 이 표면은 불변이다. |

### 결과 (Consequences)

- 좋은 점: PG 벤더가 바뀌어도 사가가 보는 이벤트 표면(3개)이 불변이라, 벤더 교체가 코레오그래피 참여 컨텍스트에 영향을 주지 않는다.
- 좋은 점: 진실 원천을 PG 원장으로 못 박아, 위조·재전송 가능한 콜백만으로 예약이 확정되는 경로가 원천 차단된다.
- 좋은 점: 의도-먼저 기록 + 멱등키 릴레이로 dual-write 함정(이중 청구)을 피한다.
- 좋은 점: 사가 본류(다른 컨텍스트)는 PG의 비동기·실패를 보지 않고 3 이벤트로만 결과를 받는다 — 외부 연동의 불확실성이 예약 사가 본류로 새지 않는다.
- 나쁜 점 / 트레이드오프: 단방향 대사는 안전망일 뿐 SLA를 가진 확정 경로가 아니다 — 웹훅 유실 시 확정이 대사 주기만큼 지연될 수 있다.
- 나쁜 점 / 트레이드오프: ACL 인바운드 3겹·아웃바운드 릴레이·대사 큐라는 별도 machinery가 요구되어 구현 표면이 늘어난다.

### 확인 (Confirmation)

구현 사이클에서 정의. RFC-016은 상태 모델·인바운드 ACL 코드 구조·릴레이 배치·대사 주기 수치·PG 선정을 Design/구현 사이클로 명시적으로 위임했다([[DESIGN-015-payment-integration]] §3 Non-Goal).

## 선택지 상세 (Pros and Cons of the Options)

### B. 리다이렉트 콜백을 결제 확정 근거로 사용 (기각)

- 장점: 브라우저 경유라 빠르게 확정할 수 있다.
- 단점: 콜백은 "사용자가 결제창을 마쳤다"는 UX 신호일 뿐 돈이 움직였다는 근거가 아니다.
- 기각 사유: 콜백을 위조·재전송하면 미결제 예약이 확정될 수 있다.

### D. dual-write (PG 호출 + 이벤트 기록을 한 트랜잭션으로) (기각)

- 장점: 구현이 단순해 보인다.
- 단점: PG 호출과 로컬 커밋은 원자 단위가 아니다 — PG 호출은 성공했는데 커밋 직전 죽으면 돈은 빠져나갔는데 우리는 모른다.
- 기각 사유: at-least-once 재처리 아래선 곧장 이중 청구가 된다.

### F. 양방향 동기화 (기각)

- 단점: 우리 상태를 PG에 반영하는 방향까지 자동화하면, 우리 쪽 오류가 PG 원장(진실)을 오염시킬 위험이 생긴다.
- 기각 사유: 결제 거래의 진실 원천은 PG 원장이고 우리 이력은 그림자이므로, 보정은 PG 방향으로만 흘러야 한다.
