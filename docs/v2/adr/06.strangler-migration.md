# ADR: Strangler 점진 마이그레이션

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[04-migration]]

## 맥락

V1 → V2 전환은 모듈 구조([[01.cqrs-command-query-module-split]])·쓰기 모델([[02-write-model]])·읽기 모델([[03-read-model]])을 크게 바꾼다. 9개 컨텍스트를 한 번에 바꿀지, 점진적으로 옮길지 정해야 한다. `timetable` 은 이미 이벤트/Outbox를 보유해 부분 전환이 진행된 상태다.

## 고려된 옵션들

### Option A: 빅뱅 일괄 전환
- 장점: 과도기 혼재 없음, 일관된 V2.
- 단점: 위험 매우 높음. 긴 중단·회귀 위험. 솔로/사이드 규모에 비현실적.

### Option B: 점진 전환 — 한 번에 하나씩 이전 (선택됨)
- 장점: 컨텍스트 단위 저위험 이동. 미전환분은 그대로 두고 순차 이전. 이미 진행된 `timetable` 을 템플릿화.
- 단점: 과도기 동안 V1/V2 혼재(이벤트로 통합 필요). 전환 기간 장기화.

## 결정사항

**Option B — 점진 전환. 컨텍스트를 한 번에 하나씩 V2로 옮긴다.**

> 두 시스템을 동시에 가동하는 "병행 운영"이 아니라, **코드 레벨에서 컨텍스트를 순차 이전**하는 것이다. 아직 안 옮긴 컨텍스트는 기존(V1) 코드를 그대로 둔다.

전환 순서(초안, 의존성 기반):

1. **`timetable`** — 기존 Outbox/Kafka를 V2 command/query 구조로 정리 → **레퍼런스 템플릿**.
2. **`reservation`** — 핵심 ES화([[07.reservation]] EDA 계승).
3. **`restaurant`** — ES화 + 검색/상세 프로젝션.
4. **`schedule`·`user`·`authenticate`** — 상태+Outbox로 CQRS 참여.
5. **`menu`·`category`·`company`** — 현행 유지, 필요 시 Outbox.

- 미전환 컨텍스트는 V1 경로 유지, 통합은 이벤트(Outbox→Kafka)로. Zero Payload라 혼재 구간에서도 안전([[02-write-model]]).
- 각 단계는 별도 사이클로 다룰 수 있다(이 사이클은 *설계*까지). 상세는 [[04-migration]].

## 장점
1. 단계별 저위험, 회귀 격리.
2. `timetable` 선행을 템플릿으로 재사용.
3. fail-fast — 위험·핵심(ES)을 앞에 배치.

## 트레이드오프

### 선택한 방식의 한계
- 과도기 V1/V2 혼재 — 이벤트 기반 통합과 정합성 관리 필요.
- 전체 전환 기간이 길어진다.

### 포기한 대안들
- **빅뱅(A)**: 위험·중단 비용 과대.

## 미결정 사항 및 추가 논의
- 단계별 사이클 분할·일정.
- 신규 기능(리뷰·포인트·신고) 투입 시점(전환된 패턴 위에서 추가).

## 결과 (기대)
- 운영 중단 없이 컨텍스트 단위로 V2 이행.
- 각 단계가 검증 가능한 체크포인트를 가짐.
