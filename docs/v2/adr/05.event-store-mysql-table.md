# ADR: 이벤트 스토어 — MySQL 이벤트 테이블 직접 구현

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[02-write-model]]

## 맥락

[[02.selective-event-sourcing-scope]]에서 `reservation`·`timetable`·`restaurant` 를 진짜 ES로 정했다. 이들의 쓰기 저장소(이벤트 스토어)를 **무엇으로 구현**할지 정해야 한다. 프로젝트는 이미 MySQL·Flyway·JPA·기존 Outbox([[07.reservation]])를 운영 중이다.

### 요구사항
- append-only 이벤트 저장, 애그리거트별 스트림.
- 낙관적 동시성(기대 시퀀스에 append).
- 리플레이로 상태 재구성, 스냅샷으로 단축.

## 고려된 옵션들

### Option A: 전용 이벤트 스토어 제품 (EventStoreDB / Axon 등)
- 장점: ES 기능(스트림·구독·스냅샷) 기성 제공.
- 단점: 신규 인프라·운영·학습 비용. 현 규모에 과함. 기존 MySQL/Outbox 자산과 이중화.

### Option B: MySQL 이벤트 테이블 직접 구현 (선택됨)
- 장점: 기존 인프라 재사용. Flyway 마이그레이션·트랜잭션·Outbox와 한 트랜잭션. 운영 단순.
- 단점: 스트림·스냅샷·동시성 제어를 직접 구현. 대규모에서 성능 한계 가능.

## 결정사항

**Option B — MySQL의 append-only 이벤트 테이블로 직접 구현.**

```
event_store(
  aggregate_type, aggregate_id, sequence_no,   -- (aggregate_id, sequence_no) UNIQUE
  event_type, event_version, payload(JSON),
  occurred_at
)
```

- **낙관적 동시성**: 기대 시퀀스로 append, `(aggregate_id, sequence_no)` UNIQUE 위반 시 재시도([[02-domain-limitations]] #6 해소).
- **스냅샷 최적화**: 기존 `*Snapshot` 패턴을 재활용해 N 이벤트마다 스냅샷 → 리플레이 단축.
- **Outbox 연계**: 이벤트 저장과 통합 이벤트 발행을 한 트랜잭션으로([[07.reservation]] 계승).
- 메커니즘 상세는 [[02-write-model]].

## 장점
1. 신규 인프라 0 — MySQL/Flyway/Outbox 그대로.
2. 이벤트 저장·상태·Outbox가 한 트랜잭션 → 원자성.
3. 운영·디버깅 단순(기존 도구로 조회).

## 트레이드오프

### 선택한 방식의 한계
- 스트림·스냅샷·구독·동시성을 **직접 구현**(코드 책임 증가).
- 초대규모에서는 전용 제품 대비 성능·기능 한계.

### 포기한 대안들
- **전용 제품(A)**: 현 규모에 과한 운영/학습 비용, 자산 이중화.

## 미결정 사항 및 추가 논의
- 스냅샷 주기(N), 페이로드 직렬화·스키마 진화 정책.
- 이벤트 테이블 파티셔닝/아카이빙(데이터 증가 시).
- 트래픽 증가 시 전용 제품/CDC로의 전환 기준(점진적 확장 — [[07.reservation]]의 CDC 후속 계획과 정합).

## 결과 (기대)
- 핵심 컨텍스트의 상태 변화가 MySQL 이벤트 스트림으로 추적·재구성.
- 기존 인프라 위에서 ES 도입 비용 최소화.
