# ADR: 이벤트 순서 보장과 전달 보장

- **상태**: Proposed (2026-06-13) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[07-messaging-topology]]
- **인접**: [[03-read-model]] · [[06-consistency-and-sagas]]
- **계승**: [[07.reservation]] (v1 — Kafka·Outbox·Zero Payload·PoisonMessage)

## 맥락

command↔query 의 유일한 접점은 이벤트(contract)이고([[03.command-hexagonal-query-layered]]), 그 이벤트는 Kafka 로 흐른다([[07-messaging-topology]]). 그렇다면 두 가지를 못 박아야 나머지 메시징 설계가 따라온다.

1. **순서**: 이벤트는 어디까지 순서가 보장되는가? ES 컨텍스트의 이벤트는 `(aggregate_id, sequence_no)` 로 순서가 의미를 갖는다([[05.event-store-mysql-table]]). 이 순서가 전달 채널에서 유지되지 않으면 프로젝션이 깨진다.
2. **전달**: 이벤트는 몇 번 전달되는가? 누락이면 read model 이 영구히 어긋나고, 무한 중복이면 프로젝션이 오염된다.

프로젝트는 이미 Kafka·Outbox·Zero Payload·PoisonMessage 자산을 운영 중이다([[07.reservation]]). 그 위에서 결정한다.

### 요구사항
- 한 애그리거트의 이벤트는 발생 순서대로 프로젝션에 적용되어야 한다.
- 이벤트는 유실되지 않아야 한다(최종 일관성이라도 결국 도달).
- 중복이 read model 을 오염시키지 않아야 한다.

## 고려된 옵션들

### 순서 보장

#### Option O-A: 파티션 키 = aggregate_id, 토픽 = 컨텍스트/aggregate-type 단위 (선택됨)
- 장점: Kafka 의 파티션 내 순서 보장으로 **애그리거트별 순서**가 자연 성립. event_store 의 `aggregate_type`·`aggregate_id` 축과 정렬. 추가 인프라 0.
- 단점: 전역 순서는 보장 안 됨(불필요). 파티션 수 변경 시 재해싱으로 순서 깨짐 → 운영 제약.

#### Option O-B: 단일 파티션으로 전역 순서
- 장점: 전 이벤트 전역 순서.
- 단점: 병렬성 0(처리량 한계). 도메인이 요구하지 않는 전역 순서를 비싸게 사는 것 — 과잉.

#### Option O-C: 페이로드의 sequence_no 로 컨슈머가 재정렬
- 장점: 전달 순서와 무관하게 컨슈머가 순서 복원.
- 단점: 컨슈머에 버퍼·갭 감지·타임아웃 로직 필요(복잡). 파티션 키로 이미 풀리는 문제를 코드로 다시 푸는 격.

### 전달 보장

#### Option D-A: at-least-once + 멱등 컨슈머/inbox → effectively-once (선택됨)
- 장점: Outbox 재시도([[02-write-model]])·Kafka 재소비와 정합. 멱등으로 중복 흡수. Zero Payload 와 결합 시 자연 멱등. 비용 합리적.
- 단점: 컨슈머가 멱등·inbox 책임을 짐. "정확히 한 번 전달"은 아님(효과만 1회).

#### Option D-B: 진짜 exactly-once (Kafka EOS, 트랜잭셔널 producer/consumer)
- 장점: 이론상 중복·누락 동시 제거.
- 단점: Outbox 가 트랜잭션 밖(AFTER_COMMIT)이고 read model 이 외부 MySQL 이라 **전 구간을 Kafka 트랜잭션으로 묶어야** 성립 → 비용·복잡도 과함. 현 규모·학습 목표에 YAGNI.

#### Option D-C: at-most-once (재시도 없음)
- 장점: 중복 0, 단순.
- 단점: 누락 시 read model 영구 불일치. 받아들일 수 없음.

## 결정사항

**순서 = O-A, 전달 = D-A.**

### 순서 — 애그리거트별 순서만 보장
- **파티션 키 = `aggregate_id`**. 토픽은 **`<context>.<aggregate-type>` 단위**([[07-messaging-topology]] §1). 같은 애그리거트의 이벤트는 한 파티션 → 발행 순서대로 소비.
- **전역 순서는 보장하지 않는다** — 불변식은 애그리거트 경계 안([[05-aggregate-design]])이라 도메인 요구가 아니다.
- **파티션 수는 순서 계약의 일부** — 넉넉히 잡고 가급적 고정. 증설은 컨슈머 드레인 후 정지 상태에서. (재해싱이 순서를 깬다.)

### 전달 — effectively-once
- **at-least-once** 를 기본으로 한다(누락보다 중복 허용). Outbox AFTER_COMMIT + 스케줄러 재시도([[02-write-model]]), Kafka 처리-후-커밋이 그 출발점.
- **멱등 컨슈머/inbox 로 중복 흡수**. inbox = 처리한 **`event_id`**(전 컨텍스트 공통 정체성 — [[22.event-identity-and-global-ordering]]) 기록, read model 갱신과 **한 트랜잭션**. (ES 이벤트의 `(aggregate_id, sequence_no)`는 dedup이 아니라 *순서·버전 가드*로 병행 쓰인다 — "봤는가"와 "더 과거를 덮지 마라"는 다른 일이다.) Zero Payload upsert 는 자연 멱등이라 inbox 생략 가능(같은 애그리거트 순서가 §순서로 보장된다는 전제).
- **진짜 exactly-once 는 채택하지 않는다** — "정확히 한 번 전달"이 아니라 "정확히 한 번의 효과(effectively-once)"가 목표.

### 보장 성립 조건 — 그레이스풀 셧다운/드레인
- 위 보장은 **깔끔한 종료**에서만 성립. 프로젝터는 셧다운·리밸런싱 시 인플라이트 배치를 처리·커밋 후 종료(드레인). command 는 진행 트랜잭션을 마치고 Outbox 스케줄러를 멈춘다.
- **멱등은 안전망, 드레인은 효율** — 드레인 없이 죽어도 멱등이 막지만 재처리량이 는다.

### 컨슈머 그룹·백프레셔
- 프로젝터마다 전용 컨슈머 그룹(팬아웃). 수평 확장은 같은 그룹 내 인스턴스 증설(competing consumers), **병렬 상한 = 파티션 수**. — **단 이 상한은 competing-consumers 한정**(트리아지 C08/C28, 2026-07-05): Parallel Consumer 를 `KEY` ordering(key = `aggregate_id`)으로 쓰면 파티션 내 key 병렬로 상한이 파티션 수에서 분리된다. 애그리거트별 순서는 그대로 보장되므로 위 순서 계약과 양립. 채택 근거·전달 보장(at-least-once + 멱등, EOS 불채택)·V1 선례는 [[07-messaging-topology]] §4.4. 따라서 "파티션 수 넉넉히 + 증설=토픽 마이그레이션"은 최후 수단이지 1차 확장 경로가 아니다.
- **consumer lag = 읽기 신선도 지표**([[03-read-model]] 최종 일관성). 백프레셔는 "읽기 지연"으로 흡수되며 command 를 막지 않는다 — CQRS 비대칭과 정합.

> 한 줄: **aggregate_id 로 애그리거트별 순서, at-least-once+멱등으로 effectively-once. 전역 순서·진짜 EOS 는 사지 않는다.**

## 장점
1. 추가 인프라 0 — 기존 Kafka·Outbox([[07.reservation]]) 그대로.
2. event_store 의 `aggregate_id`·`sequence_no` 축이 토픽·파티션·inbox 키로 일관 재사용.
3. 도메인이 요구하는 순서(애그리거트별)만 비용 지불, 불필요한 전역 순서·EOS 회피(YAGNI).
4. Zero Payload 와 결합해 멱등이 자연스럽게 성립 → inbox 부담 최소.

## 트레이드오프

### 선택한 방식의 한계
- 전역 순서 없음 — 교차 애그리거트 순서가 필요한 요구가 생기면 saga/프로세스 매니저로 풀어야 한다([[06-consistency-and-sagas]]).
- 파티션 수가 순서 계약에 묶임 — 증설이 무중단이 아니라 드레인-정지를 요구.
- 컨슈머가 멱등·inbox·드레인 책임을 짐(코드 책임 증가).
- effectively-once 는 "효과만 1회" — 부수효과(외부 알림 발송 등)가 멱등이 아니면 별도 대책 필요.

### 포기한 대안들
- **단일 파티션 전역 순서(O-B)**: 처리량 희생, 불필요한 보장.
- **컨슈머 재정렬(O-C)**: 파티션 키로 풀리는 문제를 코드로 중복 해결.
- **진짜 EOS(D-B)**: 전 구간 Kafka 트랜잭션 강제 — 과한 비용/복잡도.
- **at-most-once(D-C)**: 누락 시 영구 불일치 — 수용 불가.

## 미결정 사항 및 추가 논의
- 컨텍스트별 **파티션 수** 초기값·증설 절차(처리량 추정 의존, 운영 사이클 TBD).
- inbox 보존 기간·정리(GC) 정책, 자연 멱등으로 inbox 를 생략할 컨텍스트의 판정 기준.
- **consumer lag 임계치·알람**, 동기 프로젝션이 필요한 예외 화면([[03-read-model]]와 동일하게 화면 요구 의존).
- 비-멱등 부수효과(알림·결제 연동 등)의 effectively-once 보강 방안 — 추후 컨텍스트 추가 시.
- 도메인 이벤트 카탈로그(TBD, 이벤트 스토밍 의존) 확정 후 **토픽 목록** 확정.

## 결과 (기대)
- 한 애그리거트의 상태 변화가 프로젝션에 **순서대로, 누락 없이, 중복 흡수되어** 반영.
- read model 신선도가 consumer lag 로 관측 가능.
- 기존 메시징 자산 위에서 전달 보장 도입 비용 최소화.
