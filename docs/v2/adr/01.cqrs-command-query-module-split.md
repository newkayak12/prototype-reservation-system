# ADR: command / query 모듈 분리

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[01-module-structure]]

## 맥락

V2의 목표 중 하나는 Read/Write 모델 분리(CQRS)다([[02-domain-limitations]] #4 — 현재 읽기/쓰기가 같은 모델·DB를 공유). 단순히 포트 인터페이스만 나누는 V1 수준을 넘어, **모듈 경계로 분리를 강제**하고 싶다. 동시에 향후 "도메인(바운디드 컨텍스트)별 서비스 분할" 가능성도 열어두고자 한다.

### 요구사항
- command(쓰기)와 query(읽기)를 컴파일 단위로 격리한다.
- query가 쓰기 도메인/스키마에 의존하지 못하게 한다(읽기가 쓰기 모델을 오염시키지 않도록).
- 단일 배포(모듈러 모놀리스)로 시작하되, 나중에 분리 가능한 구조여야 한다.

## 고려된 설계 옵션들

### Option A: 공유 core + 애플리케이션/읽기 계층만 분리
- 장점: 모듈 수가 적다. 도메인 core를 한 곳에 유지.
- 단점: CQRS 축이 약하다. query가 도메인 core에 가까워 결합 유혹이 남는다.

### Option B: 풀 버티컬 — top-level `command` / `query` 모듈 분리 (선택됨)
- 장점: command↔query 격리가 가장 깔끔. "읽기 전체를 query 서비스로 분리"가 쉽다. query가 core에 의존할 경로 자체가 없다.
- 단점: top-level 축이 CQRS라, 나중에 **"도메인별 서비스 분할"이 비싸진다**(한 도메인이 두 트리에 걸침).

### Option C: 컨텍스트(도메인)-top 분리
- 장점: "도메인별 분할"이 가장 쉽다(폴더 통째로 들어냄).
- 단점: "command/query 모듈 분리"라는 의도와 축이 다르다. 대규모 재구성.

## 결정사항

**Option B — 풀 버티컬 command/query top-level Gradle 모듈 분리, 도메인은 각 모듈 내 패키지.**

- `command-module`, `query-module` 을 top-level 모듈로 둔다.
- 각 모듈 내부에서 바운디드 컨텍스트를 **패키지**로 나눈다 (`com.reservation.command.reservation` 등).
- **의존성 규칙**: `query` → `command`/도메인 core 의존 **금지**. 두 모듈의 유일한 접점은 `contract` 모듈의 이벤트.
- 모듈 경계는 Gradle로 1차 강제, 도메인 패키지 간 경계는 **ArchUnit/Konsist** 로 강제.

상세 트리·의존성 표는 [[01-module-structure]].

## 장점

1. **CQRS 강제**: 읽기/쓰기가 컴파일 단위로 격리된다.
2. **결합 차단**: query가 command 도메인을 import할 경로가 없다.
3. **물리 분리 용이**: `query-module` 을 별도 배포로 떼기 쉽다.

## 트레이드오프

### 선택한 방식의 한계
- **도메인별 분할 비용**: 나중에 한 컨텍스트를 서비스로 떼려면 command/query 양쪽에서 같은 이름 패키지를 함께 들어내야 한다.
  - 완화: 도메인을 **깨끗한 패키지**로 유지하면 수용 가능하다고 판단(이 트레이드오프를 알고 선택).
- 모듈 수 증가.

### 포기한 대안들
- **공유 core(A)**: CQRS 축이 약하고 결합 유혹이 남음.
- **컨텍스트-top(C)**: 의도(command/query 분리)와 축이 다르고 재구성 비용 큼.

## 미결정 사항 및 추가 논의
- query를 물리적으로 분리할 시점·기준 (현재는 단일 배포).
- ArchUnit vs Konsist 중 경계 강제 도구 선택.

## 결과 (기대)
- 읽기와 쓰기가 독립적으로 진화·확장 가능.
- 향후 query 서비스 분리 또는 도메인별 분할로 가는 경로 확보.
