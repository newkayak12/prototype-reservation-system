# ADR: 인증 토큰 — transport(refresh=쿠키·access=헤더) 계승, 무상태 refresh, 즉시 폐기 포기

- **상태**: Proposed (2026-06-16) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-019-auth-token-transport]] · **설계**: [[16-auth-token]]
- **연관**: [[17.authorization-model]] (클레임 원천·발급 시점 스냅샷) · [[19.caching-redis-role]] (인증 부산물 제거→단일 durability) · [[02.selective-event-sourcing-scope]] (`user`·`authenticate`=상태+Outbox)

## 맥락

V1을 열어 보면 토큰 transport는 이미 갈려 있다 — access는 응답 body, refresh는 `HttpOnly`·`Secure` 쿠키(`RefreshTokenDefinitions`, `path=/`). 클라는 access를 Authorization(Bearer) 헤더로 들고, refresh는 브라우저가 `/refresh`에 자동 전송한다. **"refresh=쿠키, access=헤더"는 V2가 새로 정하는 게 아니라 V1 계승**이다.

V1은 그 위에 하나 더 얹었다 — refresh를 Redis에도 저장(`SaveGeneralUserRefreshToken`)해 `/refresh`마다 조회·대조 후 새 토큰을 발급(rotation)했다. 즉 V1 refresh는 쿠키로 오가는 *동시에* 서버가 사본을 들고 검증하는 토큰이었다(가르는 두 개념 — **transport**: 어떻게 오가나. **server-side state**: 서버가 사본·상태를 드나). 한편 V1 `signOut`은 쿠키만 `maxAge=0`으로 지울 뿐 Redis 사본을 끊지 않았다 — 즉시 폐기를 실은 못 했다.

V2는 access를 무상태 서명 JWT로 정리했고([[RFC-015-authorization-model]]), Redis 역할을 "분산 조정·휘발성 상태"로 좁혔다([[RFC-018-caching-redis-role]]). 본 ADR은 그 위에서 refresh의 server-side state와 폐기를 정한다. (키 호스팅·회전은 인증 인프라 백로그 T-13·[[RFC-007-deployment-infra-ops]].)

## 고려된 옵션들

### refresh를 무엇으로 검증하나
- **V-1 V1식 Redis 사본 조회**: `/refresh`마다 저장분 대조. must-not-evict 서버 상태를 유지해야 해 [[RFC-018-caching-redis-role]] Redis 역할 축소를 무르게 함.
- **V-2 무상태 서명 JWT (선택)**: 검증을 서명·만료·클레임만으로. access가 무상태인 것과 같은 논리 — 서명이 위변조를, 만료가 수명을 막으면 검증 위해 사본 들 이유가 없다. 서버 사본은 검증이 아니라 *폐기*에만 정당한데 그건 별도 요구.

### transport
- **T-1 V1 그대로(SameSite 없음)**: refresh 쿠키 자동 전송이라 `/refresh`가 CSRF 표면인데 V1은 `SameSite` 미설정.
- **T-2 V1 계승 + SameSite·path 보강 (선택)**: 분담(refresh=쿠키, access=헤더)은 그대로, V1이 빠뜨린 `SameSite`(기본 Lax)·path 스코프를 채움. access=body 선택이 *오히려 CSRF 노출을 낮춤*(위조 `/refresh` 호출의 새 access는 cross-origin body라 못 읽음).

### 즉시 폐기(denylist)
- **D-1 denylist 유지**: §V-2에서 막 들어낸 must-not-evict 상태를 다시 들임 → Redis 역할 축소 무의미. V1도 못 했던 것.
- **D-2 폐기 포기, 짧은 TTL로 덮기 (선택)**: 짧은 access TTL + refresh 만료로 대부분의 "로그아웃"을 덮음. 즉시성 요구가 입증되면 그때만 denylist 부활.

## 결정사항

**V-2 + T-2 + D-2 채택: refresh를 무상태 서명 JWT로 두어 Redis 사본을 제거하고, transport는 V1을 잇되 SameSite를 보강하며, 즉시 강제 폐기는 V2 기본에서 포기한다.**

- **refresh = 무상태 서명 JWT**: 검증은 서명·만료·클레임 검사만 — 서버 사본 조회 없음. 파급으로 [[RFC-018-caching-redis-role]]의 "인증 부산물 = must-not-evict" 워크로드가 Redis에서 사라져 단일 durability 등급(`allkeys-lru`)으로 단순화된다.
- **transport = V1 계승 + SameSite 보강**: refresh=`HttpOnly`·`Secure` 쿠키, access=body→Authorization 헤더. `SameSite`(기본 Lax)·path 스코프를 채워 `/refresh` CSRF 표면을 막는다. 비대칭이 원리적 — 자동 전송이 필요한 refresh는 쿠키, CSRF 면역이 필요한 access는 헤더. access의 *클라이언트* 저장은 in-memory(localStorage는 XSS-readable이라 금지), 새로고침 시 refresh 쿠키로 재발급.
- **즉시 폐기 포기**: 근거 셋 — ① denylist는 막 들어낸 must-not-evict 상태를 재도입해 Redis 축소를 무의미하게 함, ② V1도 즉시 폐기를 못 했으니(signOut이 쿠키만 지움) 무상태로 가도 잃을 게 없음, ③ 짧은 access TTL + refresh 만료로 대부분의 로그아웃이 덮임. **rotation은 잇되 재사용 탐지(도난 감지)는 서버 상태가 필요하므로 함께 포기**.
  - **⚠ 정합화 (2026-07-06, 트리아지 C25) — 이 항목의 "재사용 탐지 포기"는 후속 설계에서 번복됨.** 본 ADR은 "재사용 탐지 = 서버 상태(Redis must-not-evict 사본) 필요"로 전제해 함께 기각했으나, [[DESIGN-017-auth-token]] §4.3이 **재사용 탐지는 denylist가 아니라 쓰기 모델 `authenticate` 행 위의 단일 `current_refresh_jti` 컬럼 하나로 충분**함을 보였다(must-not-evict Redis 워크로드 되살리지 않음). 따라서 **기각된 것은 denylist/서버 사본이지 재사용 탐지 자체가 아니다** — 재사용 탐지+강제 로그아웃은 최소 단일-jti로 **채택**된다. "즉시 강제 폐기(denylist)" 포기는 그대로 유효.
- **예외 = 요구 입증 시 denylist 부활**: "즉시 강제 로그아웃"이 도메인·규제 요구로 입증되면 그때만 [[RFC-018-caching-redis-role]] must-not-evict 등급을 되살려 denylist를 둔다(토큰 잔여 수명만큼만 사는 목록이라 TTL 자청소). 이는 [[17.authorization-model]]의 "역할=발급 시점 스냅샷" 권한 강등 즉시성 문제와 한 몸 — 토큰 수명이 짧을수록 폐기 없이도 덮인다.

> 결정의 한 줄: "transport는 V1을 잇고(refresh=쿠키, access=헤더) SameSite만 채운다. refresh를 무상태 서명 JWT로 두어 Redis 사본을 들어내고, 즉시 폐기는 포기한다 — V1도 못 했고, 짧은 수명이 그 자리를 메운다."

## 장점
1. **Redis 역할 축소 완성** — must-not-evict 워크로드 제거로 단일 durability·단일 인스턴스([[19.caching-redis-role]]).
2. **검증 비용 0(서버 상태)** — 서명·만료만으로 검증, `/refresh`마다의 저장소 조회 제거.
3. **CSRF 노출 감소** — access=body 비대칭이 위조 `/refresh`의 새 access 탈취를 구조적으로 막음.
4. **V1 대비 손실 없음** — V1도 즉시 폐기를 못 했으므로 포기로 잃는 실효 기능이 없다.
5. **transport 안정** — 검증된 V1 분담을 잇고 SameSite 빈틈만 메움.

## 트레이드오프

### 선택한 방식의 한계
- 무상태 refresh는 한 번 발급되면 만료까지 서버가 *즉시* 강제 폐기하지는 못한다(denylist 포기와 한 몸). 단 도난된 refresh가 rotation 이후 재사용되면 `current_refresh_jti` 불일치로 탐지·세션 무효화됨(재사용 탐지 채택 — 정합화 주석). 탐지 못 하는 창은 "도난 refresh가 정상 사용자보다 *먼저* 한 번 rotation하는" 경우에 한정.
- 즉시 강제 로그아웃·권한 강등 즉시 반영이 불가 — 토큰 수명을 짧게 잡아 완화하되 완전히 못 막음.
- 짧은 access TTL은 `/refresh` 빈도를 높여 그만큼 재발급 트래픽 증가.

### 포기한 대안들
- **V-1 Redis 사본 검증**: must-not-evict 재도입 — **기각**.
- **D-1 denylist 유지**: 같은 이유 — **기각**(요구 입증 시에만 부활).
- ~~**재사용 탐지 유지**: 서버 상태 필요 — **기각**.~~ → **정정 (트리아지 C25)**: 재사용 탐지는 Redis 서버 사본이 아니라 쓰기 모델 단일 `current_refresh_jti` 컬럼으로 **채택**([[DESIGN-017-auth-token]] §4.3). 기각 대상은 denylist/must-not-evict 사본에 한정. (§결정 정합화 주석 참조)

## 미결정 사항 및 추가 논의 (→ Design / 인프라 백로그)
- refresh JWT 클레임 구성·TTL·서명 키와 access TTL 구체 값 — [[17.authorization-model]] "발급 시점 스냅샷" stale 창과 한 몸.
- 쿠키 속성 확정 — `SameSite` Lax vs Strict(외부 링크 진입), path 스코프(`/` vs `/…/refresh`), 도메인.
- rotation 정책 — 만료 연장 방식, 같은 기기 병렬 `/refresh` 경합의 오탐 처리(grace window·체이닝). (재사용 탐지는 채택 확정 — 위 정합화 주석; 다기기 동시 세션은 단일 세션 스코프로 제외 — [[DESIGN-017-auth-token]] §4.3.)
- 즉시 폐기 입증 시 denylist 부활 트리거 — [[RFC-018-caching-redis-role]] must-not-evict 등급과.
- 서명 키 호스팅·회전(키 롤오버, OIDC/Vault) — 인증 인프라 백로그 T-13·[[RFC-007-deployment-infra-ops]].
- V1 `General`/`Seller` 분리 sign-in/refresh/signout 컨트롤러의 V2 통합 여부.

## 결과 (기대)
- 인증 토큰이 무상태로 정리돼 [[RFC-018-caching-redis-role]]의 Redis 단일 durability 가정이 성립하고, [[17.authorization-model]]의 클레임 전파가 무상태 토대 위에 선다.
- RFC-020이 본 ADR로 닫힘 — RFC→design_doc([[16-auth-token]])→ADR 체인 완결.
