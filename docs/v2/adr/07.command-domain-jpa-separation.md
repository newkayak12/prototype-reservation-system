# ADR: command 측 DDD 엔티티 / JPA 엔티티 분리 유지

- **상태**: 합의됨 (2026-06-13) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[02-write-model]] · [[05-aggregate-design]]
- **계승**: [[01.ddd]] (v1 — 도메인/JPA 엔티티 분리)

## 맥락

V2 command 측 도메인 모델링에서, V1의 결정([[01.ddd]] — 순수 도메인 엔티티와 JPA 엔티티 완전 분리)을 **유지할지** 정해야 한다. command 는 hexagonal로 가기로 했고([[03.command-hexagonal-query-layered]]), 애그리거트는 리치하게 재설계된다([[05-aggregate-design]]). 한편 영속화 방식이 컨텍스트별로 다르다([[02-write-model]]).

### 쟁점
- 애그리거트를 `@Entity` 로 만들어 매핑을 없앨까(통합), 아니면 순수 도메인 + 별도 JPA 엔티티로 둘까(분리)?
- 통합 시 도메인이 JPA 제약(무인자 생성자·가변·open)에 **오염**된다 — `core` 순수성 상실.

## 고려된 옵션들

### Option A: 분리 유지 (선택됨)
순수 도메인 애그리거트 + 별도 JPA 엔티티 + 매핑. (V1 방식)
- 장점: 도메인 순수성·테스트성. `command = hexagonal` 과 일관(도메인은 JPA를 모름, JPA는 `adapter/out`). ES·비-ES 전체가 "순수 애그리거트" 한 가지 멘탈 모델.
- 단점: 매핑 비용([[01.ddd]]이 겪은 Mutator/`toEntity` 고통).

### Option B: 통합 (애그리거트 = @Entity)
- 장점: 매핑 0.
- 단점: **JPA가 도메인을 오염** — V1이 분리로 피하려던 바로 그 문제. hexagonal 결정과 모순.

### Option C: 하이브리드 (불변식 풍부=분리, trivial CRUD=통합)
- 장점: 빈약한 곳에 격식 절약.
- 단점: 멘탈 모델 이원화. 일관성↓.

## 결정사항

**Option A — DDD 엔티티 / JPA 엔티티 분리 유지. 도메인은 JPA를 갖지 않는다.**

- **ES 컨텍스트** (`reservation`·`timetable`·`restaurant`): 애그리거트는 순수 도메인. 영속화는 `event_store`·`snapshot` 테이블(JPA)로 — **JPA는 인프라 레코드이지 애그리거트의 필드 거울이 아니다**(스냅샷은 직렬화 저장). 따라서 v1식 1:1 매핑 자체가 없다.
- **비-ES 컨텍스트** (`schedule`·`user`·`menu` 등): 순수 도메인 애그리거트(`domain`) + 별도 JPA 엔티티(`adapter/out`) + 매핑. **V1 방식 그대로 유지.**
- **배치**: 순수 도메인은 `command-module/<ctx>/domain`, JPA 엔티티·매핑은 `command-module/<ctx>/adapter/out` ([[01-module-structure]]). 도메인 패키지는 JPA에 의존하지 않음(ArchUnit/Konsist로 강제).

> 결정의 한 줄: "core(도메인)가 JPA를 갖게 되는 통합은 받지 않는다 → 분리 현행 유지."

## 장점
1. 도메인 순수성 유지 — V1이 달성한 "도메인 외부 의존성 0" 계승.
2. `command = hexagonal` 결정과 일관.
3. ES·비-ES가 동일하게 순수 애그리거트 — 멘탈 모델 통일.
4. JPA 교체·테스트가 도메인에 영향 없음.

## 트레이드오프

### 선택한 방식의 한계
- 매핑 비용(도메인 ↔ JPA 엔티티). V1이 Mutator 패턴·`toEntity` 복잡성으로 겪음([[01.ddd]] 실제 결과).
- 완화: 애그리거트가 리치해지고([[05-aggregate-design]]) ES 컨텍스트는 매핑이 사라지므로(이벤트/스냅샷), 매핑 부담이 비-ES로 한정·축소된다.
- 매핑은 컨텍스트별로 손으로 쓴 매핑 함수가 잇고, 경계 안쪽(`adapter/out`)에 명시적으로 남긴다 — 코드 생성 도구(MapStruct류)·공통 매퍼 추상은 비채택. 보일러플레이트는 분리의 정당한 대가이지 제거할 결함이 아니며, 명시적·예측 가능한 수동 매핑이 경계 엄격함을 지키는 값이다([[RFC-010-module-structure-migration]]).

### 포기한 대안들
- **통합(B)**: 도메인 JPA 오염, hexagonal 모순.
- **하이브리드(C)**: 멘탈 모델 이원화.

## 미결정 사항 및 추가 논의
- 도메인↔JPA 매핑 방식은 **확정**: V1식 엄격한 hexagonal 수동 매핑을 그대로 유지한다([[RFC-010-module-structure-migration]]). 코드 생성 도구·공통 매퍼 추상은 비채택. 컨텍스트가 크게 늘어 동일 패턴 반복이 과해지면, 답은 공통 추상이 아니라 경계를 흐리지 않는 국소 컨벤션(같은 자리·같은 시그니처)이며, 실제 반복량은 한두 컨텍스트 전환 후 본다.
- 순수 도메인을 `command-module` 내 `domain` 패키지로 둘지(현재 [[01-module-structure]]), 아니면 V1처럼 **물리적으로 별도 `core-module`** 로 유지할지 — 분리 원칙은 동일하므로 구조 세부는 모듈 설계에서 확정.

## 결과 (기대)
- 도메인 계층이 JPA 없이 순수하게 유지되어 ES 전환·테스트가 용이.
- 비-ES는 매핑 비용을 지되, 분리의 이점(순수성)을 유지.
