# ADR: 캐싱·Redis의 V2 역할 — 읽기 캐시 아님, 분산 조정·휘발성 상태 전용(단일 durability)

- **상태**: Proposed (2026-06-16) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-018-caching-redis-role]] · **설계**: [[03-read-model]]
- **연관**: [[04.read-model-projection-and-replica]] (프로젝션=머티리얼라이즈드 뷰) · [[20.auth-token-transport]] (인증 부산물 제거) · [[16.optimistic-concurrency-control]] (도메인 동시성 = 애그리거트 비관 락 = Redisson, 2026-06-17 개정) · [[13.db-hosting-and-read-write-topology]] (읽기 확장=레플리카)

## 맥락

V1에서 Redis(+Redisson)는 한 역할이 아니었다 — 분산 락·세마포어, 레이트리미터, 리프레시 토큰 저장, 피처 플래그, 재시도 컨텍스트 캐시, `RedisCacheManager`. "캐시"라기보다 *동기 모놀리식이 못 들던 휘발성·분산 상태를 한 군데 모은 사이드 저장소*였다(참고: "Redis 세션"은 V1에 실제로는 없다 — `HttpSession` 미사용, 인증 상태는 리프레시 토큰뿐).

V2가 이 그림을 둘에서 흔든다. 읽기가 별도 프로젝션 조회로 갈렸고([[03-read-model]]) — 프로젝션 자체가 이미 비정규화된 머티리얼라이즈드 뷰(영속 캐시)다. 인증이 무상태 JWT로 정리됐다([[RFC-015-authorization-model]]·[[RFC-019-auth-token-transport]]). 본 ADR은 V2에서 Redis의 *아키텍처 역할*을 정한다. (호스팅·토폴로지는 배포 사이클 [[RFC-007-deployment-infra-ops]].)

## 고려된 옵션들

### 프로젝션 위에 캐시를 얹나
- **C-1 read model 앞에 Redis 캐시 층**: 프로젝션이 이미 캐시인데 *캐시 위의 캐시* — 같은 일을 두 번. 최종 일관 세계에서 staleness가 두 겹(이벤트→프로젝션 + 프로젝션→캐시 TTL).
- **C-2 캐시 안 얹음, 핫 쿼리는 전용 프로젝션 / 읽기 확장은 레플리카 (선택)**: read model은 용도마다 여럿 둘 수 있으니 핫 쿼리엔 전용 프로젝션 추가가 정공법. 캐시는 측정으로 드러난 특정 패턴에만.

### 세션·토큰 상태를 Redis에 두나
- (이 갈래는 [[RFC-018-caching-redis-role]]가 열어 뒀으나 [[RFC-019-auth-token-transport]]가 닫았다 — refresh를 무상태 서명 JWT로 두고 Redis 사본 제거, 즉시 폐기 포기. 따라서 **인증 부산물은 V2 기본에서 Redis에 남지 않는다**.)

### 남는 Redis 워크로드의 durability
- **D-1 기능별 인스턴스 분리(must-not-evict vs evict 가능)**: 인증 부산물(must-not-evict)과 조정 상태(evict 가능)가 `maxmemory-policy` 하나로 양립 못 해 인스턴스를 갈라야 했음.
- **D-2 발산 워크로드 제거로 단일 등급 (선택)**: [[RFC-019-auth-token-transport]]가 must-not-evict(인증 부산물)를 Redis 밖으로 들어냈으므로 남는 건 손실 허용 조정 상태뿐 — 단일 durability, 단일 인스턴스.

## 결정사항

**C-2 + D-2 채택: V2에서 Redis는 읽기 캐시가 아니라 "분산 조정·휘발성·짧은 TTL 상태" 전용이다. 프로젝션 위에 캐시를 얹지 않고, 인증 부산물이 빠져 단일 durability 등급(`allkeys-lru`)으로 단순화한다.**

- **프로젝션 위 캐시 안 얹음**: 핫 쿼리의 1차 대응은 Redis 한 겹이 아니라 **그 화면 전용 프로젝션 추가**(이미 가진 메커니즘 재사용). 읽기 확장은 query 인스턴스 **HA 레플리카**로([[13.db-hosting-and-read-write-topology]]). 캐시를 정말 둘 패턴은 읽기 분포 *측정 후* 그 패턴에 한해, 전역 캐시 정책을 먼저 세우지 않는다.
- **2차 staleness 회피**: TTL 캐시는 이벤트→프로젝션 지연 위에 프로젝션→캐시 TTL을 더해 staleness를 두 겹으로 쌓고 디버깅을 흐린다 — 기본적으로 사들이지 않는다.
- **Redis = 분산 조정·휘발성 상태 전용**: 정당한 자리는 셋 — ① 요청-단 멱등 디듀프(짧은 윈도, [[12-api-contract]] 잔여 케이스), ② 레이트리밋 카운터(V1 계승, 다중 인스턴스 공유), ③ **분산 락(Redisson) — V2 도메인 동시성의 1차 직렬화 수단**([[16.optimistic-concurrency-control]] 2026-06-17 비관 락 개정). 단 이 락은 *liveness*(경합 완화)지 *safety*가 아니다 — 정확성은 `(aggregate_id, sequence_no)` UNIQUE가 백스톱으로 보장하고, 본 ADR의 단일 인스턴스·`allkeys-lru`(락 키 evict 가능)·페일오버가 정확성을 위협하지 않는 건 그 때문이다. Redis 불가 시 DB 비관 락으로 폴백([[16.optimistic-concurrency-control]]). 공통점: 읽기 가속이 아니라 "인스턴스 간 공유해야 하는, 본질적으로 휘발성이고 TTL이 자연스러운 조정 상태".
- **단일 durability 등급**: 인증 부산물([[20.auth-token-transport]])이 빠져 must-not-evict 워크로드가 사라졌으므로 남는 건 손실 허용 조정 상태뿐 → `allkeys-lru`(또는 `volatile-lru`) 하나, 인스턴스 하나면 충분. "Redis가 다재다능해 쪼개야 하나"는 *쪼개기가 아니라 워크로드 축소로* 닫힌다.

> 결정의 한 줄: "프로젝션이 이미 캐시다 — 그 위에 또 얹지 않는다. V2 Redis는 읽기 캐시가 아니라 *분산 조정·휘발성 상태* 전용이고, 인증 부산물이 빠져 단일 durability로 단순해진다."

## 장점
1. **중복 제거** — 프로젝션이 곧 읽기 캐시라 2차 캐시 층의 무효화 부담을 안 진다.
2. **staleness 단일화** — 일관성 지연이 한 단계(프로젝션)로 유지돼 디버깅이 명료.
3. **Redis 역할 명확** — 캐시/세션이 아니라 조정 상태라는 한 줄로 V1 잡동사니가 정리.
4. **토폴로지 단순화** — must-not-evict 제거로 단일 정책·단일 인스턴스.
5. **동시성 일원화** — 도메인 동시성은 애그리거트 단위 비관 락(Redisson 1차/DB 폴백)이 직렬화하고, 정확성은 UNIQUE 백스톱이 보장([[16.optimistic-concurrency-control]]). Redis는 그 락의 1차 제공자.

## 트레이드오프

### 선택한 방식의 한계
- 프로젝션으로도 비싼 진짜 핫 패턴(초당 수천 회 같은 키, 매번 무거운 집계)이 있으면 "프로젝션 재설계 vs 캐시 한 겹"의 손익분기가 측정 후에야 갈린다 — 그때까지 캐시 없음.
- 핫 쿼리마다 전용 프로젝션을 늘리면 프로젝터·저장 비용이 증가(캐시 한 겹 대비).
- 즉시 폐기 요구가 입증되면 must-not-evict 등급이 되살아나 단일 durability·단일 인스턴스 가정이 깨진다(그땐 [[RFC-007-deployment-infra-ops]]와 등급별 분리 재검토).

### 포기한 대안들
- **C-1 프로젝션 위 캐시 기본 적용**: 캐시 위의 캐시·2차 staleness — **기각**(측정된 특정 패턴만 예외).
- **D-1 기능별 인스턴스 분리**: [[RFC-019-auth-token-transport]]가 발산 워크로드를 제거해 불필요 — **기각**(denylist 부활 시에만 재검토).
- **논리 DB(`SELECT 0~15`)·키 프리픽스로 격리**: 메모리·단일 스레드 코어 공유라 eviction·blast-radius 격리 못 함 — 진짜 격리는 별도 인스턴스.

## 미결정 사항 및 추가 논의 (→ Design / 배포 사이클)
- 캐시를 둘 "프로젝션이 싸게 못 푸는 패턴" 식별 — 읽기 분포 측정 트리거·손익분기 임계([[RFC-002-read-model-consistency]] 측정 정책과 연동).
- 캐시를 둘 경우 그 한 패턴의 무효화 전략(이벤트 기반 vs TTL)·허용 staleness — 화면별.
- 요청-단 멱등 디듀프의 Redis 키 구성·윈도 길이 — [[12-api-contract]] 잔여 케이스 확정과.
- V1 Redis 잔재(피처 플래그·재시도 컨텍스트·Redisson 락 사용 면적)의 V2 항목별 귀속표.
- `maxmemory-policy` 확정(`allkeys-lru`/`volatile-lru` 계열) — denylist 부활 시 등급별 분리·인스턴스 분리 재검토([[RFC-007-deployment-infra-ops]]).
- Redis 호스팅(관리형 vs 자가)·토폴로지(단일/센티넬/클러스터) — 배포 사이클.

## 결과 (기대)
- Redis가 "읽기 가속 캐시"에서 "분산 조정·휘발성 상태 저장소"로 역할이 좁혀지고, 프로젝션이 읽기 최적화를 전담한다.
- RFC-019가 본 ADR로 닫힘 — RFC→design_doc([[03-read-model]])→ADR 체인 완결.
