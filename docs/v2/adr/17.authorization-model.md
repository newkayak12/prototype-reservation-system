# ADR: V2 인가 모델 — 역할=엣지, 소유권=앱(애그리거트 불변식·프로젝션 스코프 키)

- **상태**: Proposed (2026-06-16) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-015-authorization-model]] · **설계**: [[13-authorization]]
- **연관**: [[03.command-hexagonal-query-layered]] (command/query 비대칭) · [[01.cqrs-command-query-module-split]] (쓰기·읽기 분리) · [[20.auth-token-transport]] (인증 토큰 — 클레임 원천)

## 맥락

V1에서 "누가 무엇을 해도 되는가"는 한 군데에 모여 있었다. `SecurityConfig`가 경로 prefix에 역할을 박고(`hasRole`), 컨트롤러가 호출자 신원으로 자기 DB를 읽으니 "내 것만 보인다"가 자연히 걸렸다 — 인가가 데이터 접근 경로에 녹아 있었다.

V2는 이 녹아 있던 것을 둘로 찢는다. 쓰기는 ES/Outbox command, 읽기는 별도 프로젝션 조회로 갈렸고([[03.command-hexagonal-query-layered]]) 둘은 더는 같은 트랜잭션·테이블을 공유하지 않는다. "DB를 자기 신원으로 읽으니 알아서 걸리던" 층이 사라진다. 본 ADR은 그 인가가 갈 곳을 정한다. (인증 — 호출자가 누구인지 — 은 전제다: 게이트웨이·인증 서버가 토큰을 검증해 신원·역할 클레임을 확정한다 — 그 인증 경계는 [[RFC-020-authentication-boundary-gateway]]. 토큰 transport·무상태성은 [[RFC-019-auth-token-transport]].)

## 고려된 옵션들

### 역할 인가와 소유권 인가를 어디서 거나
- **A-1 둘 다 엣지**: 게이트웨이가 소유권까지 검사 → 엣지가 도메인 데이터("이 reservationId 주인이 이 userId인가")를 알아야 함 → 게이트웨이를 도메인에 결합하는 안티패턴.
- **A-2 둘 다 앱**: 역할 게이트까지 앱이 — 자원 무관 거친 거름을 엣지에서 못 해 모든 트래픽이 앱까지 들어옴.
- **A-3 역할=엣지, 소유권=앱 (선택)**: 역할은 자원을 몰라도 판단(토큰에 SELLER 있나)되니 엣지에서 거칠게(V1 경로-prefix 계승). 소유권은 자원 상태를 봐야 아니 도메인 안에서.

### 소유권 검사를 command 측 어디에 두나
- **B-1 핸들러(application)**: 도메인이 "누구나 취소 가능"한 빈약 모델로 샘 → V2가 탈피하려는 빈약 도메인 회귀.
- **B-2 애그리거트 불변식 (선택)**: "예약은 그 주인만 취소"는 상태 전이의 정당성 조건 = 도메인 규칙. 검증된 주체 신원을 핸들러가 애그리거트에 전달하면 애그리거트가 자기 상태(주인 userId)와 대조해 허용/거부.

### query 측 소유권 필터를 어디에
- **Q-1 사후 필터링**: 받아온 목록에서 남의 것 제거 → 페이징 깨지고(100건 받아 90건 버림) 한 줄 빠뜨리면 전량 유출.
- **Q-2 쿼리 조건에 주체 스코프 (선택)**: `WHERE owner_id = :subject` — "내 것만"이 쿼리의 구조적 일부라 빠뜨릴 자리가 없고 페이징도 맞는다.

## 결정사항

**A-3 + B-2 + Q-2 채택: 역할은 엣지에서, 소유권은 앱에서 — command 측은 애그리거트 불변식, query 측은 쿼리 스코프 조건. 인가에 쓰이는 신원·역할은 검증된 클레임으로만 흐르고, 클라이언트 페이로드의 자칭 신원은 믿지 않는다.**

- **역할=엣지, 소유권=앱**: 역할 게이트는 게이트웨이/엣지에서 거칠게(V1 경로-prefix 계승). 소유권은 도메인 지식이라 앱 안에서.
- **command 측 = 애그리거트 불변식**: 소유권 검사는 애그리거트의 상태 전이 정당성 조건. 핸들러가 **검증된 클레임**(게이트웨이/인증 확정)을 애그리거트에 전달하고, 애그리거트가 자기 상태와 대조해 허용/거부 → 도메인 예외 → [[12-api-contract]] 에러 분류 매핑. **신원은 토큰에서 나온 검증된 값만** 쓰고 command 페이로드의 자칭 신원은 무시하거나 일치를 강제한다.
- **query 측 = 쿼리 스코프 조건**: 조회엔 애그리거트가 없으므로 검증된 주체(ownerId/식당 식별자)를 query 측 application 레이어가 클레임에서 받아 `WHERE` 조건으로 내린다. 스코프 키도 클라 파라미터가 아니라 검증된 클레임에서(`?ownerId=남` 불가).
- **프로젝션이 스코프 키를 1급 컬럼으로**: Q-2가 성립하려면 프로젝션이 `owner_id`·`restaurant_owner_id` 같은 스코프 키를 비정규화해 들고 있어야 한다([[03-read-model]] 비정규화 원칙과 같은 결, 단 표시용이 아니라 *인가용*). 프로젝터가 인가용 키를 반드시 채우게 강제. 소유권 변경(식당 양도)은 **도메인 이벤트로 모델링**하고 그 이벤트가 스코프 키를 갱신.
- **역할은 클레임으로 전파, 소유권은 자기 컨텍스트에서**: 역할(누구냐의 속성)은 command/이벤트 메타에 실린 검증된 클레임으로 컨텍스트를 횡단([[02-write-model]] 공통 발행 경로에서 `correlationId`와 함께 봉투에 직렬화) — `user` 컨텍스트 런타임 동기 조회를 만들지 않는다. 소유권은 `reservation` 자기 이벤트/상태에 박혀 있어 컨텍스트를 건너오지 않는다. 클레임의 역할은 **토큰 발급 시점 스냅샷**으로 둔다.

> 결정의 한 줄: "역할은 자원을 모르니 엣지에서, 소유권은 도메인이니 안에서 — command는 애그리거트 불변식으로 거부하고, query는 검증된 클레임을 `WHERE`로 박는다. 프로젝션은 인가용 스코프 키를 1급 컬럼으로 든다."

## 장점
1. **빈약 도메인 회귀 방지** — 소유권이 도메인 규칙으로 애그리거트에 남는다.
2. **전량 유출 차단** — 스코프가 쿼리의 구조적 일부라 빠뜨릴 자리가 없고 페이징도 맞는다.
3. **게이트웨이-도메인 결합 회피** — 엣지는 자원을 모른 채 역할만 거른다.
4. **컨텍스트 간 동기 결합 없음** — 역할은 클레임으로 흐르고 `user` 런타임 조회가 없다.
5. **신원 위조 차단** — 검증된 클레임만 신뢰, 페이로드 자칭 신원 무시.

## 트레이드오프

### 선택한 방식의 한계
- 프로젝션이 결과적 일관성이라, 소유권이 *바뀌는* 순간(양도) 스코프 키 반영 지연 동안 인가가 옛 키로 이뤄질 수 있다(소유권 변경을 이벤트로 모델링해 좁히되, 좁은 일관성 창은 남는다).
- 클레임 역할이 토큰 발급 후 강등되면 한 토큰 수명만큼 stale할 수 있다(즉시성 요구는 토큰 정책 = 인프라 백로그 T-13·[[RFC-019-auth-token-transport]]).
- 모든 조회를 command 측 권위 상태로 재확인하면 CQRS 분리가 무의미 — "어떤 자원이 그 정도로 민감한가"의 분류가 선행해야 한다.

### 포기한 대안들
- **A-1 소유권까지 엣지**: 게이트웨이-도메인 결합 — **기각**.
- **B-1 핸들러 소유권**: 빈약 도메인 — **기각**.
- **Q-1 사후 필터**: 페이징 붕괴·유출 위험 — **기각**.

## 미결정 사항 및 추가 논의 (→ 구현 사이클)
- 역할 게이트(엣지)·소유권(앱) 이중화(defense-in-depth) 여부 — [[RFC-007-deployment-infra-ops]] 토폴로지와.
- 애그리거트 소유권 불변식 형태("주인 본인 OR 충분 권한 역할")에서 도메인이 보안 역할 어휘를 직접 알지, 핸들러가 우회 플래그로 넘길지.
- query 측 스코프 술어의 역할별 분기 방식(쿼리 빌더 분기 vs 역할별 핸들러), USER/SELLER/ADMIN 스코프 폭 정의.
- 컨텍스트별 프로젝션 스코프 키 컬럼 목록과 프로젝터 강제 규칙([[14.testing-strategy]] ArchUnit/Konsist에 얹을지).
- 소유권 변경 일관성 창에서 옛 주인이 잠깐 더 보는 위험의 자원별 허용 범위([[RFC-002-read-model-consistency]] 종속), 민감 자원의 command 측 재확인 분류.
- 🌱 V2 역할 체계 재검토 — V1 3역할(ROOT/RESTAURANT_OWNER/USER) 계승 vs 권한(permission) 집합 분해 — 도메인·제품 요구 후 별도 비준.

## 결과 (기대)
- 인가가 command(애그리거트)·query(쿼리 스코프) 양측에 명확히 자리잡고, 컨텍스트 간 동기 결합 없이 클레임으로 흐른다.
- RFC-016이 본 ADR로 닫힘 — RFC→design_doc([[13-authorization]])→ADR 체인 완결.
