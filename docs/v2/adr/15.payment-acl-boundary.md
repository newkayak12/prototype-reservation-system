# ADR: 결제 연동 경계 — payment = ACL(상태+Outbox), 실 PG는 별도 사이클로 연기

- **상태**: Proposed (2026-06-16) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-016-payment-integration-boundary]] · **설계**: [[14-payment-integration]] · [[06-consistency-and-sagas]]
- **연관**: [[08.saga-orchestration-vs-choreography]] (사가가 결제 단계를 소비) · [[09.event-ordering-and-delivery-guarantee]] (전달 멱등·부수효과 Outbox) · [[02.selective-event-sourcing-scope]] (ES vs 상태 선택 기준)

## 맥락

[[RFC-006-saga-process-manager]]가 예약 사가에 결제 단계(`PaymentConfirmed`/`PaymentFailed`/`PaymentRefunded`)를 끼워 넣으면서 `payment`라는 컨텍스트를 새로 끌어들였다. 사가는 이 이벤트들을 *단계*로 소비할 뿐 `payment`가 *무엇인지*는 [[RFC-016-payment-integration-boundary]]가 정의한다. 본 ADR은 그 RFC를 닫으며 경계의 결정을 원자적으로 박는다.

두 사실이 이 결정을 다른 컨텍스트와 다르게 만든다.
1. **계승할 V1이 없다.** V1 코드베이스에 결제 흔적(payment·refund `.kt`·마이그레이션)이 0건 — "어떻게 옮기나"가 아니라 **그린필드 경계 설계**다.
2. **우리가 통제하지 못하는 외부 PG와 말한다.** `PaymentConfirmed`는 우리가 마음대로 내는 이벤트가 아니라 외부가 그렇다고 말해 줘야 비로소 낼 수 있는 이벤트다. PG는 트랜잭션에 못 묶이는 부수효과(HTTP 한 번이 돈을 움직임)이고, 결과를 비동기 웹훅/콜백으로 — 늦고·순서 어긋나고·중복·유실되게 — 돌려준다.

그리고 **지금 붙일 실 PG가 없다.** 따라서 본 ADR이 박는 것은 "결제를 만든다"가 아니라 **경계의 모양을 동결하고 실 PG 연동을 별도 사이클로 연기한다**는 결정이다.

## 고려된 옵션들

### `payment`를 무엇으로 짓나
- **P-1 ES 컨텍스트** (reservation·timetable과 동렬): 진실 원천이 우리가 아니라 PG 원장이라 append-only 이력은 외부 진실의 *사본*일 뿐 — 우리 결정으로 상태가 진화하는 애그리거트가 아니다. ES 비용을 정당화하기 약함.
- **P-2 단순 상태 컨텍스트** (user·schedule처럼): 데이터 모델만 보고 PG의 어휘(`transactionId`·`paid`/`cancelled`·자기 재시도 규약)를 도메인에 날것으로 흘림 → 벤더 모델이 사가로 새어 들어와 벤더 교체 시 사가가 깨짐.
- **P-3 ACL(부패방지층), 내부는 상태+Outbox (선택)**: `payment`의 본질을 *데이터 모델*이 아니라 **외부 시스템과의 번역**으로 본다. 바깥의 PG 언어를 받아 안쪽 도메인 이벤트 세 개로 번역하는 것이 유일 책임. 내부 데이터는 상태+Outbox([[02-write-model]] §B).

### 실 PG를 언제 붙이나
- **지금 실 PG 연동**: 붙일 벤더·계정·시점 없음. 불가.
- **가짜 인라인 호출로 때움**: ACL·웹훅·멱등·대사라는 *배울 가치가 있는 구조*가 통째로 증발 — V2 학습 목표 훼손.
- **PG 포트 정의 + 스텁/시뮬레이터, 실 PG는 별도 사이클 (선택)**: 경계의 모양은 실 PG 유무와 무관하게 동일. 스텁이 지연·중복·유실·순서뒤집기를 주입해 인바운드 방어를 실제로 검증.

## 결정사항

**P-3 채택: `payment`를 ACL로 짓고 내부는 상태+Outbox. 사가 표면은 3개 이벤트로 동결. 실 PG 연동은 포트+스텁으로 시작하고 실제 벤더 연동은 별도 사이클로 연기한다.**

- **경계 = ACL**: 바깥으로 PG 언어를 받고 안쪽으로 `PaymentConfirmed`/`PaymentFailed`/`PaymentRefunded`로 번역. PG가 무엇이든(토스·아임포트·스트라이프·스텁) 사가가 보는 표면은 이 셋으로 고정.
- **내부 데이터 = 상태+Outbox**: 거래 현재 상태(requested/confirmed/failed/refunded)를 테이블로 들고 같은 트랜잭션에서 도메인 이벤트를 Outbox에 적어 사가로 흘림. ES는 *컨텍스트 내부 결정*으로 미룸 — 분쟁·부분환불·재시도로 내부 상태 전이가 풍부해지면 ES를 재검토(사가 계약은 어느 쪽이든 불변).
- **인바운드 진실 = 웹훅 + verify**: 콜백은 UX 신호일 뿐. 확정은 PG 역조회(금액·상태 대조)로만 승격. 입구에 세 겹 — ① 서명 진위 검증 ② PG 거래 ID 멱등 디듀프 테이블 ③ 도착 순서 무력화(PG 측 상태/타임스탬프로 수렴).
- **아웃바운드 = 의도 먼저 기록 + 부수효과 릴레이**: `RequestPayment`를 받으면 PG를 부르지 않고 의도(state=requested + 멱등키)를 로컬 트랜잭션으로 먼저 적고, 별도 릴레이가 PG의 Idempotency-Key에 그 멱등키를 실어 호출. dual-write로 인한 **이중 청구**를 회피, at-least-once 호출을 effectively-once 청구로([[09.event-ordering-and-delivery-guarantee]]와 같은 결).
- **환불 = 새 정방향**: 롤백이 아니라 또 하나의 아웃바운드 호출. 같은 "의도→멱등키 릴레이→결과 이벤트" 경로를 쓰고 **반드시 멱등**(이중 환불 가드는 PG verify로).
- **대사(reconciliation) = 상시 안전망, 자동 보정은 단방향**: 주기적으로 PG 원장과 우리 상태 대조. 우리 상태를 PG에 맞추되 PG를 우리에 맞추려 들지 않음. 자동으로 못 푸는 어긋남은 운영 보정 큐로.
- **실 PG 연기**: PG 포트를 실제처럼 정의하고 스텁/시뮬레이터를 꽂아 시작. 실 벤더·연동 시점은 별도 사이클.

> 결정의 한 줄: "`payment`는 데이터 모델이 아니라 **외부와의 번역(ACL)**이다. 사가엔 3개 이벤트만 보이고, 청구·환불은 *의도 먼저 + 멱등키*로 이중 청구를 막는다. 실 PG는 없으니 포트+스텁으로 모양만 동결하고 연동은 미룬다."

## 장점
1. **벤더 격리** — PG가 바뀌어도 ACL 안쪽만 바뀌고 사가 계약(3 이벤트)은 불변.
2. **이중 청구 구조적 차단** — 의도 기록 + 멱등키 릴레이로 at-least-once 재시도를 무해화.
3. **외부 비신뢰 입력을 경계에서 흡수** — 서명·디듀프·verify·대사가 도메인 안으로 새는 것을 막음.
4. **학습 가치 보존** — 가짜 인라인이 아니라 진짜 경계 구조를 스텁으로 검증.
5. **사가 계약 조기 동결** — 결제 내부가 무엇이 되든 사가/PM는 안정.

## 트레이드오프

### 선택한 방식의 한계
- 릴레이가 하나 더 늘어남(부수효과 릴레이) — 운영 표면 증가([[RFC-003-messaging-delivery]]가 이미 인정한 비용).
- 모든 PG가 Idempotency-Key를 지원하진 않음 — 미지원 PG에선 호출 전 verify로 "이미 청구됐나"를 확인하는 보수 경로 필요.
- 외부 경계엔 항상 잔여 불일치가 남아 대사를 상시 돌려야 함 — 진실이 우리 상태가 아니라 PG 원장임을 전제.
- 스텁의 충실도가 곧 검증의 신뢰도 — 결함 주입이 빈약하면 인바운드 방어 검증이 헛돈다.

### 포기한 대안들
- **P-1 ES**: 진실 원천이 외부라 append-only 비용 정당화 약함 — **기각**(내부 상태 전이 폭증 시에만 재검토).
- **P-2 단순 상태**: 벤더 모델 누출 — **기각**.
- **가짜 인라인 호출**: 학습 목표 훼손 — **기각**.

## 미결정 사항 및 추가 논의 (→ 구현 사이클)
- 결제 거래 상태 모델 — 상태+Outbox 스키마, 부분환불 표현, ES 재검토 트리거.
- 인바운드 ACL 상세 — 웹훅 서명 검증 알고리즘, 디듀프 테이블 키·GC, verify 조회 정책.
- 아웃바운드 릴레이 — 결제 전용 vs 공용, 멱등키 생성·전달 규약, Idempotency-Key 미지원 시 verify-before-call.
- 보상·멱등키 공간 — 청구·환불 멱등키 공유 모델, 이중 환불 가드.
- 대사 — 주기·소스(정산 파일 vs 조회 API)·미스매치 처리(자동 보정 범위 vs 운영 큐).
- PG 스텁/시뮬레이터 — 충실도, 결함 주입(지연·중복·유실·순서뒤집기) 시나리오.
- 실 PG 벤더·연동 시점 — **별도 사이클**.

## 결과 (기대)
- 사가는 `payment` 내부를 모른 채 3개 이벤트만 소비 — 결제 구현이 사가를 흔들지 않음.
- 실 PG 없이도 ACL·웹훅·멱등·대사 구조를 스텁으로 검증 — 실 연동 시점에 경계는 그대로.
- RFC-017이 본 ADR로 닫힘 — RFC→design_doc([[14-payment-integration]])→ADR 체인 완결.
