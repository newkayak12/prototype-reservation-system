# ADR: Kafka 호스팅 — AWS MSK vs EKS 위 self-managed (Strimzi)

- **상태**: Proposed (2026-06-13, 결정 갱신 2026-06-14) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[09-deployment-runtime]]
- **계승**: [[07.reservation]] (v1 — Kafka 기반 EDA)

## 맥락

V2의 command↔query 유일 접점은 이벤트(Kafka)다([[RFC-001-v2-cqrs-and-event-sourcing]]). Outbox→Kafka→projector 경로([[02-write-model]]·[[03-read-model]])가 읽기 모델 전체의 생명선이므로 Kafka는 **1급 인프라**다. 이 Kafka를 *어디서 운영할지* 정해야 [[09-deployment-runtime]]의 데이터 면이 닫힌다.

전제: 런타임은 EKS 위에 선다([[09-deployment-runtime]]). 본 프로젝트는 **학습용 사이드 프로젝트**이며, 분산 패턴의 운영 체득이 학습 목표 중 하나다.

### 요구사항
- at-least-once 발행, 컨슈머 그룹·파티션·오프셋 관리.
- v1 EDA 패턴(Outbox·Zero Payload·PoisonMessage) 그대로 동작([[07.reservation]]).
- 운영 부담과 학습 가치의 균형.

## 고려된 옵션들

### Option A: AWS MSK (매니지드 Kafka)
- 장점: 브로커·ZooKeeper/KRaft·패치·복제·모니터링을 AWS가 운영. EKS와 같은 VPC에서 낮은 지연. 운영 표면 최소 → command/query/projector 로직에 집중.
- 단점: 비용(상시 브로커 과금). Kafka 내부(브로커 튜닝·리밸런싱·장애 복구)를 직접 만질 일이 적어 **운영 체득 기회가 줄어든다**. 매니지드 추상 뒤로 디테일이 가려짐.

### Option B: EKS 위 self-managed (Strimzi Operator)
- 장점: Kafka 클러스터를 직접 운영 → 브로커·파티션·리밸런싱·장애를 손으로 겪는다(**학습 가치 최대**, 학습 목표 a 분산패턴 직격). EKS 노드 자원 재활용으로 상시 매니지드 과금 회피 가능. 매니페스트가 Git에 남아 GitOps와 정합.
- 단점: 브로커 운영·업그레이드·스토리지(PV)·장애 복구가 **전부 내 책임**. EKS 노드 장애가 Kafka 가용성에 직결. 사이드 프로젝트의 운영 시간 대비 부담이 큼.

### Option C: 외부 SaaS (Confluent Cloud 등)
- 장점: 운영 0.
- 단점: 비용·벤더 종속. AWS 단일 클라우드 정합성↓. 학습 가치는 MSK보다도 낮음(완전 블랙박스).

## 결정사항

**결정: Option B (EKS/k3s 위 self-managed, Strimzi Operator).**

근거 — 현실 제약이 학습목표와 일치하는 드문 경우:
1. **현실 제약(결정적)**: MSK는 본 프로젝트에서 **실제 사용 불가** — 개인 사이드 프로젝트로 상시 매니지드 과금을 감당하지 않고, Kafka를 내가 직접 세워 운영한다. self-managed는 *선택*이 아니라 *전제*. localstack도 MSK를 충실히 에뮬하지 못해 로컬 패리티([[11-environments-and-testing]]) 역시 오픈소스/self-managed Kafka가 맞다.
2. **제약이 곧 학습 자산**: 그 제약이 학습목표 a(분산 패턴 *운영* 체득)와 정확히 일치한다. 브로커·파티션·리밸런싱·장애·스토리지를 손으로 겪는 것이 오히려 목표 — 비용 제약이 학습 이득으로 전환된다.
3. **GitOps·환경 정합**: Strimzi 매니페스트가 Git에 남아 배포·환경([[09-deployment-runtime]]·[[11-environments-and-testing]])과 선언적으로 정합. 로컬(k3s)~타깃(EKS)이 동일 운영 모델.

> 결정의 한 줄: "MSK를 못 쓰는 건 제약이지만, Kafka *운영*까지 손으로 배우는 게 이 프로젝트 학습 a와 정확히 맞는다 — 제약을 학습으로 전환."

## 장점
1. 브로커·파티션·리밸런싱·장애 복구를 직접 운영 → 학습목표 a 직격.
2. 상시 매니지드 과금 회피 — EKS 노드/로컬 k3s 자원 재활용.
3. Strimzi 매니페스트가 GitOps와 정합, 로컬~타깃 동일 운영 모델로 패리티 확보.
4. v1 EDA 패턴([[07.reservation]])은 호스팅과 무관하게 그대로 동작 — 코드 영향 없음.

## 트레이드오프

### 선택한 방식의 한계
- 브로커 운영·업그레이드·스토리지(PV)·장애 복구가 **전부 내 책임** — 운영 시간 소모. 단 이는 학습목표라 정당화됨(의도된 비용).
- EKS/k3s 노드 장애가 Kafka 가용성에 직결 → 복제 팩터·PodDisruptionBudget·스토리지 클래스 설계 필요(구현 사이클).
- 애플리케이션 설계 학습에서 시간을 일부 가져감 — 의식적 수용.

### 포기한 대안들
- **MSK(A)**: 실 사용 불가(상시 과금 + 운영 위임이 본 프로젝트 제약·학습목표 양쪽과 안 맞음). 비용 감당이 가능해지고 운영 부담이 과해지는 시점에만 *부분* 재고 여지.
- **SaaS(C)**: 비용·벤더 종속·최저 학습 가치.

## 미결정 사항 및 추가 논의
- Strimzi 클러스터 규격(브로커 수·복제 팩터·스토리지 클래스·리소스 한도) — 구현 사이클.
- KRaft vs ZooKeeper 모드(신규 Strimzi는 KRaft 권장) — 구현 사이클.
- 로컬(k3s)~타깃(EKS) 간 Strimzi 구성 패리티 수준([[11-environments-and-testing]]).
- 토픽 설계(컨텍스트별 토픽 vs 공유, 파티션 키=aggregate_id 여부) — 이벤트 스토밍·projector 스케일과 함께(파티션 수가 projector HPA 상한을 정함, [[09-deployment-runtime]]).
- Kafka Connect/Debezium 도입 시(폴링 relay → CDC, [[09-deployment-runtime]]) self-managed Connect 운영.

## 결과 (기대)
- 이벤트 백본을 직접 운영하며 분산 시스템 *운영*을 체득 — 학습목표 a 충족.
- 비용은 노드 자원 재활용으로 통제, 로컬~타깃 동일 운영 모델 확보.
