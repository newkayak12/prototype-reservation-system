# ADR: 사가 조율 — 코레오그래피(Choreography) 기본

- **상태**: Proposed (2026-06-13, 개정 2026-06-28) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[06-consistency-and-sagas]]
- **계승**: [[07.reservation]] (v1 — Timetable·Reservation EDA, 보상 트랜잭션 미결정 항목을 본 ADR이 이어받음)

## 맥락

V2는 애그리거트를 트랜잭션 일관성 경계로, 그 바깥을 이벤트 기반 최종 일관성으로 둔다([[06-consistency-and-sagas]]). 그러면 **여러 컨텍스트에 걸친 비즈니스 트랜잭션**(예: 예약하기 = 자리 임시 점유 `SeatHeld` → 결제 대기 `PaymentConfirmed` → 예약 확정 `ReservationConfirmed`)을 무엇으로 조율할지 정해야 한다([[RFC-006-saga-process-manager]]).

### 요구사항
- 예약하기는 멀티스텝이고 중간 실패 시 **보상**이 필요하다 — 결제 미도착 시 점유 해제(`SeatReleased`), 확정 후 깨지면 환불(`PaymentRefunded`).
- 사용자가 결제를 미루면 **만료/타임아웃**으로 사가를 닫아야 한다([[07.reservation]]이 남긴 보상 트랜잭션 숙제).
- 예약 흐름(확정·취소·노쇼)은 전부 **2~3스텝 선형 흐름**이다.
- 단순 통지(예: "식당 이름 바뀜 → 예약 read model 갱신")는 흐름이라 할 것도 없다.

## 고려된 옵션들

### Option A: 코레오그래피 기본 (선택됨)
모든 컨텍스트 횡단 흐름을 이벤트 반응의 연쇄로 구성. 각 컨텍스트가 자기 보상을 책임진다.
- 장점: 컴포넌트 추가 없음. 가장 느슨한 결합. 각 컨텍스트가 자기 도메인 불변식을 자기가 지킨다(DDD 원칙). 관리 포인트가 N(이벤트 핸들러)뿐. v1 Timetable→Reservation 흐름을 자연 계승.
- 단점: 전체 흐름의 "지금 어느 단계인가"를 한눈에 볼 수 없다. → 각 aggregate 상태를 조합해야 한다.
- 타임아웃: `timetable`이 자기 점유의 TTL을 스케줄러로 관리 — 데이터 소유자가 자기 생명주기를 책임지는 것이 DDD적으로 자연스럽다.
- 보상: 각 컨텍스트가 이벤트를 듣고 자기 aggregate 상태를 보고 자기 보상을 판단한다. "전체 흐름 위치"를 중앙에서 알 필요 없다.
- 경합(paid-after-expiry): aggregate 상태 가드로 방어 — `reservation`이 EXPIRED 상태에서 결제 이벤트를 받으면 확정 거부 + 환불 트리거.

### Option B: 프로세스 매니저(PM) 기본
결제·보상·타임아웃이 끼면 PM이 기본, 코레오그래피는 단발 통지로 한정.
- 장점: 전체 흐름의 가시성이 한 곳에 모인다.
- 단점:
  - 관리 포인트가 1+N으로 증가(PM + 각 컨텍스트 커맨드 핸들러).
  - 복잡도를 줄이지 않고 위치만 옮긴다 — 각 컨텍스트의 보상 로직은 여전히 필요하고 PM 상태 머신이 추가된다.
  - PM이 모든 참여 컨텍스트의 커맨드를 알아야 하므로 결합이 증가한다.
  - PM 전용 상태 모델·영속화·재구성(rehydrate)이 별도 인프라로 필요하다.
  - 2~3스텝 선형 흐름에서 상태 머신 인프라 비용을 정당화하기 어렵다.
  - 프로토타입 단계에서 과투자.

### Option C: 혼합 (라운드1 방향 — 기각)
라이프사이클은 PM, 단순 반응은 코레오그래피.
- 기각 근거: PM이 주장하는 두 가지 이점(타임아웃 감시, 되감기 주인)이 코레오그래피로 해결 가능함이 확인됨(아래 결정사항). "혼합"의 무게중심이 사실상 PM이었으므로 Option B와 실질적 차이 없음.

## 결정사항

**Option A — 코레오그래피 기본. 모든 예약 흐름(확정·취소·노쇼)을 이벤트 반응으로 조율한다.**

### PM 논거 격파

PM을 정당화하던 두 논거가 코레오그래피로 해결 가능함이 확인되었다.

**논거 1 "타임아웃은 이벤트의 부재"**: `timetable`이 자기 점유의 TTL을 자기가 관리하면 된다. "내 점유가 언제 죽는가"는 timetable의 불변식이지 외부 PM이 알려줘야 할 것이 아니다. V1 스케줄러 패턴 재사용.

**논거 2 "되감기는 어디까지 왔는지를 알아야"**: 각 aggregate가 자기 상태를 이미 알고 있다. `timetable`은 자기가 `SeatHeld`인지, `payment`는 자기가 `PaymentConfirmed`인지 안다. 확정이 깨지면 `reservation`이 실패 이벤트를 발행하고, 각 컨텍스트가 자기 상태를 보고 자기 보상을 판단한다. "전체 흐름 위치"를 중앙에서 알 필요 없다.

### 결정 기준 (PM이 필요해지는 조건)

현재 예약 도메인에서는 PM이 불필요하다. 미래에 다음 조건이 **모두** 해당하는 흐름이 생기면 그때 PM 도입을 재검토한다:
1. 단계가 5개 이상이고 조건부 분기가 복잡하다.
2. 여러 컨텍스트의 상태를 중앙에서 조합해야만 다음 단계를 결정할 수 있다.
3. 각 컨텍스트의 자치적 보상으로는 정합성을 보장할 수 없다.

### 적용

| 흐름 | 스텝 수 | 조율 |
|------|---------|------|
| **예약 확정** (점유 → 결제 → 확정) | 3 | **코레오그래피** — 각 컨텍스트 이벤트 반응 |
| **예약 취소** (취소 → 환불 → 좌석해제) | 3 | **코레오그래피** — `reservation` 취소 이벤트에 각 컨텍스트 반응 |
| **노쇼** (시간만료 → 판정 → 수수료) | 3 | **코레오그래피** — 스케줄러 트리거 + 이벤트 반응 |
| **식당명 변경 → read model 갱신** | 1 | **코레오그래피** (projector 구독) |
| **회원 탈퇴 → 연관 통지** | 1 | **코레오그래피** |

> 결정의 한 줄: "2~3스텝 선형 흐름에 PM 상태 머신은 과투자다. 각 컨텍스트가 자기 aggregate 상태를 보고 자기 보상을 책임지면 충분하다."

## 장점
1. 관리 포인트가 N(이벤트 핸들러)뿐 — PM(1+N)보다 경량.
2. 각 컨텍스트가 자기 불변식·보상을 자기가 지킨다 — DDD 경계 존중.
3. v1의 Timetable→Reservation 코레오그래피를 그대로 계승.
4. 타임아웃을 데이터 소유자(`timetable`)가 자치적으로 관리 — V1 스케줄러 재사용.
5. 프로토타입 단계에 맞는 복잡도.

## 트레이드오프

### 선택한 방식의 한계
- "이 예약이 지금 사가의 어느 단계인가"를 한 곳에서 질의할 수 없다 — 각 aggregate 상태를 조합해야 한다.
- 흐름이 5스텝 이상으로 복잡해지거나 조건부 분기가 늘면 PM 재검토 필요.

### 포기한 대안들
- **PM 기본(B)**: 2~3스텝 선형 흐름에 상태 머신 인프라 과투자. 복잡도를 줄이지 않고 위치만 옮김. 관리 포인트 증가.
- **혼합(C)**: 실질적으로 PM 기본과 동일. "이건 어느 쪽이지?" 판단 비용만 추가.

## 결과 (기대)
- 예약 흐름이 이벤트 반응의 연쇄로 조율된다 — PM 인프라 불필요.
- 타임아웃·보상·경합이 각 컨텍스트 자치로 해결된다.
- v1이 남긴 보상 트랜잭션 숙제가 코레오그래피 보상 이벤트로 정식화된다.
