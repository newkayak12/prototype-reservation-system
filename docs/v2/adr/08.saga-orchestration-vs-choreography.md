# ADR: 사가 조율 — 안무(Choreography) vs 오케스트레이션(Orchestration)

- **상태**: Proposed (2026-06-13) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[06-consistency-and-sagas]]
- **계승**: [[07.reservation]] (v1 — Timetable·Reservation EDA, 보상 트랜잭션 미결정 항목을 본 ADR이 이어받음)

## 맥락

V2는 애그리거트를 트랜잭션 일관성 경계로, 그 바깥을 이벤트 기반 최종 일관성으로 둔다([[06-consistency-and-sagas]]). 그러면 **여러 컨텍스트에 걸친 비즈니스 트랜잭션**(예: 예약 확정 = timetable 점유 + restaurant 가용성 + reservation 확정)을 무엇으로 조율할지 정해야 한다.

분산 사가의 조율 방식은 둘이다 — 중앙 조율자 없는 **안무**, 프로세스 매니저가 흐름을 쥐는 **오케스트레이션**. V2 전체를 한쪽으로 통일할지, 혼합할지가 쟁점이다.

### 요구사항
- 예약 확정은 멀티스텝이고 중간 실패 시 **보상**(임시 점유 해제)이 필요하다.
- 사용자가 확정을 미루면 **만료/타임아웃**으로 사가를 닫아야 한다([[07.reservation]]이 남긴 보상 트랜잭션 숙제).
- 단순 통지(예: "식당 이름 바뀜 → 예약 read model 갱신")는 흐름이라 할 것도 없다.

## 고려된 옵션들

### Option A: 전면 안무 (Choreography-only)
모든 컨텍스트 횡단 흐름을 이벤트 반응의 연쇄로만 구성. 중앙 조율자 없음.
- 장점: 컴포넌트 추가 없음. 가장 느슨한 결합. 단순 흐름엔 가장 자연스럽다. v1 Timetable→Reservation 흐름이 이미 이 모양.
- 단점: 멀티스텝·보상·타임아웃이 끼면 **흐름이 코드 어디에도 없다** — "지금 예약이 사가의 어느 단계인가"를 한눈에 못 본다. 보상 순서·타임아웃을 여러 컨슈머에 흩뿌려야 해 추적·디버깅이 어렵다(분산된 암묵 상태 머신).

### Option B: 전면 오케스트레이션 (Orchestration-only)
모든 횡단 흐름에 프로세스 매니저를 둔다.
- 장점: 모든 흐름이 명시적·중앙집중. 일관된 멘탈 모델.
- 단점: "식당 이름 변경 → read model 갱신" 같은 1-스텝 반응에까지 프로세스 매니저는 과잉. 단순 통지가 불필요하게 중앙 조율자를 거쳐 결합이 도로 생긴다.

### Option C: 혼합 — 라이프사이클은 오케스트레이션, 단순 반응은 안무 (선택됨)
조율 방식을 흐름의 성격으로 가른다.
- **멀티스텝 + 보상/타임아웃 있는 라이프사이클 → 오케스트레이션(프로세스 매니저).**
- **1~2스텝 단순 통지·동기화 → 안무(이벤트 반응).**
- 장점: 각 흐름에 맞는 비용만 지불. 예약 같은 복잡 흐름은 한 곳에서 보고, 단순 통지는 가볍게. 학습 목표상 두 패턴을 모두 다룬다(분산 패턴 학습).
- 단점: "이건 어느 쪽이지?" 판단 기준이 필요(일관성↓ 우려). → 아래 결정 기준으로 해소.

## 결정사항

**Option C — 혼합. 흐름의 성격으로 조율 방식을 가른다.**

### 결정 기준 (어느 쪽인가)
다음 중 둘 이상이면 **오케스트레이션**, 아니면 **안무**:
1. 단계가 3개 이상이다.
2. 중간 실패 시 앞 단계를 **보상**해야 한다.
3. **타임아웃/만료**로 흐름을 닫아야 한다.
4. "지금 어느 단계인가"라는 **흐름 상태**를 질의할 가치가 있다.

### 적용 (초안)
| 흐름 | 성격 | 조율 |
|------|------|------|
| **예약 확정** (timetable 점유 → restaurant 가용성 → reservation 확정 → 점유 확정/해제) | 멀티스텝·보상·만료 | **오케스트레이션** — `ReservationProcessManager` (`command.reservation`) |
| **예약 취소 → 점유 환원** | 보상 동반 | 오케스트레이션(같은 프로세스 매니저의 취소 경로) 권고 |
| **식당명 변경 → 예약/검색 read model 갱신** | 1-스텝 통지 | **안무** (projector 구독 — [[03-read-model]]) |
| **회원 탈퇴 → 연관 컨텍스트 통지** | 단순 팬아웃 | **안무** |
| **메뉴/카테고리 변경 → lookup read 갱신** | 단순 통지 | **안무** |

- 프로세스 매니저는 라이프사이클 주인 컨텍스트(`reservation`)의 `command-module` 안에 둔다. 단계 진입은 이벤트 구독, 다음 단계는 커맨드 발행, 실패는 보상 커맨드.
- 프로세스 매니저 상태는 `reservation`이 ES이므로 이벤트로 기록 가능. 상태 모델은 구현 사이클에서 확정.
- 조율 방식과 무관하게 **대외 발행 경로는 Outbox→Kafka 동일**, 보상은 append-only 이벤트, 컨슈머·보상은 멱등([[06-consistency-and-sagas]]).

> 결정의 한 줄: "흐름에 보상·타임아웃·다단계가 있으면 한 곳(프로세스 매니저)에서 본다. 단순 통지는 이벤트가 알아서 흐르게 둔다."

## 장점
1. 복잡 흐름(예약)은 명시적 상태 머신으로 추적·디버깅·보상이 한 곳에 모인다.
2. 단순 통지는 안무로 가볍게 — 불필요한 중앙 결합 없음.
3. v1의 Timetable→Reservation 안무를 보존하면서, v1이 미룬 보상/만료를 오케스트레이션으로 정식화([[07.reservation]]).
4. 두 패턴을 모두 구현 — 분산 시스템 학습 목표 충족.

## 트레이드오프

### 선택한 방식의 한계
- 흐름마다 "어느 쪽?" 판단이 필요해 균일성이 낮다 → 결정 기준 4항목으로 완화.
- 프로세스 매니저는 새 컴포넌트라 구현·테스트 비용이 있다(상태·타임아웃·보상 경로).

### 포기한 대안들
- **전면 안무(A)**: 멀티스텝·보상·타임아웃이 흐름 코드로 드러나지 않아 추적난.
- **전면 오케스트레이션(B)**: 단순 통지에 과잉, 결합 도로 증가.

## 미결정 사항 및 추가 논의 (TBD)
- 프로세스 매니저의 **상태 모델**(단계 enum vs ES 이벤트) 및 영속화 위치.
- **타임아웃 임계치·임시 점유 TTL** 구체 값 — 화면/UX 요구 의존, 구현 사이클에서.
- 사가 단계 실패의 PoisonMessage 운영 흐름 편입 방식([[07.reservation]] 계승 범위).
- 예약 외 흐름(취소·노쇼·환불 등)의 조율 분류 — 이벤트 스토밍 재실시 후 카탈로그와 함께 확정.

## 결과 (기대)
- 예약 확정 같은 횡단 트랜잭션이 명시적 사가로 추적·보상·만료 가능.
- 단순 통지는 안무로 느슨하게 유지.
- v1이 남긴 보상 트랜잭션 숙제가 V2에서 정식 메커니즘으로 닫힌다.
