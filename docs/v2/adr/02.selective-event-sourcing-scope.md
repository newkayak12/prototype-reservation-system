# ADR: 선택적 이벤트 소싱 범위

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[02-write-model]]

## 맥락

V2는 이벤트 소싱을 도입한다. 그러나 9개 바운디드 컨텍스트([[01-current-state]])는 변화 빈도·이력/감사 필요성이 제각각이다. lookup 성격(`category` 등)에 이벤트 스토어를 씌우는 것은 과잉이고, 핵심 예약 플로우는 이력·동시성이 본질이다. **어디까지 진짜 ES로 갈지**를 정해야 나머지 설계가 따라온다.

### 도메인 관계
- 핵심 도메인 = `reservation`. `restaurant`·`timetable`·`user` 에 의존, 역참조 없음.
- `timetable` 은 이미 이벤트/Outbox 보유([[07.reservation]]).

## 고려된 옵션들

### Option A1: 선택적 ES (선택됨)
핵심 예약 플로우만 진짜 ES, 나머지는 CQRS+Outbox 또는 현행.
- 장점: 위험·비용 최소. timetable 패턴 자연 확장. ES 비용을 값어치 있는 곳에만 지불.
- 단점: 컨텍스트별 쓰기 모델이 두세 갈래로 갈림(균일성↓).

### Option A2: 전면 ES
9개 전부 이벤트 스토어가 진실의 원천.
- 장점: 최대 감사성·일관성.
- 단점: lookup 컨텍스트에 과잉. 비용·복잡도 매우 높음.

### Option A3: CQRS 먼저, ES는 후속
V2는 R/W 분리 + Outbox까지만, ES는 다음으로.
- 장점: 점진·저위험.
- 단점: V2 목표(이벤트 소싱) 미달.

## 결정사항

**Option A1 — 선택적 이벤트 소싱.**

| 분류 | 컨텍스트 | 쓰기 모델 |
|------|----------|-----------|
| 진짜 ES (이벤트 스토어 + 리플레이) | `reservation` · `timetable` · `restaurant` | append-only 이벤트 스트림 |
| 상태 + Outbox (CQRS, 비-ES) | `schedule` · `user` · `authenticate` | 상태 테이블 + 통합 이벤트 |
| 현행 / lookup | `menu` · `category` · `company` | 상태 테이블 (구독 필요 시 Outbox) |

- **비-ES도 이벤트 드리븐에 참여**: 다른 컨텍스트가 변화를 구독해야 하면 Outbox로 통합 이벤트를 발행한다. ES냐 아니냐의 차이는 "상태를 이벤트로 쌓느냐 테이블로 들고 있느냐"일 뿐, **대외 발행 경로(Outbox→Kafka)는 동일**.
- 쓰기 모델 메커니즘 상세는 [[02-write-model]].

## 장점
1. 이력·감사·동시성이 본질인 핵심 플로우만 ES 비용 부담.
2. `timetable` 선행([[07.reservation]])을 템플릿으로 확장.
3. lookup 컨텍스트는 과한 전환 회피.

## 트레이드오프

### 선택한 방식의 한계
- 쓰기 모델이 세 갈래라 컨텍스트마다 패턴이 다르다(인지 비용).
- `restaurant` 의 ES 편입은 이력 요구가 크지 않으면 과할 수 있다(검토 후 ES로 결정).

### 포기한 대안들
- **전면 ES**: 과잉·고비용.
- **CQRS 먼저**: 목표 미달.

## 미결정 사항 및 추가 논의
- 경계가 모호한 `schedule`·`menu` 의 분류는 **이벤트 스토밍 재실시 후 재검토**.
- `restaurant` ES 편입의 실제 이득은 구현 사이클에서 검증.
- 컨텍스트별 도메인 이벤트 카탈로그는 TBD(이벤트 스토밍 의존).

## 결과 (기대)
- 핵심 예약 플로우의 상태 변화가 이벤트로 추적·재구성 가능.
- 전 컨텍스트가 이벤트로 느슨하게 통합.
