# ADR: 읽기 모델 — 이벤트 프로젝션 + read replica

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[03-read-model]]

## 맥락

[[01.cqrs-command-query-module-split]]에서 command/query를 top-level 모듈로 분리했다. 그 귀결로 **query는 command의 테이블을 직접 조회할 수 없다**(스키마 결합 = 안티패턴). 그렇다면 query는 무엇을 읽는가? 특히 "프로젝션을 만들지 않는 컨텍스트"의 읽기 소스를 정해야 한다.

### 원칙
- CQRS에서 command의 책임은 검증+쓰기뿐. **조회는 항상 query 측**이 처리한다.
- ES 컨텍스트의 이벤트 스트림은 append-only라 임의 조회에 쓸 수 없다.

## 고려된 옵션들

### Option A: 전부 프로젝션
모든 컨텍스트가 query 측에서 이벤트로 read model을 채운다.
- 장점: 균일·깔끔. query가 완전히 독립.
- 단점: 저빈도 lookup까지 projector를 만들어야 함(과투자).

### Option B: 프로젝션 + read replica/공유 read 스키마 (선택됨)
프로젝션이 기본이되, 미적용 저빈도분은 replica/뷰로 조회.
- 장점: 실용적. 필요한 곳만 프로젝션(YAGNI).
- 단점: replica 경유라 약한 결합·약간의 일관성 지연.

### Option C: query가 command DB 직접 조회
- 장점: 단순.
- 단점: **스키마 결합 안티패턴**. 모듈 분리의 의미 상실. → 배제.

## 결정사항

**Option B — 이벤트 프로젝션을 기본, 미프로젝션 저빈도는 read replica/공유 read 스키마.**

- **(가) 프로젝션 read model (기본)**: `query.*.projection` 이 `contract` 이벤트를 구독해 비정규화 `model` 갱신. 교차 조인·고읽기·다른 모양 조회에 사용.
  - **ES 컨텍스트는 최소 1개의 현재상태 프로젝션을 반드시 가진다** (이벤트 스트림으로 임의 조회 불가). "프로젝션 미적용"은 *추가* 프로젝션을 안 만든다는 뜻.
- **(나) read replica / 공유 read 스키마**: 프로젝션을 두지 않는 저빈도 lookup(`category`·`company` 등)은 replica/뷰로 조회. **command 테이블 직접 조회 금지**.
- 컨텍스트별 초기 전략·일관성은 [[03-read-model]].

## 장점
1. 읽기가 쓰기와 독립적으로 최적화·확장.
2. YAGNI — 프로젝션은 실제 읽기 요구가 있는 곳부터.
3. 결합 차단 — replica/이벤트 경유만, command 스키마 직접 의존 없음.

## 트레이드오프

### 선택한 방식의 한계
- 프로젝션은 **최종 일관성**(짧은 지연 허용).
- replica 경유는 약한 인프라 결합(스키마 변화 전파 고려 필요).

### 포기한 대안들
- **전부 프로젝션(A)**: 저빈도까지 과투자.
- **command DB 직접 조회(C)**: 안티패턴, 배제.

## 미결정 사항 및 추가 논의
- 프로젝션 지연 허용치, 동기 프로젝션이 필요한 예외 화면.
- replica vs 공유 read 스키마(뷰) 중 무엇을 쓸지(컨텍스트별).

## 결과 (기대)
- 조회 성능·모양을 화면 요구에 맞춰 자유롭게 최적화.
- 컨텍스트 간 결합은 이벤트로만.
