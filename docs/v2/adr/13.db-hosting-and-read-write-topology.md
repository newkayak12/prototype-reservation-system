# ADR: 읽기/쓰기 물리 분리 — command/query DB 분리 + Kafka 다리, binlog=HA (호스팅 투명)

- **상태**: Proposed (2026-06-13, 결정 갱신 2026-06-14) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[09-deployment-runtime]] · [[03-read-model]]
- **연관**: [[05.event-store-mysql-table]] (이벤트 스토어=MySQL) · [[09.event-ordering-and-delivery-guarantee]] (Kafka 다리) · [[12.kafka-hosting-msk-vs-self-managed]] (호스팅 투명성 동일 논리)

## 맥락

V2 목표 #1은 **Read/Write 모델 분리(CQRS)**다. 논리 분리는 모듈([[01-module-structure]])·읽기 전략([[03-read-model]])으로 이미 결정됐다. 본 ADR은 그 **물리 구현**을 정한다.

### 두 관찰
1. **호스팅은 앱에 투명하다.** RDS vs 자가 MySQL, ElastiCache vs 자가 Redis는 Spring 앱에 투명 — 앱은 Spring Data 클라이언트 + 연결 설정에만 의존, 교체는 배포/설정 문제([[12.kafka-hosting-msk-vs-self-managed]]와 같은 논리). 본 ADR의 무게는 *호스팅*이 아니라 **DB를 어떻게 나누고 무엇으로 잇느냐**다.
2. **앱 레벨 R/W 라우팅 코드는 불필요.** command/query를 모듈로 쪼갠 순간 "어느 DB로 보낼까"의 런타임 분기점이 사라진다 — 각 모듈은 *자기 DB 하나*에 정적 바인딩될 뿐이다.

### 제약
- 이벤트 스토어·상태·Outbox는 한 트랜잭션 → command 측 *한 인스턴스*([[05.event-store-mysql-table]]).
- query는 command의 도메인/스키마를 몰라야 한다([[03-read-model]]).

## 고려된 옵션들

### R/W 물리 토폴로지
- **T-1 단일 인스턴스(논리 분리만)**: 읽기 부하가 쓰기를 압박 — 목표 #1 물리 분리 미달.
- **T-2 단일 primary + read replica(query가 primary의 binlog 미러를 읽음)**: R/W를 인스턴스로 나누나, **replica가 command 테이블까지 미러**해 query가 물리적으로 command 스키마를 보게 된다(경계가 디스플린에만 의존). command→query를 binlog로 잇는 셈이라 query가 쓰기 스키마에 결합.
- **T-3 command DB / query DB 완전 분리, 다리는 Kafka/projector (선택)**: 쓰기 모델 DB와 읽기 모델 DB가 별개. projector가 Kafka 이벤트를 받아 query DB에 프로젝션을 쓴다. 각 DB는 binlog로 **이중화(HA)**.

### 복제(binlog)의 용도
- **HA(이중화) — 각 DB의 primary→standby (선택)**: 장애 시 페일오버. binlog는 *같은 모델 DB의 중복화*에만 쓴다.
- ~~command→query 다리~~: binlog를 모델 간 다리로 쓰면 query가 쓰기 스키마에 결합 → 기각(T-2의 문제).

## 결정사항

**T-3 채택: command DB와 query DB를 물리 분리하고, 다리는 Kafka/projector(이벤트). 각 MySQL은 binlog로 이중화(HA). 앱은 모듈별 단일 datasource 정적 바인딩(라우팅 코드 없음). 호스팅은 투명.**

- **command MySQL** (쓰기 모델): event_store·상태·Outbox(한 트랜잭션, [[05.event-store-mysql-table]]). command-module이 애그리거트 재구성 읽기도 여기서(강한 일관성). → command-module datasource = command DB.
- **query MySQL** (읽기 모델): projector가 Kafka 이벤트를 소비해 프로젝션 read model을 여기에 쓰고, query-module이 읽는다. inbox(멱등)·프로젝션이 한 트랜잭션([[09.event-ordering-and-delivery-guarantee]]). → query-module datasource = query DB.
- **다리 = Kafka/projector**: command→query 데이터 흐름은 *이벤트*로만. binlog가 아니다.
- **binlog = HA 전용**: command DB(primary+standby), query DB(primary+standby) 각각 이중화. 페일오버·읽기 오프로드용.
- **Kafka는 클러스터 하나**를 공유 — command가 produce, query projector가 consume(별도 클러스터 아님).
- **라우팅 없음**: 각 모듈이 자기 DB datasource에 정적 바인딩. `RoutingDataSource`·`@Transactional(readOnly)` 분기 불필요.

> 결정의 한 줄: "쓰기 DB와 읽기 DB를 물리로 나누고 **Kafka로 잇는다**. binlog는 다리가 아니라 *각 DB의 이중화*다. 모듈 분리라 앱엔 라우팅이 없다."

### 호스팅 — 투명(ops/비용 결정, 앱 무관)
- **MySQL**(command·query 양쪽): RDS(매니지드) vs 자가(EKS/k3s). 앱 무관·환경별 교체가능. 상태 저장소라 자가는 Kafka 자가([[12.kafka-hosting-msk-vs-self-managed]])보다 보수적으로 본다.
- **Redis**: ElastiCache vs 자가 — 투명. 단 Redis도 **읽기/쓰기 엔드포인트가 갈린다**: read=replica(Lettuce `READ_FROM`), write=master(+failover Sentinel/Cluster, v1 계승). 호스팅 무관한 클라이언트 토폴로지 와이어링.

## 장점
1. **목표 #1을 가장 순수하게** — 읽기/쓰기가 별 DB로 물리 분리, 독립 스케일·독립 장애.
2. **경계가 물리적으로 성립** — query DB엔 프로젝션만 있어 "query가 command 테이블을 못 본다"가 디스플린이 아니라 물리(이전 T-2 우려 해소).
3. 앱 코드에 라우팅 로직 0 — 모듈 경계가 R/W를 가른다.
4. event_store·Outbox 트랜잭션 원자성 보존([[05.event-store-mysql-table]]).
5. binlog가 본래 용도(HA)로 쓰여 각 DB 페일오버 확보.
6. 호스팅 투명 — 로컬(자가)~타깃(RDS) 코드 동일, 설정만 교체([[11-environments-and-testing]]).

## 트레이드오프

### 선택한 방식의 한계
- DB 인스턴스가 늘어난다(command primary/standby + query primary/standby) → 비용·운영 표면 증가. 로컬·소규모는 standby 생략·단일 인스턴스로 축소([[11-environments-and-testing]]).
- query DB는 **이벤트로만 채워진다** → 프로젝션 지연(최종 일관성, [[03-read-model]]). 신선도 필요한 조회는 예외 설계 필요(요구 증명 시).
- 모든 query 조회 대상이 query DB에 프로젝션으로 존재해야 함 — 저빈도 lookup도 경량 프로젝션이 필요(아래 미결정).
- Redis write master 단일 + failover 설계.

### 포기한 대안들
- **T-1 단일 인스턴스**: 물리 분리 미달.
- **T-2 primary+replica(binlog 다리)**: query가 쓰기 스키마에 물리 결합, 경계가 디스플린 의존 — CQRS 정신 약화. **기각.**
- **앱 RoutingDataSource**: 모듈 분리로 불필요.

## 미결정 사항 및 추가 논의
- 저빈도 lookup(`category`·`company`·`menu`)을 query DB에 어떻게 둘지 — 경량 프로젝션 vs lookup 컨텍스트의 published 테이블([[03-read-model]] (나) 정렬 필요).
- 신선도 필요한 조회의 예외(동기 프로젝션/command DB 직접 읽기 허용 여부) — 요구 증명 시.
- standby 개수·복제 지연 허용치·페일오버 자동화.
- Redis failover 토폴로지(Sentinel vs Cluster) — 구현 사이클.
- 호스팅(RDS vs 자가)은 환경·비용 결정으로 배포 사이클 위임 — 앱 무관.
- [[04.read-model-projection-and-replica]]의 "replica" 표현이 본 결정(query DB)과 정렬되도록 후속 점검.

## 결과 (기대)
- 쓰기·읽기가 별 DB로 물리 분리되고 **Kafka가 잇는다** — 정통 CQRS 형태.
- 앱은 모듈별 datasource 설정만(라우팅 코드 0), 경계는 물리로 강제.
- binlog 이중화로 각 DB 페일오버, 호스팅 교체엔 영향 없음.
