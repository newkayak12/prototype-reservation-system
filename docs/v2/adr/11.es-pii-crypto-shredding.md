# ADR: 이벤트 스토어 PII 대응 — 크립토 셰딩(crypto-shredding)

- **상태**: Proposed (2026-06-13) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[02-write-model]] · [[08-event-store-lifecycle]]
- **근거 ADR**: [[05.event-store-mysql-table]]

## 맥락

[[05.event-store-mysql-table]]에서 ES 컨텍스트(`reservation`·`timetable`·`restaurant`)의 진실의 원천을 **append-only 이벤트 스토어**로 정했다. append-only는 ES의 핵심 가치(완전한 이력·재구성·감사)지만, 개인정보(PII) 앞에서 정면으로 충돌한다.

### 충돌

- 이벤트에 PII가 섞일 수 있다 — 예약자 이름·연락처, 사용자 식별 정보 등이 이벤트 페이로드에 박힌다.
- GDPR "잊힐 권리"(Art.17)·국내 개인정보보호법은 **삭제 요청 시 파기**를 요구한다.
- 그런데 이벤트 스토어는 **수정·삭제하지 않는 것이 불변식**이다(낙관적 동시성·리플레이·감사가 여기 의존). 행을 지우면 ES가 깨지고, 안 지우면 법을 어긴다.

> 이건 [[08-event-store-lifecycle]]가 정리한 "append-only의 대가" 중 하나다. 보존·스냅샷과 달리, 이건 **법적 의무**라 회피할 수 없다.

### 전제

- V1은 민감정보 암호화 저장을 이미 한다(CLAUDE.md — encrypted sensitive data). 다만 셰딩 키는 V1 `encryption_key` 자산을 재활용하지 않고 **전용 키 테이블을 새 스키마로 따로 판다**([[RFC-005-pii-security]]) — 이벤트 데이터와 갈라 백업·복원 한 번에 셰딩이 무효화되지 않게.
- 학습 프로젝트지만, ES + 개인정보의 정석 패턴을 익히는 것이 본 ADR의 학습 목표(분산 패턴).

## 고려된 옵션들

### Option A: 이벤트 행 물리 삭제 / 수정
- 장점: 직관적, 진짜로 사라진다.
- 단점: **append-only 불변식 파괴.** `(aggregate_id, sequence_no)` 연속성·리플레이·감사 무너짐. [[05.event-store-mysql-table]] 결정과 정면 모순. **기각.**

### Option B: PII를 이벤트에 아예 안 넣기 (참조만)
- 이벤트엔 식별자만, PII는 외부 가변 저장소(삭제 가능)에 두고 참조.
- 장점: 이벤트 스토어가 PII-free → 삭제 문제 자체가 소멸. [[02-write-model]]의 **Zero Payload** 원칙([[07.reservation]] 계승)과 결이 같다.
- 단점: 모든 PII를 100% 분리하기 어렵다(맥락상 페이로드에 들어오는 값 존재). as-of 재구성 시 "그때의 PII"는 복원 불가(현재값만). 단독으로는 불충분.

### Option C: 크립토 셰딩 (선택 권고)
- PII를 **데이터 주체별 키**로 암호화해 이벤트에 저장. 삭제 요청 시 **이벤트가 아니라 그 주체의 키를 폐기**한다 → 암호문은 남지만 **복호 불가능**해져 사실상 파기.
- 장점: append-only 불변식 보존. 이벤트 행·시퀀스·리플레이 구조 그대로. 키 1개 삭제로 GDPR 대응.
- 단점: 키 관리 인프라(주체별 키 생성·보관·폐기) 필요. 키 폐기 후 그 주체 PII가 든 이벤트는 **온전히 리플레이 불가**(비-PII 필드만 복원).

## 결정사항

**Option C(크립토 셰딩)를 주 전략으로, Option B(PII 최소화)를 보완으로 채택한다.**

### 메커니즘

셰딩 키는 **데이터 주체당 하나**다 — 한 사람 = 키 하나여서 삭제 요청 단위와 셰딩 단위가 정확히 일치한다([[RFC-005-pii-security]]). 키는 V1 자산 재활용이 아니라 **전용 키 테이블을 새 스키마로 따로 파서** 둔다.

```
-- 이벤트 데이터와 분리된 별도 스키마
key_store.subject_key(
  subject_id,            -- 데이터 주체 (예: userId), 주체당 1행
  key_id,
  key_material,          -- 주체 생성 시 동적 생성된 키
  status,                -- ACTIVE | SHREDDED
  created_at, shredded_at
)

event_store.payload(JSON) = {
  ...비-PII 필드(평문)...,
  "_encrypted": { "key_id": "...", "subject_id": "...", "cipher": "..." }  -- PII만 암호화 봉투
}
```

**키 저장소 요건 넷**([[RFC-005-pii-security]]) — (a) 주체 생성 시 키 **동적 생성**(미래 주체를 미리 알 수 없으니 사전 등록이 아니라 런타임 생성, INSERT), (b) 재생·조회 시 **조회**(SELECT), (c) 삭제 요청 시 **즉시 하드 삭제**(DELETE — KMS CMK식 7~30일 예약 삭제 지연 없음), (d) **이벤트 데이터와 분리된 스키마**(백업·복원 한 번에 셰딩이 무효화되지 않게). 키 라이프사이클(생성·조회·삭제)은 **한 포트 뒤에 캡슐화**해 매체를 갈아끼울 수 있게 둔다 — 셰딩의 신뢰성은 매체가 무엇이냐보다 *키를 정말 지웠는가*에 달렸기 때문이다. 키 자체를 상위 마스터 키로 감싸는 **봉투 암호화는 격리·규제 요구가 실재할 때 도입하는 졸업 경로**로 남긴다.

- **쓰기**: PII 필드는 주체 키로 암호화한 **봉투**로 페이로드에 넣는다. 비-PII(예약 시각·상태·식당 식별자)는 평문 — 리플레이·정합성에 필요.
- **읽기/리플레이**: `apply` 시 키가 `ACTIVE`면 복호해 PII 채움. `SHREDDED`(키 행이 삭제돼 조회 불가)면 **PII 자리는 익명 토큰**으로 두고 나머지 상태는 정상 복원.
- **삭제 요청**: 해당 `subject_id` 키를 **즉시 하드 삭제**(키 머티리얼 폐기). 이벤트는 **건드리지 않는다** → append-only 유지.
- **B 보완**: 처음부터 페이로드 PII를 최소화(Zero Payload 정신). 식별자로 충분하면 PII를 아예 안 싣는다 — 암호화할 표면을 줄인다.

### 암호화된 PII 검색

암호문은 동등·부분·범위 검색이 막힌다. 그래서 **기본적으로 PII를 쿼리 키로 쓰지 않는다**([[RFC-005-pii-security]]) — read model은 불투명 식별자(`userId`·`reservationId`)로 조회하고, PII는 그 위에 *표시용* 암호문으로 따라붙는다(복호는 표시 시점에만). 진짜 PII *동등* 검색이 필요한 좁은 경우(관리자 조회·로그인 식별)에는 **blind index**(PII의 keyed-HMAC를 암호문 옆에 저장)를 쓰되, 이 인덱스는 반드시 **주체별 셰딩 키에서 파생**해야 한다 — 전역 키로 만들면 키를 지워도 인덱스가 남아 "그 사람이 있었다"를 확인시켜주는 *셰딩 누수*가 된다. 주체 키 파생이면 키 삭제가 인덱스도 함께 무효화한다. 부분·범위 검색을 PII에 요구하는 요구사항은 암호화를 푸는 신호가 아니라 **요구사항을 재검토할 신호**다.

### 경계

- 스냅샷([[08-event-store-lifecycle]] §1)도 PII를 담을 수 있으므로 **동일하게 암호화 봉투** 적용. 키 폐기 시 스냅샷 PII도 복호 불능.
- 비-ES 컨텍스트(`user`·`authenticate` 등)는 상태 테이블을 직접 수정·삭제할 수 있으므로 셰딩이 필수는 아니다. 단, 그들이 **Outbox로 발행한 이벤트가 ES 컨텍스트/콜드 로그에 남는다면** 같은 봉투 규약을 적용한다.
- "어떤 필드가 PII인가"의 분류는 도메인 작업 — **TBD**.

## 장점
1. append-only 불변식([[05.event-store-mysql-table]])을 깨지 않고 GDPR/개인정보법 대응.
2. 키 1건 폐기로 주체 단위 파기 — 이벤트 스캔·재작성 불필요.
3. Zero Payload([[02-write-model]]) 원칙과 정합 — PII 표면 최소화가 자연 보완.
4. 비-PII 이력·감사·리플레이는 폐기 후에도 보존(부분 복원).

## 트레이드오프

### 선택한 방식의 한계
- **키 관리 인프라 부담**: 주체별 키 동적 생성·보관·즉시 하드 삭제·로테이션. 전용 키 스키마 운영과 그 접근통제·분리 백업 책임.
- **셰딩 후 비가역**: 폐기된 주체의 이벤트는 PII 부분 영구 복호 불가 → 그 구간 완전 리플레이·as-of 재구성 불가([[08-event-store-lifecycle]] §3). 이는 의도된 결과지만 디버깅 시 제약.
- **암호화 누락 위험**: PII가 봉투를 거치지 않고 평문으로 새면 셰딩이 무력. 분류·검증 책임이 코드에 남는다.

### 포기한 대안들
- **물리 삭제(A)**: ES 불변식 파괴 — [[05.event-store-mysql-table]]와 모순. 기각.
- **참조만(B) 단독**: 모든 PII 분리가 비현실적, as-of PII 복원 불가. C의 보완으로만 채택.

## 결과 (기대)
- ES 컨텍스트가 append-only를 지키면서도 개인정보 파기 요청에 대응 가능.
- PII는 주체 키 폐기로 복호 불능화, 비-PII 이력·감사·리플레이는 유지.
