# ADR: command = hexagonal, query = layered (아키텍처 비대칭)

- **상태**: 합의됨 (2026-06-12) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[01-module-structure]]

## 맥락

[[01.cqrs-command-query-module-split]]로 command/query를 모듈 분리하기로 했다. 그렇다면 각 모듈을 **어떤 아키텍처 스타일**로 구성할지 정해야 한다. 쓰기는 불변식·상태 전이가 풍부한 리치 도메인이고, 읽기는 본질적으로 "저장소 → DTO" 변환이다 — 둘의 복잡도가 다르다.

## 고려된 옵션들

### Option A: 양측 모두 hexagonal
- 장점: 일관성. 양쪽 동일 멘탈 모델.
- 단점: query 측에 포트/어댑터·도메인 격식이 **낭비**. 읽기는 격리할 도메인 로직이 없다.

### Option B: 양측 모두 layered
- 장점: 단순.
- 단점: command 측 리치 도메인을 layered가 담기 어렵다(도메인이 다시 빈약해질 위험 — [[02-domain-limitations]] #1 회귀).

### Option C: 비대칭 — command=hexagonal, query=layered (선택됨)
- 장점: 각 측의 복잡도에 맞는 경제적 선택. 쓰기는 도메인 격리, 읽기는 군더더기 없음.
- 단점: 두 모듈의 스타일이 달라 인지 비용. 신규 합류자가 두 패턴을 익혀야.

## 결정사항

**Option C — 의도된 아키텍처 비대칭.**

- **command-module = hexagonal**: 도메인 패키지마다 `domain / application(port in·out) / adapter(in·out)`. 애그리거트가 `handle→event`, `apply→state` 책임을 진다([[02-write-model]]).
- **query-module = layered**: 도메인 패키지마다 `web / service / repository / projection / model`. 포트/어댑터 없음.
- query는 도메인 core에 의존하지 않고, `contract` 이벤트를 구독하는 `projection`이 read model을 채운다([[03-read-model]]).

## 장점
1. **경제성**: 읽기에 hexagonal 격식을 부과하지 않는다.
2. **도메인 보호**: 쓰기 측은 헥사고날로 리치 도메인을 격리 → 빈약 도메인 회귀 방지.
3. **명확한 책임**: command=의사결정/불변식, query=조회/표현.

## 트레이드오프

### 선택한 방식의 한계
- 두 모듈의 아키텍처가 달라 **일관성↓·학습 곡선↑**.
- 코드 리뷰·컨벤션을 모듈별로 따로 가져가야 한다.

### 포기한 대안들
- **양측 hexagonal**: query 측 과설계.
- **양측 layered**: command 측 도메인 빈약화 위험.

## 미결정 사항 및 추가 논의
- query 측 layered의 세부 레이어 규약(트랜잭션 경계, projection과 service 책임 분리).

## 결과 (기대)
- 쓰기는 견고한 도메인, 읽기는 가벼운 조회 — 각자 최적 형태로 진화.
