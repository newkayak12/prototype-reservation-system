# ADR: V2 테스트 전략 — 정확성·경계·진화 (아키텍처를 테스트로 강제)

- **상태**: Proposed (2026-06-14) · 사이클 `20260612-v2-cqrs-es-architecture`
- **상위**: [[RFC-001-v2-cqrs-and-event-sourcing]] · **설계**: [[11-environments-and-testing]] (§5 테스트 피라미드·§5.5)
- **연관**: [[10.event-schema-evolution]](업캐스팅 회귀) · [[07.command-domain-jpa-separation]]·[[01-module-structure]](경계 규칙) · [[03-read-model]](멱등·최종일관성)

## 맥락

V2는 V1의 슬라이스 테스트(레이어별 Testcontainers, [[01-current-state]])를 계승한 위에 새 표면을 들였다 — **비동기·최종일관성·이벤트 리플레이·영구 이벤트의 스키마 진화.** 동시에 헥사고날·DDD 경계(특히 빈약 도메인 극복, [[02-domain-limitations]] W-1)가 핵심 목표인데, **경계는 사람 리뷰만으로 지키면 시간이 지나며 침식된다.** 부하 테스트([[11-environments-and-testing]] §5.4)는 *성능*(얼마나 빠른가)을 답하지 정확성·경계를 지키지 않는다.

→ 정확성·경계·진화를 **1급 테스트 범주**로 못박을지, 그리고 경계 규칙을 어떻게 *강제*할지 결정한다.

## 고려된 옵션들

### Option A: 기존 피라미드 + 부하만, 경계·진화는 리뷰/문서로
- 비용 0. 그러나 경계 침식·진화 회귀를 *사람*에 의존 → 빈약 도메인 재발·이벤트 호환성 사고 위험.

### Option B: 정확성·경계·진화를 1급 범주로 추가, 경계는 ArchUnit/Konsist로 *강제* (선택)
- CI가 경계를 지킨다. 작성 비용이 있으나 1회 작성 후 회귀 비용 0.

### Option C: 형식 검증(TLA+ 등)
- 분산 프로토콜 학습 가치는 크나 현 규모·시간 대비 과함(YAGNI). 속성 기반 테스트로 실용 대체.

## 결정사항

**Option B 채택. 5개 테스트 범주를 V2 표준으로 둔다.**

1. **아키텍처/의존성 강제 (ArchUnit·Konsist) — 1순위.** 규칙을 JUnit 테스트로 박아 CI가 강제한다:
   - **query-module은 command 도메인/스키마를 import·직접 조회하지 않는다** ([[03-read-model]]).
   - **도메인(애그리거트)은 JPA/`@Entity`를 모른다** ([[07.command-domain-jpa-separation]]).
   - **command↔query 접점은 contract 이벤트뿐** ([[01-module-structure]]).
   - 모듈 의존 방향(adapter→application→core)·헥사고날 포트/어댑터 규칙.
2. **속성 기반 (Fixture Monkey 확장):** 무작위 command 시퀀스 → `fold(events)==state`·불변식·read model 수렴. ES 정확성의 정수.
3. **계약 (consumer-driven):** 이벤트 스키마를 producer가 깨면 consumer 테스트가 CI에서 잡는다 — command↔query 경계 보호.
4. **스키마 진화 회귀:** `(eventType, eventVersion)`별 고정 JSON 픽스처를 최신 코드가 모두 읽어내는지 리플레이 검증 ([[10.event-schema-evolution]]) — 영구 이벤트 안전망.
5. **카오스/장애 주입:** 앱 레벨 = **Chaos Monkey for Spring Boot**(빈·엔드포인트에 지연·예외 주입); 인프라 레벨 = k3s pod kill·broker 파티션·DB failover. *"깨져도 사는가"*·effectively-once 검증.

> 한 줄: "성능은 부하로, **정확성·경계·진화는 별도 1급 범주**로. 그중 경계는 리뷰가 아니라 ArchUnit/Konsist 테스트가 *강제*한다."

## 장점
1. 경계 침식·빈약 도메인 재발을 **CI가 머지 전에 차단** — 사람 리뷰 의존 제거.
2. ES/EDA 정확성(리플레이·멱등·수렴)·스키마 진화 안전망을 자동화.
3. 분산·시간적 속성을 테스트로 표현하는 훈련 — 학습목표(a 분산패턴·c DDD) 직결.

## 트레이드오프

### 선택한 방식의 한계
- 초기 작성 비용(ArchUnit 규칙·픽스처·계약 정의). 단 경계 규칙은 1회 작성 후 회귀 비용 0.
- 속성 기반·계약은 러닝커브.
- 카오스는 k3s(E2E) 위에서만 의미 → 실행 빈도 낮게(PR/릴리스 게이트).

### 포기한 대안들
- **A(리뷰 의존)**: 경계 침식 위험 — 빈약 도메인이 핵심 취약점인 프로젝트에서 수용 불가.
- **C(형식 검증)**: 현 규모 과잉(YAGNI), 속성 기반으로 대체.

## 미결정 사항 및 추가 논의
- **ArchUnit vs Konsist** 택일 — 구현 사이클(Konsist가 Kotlin 네이티브라 유력).
- 계약 도구(Pact vs Spring Cloud Contract) — 구현 사이클.
- 카오스 인프라 레벨 도구(Chaos Mesh/Litmus vs 수동 kill) — T-05 확장 시.
- 각 범주 커버리지 목표·CI 게이트화 임계 — 베이스라인 후.

## 결과 (기대)
- 부하(성능) + 정확성·경계·진화(자동 강제)로 테스트가 두 축을 커버.
- **경계가 테스트로 고정**돼 V2 모듈 분리·도메인 리치화가 시간이 지나도 침식되지 않는다.
