### C03 — core↔contract 의존 금지가 도메인 이벤트 반환과 리플레이 apply 오케스트레이션과 충돌
`HIGH` · 판정 open · 처분안 새 RFC 제안 → **✅ 종결 (2026-07-06, 드래프트 착지)**: → RFC-024(합의)로 착지 — core vs contract 이벤트 타입·리플레이 레이어링. ADR 비준은 사용자 권한(재촉 안 함)

**한 줄로:** 애그리거트가 만드는 "도메인 이벤트"를 어느 모듈 타입으로 만들지, 그리고 이벤트로 상태를 되감는 리플레이를 누가 돌릴지를 아직 아무 문서도 안 정했다. 지금의 계층(의존) 규칙과 부딪혀서, 그냥 두면 코드가 규칙을 어기거나 규칙을 지키려다 붕 뜬다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| core (command-core) | 순수 도메인 로직 모듈. 바깥 의존 금지. |
| contract | 컨텍스트끼리 주고받는 공용 계약 타입. Kafka로 나가는 통합 이벤트가 여기 산다. |
| 의존성 매트릭스 | 어느 모듈이 어느 모듈을 import 해도 되는지 표. core는 contract 못 봄, infrastructure는 core 못 봄. |
| apply(event) | 이벤트를 상태에 적용하는 메서드. 애그리거트(core) 소유. |
| 리플레이 | 저장된 이벤트를 처음부터 다시 apply 해서 현재 상태를 재조립. |
| ES 엔진 | event_store에서 이벤트를 읽어 리플레이를 돌리는 놈. infrastructure에 산다. |

**뭐가 문제냐:**
① 애그리거트의 `handle(cmd) → List<이벤트>`에서 이 이벤트가 contract 타입이면 규칙 위반(core는 contract 못 봄), core 타입이면 Kafka로 내보낼 때 core→contract 번역 계층이 필요한데 그걸 누가 하는지 문서에 없다.
② 리플레이 `events.fold(초기){s,e->s.apply(e)}`의 apply는 core 소유인데, 이걸 돌리는 ES 엔진은 infrastructure라 core를 import 못 한다. 그럼 재조립을 누가 하나? 로직이 어댑터로 새고 엔진은 반쪽이 된다.

**지금 상태:** open. D-002 문서가 스스로 미결 숙제로 적어둔 것(라인 299–300). 인접 RFC들은 프레이밍만 하고 안 닫음.

**그래서 뭘 해야 하나:** (1) 애그리거트가 뱉는 이벤트는 core냐 contract냐 (2) core→contract 번역은 어느 모듈이 (3) 리플레이 재조립은 누가 오케스트레이션 — 이 셋을 한 RFC로 확정.

### C09 — SKIP LOCKED와 DLQ 수동 재생이 애그리거트별 발행·소비 순서 계약을 파괴한다
`HIGH` · 판정 open · 처분안 새 RFC 제안 → **✅ 종결 (2026-07-06, 드래프트 착지)**: → RFC-025(합의)로 착지 — 단일 순차 relay·seq_no LWW·DLQ=재구축. ADR 비준은 사용자 권한

**한 줄로:** "같은 예약 건의 사건들은 일어난 순서 그대로 전달된다"는 약속을 지키기로 해놓고, 정작 그걸 깨는 두 가지 동작(여러 일꾼이 경쟁해서 이벤트를 집어가는 방식, 실패한 이벤트를 나중에 손으로 다시 흘려보내는 방식)을 그대로 채택해버려서 순서가 뒤집힐 수 있는데 아무도 이 충돌을 정리하지 않았다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| aggregate_id | 하나의 예약처럼 "같은 대상"을 묶는 식별자. 이 단위로만 순서를 보장한다. |
| 파티션 키 = aggregate_id | 같은 예약의 이벤트는 Kafka 같은 칸(파티션)에 몰아넣어 순서를 지킨다는 약속. |
| outbox / relay | 이벤트를 DB에 먼저 쌓아두고(outbox), 그걸 읽어 Kafka로 내보내는 일꾼(relay). |
| SKIP LOCKED | 여러 relay가 동시에 outbox를 집어갈 때, 남이 잡은 행은 건너뛰고 다음 걸 가져가는 경쟁 방식. 빠르지만 순서를 직렬화하지 않는다. |
| sequence_no | outbox에 쌓인 순번. "원래 이 순서로 나가야 한다"는 기준. |
| DLQ | 처리에 실패한 이벤트를 따로 격리해두는 대기소(Dead Letter Queue). |
| inbox / dedup | 소비 쪽에서 "이 이벤트 이미 봤나?"를 확인하는 중복 방지 장치. |

**뭐가 문제냐:**
① 예약 A에 이벤트 e1(좌석확보) → e2(취소)가 순서대로 outbox에 쌓였다. relay를 여러 개 두고 SKIP LOCKED로 경쟁시키면, relay-1이 e1을, relay-2가 e2를 동시에 집는다. relay-2가 더 빨라 e2(취소)가 Kafka에 먼저 도착하면, 소비 측은 "취소 다음 좌석확보"로 읽어 상태가 꼬인다.
② e1이 처리 실패로 DLQ에 격리된 사이 e2가 먼저 처리된다. 나중에 사람이 DLQ에서 e1을 손으로 다시 흘려보내면, 이미 지나간 앞 순서를 건너뛴 뒤 재생하는 꼴이라 파티션 순서를 정면으로 깬다.
③ inbox는 "이 이벤트 봤나?"만 볼 뿐 "앞 순서를 건너뛰고 왔나?"는 못 본다. 그래서 이 역전을 흡수하지 못하고 read model이 오염된다.

**지금 상태:** open. 메커니즘(파티션 키, SKIP LOCKED, DLQ 수동 재생)은 각각 결정됐지만 상호작용을 봉합한 결정이 없다. D-008 자신의 Weakness §264가 "SKIP LOCKED는 순서를 직렬화하지 않는다 — 이 상호작용이 문서에 없다"고 자인했고, completeness audit §101이 "순서 깨고 재주입 시 정확성 위험"을 미체크 항목으로 등재했다. ADR-09 §63·RFC-021은 inbox가 dedup만 하고 "앞 순서 건너뜀"은 감지 못 한다고 명시한다.

**그래서 뭘 해야 하나:** 순서 계약과 두 메커니즘의 충돌을 한 RFC로 봉합. (1) relay를 aggregate_id 단위로 직렬화할지, 아니면 outbox가 순서를 강제할지 (2) DLQ 재생 시 앞 순서를 어떻게 보존할지 (3) inbox가 갭(건너뛴 앞 순서)을 감지할 책임을 질지 — 이걸 정해야 한다. 문서 각주로 봉합 불가, 별도 결정 필요.

### C16 — 마이그레이션의 genesis 시딩·단방향 동기·롤백 접합점 미정의로 이중반영·데이터 유실
`HIGH` · 판정 open · 처분안 새 RFC 제안

**한 줄로:** 구시스템(V1)에서 신시스템(V2)으로 옮겨가는 긴 전환 기간에, 기존 데이터를 처음에 통째로 심는 작업과 그 뒤 계속 따라 흘려보내는 작업의 "이음매"를 안 정해서, 같은 데이터가 두 번 들어가거나 아예 빠질 수 있고, 문제가 생겨 V1로 되돌리면 그 사이 V2에만 쌓인 예약이 증발한다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| genesis 시딩 | V1의 현재 상태를 V2의 최초 이벤트로 통째로 심는 초기 적재. |
| 단방향 동기 | 전환 기간에 V1의 변경을 V2로만 계속 흘려보내는 파이프(V2→V1은 없음). |
| 병행 창 | V1과 V2를 함께 돌리는 전환 기간. |
| 스냅샷 커서 | genesis 시딩이 "어느 시점의 V1 상태까지 떴는가"를 가리키는 지점. |
| 동기 스트림 오프셋 | 단방향 동기 파이프가 "어느 변경부터 흘려보내기 시작하는가"를 가리키는 지점. |
| 접합점 | 위 커서와 오프셋이 맞물려야 하는 이음매. 겹치지도 비지도 않아야 한다. |
| 컷오버 | 트래픽을 V1에서 V2로 넘기는 전환 순간. |
| 롤백 | 문제 시 트래픽을 다시 V1로 되돌리는 것. |

**뭐가 문제냐:**
① genesis 시딩이 "3시 정각의 V1 상태"를 떴다고 하자. 3시 정각~컷오버 사이에 V1에서 예약이 하나 더 생기면, 이게 (a) genesis에도 들어가고 (b) 동기 파이프로도 흘러오면 이중 반영, (a)에도 (b)에도 안 잡히면 유실이다. 스냅샷 커서와 동기 오프셋의 접합점을 문서가 안 다뤘다.
② 동기는 V1→V2 단방향뿐이다. 컷오버 후 V2에서 새로 생긴 예약·취소는 V1에 반영되지 않는다. 이 상태에서 트래픽을 V1로 롤백하면 그 사이 V2에만 있던 예약이 통째로 증발한다. 보존 기간이 길수록 유실 창이 커진다.
③ 마이그레이션 성공 게이트가 "재구성 상태 = V1 현재 상태"인데, genesis가 V1을 통째 옮긴 것이라 이건 정의상 참이다. 순환 논리라 게이트로서 아무것도 검증 못 한다.

**지금 상태:** open. 세 축 모두 D-005의 Weakness §4.3·§4.6·§4.7에 문서가 스스로 미해결로 적어둔 것("경계가 없다", "게이트로서 약하다", "후속 검토 대상", 라인 173·176·174·179). 이행을 소유한 RFC-013은 접합점·보존기간·부분 역방향을 전부 "Design에서 검증"으로 이월하고 클린 슬레이트라며 하류 산출물 없이 종결(라인 120·140·156-163). 대응 ADR도 없다(결정 표 전 행 ADR=—). ADR-06은 점진 전환·단방향·긴 병행 방향만 확정하고 접합/롤백은 안 다룸.

**그래서 뭘 해야 하나:** 마이그레이션 접합·롤백을 한 RFC로 확정. (1) 스냅샷 커서와 동기 오프셋을 어떻게 맞물려 이중반영·유실을 막을지 (2) 컷오버 후 롤백 시 V2 신규 이벤트를 어떻게 보존/역반영할지, 아니면 롤백을 어느 시점부터 포기할지 (3) 순환이 아닌 실효 마이그레이션 성공 기준 — 이 셋을 정해야 한다.

### C34 — 결제 사가 표면 동결이 부분환불·분쟁·재시도 소진을 표현 못 하고 확정 경로가 얕다
`HIGH` · 판정 open · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, OVER)**: 결제=log-stub·internal-only(RFC-027); 부분환불·4xx/5xx·재시도소진·정산 SLA는 실PG 승격 사이클 위임

**한 줄로:** 결제가 겉으로 3가지 결과(확정·실패·환불)만 낸다고 못 박아놨는데, 현실엔 이미 "부분환불"이 있고 재시도 소진·분쟁 같은 상황이 있다. 이 3개로 그걸 어떻게 표현할지, 언제 재시도를 포기하고 실패로 넘길지, 웹훅을 놓쳤을 때 언제까지 확정을 보장할지가 다 안 정해져 있다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 사가 | 결제처럼 여러 단계가 얽힌 흐름을 이벤트로 조율하는 방식. |
| 표면 동결 | 밖으로 내보내는 이벤트를 3개(PaymentConfirmed/Failed/Refunded)로 고정한다는 선언. |
| partially_refunded | 일부만 환불된 상태. 이미 상태표에 존재한다. |
| PG | 외부 결제 대행사(Payment Gateway). |
| 4xx / 5xx·타임아웃 | PG 응답 종류. 4xx는 영구 거절(재시도 무의미), 5xx·타임아웃은 재시도 가능. |
| 재시도 소진→failed | 정해진 횟수만큼 재시도해도 안 되면 실패로 확정하는 전이. |
| 대사(reconciliation) | PG 정산 파일과 우리 기록을 주기적으로 대조해 누락을 메우는 백스톱. |
| 웹훅 | PG가 결제 결과를 우리에게 알려주는 콜백. 유실될 수 있다. |
| ACL | 외부 PG 어휘를 내부 도메인 이벤트로 번역하는 경계층. |

**뭐가 문제냐:**
① 표면을 3이벤트로 "동결"했다면서 상태표엔 이미 `partially_refunded`가 있다. 전액 기준으로 되감는 보상 로직과 "5만원 중 2만원만 환불" 같은 부분환불 현실 사이의 간극을, 이 3이벤트 경계가 어떻게 흡수하는지(환불 이벤트에 금액 페이로드를 싣는지 등) 계약이 없다. "상세 표현은 구현 사이클"로 미뤄져 있어 동결이 이름뿐이다.
② PG가 4xx(영구 거절)를 줬는데 재시도 가능한 5xx·타임아웃으로 오판하면, 사가가 될 리 없는 호출을 타임아웃까지 붙잡고 매달린다. 게다가 "재시도 다 썼으면 failed로 전이" 자체가 Phase 2 산출물에 없어서, 소진 후 어디로 가는지가 비어 있다.
③ 웹훅을 놓치면 대사가 "늦게라도" 확정을 발행한다는데, 대사 주기가 "벤더 의존·구현 사이클 위임"이라 지연 상한(SLA)이 없다. 하루 1회 정산 파일이면 확정이 최대 24시간 지연될 수 있다.

**지금 상태:** open. 세 갈래 모두 D-015 자신의 Weakness(Devil's Advocate) §290·§294·§298이 그대로 제기한 반박이고, 이를 닫는 결정 문서가 없다. §4.4는 partially_refunded를 두면서 "상세 표현은 구현 사이클"로, §7은 "재시도 정책은 구현 사이클 위임", "대사 주기는 벤더 의존·구현 사이클"로 미룸. ADR-15와 RFC-016은 3이벤트 동결·ACL·단방향 대사라는 상위 뼈대만 확정하고 부분환불 표현·4xx/5xx 구분·재시도소진→failed·대사 지연 상한·이중환불 가드를 전부 구현 사이클로 위임. D-007 §4.6은 이 문제를 흡수 대상이라며 D-015로 넘기기만 했고(Weakness §362가 "경계 설정이 아니라 회피"로 지적), §4.8/§7은 부분 보상 상태를 v1 PoisonMessage로 담을지 TBD로 남김.

**그래서 뭘 해야 하나:** 결제 사가의 얕은 확정 경로를 한 RFC로 메움. (1) 3이벤트 표면이 부분환불을 어떻게 표현할지(금액 페이로드 계약, 또는 상태 전이가 풍부해지면 ES 재검토) (2) PG 4xx vs 5xx·타임아웃 구분 규칙과 재시도소진→failed 전이 (3) 대사 지연 상한(SLA)과 이중환불 가드 — 이 셋을 확정해야 한다.

### C35 — 멱등키·의도-먼저 기록의 문서 내 모순과 verify 경로의 dual-write·열거 공격면
`HIGH` · 판정 open · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, VOID)**: 우리측 멱등 기결(DESIGN-015 §6.6, 의도-먼저 키+event_id 디듀프); §6.1/6.2는 표기오류, 열거공격은 internal-only라 기질 없음

**한 줄로:** "같은 결제 요청은 두 번 처리하지 않는다"는 걸 보장하는 열쇠(멱등키)를 청구와 환불이 같이 쓸지 따로 쓸지가 한 문서 안에서 서로 다르게 적혀 있고, 결제 확인 도중 프로그램이 죽었을 때 다시 처리하는 방법과 가짜 결제 알림으로 서버를 괴롭히는 공격도 아직 손 안 댔다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 멱등키 | 같은 작업이 여러 번 들어와도 딱 한 번만 처리되게 해주는 식별표. 같으면 "이미 했다"고 판단해 무시. |
| 멱등키 공간 | 그 식별표들이 사는 통. 청구와 환불이 "같은 통"을 쓰면 서로의 키와 우연히 겹칠 수 있다. |
| verify | 결제사(PG)에 "이 결제 진짜 됐냐"고 되물어 확인하는 절차. |
| Outbox append | 확인된 결과(예: 결제완료)를 내보낼 메시지함에 적어두는 것. |
| dual-write | 서로 다른 두 곳(예: verify 처리 + Outbox 기록)에 나눠 쓰는데 그 사이에 죽으면 반쪽만 남는 문제. |
| 열거 공격 | 공격자가 가짜 거래 ID를 마구 찍어 넣어 서버가 쓸데없이 verify를 반복하게 만드는 것. |

**뭐가 문제냐:**
① 같은 문서 D-015가 §6.1(line 182)에서는 "환불은 청구와 **같은** 멱등키 공간을 쓴다"고 하고, §6.2(line 187)에서는 "청구 키와 환불 키는 충돌 안 나게 **분리**한다"고 한다. 정반대다. 만약 같은 공간이면, 청구 키와 환불 키가 우연히 같은 값으로 겹치는 순간 시스템이 "이미 처리함"으로 착각해 **환불이 청구를 흡수하거나 그 반대**가 일어날 수 있다 — 이중 환불을 막는 바로 그 방어선이 스스로 무너진다.
② verify로 결제를 확인한 뒤 그 결과를 Outbox에 적기 **직전에** 프로세스가 죽으면, 재기동 후 다시 verify하고 다시 적으려 한다. 이게 안전하려면 중복 판별용 키(PG 거래 ID)를 verify 시점에 이미 알고 있어야 하는데 그 전제가 확정 안 됐다. 게다가 공격자가 가짜 거래 ID를 대량으로 던져 verify를 계속 유발하는 리소스 소모·열거 공격은 아예 다루지 않았다(보안 절도 웹훅 서명 검증만 다룸).

**지금 상태:** open — 어느 결정 문서로도 안 닫힘. 둘 다 D-015가 스스로 Weakness 항목(멱등키 모순=4번째 line 296, verify 크래시·열거=2번째 line 292)에 미해결로 적어둔 숙제다. ADR-15는 line 67에서 "청구·환불 멱등키 공유 모델·이중 환불 가드"를 구현 사이클로 위임했고, RFC-016·RFC-003도 일반 원칙만 정할 뿐 이 payment-특정 쟁점(키 공간 분리, verify 재-append 멱등, 열거 공격면)은 건드리지 않는다.

**그래서 뭘 해야 하나:** 새 RFC 한 건으로 (1) 청구·환불 멱등키를 같은 공간으로 쓸지 분리할지와 그 키 생성·전달 규약, (2) verify 후 Outbox append 직전 크래시 시 재-verify·재-append가 딱 한 번만 반영되게 하는 방법(디듀프 키를 verify 전에 확보), (3) 가짜 거래 ID로 verify를 유발하는 열거·리소스 소모 공격 방어를 확정.

### C40 — 장애 폴백 미정 상태로 단일 인스턴스만 먼저 확정한 순서 역전
`HIGH` · 판정 open · 처분안 새 RFC 제안

**한 줄로:** Redis가 죽었을 때 어떻게 버틸지(요청을 그냥 통과시킬지, 막을지, 중복을 허용할지)를 아직 안 정했는데, 그보다 먼저 "Redis 서버 한 대면 충분"이라고 못 박았다. 버티는 법을 안 정한 채 대수만 확정한 건 순서가 거꾸로다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| Redis | 속도 빠른 메모리 저장소. 여기서는 요청 제한과 중복 방지 기록을 담는 데 씀. |
| 레이트리밋 | "1초에 몇 번까지만" 식으로 요청 수를 제한하는 것. |
| 폴백 | 원래 쓰던 게 고장났을 때 대신 쓰는 대비책. |
| 멱등 디듀프 | 같은 요청이 두 번 오면 두 번째를 걸러 중복 처리를 막는 것. |
| 단일 인스턴스 | 그 Redis를 한 대만 두는 것(이중화 안 함). |
| L1→L1′ | 분산 락에서 Redis가 안 되면 DB 락으로 강등하는, 이미 정해진 대비책. |

**뭐가 문제냐:** Redis가 흔들리는 순간의 행동을 두 가지나 안 정했다. (1) 레이트리밋: Redis가 죽으면 요청을 **다 통과**시킬지 **다 막을지** — 통과시키면 과부하가 그대로 밀려들고, 막으면 서비스가 멎는다. (2) 멱등 디듀프: 중복 판별 기록이 사라지면 **결제·예약이 중복 생성**될 수 있다. 이 둘의 행동을 미정으로 둔 채 "인스턴스 하나면 충분"만 확정했으니, Redis 한 대가 흔들리는 순간 무엇이 터질지 모르는 상태로 운영에 들어가게 된다. 이미 확정된 폴백은 분산 락의 L1→L1′(RFC-014/ADR-16)뿐이라 락 경로만 덮고 레이트리밋·디듀프는 공백이다.

**지금 상태:** open이지만 우려 자체는 인지·기록됨. D-018이 스스로 Devil's Advocate(line 259)에 C40과 거의 같은 문장으로 "폴백 미결인데 단일 인스턴스만 확정 = 순서 역전"을 적어뒀다. 그런데 이건 해소가 아니라 "미해소 리스크"로 남긴 것이다. 단일 인스턴스 확정은 ADR-19(D-2, 상태 Proposed)·RFC-018 결정4에 있지만, 레이트리밋·디듀프 장애 폴백은 D-018 §6.1(line 140-141)·§8에서 "후속 사이클"로 미뤄졌고 ADR-19 미결정 목록에도 안 올라 추적조차 안 된다.

**그래서 뭘 해야 하나:** 새 RFC로 Redis 장애 시 (1) 레이트리밋은 통과 허용 vs 요청 거부 중 무엇으로 폴백할지, (2) 멱등 디듀프는 허용 staleness와 중복 허용 여부를 어떻게 둘지를 먼저 확정하고, 그 폴백 시맨틱과 정합되게 단일 인스턴스 결정을 재확인. 확정 시 ADR-19 미결정 목록에도 이 폴백 항목을 올려 추적.

### C45 — '잎 먼저' 1차 기준과 허브 reservation을 앞세운 실제 순서의 모순
`HIGH` · 판정 open · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-08, OVER — 결정 불요)**: leaf-first 준수로 순서 모순 소멸(restaurant→reservation). fail-fast override를 버리면 "규칙 vs 순서" 긴장 자체가 사라진다. 파생 문제(식당명 비정규화 갭)는 갈래1에 기생한 것 — restaurant를 먼저 V2로 올리면 reservation 프로젝션 시점엔 이벤트 소스가 이미 있고, **V1→V2가 비실시간 배치 컷오버**라 두 컨텍스트가 V1/V2로 공존하는 창이 없어 임시 이벤트 브리지·백필 결정 모두 불요. 요구하던 새 RFC 2건 증발. 잔여 조치는 결정이 아니라 D-005/RFC-010 순서표를 leaf-first로 정정(문구) + "fail-fast는 leaf-first 위반 않는 범위 tie-break"로 강등 명시.
> ~~🔴 사용자 결정 대기 (GENUINE)~~ → 결정 불요 (마이그레이션 비실시간·leaf-first 준수로 해소)

**한 줄로:** 이사 순서를 정할 때 "다른 것에 의존하지 않는 것부터 옮긴다"를 1순위 규칙으로 못 박아 놓고, 정작 실제 순서표는 restaurant·timetable에 기대는 reservation을 restaurant보다 먼저 옮기게 짜여 있다. 규칙과 순서가 어긋난다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 잎 먼저(leaf-first) | 의존성 그래프에서 아무것도 안 기대는 말단(잎)부터 옮기는 것. 그래야 옮긴 게 안 깨진다. |
| 허브 | 여러 곳이 기대는 중심 노드. 여기선 reservation. |
| fail-fast | 위험하고 중요한 걸 일부러 먼저 해서 문제를 빨리 드러내는 전략. |
| tie-break | 우선순위가 같을 때 순위를 가르는 보조 기준. |
| 프로젝션 | 이벤트를 모아 조회용 화면 데이터로 만들어 두는 것. |
| 식당명 비정규화 | 조회 편의를 위해 예약 데이터에 식당 이름을 복사해 박아두는 것. |

**뭐가 문제냐:** §4.2(초안 순서)는 1 timetable → **2 reservation** → **3 restaurant** → 4 schedule·user → 5 menu 순인데, reservation(#2, 허브)이 자기가 의존하는 restaurant(#3)보다 앞이다. §4.1이 "잎 먼저"를 1차 기준으로 못 박았는데, 실제 순서는 fail-fast(위험한 핵심 ES를 앞에)를 tie-break로 1차 기준 위에 얹어서 만들어졌다 — 결과에 맞춰 규칙 우선순위를 사후에 뒤집은 셈. 실제 피해도 명확하다: reservation을 restaurant보다 먼저 옮기면, restaurant가 아직 V1(구버전)이라 식당명 비정규화(DESIGN-004 §4.5)에 필요한 이벤트를 발행하지 못해 **reservation 프로젝션의 식당명 채우기가 성립하지 않는다.**

**지금 상태:** open. 순서 "규칙"(의존성 1차 + 위험·학습 결선) 자체는 RFC-010 논점3·ADR-06에서 확정됐다. 하지만 규칙과 실제 1~5 시퀀스가 어긋난다는 이 모순을 해소하는 결정은 없다. 오히려 ADR-06·RFC-010·D-005 §4.2 모두 1~5 시퀀스를 "초안(draft)"으로만 표기했고, RFC-010 논점3(line 133)은 실제 시퀀스 확정을 Design으로 미뤘는데, Design인 D-005는 초안을 그대로 재수록하고 §Weakness 첫 항목에 이 모순을 스스로 적은 뒤 "후속 검토 대상"으로 남겼다. 파생 문제(식당명 비정규화 불성립)도 어디서도 안 다뤄졌다.

**그래서 뭘 해야 하나:** 새 RFC로 (1) 실제 의존성 그래프 위에서 1~5 전환 순서를 확정하되, reservation을 restaurant보다 먼저 옮기는 게 "잎 먼저" 규칙 위반인지 아니면 fail-fast로 정당화되는 예외인지를 규칙 우선순위 차원에서 정리하고, (2) reservation을 먼저 옮길 경우 restaurant가 V1인 동안 식당명 비정규화를 어떻게 성립시킬지(임시 이벤트 브리지 등)를 결정.

### C02 — Zero Payload 재처리가 미래 상태로 과거 이벤트를 오염시키는 time-travel 결함
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, VOID)**: Zero Payload 폐기(RFC-029)로 전제 소멸 — time-travel 결함 원천 봉인

**한 줄로:** "이벤트를 다시 재생할 때 필요한 값은 그때그때 최신 상태를 조회해 채우니 안전하다"는 설계는, 과거 이벤트를 재생하는데 **미래 시점의 값**이 박히는 시간여행 오류를 놓친다. Zero Payload는 문제를 없앤 게 아니라 "그 시점 값이 무엇이었나"를 알아내는 부담을 프로젝션 재구축 쪽으로 떠넘겼고, 그 재구축이 맞는지는 아직 검증 안 됐다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| Zero Payload | 이벤트에 데이터를 최소한만 싣고, 필요한 값은 소비 측이 따로 조회하는 방식. |
| 재처리/리플레이 | 저장된 이벤트를 처음부터 다시 재생해 상태·조회데이터를 다시 만드는 것. |
| point-in-time | "그 사건이 일어난 바로 그 시점"의 값. 지금 값이 아니라 당시 값. |
| projector | 이벤트를 받아 조회용 데이터를 갱신하는 놈. |
| sequence_no 버전 가드 | "더 과거 버전으로 최신 값을 덮어쓰지 마라"를 강제하는 순번 검사. |
| ES / 비-ES | ES=이벤트소싱 컨텍스트(이벤트가 진실의 원천), 비-ES=그렇지 않은 곳. |
| 이벤트-carried | 필요한 값을 이벤트 안에 실어 보내는 방식(조회 불필요). |

**뭐가 문제냐:** 예를 들어 가격이 v3이었던 과거의 `PriceChanged` 이벤트를 재처리하는데, projector가 "최신 상태 조회"로 값을 채우면 이미 v5로 바뀐 **현재 가격**을 가져와 과거 이벤트에 박아버린다. 즉 과거 기록이 미래 값으로 오염된다. 여러 애그리거트가 얽힌 point-in-time 파생 사실("예약 순간 그 슬롯이 열려 있었나")은 재생 순서(interleaving)에 따라 값이 달라져 더 위험하다.

**지금 상태:** 부분결정. 두 층위로 나뉜다. (1) **교차-애그리거트 point-in-time 오염**은 RFC-021 결정#4(line 105·180·210) + ADR-22 정확성 불변식(line 56-58)이 "생산 시점에 값을 이벤트 페이로드에 박제 + sequence_no 버전 가드"로 정면 결정해 이미 막았다 — C02의 강한 버전은 해결됨. (2) 그러나 C02의 리터럴 예시(단일 애그리거트의 v3 시점 복원)는 남는다: 버전 가드는 "더 과거로 덮기"만 막지, v3 시점 프로젝션에 v3 값을 넣는다는 보장은 아니다. 근본 처방인 "ES=이벤트-carried / 비-ES=Zero Payload 분기"는 RFC-002 §4.4 리뷰 노트(DESIGN-003 line 191-193)에만 있고, DESIGN-003 결정 본문·용어집(line 124·165)은 여전히 "Zero Payload=최신 상태 조회"로 남아 있다. 대응 ADR-22도 아직 Proposed(비준 전). 원칙은 정해졌지만 C02가 지목한 "재구축 정합성이 RFC로 위임만 되고 검증 안 됨"이라는 그 갭이 남아 부분결정이다.

**그래서 뭘 해야 하나:** 새 RFC — *프로젝션 페이로드 정책: ES=이벤트-carried vs 비-ES=Zero Payload 분기와 시점 복원 정합성* — 한 건으로 (1) ES 컨텍스트는 이벤트에 값을 실어(불변이라 stale 안 됨) 조회를 없애고, 비-ES는 Zero Payload를 유지하는 분기를 결정 본문·용어집에 명문화하고, (2) 재처리 시 그 시점(v3) 값이 정확히 복원되는지 검증 절차를 정한 뒤, (3) ADR-22를 Proposed에서 비준으로 접는다.

### C10 — 주인 없는 코레오그래피가 사가 상태의 단일 조회지점·정적 전역 불변식 검증을 없앤다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안

> **✅ 종결 (2026-07-05, C10·C11·C13 묶음)** — 신규 RFC 없이 기존/후속 결정 배선으로 닫음. 단일 조회지점 부재=ADR-08 트레이드오프 수용. 단일 슬롯 오버부킹=timetable 단일 애그리거트 직렬화+L0 UNIQUE([[DESIGN-006-aggregate-design]] §183-188). 교차-슬롯 정원=이벤트 스토밍/사가 punt(§104). 가드 맞물림 정적검증=[[RFC-009-testing-quality-gates]] 계약 테스트. 상세 [[DESIGN-007-consistency-and-sagas]] §4.9.

**한 줄로:** 여러 서비스가 지휘자 없이 이벤트만 주고받아 예약을 처리하는 방식이라, "지금 이 예약이 어디까지 진행됐나"를 한 곳에서 볼 수 없고, "좌석이 두 번 팔리는 일은 절대 없다" 같은 전체 규칙을 미리 자동으로 검사할 방법도 없다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 사가(saga) | 여러 서비스를 거쳐 하나의 예약을 완성하는 긴 작업 흐름(좌석 잡기→결제→확정 등). |
| 코레오그래피 | 중앙 지휘자 없이 각 서비스가 이벤트를 듣고 알아서 다음 동작을 하는 방식. |
| 오케스트레이션(PM, 프로세스 매니저) | 반대로 중앙 지휘자 하나가 전체 흐름을 지시하는 방식. |
| 상태 가드 | "이 조건이면 다음으로 못 감" 같은 각 서비스에 흩어진 검사 규칙. |
| correlationId | 같은 예약 흐름에 속한 이벤트들을 한 줄로 묶어주는 식별자. |
| 보상 | 앞 단계를 되돌리는 반대 동작(좌석 풀기, 환불 등). |
| 전역 불변식 | 시스템 전체에 항상 참이어야 하는 규칙. 여기선 "오버부킹 금지". |
| 오버부킹 | 좌석 수보다 많이 팔려버리는 사고. |

**뭐가 문제냐:** 지휘자가 없으니 "이 예약이 성공했나, 어느 단계에서 멈췄나"를 한 번에 물어볼 데가 없고, 좌석은 풀렸는데 환불은 실패한 어정쩡한 상태를 나중에 correlationId로 로그를 짜맞춰야 겨우 안다. 더 날카로운 문제는 "오버부킹 금지" 규칙이 각 서비스에 흩어진 가드들로만 지켜진다는 점이다. 한 서비스가 가드를 잘못 짜도 그 서비스 단위 테스트는 통과하고, 다른 서비스와 맞물리는 순간 좌석이 두 번 팔린다. 전체가 맞물려 규칙을 지키는지 미리 검사할 방법이 없다.

**지금 상태:** 부분결정. 일부는 이미 문서가 인정·처리했다 — "한 곳에서 질의 못 함"은 ADR-08 §트레이드오프(L83)가 명시 인정, 재처리 추적과 로그 교차조회는 RFC-008(§논점2·3)이 다룸, 부분 보상 상태를 PoisonMessage로 담을지는 RFC-006 §논점4(L125)가 TBD로 남김. 그러나 가장 날카로운 청구 — 흩어진 가드가 곧 검증 안 되는 분산 상태 머신이고 오버부킹을 정적으로 못 막는다 — 는 어떤 결정 문서도 안 닫았다. 이건 DESIGN-007 §Weakness(L354)가 스스로 남긴 숙제이며 "후속 검토 대상"(L364)으로만 못박혀 있다. ADR-08 자체도 아직 Proposed(비준 전)다.

**그래서 뭘 해야 하나:** "오버부킹 금지" 전역 불변식을 무엇으로 강제할지를 한 RFC로 정한다 — (1) 가드의 소유자는 누구고 (2) 인수/계약 테스트로 서비스 간 맞물림을 어떻게 검증하며 (3) 집계 검증으로 위반을 어떻게 잡을지. 처분안: 새 RFC 제안(RFC-024 코레오그래피 전역 불변식의 계약화·검증 전략). 단일 조회지점 부재는 ADR-08이 이미 트레이드오프로 받아들였으니 재론하지 않는다.

### C11 — 코레오그래피 채택 근거가 '선형 2~3스텝'에 걸려 있고 전환 트리거·부분보상 복구가 미결인 채 Accepted
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안

> **✅ 종결 (2026-07-05, C10·C11·C13 묶음)** — PM 전환 3조건은 ADR-08 §54-59에 이미 존재(정성적, 무트래픽 운영화는 YAGNI). 핵심인 부분보상 복구는 [[DESIGN-007-consistency-and-sagas]] §4.9에서 **꼬리 격리 채택**으로 종결(멱등 정방향 재호출 [[DESIGN-015-payment-integration]] §6.6 + 꼬리 격리 [[DESIGN-020-ordering-and-failure-handling]] §5). RFC-006 §논점4 TBD도 닫힘.

**한 줄로:** "예약 흐름이 짧고 단순하니까(2~3단계 일직선) 지휘자 없이 가도 된다"는 게 채택 이유인데, 실패했을 때 절반만 되돌아간 상태를 어떻게 복구할지를 안 정한 채 결정부터 내렸다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 선형 2~3스텝 | 분기 없이 앞으로만 가는 2~3단계짜리 짧은 흐름. |
| 전환 트리거 | "이 조건이 되면 지휘자(PM) 방식으로 갈아탄다"는 판정 기준. |
| 부분 보상 복구 | 되돌리기 중 일부만 성공하고 일부는 실패한 상태를 수습하는 것. |
| PoisonMessage 모델 | V1에서 실패한 메시지를 저장·추적·재처리·알림하던 기존 장치. |
| 순서 도치 | 근거를 확정하기 전에 결론부터 낸 것. |

**뭐가 문제냐:** 채택 근거 1번이 "예약 흐름이 전부 2~3스텝 선형"(DESIGN-007 §4.3)이라는 사실 하나에 걸려 있다. 그런데 이미 5개 흐름이 상태 가드로 서로 간섭하고, 6번째 흐름을 붙이면 이 근거가 무너진다. 진짜 핵심은 따로 있다 — "좌석은 풀렸는데 환불은 실패" 같은 절반짜리 실패 상태를 V1의 PoisonMessage 장치로 표현·복구할 수 있느냐. 이게 코레오그래피가 오케스트레이션보다 나은지를 판가름하는 지점인데, 이걸 TBD로 열어둔 채 채택을 먼저 확정했다.

**지금 상태:** 부분결정. 갈래마다 상태가 다르다 — (1) 채택과 그 근거는 결정됨(ADR-08·RFC-006·DESIGN-007). (2) C11이 "전환 트리거 없음"이라 한 건 부정확하다 — ADR-08 §결정 기준(L54–59)에 PM 재검토 3조건(5스텝 이상+조건 분기, 중앙 조합 필요, 자치 보상으로 정합성 불가)이 있다. 다만 정성적이라 "누가 언제 판정"하는 운영화는 안 됐다. (3) 핵심인 부분 보상 복구는 DESIGN-007 §4.8(L291)·§7(L319), RFC-006 §논점4(L125), DESIGN-015 모두에서 TBD/미결이다. C11 문장 대부분은 DESIGN-007 §Weakness(L352·360)가 스스로 적은 숙제와 사실상 같은 문구이고, 그 절은 "후속 검토 대상"으로만 남겨 미해소다.

**그래서 뭘 해야 하나:** "좌석 풀린 뒤 환불 실패" 같은 부분 보상 상태를 V1 PoisonMessage로 재사용해 복구할지, 아니면 사가 전용 보정 경로를 따로 둘지를 좁은 topical RFC로 정해 미결을 닫는다. 처분안: 새 RFC 제안(사가 부분 보상 복구 모델). 채택 결정과 PM 전환 3조건은 이미 정해졌으니 건드리지 않는다.

### C13 — 이미 나간 사가 부수효과·결제 실패는 보상·상태 가드로 되돌릴 수 없다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안

> **✅ 종결 (2026-07-05, C10·C11·C13 묶음)** — 두 갈래는 문서가 반박(UNIQUE 거절 시 선행 결제 없음·paid-after-expiry는 §4.7라 RefundRequired). 진짜 잔여인 "환불 호출 자체 실패"는 C11과 동일 질문 → [[DESIGN-007-consistency-and-sagas]] §4.9 꼬리 격리 + 운영 보정 큐(재구축 불가한 외부 효과라 수동 드레인 런북). 상세 [[DESIGN-015-payment-integration]] §6.6.

**한 줄로:** 사용자가 결제까지 했는데 예약이 확정 안 돼서 환불해줘야 하는데, 그 환불 자체가 실패하면(PG사 문제 등) 시스템은 좌석은 풀리고 돈은 안 돌아간 어정쩡한 상태에 갇힌다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 락 키 evict | 동시성 제어용 임시 잠금이 강제로 풀리는 것. |
| UNIQUE 거절 | DB의 유일성 제약이 중복 예약을 막고 거절하는 것. |
| append 계층(L0) | 이벤트를 덧붙여 기록하는 최하위 저장 계층. 여기선 "부정확한 데이터는 안 들어간다"는 뜻으로 씀. |
| paid-after-expiry | 좌석 점유가 만료된 뒤에 결제가 뒤늦게 확정되는 경합 상황. |
| 상태 가드 | "만료됐으면 확정 거부" 같은 조건 검사 규칙. |
| RefundRequired | "환불 필요" 보상 이벤트. |
| PG | 결제 대행사(payment gateway). |
| 대사(reconciliation) | PG 원장과 우리 기록을 주기적으로 맞춰보는 것. PG를 진실로 봄. |

**뭐가 문제냐:** 리뷰어의 원 주장은 "거절된 쪽이 이미 한 결제가 안 되돌려진다"인데, 이 중 둘은 문서가 반박한다. 좌석 확정은 결제보다 앞서므로(DESIGN-007 §4.4) UNIQUE 거절 시점엔 되돌릴 선행 결제가 아예 없고, 결제가 앞서는 유일 경로(paid-after-expiry)는 §4.7(라)가 EXPIRED+결제확정→확정거부→RefundRequired→환불로 명시 처리한다. 즉 보상은 상태 가드가 이벤트를 쏴서 트리거된다. 진짜 남는 구멍은 세 번째다 — 그 환불 호출 자체가 PG에서 실패하면? 좌석은 이미 풀렸는데 환불은 안 된 부분 보상 잔류 상태가 남는다.

**지금 상태:** 부분결정. 두 갈래는 해소됨 — DESIGN-007 §4.4/§4.7(라)가 "보상이 트리거 안 된다"는 전제를 문서상 거짓으로 만든다. 환불로 정합성을 푸는 것도 RFC-006 §논점5의 채택된 트레이드오프다(예방이라 주장한 적 없음). ADR-15/RFC-016은 환불=멱등 정방향 재호출 + 단방향 대사(PG=진실) + 운영 보정 큐로 구조적 방향까지 제시한다. 하지만 "환불 자체 실패로 남는 잔류 부분 보상 상태를 PoisonMessage 모델이 담을 수 있나"는 RFC-006 §논점4(L125)와 DESIGN-007 §4.8/§7이 명시적 TBD로 남겼다. 리뷰어 자신도 DESIGN-007 L356·360에서 이걸 코레오그래피 채택의 핵심 미결로 지목한다.

**그래서 뭘 해야 하나:** "좌석 풀림 성공 + 환불 실패"로 남는 부분 보상 잔류 상태를 어떻게 표현하고 복구할지 — PoisonMessage 계승 vs 사가 전용 보정 경로 — 를 좁은 RFC로 정한다. 처분안: 새 RFC 제안. 이미 해소된 두 갈래(UNIQUE 거절 시 선행 결제 없음, paid-after-expiry의 RefundRequired 보상)는 스코프에서 뺀다. 완화 노트로 덮을 갭이 아니다.

### C24 — 인가 클레임을 이벤트 봉투에 실어 전파하면 봉투가 위변조·재생 공격면이 된다
`MED` · 판정 open · 처분안 새 RFC 제안(검토 필요)

> **✅ 종결 (2026-07-05, mitigate-note · 신규 RFC 없음)** — 두 축을 섞은 프레임을 분리해 해소. (1) *authz 클레임*: 봉투 신원=불변 사실, 다운스트림 재인가 없음(인가=엣지 역할 + 조회 시점 소유권) → 위변조=권한상승 불가·재생=상태재구성만, 내부-only라 봉투 서명 과설계. [[DESIGN-014-authorization]] §4.5 신뢰 경계로 명문화. (2) *PII 복호*: 별개 축 = 크립토 셰딩([[DESIGN-016-pii-security]] §4.2 AEAD+**AAD 바인딩** 추가로 오려붙이기·재생 방지, Tink 참조). gateway 인증/인가(RFC-015/020)는 또 다른 층.

**한 줄로:** "누가, 무슨 권한으로" 같은 정보를 이벤트 메시지 안에 적어서 다른 서비스로 넘기는데, 그 메시지가 위조되거나 오래된 게 다시 흘러들어와도 막을 장치(서명·불변 보장)를 아무 문서도 안 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 인가 클레임 | "이 사람은 SELLER 역할" 같은 신원·권한 정보. |
| 봉투(envelope) | 이벤트/커맨드를 감싸는 메타데이터 껍데기(추적 ID 등이 담김). |
| 다운스트림 | 이 봉투를 받아 읽는 뒷단 서비스들. |
| 재생(replay) 공격 | 예전에 유효했던 메시지를 다시 흘려보내 권한을 악용하는 것. |
| 서명 | 내용이 위조되지 않았음을 증명하는 암호 도장. |
| inbox/Kafka | 서비스 간 메시지가 지나가는 내부 큐. |
| 게이트웨이 strip | 관문에서 클라이언트가 보낸 위험한 헤더를 떼어내는 것. |
| JWT | 사용자 인증에 쓰는 서명된 토큰. |

**뭐가 문제냐:** 다운스트림 서비스가 봉투에 적힌 역할·신원을 그대로 믿고 권한 판단을 한다. 그러면 인가의 정확성이 "봉투가 변조 안 됐다"는 가정에 통째로 매달린다. 그런데 내부 큐에 접근한 누군가가 봉투의 역할 필드를 USER→ADMIN으로 바꿔 다시 넣거나, 예전에 유효했던 봉투를 재전송해도 이를 막을 서명·불변성 보장이 없다. 더구나 이벤트 소싱 특성상 오래된 이벤트가 다시 오는 "재처리"가 정상 동작으로 못박혀 있어서, 재생 시나리오가 실제로 상시 발생한다.

**지금 상태:** open. 어떤 ADR/RFC도 이 봉투의 무결성·재생 방어를 안 닫았다. 인접 결정들은 다 다른 경계를 다룬다 — RFC-020은 요청 시점 HTTP 헤더(X-User-Id strip + NetworkPolicy)이지 내부 봉투가 아니고, ADR-20/RFC-019의 "서명"은 JWT 토큰 자체이지 봉투가 아니며, ADR-10/DESIGN-003의 불변성(append-only)은 감사·스키마 진화용이다. DESIGN-003 §127과 ADR-22 확정 스키마의 봉투 메타는 correlation_id·causation_id·traceparent만 정하고 신원·역할 클레임의 봉투 표현·서명·재생 방어는 빠졌다. RFC-003은 "재처리는 정상"(L87)을 불변식으로 못박아 재생 시나리오를 오히려 실재화한다. 이건 DESIGN-014 §4.5(L98)가 낳은 문제를 §Risks(L195)가 스스로 지적하고 §6(L131)이 "직렬화 표현"만 후속으로 남겨 봉투 신뢰 경계는 열어둔, 문서가 남긴 숙제다.

**그래서 뭘 해야 하나:** 봉투에 실린 인가 클레임의 신뢰 경계를 한 RFC로 정한다 — (1) 봉투(또는 클레임 필드)에 서명을 붙일지 (2) 재생 방어를 어떻게 할지(nonce/타임스탬프/시퀀스) (3) 다운스트림이 봉투 클레임을 그대로 믿을지, 아니면 자체 재검증할지. 처분안: 새 RFC 제안(open·MED 기준 자동도출, 승격 전 검토 필요).

### C33 — 추적 3필드 의무화 저장·전송 비용과 SLI 카탈로그 이중 계측·AOP 스코프 경계 미정의
`MED` · 판정 open · 처분안 새 RFC 제안
> **✅ 종결 (2026-07-05) — 대부분 무효/이월, 핵심은 세탁된 결정:** ① 3필드 비용·Zero Payload 역전 = [[RFC-029-event-carried-payload-uniform]]로 Zero Payload 폐기되며 소멸(무트래픽이라 비용 논의 자체가 공허). ② SLI/카탈로그 이중계측 = 층 분리 원칙은 이미 있고, 메트릭 목록·라벨 카디널리티는 측정할 트래픽이 생기는 **구현 사이클 이월**(설계 결함 아님). ③ Baggage PII 유출 = **팬텀** — 설계 어디에도 PII를 Baggage에 싣는 결정이 없다(스코프 키는 operation·aggregate_id 등 non-PII, 로그용이라 메트릭 라벨 카디널리티와도 무관). 더구나 'Baggage 전파' 자체가 RFC-008 논점5에서 AI가 채워 "네 결정"으로 기록한 **미비준 초안**(〔근거 확인/보강 필요〕 붙음 — [[ai-draft-laundered-as-user-decision]]): 닫힌 결정으로 취급하지 않고 **열린 구현-시점 선택**으로 남긴다. correlation 사슬은 봉투 필드(correlationId·causationId·traceparent)만으로 충분하다. → **설계 조치 없음**, 클러스터 종결.

**한 줄로:** 모든 이벤트에 "추적용 꼬리표 3개"를 무조건 붙이기로 정했는데, 그게 저장·전송에 얼마나 비싼지, 같은 현상을 두 대시보드에서 중복으로 재는 걸 어떻게 정리할지, 그 꼬리표를 코드 어디에 자동으로 붙일지를 아직 안 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| correlationId / causationId / traceparent | 이벤트가 "어느 요청에서 시작됐고, 무엇 때문에 생겼는지" 추적하려고 붙이는 꼬리표 3종 |
| Zero Payload 이벤트 | 본문(실제 데이터)은 거의 없고 식별자만 담은 아주 가벼운 이벤트 |
| 메타데이터 | 이벤트 본문이 아니라, 이벤트에 딸린 부가정보(위 꼬리표 같은 것) |
| SLI | 사용자가 체감하는 서비스 품질 지표(예: 화면이 얼마나 늦게 갱신되나) |
| 카탈로그(메트릭 카탈로그) | 시스템 내부 파이프라인 건강 지표 모음(예: 처리 지연, 밀린 큐 길이) |
| lag / Outbox 적체 | 컨슈머가 못 따라가 쌓인 양 / 내보낼 이벤트가 쌓인 양 |
| 라벨 카디널리티 | 메트릭에 붙는 라벨 값의 가짓수. 많을수록 모니터링 비용이 폭증 |
| AOP | 코드 곳곳에 공통 처리(여기선 꼬리표 주입)를 자동으로 끼워 넣는 기법 |
| Baggage / MDC | 요청을 따라 흐르며 하류로 전파되는 컨텍스트 값 / 로그에 찍히는 값 |

**뭐가 문제냐:**
① **비용 저울이 비었다.** 3필드를 매 이벤트·매 Kafka 헤더·event_store 매 행에 강제로 붙이는데, Zero Payload 이벤트에서는 본문보다 꼬리표가 더 커지는 역전이 생긴다. 그런데 이 저장·전송 비용을 저울에 올린 문서가 없다 — DESIGN-011 line 234가 "이 비용과 카디널리티를 문서가 저울에 올리지 않는다"고 스스로 인정하고, §7 Risks(lines 196-200)도 다른 리스크는 나열하면서 이 비용 역전 리스크는 빠뜨렸다.
② **같은 현상을 두 곳에서 잰다.** 프로젝션 지연·lag·Outbox 적체를 SLI 대시보드와 내부 카탈로그가 양쪽에서 재면 지표가 중복되고 혼선이 생긴다. RFC-008 논점 6과 DESIGN-011 §4.6(line 162)은 "SLI=사용자 체감, 카탈로그=내부 건강"이라는 층 분리 원칙만 세우고, 실제 메트릭 목록·라벨 카디널리티·RFC-007 SLI와의 경계 조정은 Design으로 미뤘다. RFC-007 line 69도 이 조정 책임을 RFC-008로 되던졌다.
③ **꼬리표를 어디에 붙일지 경계가 없다.** RFC-008 논점 5는 AOP로 자동 주입한다는 메커니즘만 정하고, "어떤 스코프 키를 표준으로 넣을지·어느 경계마다 걸지·Baggage를 어디까지 전파할지"는 Design으로 이월했다(line 149, DESIGN-011 §4.5 line 148). 경계가 없으면 주입이 불균일해지고, Baggage가 하류로 통째로 흘러 PII(개인정보)가 새거나 카디널리티가 커지는 표면이 남는다 — DESIGN-011 Weakness line 236이 이 문제를 제기만 하고 닫지 않았다.

**지금 상태:** open. 세 갈래 모두 "메커니즘"은 RFC-008/DESIGN-011에서 정해졌지만, concern이 찌른 구체 gap은 어느 결정 문서로도 안 닫혔다. 두 갈래(②③)는 결정 문서가 스스로 "Design에서 구체화"로 명시 이월했고, ①은 문서가 스스로 비용 부재를 자인했다.

**그래서 뭘 해야 하나:** (1) 3필드 의무화의 저장·전송 비용과 Zero Payload 역전을 저울에 올려 정책을 정하고 (2) 프로젝션 지연·lag·Outbox 적체를 SLI와 카탈로그 중 어디서 재는지 메트릭 목록·라벨 카디널리티까지 경계를 확정하며 (3) AOP 표준 스코프 키 집합·적용 경계·Baggage 전파 범위(PII 차단 포함)를 확정 — 이 셋을 한 RFC로 착지시킨다.

### C01 — Zero Payload가 command DB 역참조를 강제해 CQRS 유일접점 불변식을 무너뜨린다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안
> **✅ 종결 (2026-07-05) — 사실상 무효(premise void):** 이 클러스터의 전제(Zero Payload → command DB 역참조 → CQRS 붕괴)가 [[RFC-029-event-carried-payload-uniform]](C02, Zero Payload 폐기)로 통째로 사라졌다. 붕괴 메커니즘은 원래도 ADR-04·RFC-002·RFC-021로 닫혀 있었고, 남았던 thin/fat 리치니스도 event-carried 일원화가 곧 답이라 별도 "정책"이랄 게 없다(fat 일원, 큰 blob만 불변 참조). 즉 해결이라기보다 **전제 소멸로 무효화.** RFC-003이 "별도 RFC로" 미룬 흔적만 DESIGN-003 line 124에서 정리하고, 제안됐던 새 RFC는 폐기.

**한 줄로:** "가벼운 이벤트(식별자만 담음)를 쓰면 받는 쪽이 원본 DB를 다시 뒤져야 해서 읽기/쓰기 분리가 무너진다"는 걱정은 이미 여러 결정으로 막아뒀다. 다만 "이벤트에 데이터를 얼마나 담을지"라는 정책만은 아직 아무 문서도 안 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| CQRS | 쓰기(command)와 읽기(query)를 서로 다른 경로·저장소로 분리하는 설계 |
| command / query 측 | 쓰기 담당 / 읽기 담당 |
| Zero Payload | 이벤트에 본문 없이 식별자만 담는 방식 |
| projector / 컨슈머 | 이벤트를 받아 읽기용 화면 데이터(read model)를 만드는 쪽 |
| 역참조(역조회) | 받은 식별자로 원본(command) DB를 다시 조회하는 것 |
| read 팬아웃 | 읽기 요청이 여러 갈래로 퍼지는 양 |
| ES(이벤트 소싱) / 리플레이 | 상태를 이벤트로 저장하고, 그 이벤트를 되감아 현재 상태를 재조립하는 방식 |
| thin/fat 페이로드 | 이벤트에 데이터를 적게 담기(thin) vs 많이 담기(fat) |
| point-in-time 파생 사실 | "그 시점 기준"으로만 값이 정해지는 계산 결과 |

**뭐가 문제냐 (와 왜 대부분 이미 막혔나):**
걱정의 핵심은 "가벼운 이벤트를 받으면 projector가 최신 상태를 알려고 command DB를 다시 뒤지게 되고, 그러면 CQRS가 없애려던 읽기-쓰기 결합이 뒷문으로 되살아나며 command 부하가 읽기 양에 비례해 는다"는 것이다. 그런데 이 경로 자체가 금지돼 있다:
- ADR-04(§Option C, §34-36, §52): "query가 command DB나 replica를 직접 조회"하는 방식을 검토했다가 "스키마 결합 안티패턴, ES에선 불가능"으로 배제. query는 query DB의 projection만 읽는다.
- RFC-002(§96·§109·§111): 다른 컨텍스트 데이터가 필요하면 미리 async로 만들어 둔 로컬 복사본(projection 또는 published-subscription)만 쓰고, "조회 시점에 원본을 동기 호출"하는 건 금지. → read 양에 비례해 command 부하가 는다는 전제가 성립하지 않음.
- RFC-021(§105·§111): 여러 애그리거트의 상대 시점에 달린 값은 "생산 시점에 이벤트 페이로드에 박제"해서, projector가 나중에 여러 스트림을 재구성(리플레이성 역조회)하지 않게 한다.

**남은 진짜 문제:** "이벤트에 데이터를 얼마나 담을 것인가(thin/fat), 그리고 ES냐 비-ES냐에 따라 어떻게 나눌 것인가"는 미결이다. RFC-003(§71·§162~166)이 "통합 이벤트라는 경계만 확정하고, 페이로드의 모양(thin/fat·직렬화·버저닝)은 별도 RFC로 분리"라고 명시적으로 미뤘는데, 그 thin/fat 결정이 어느 RFC에도 착지하지 않았다. RFC-022는 스키마 진화·업캐스팅, RFC-023은 wire 계약 테스트로, 둘 다 "모양 합의"일 뿐 "얼마나 담느냐" 판단이 아니다. ADR-10/09/11도 Zero Payload를 멱등 upsert 근거로만 쓸 뿐 리치니스를 정책으로 확정하지 않았다.

**지금 상태:** 부분결정. 불변식 붕괴 메커니즘은 ADR-04·RFC-002·RFC-021로 닫혔고, 페이로드 리치니스 정책만 열려 있다. RFC-003이 스스로 "별도 RFC로" 미룬 숙제인데 그 별도 RFC가 끝내 안 만들어졌다.

**그래서 뭘 해야 하나:** 좁은 토픽 RFC 하나로 미결 gap만 착지 — 제안: **RFC-024 통합 이벤트 페이로드 리치니스 정책(thin/fat 기준·ES/비-ES 분기)**. 담을 판단 기준과 ES/비-ES 경우의 분기를 명문화한다.

### C08 — 다중 소스·교차 스트림 프로젝션의 순서·원자성이 부분 갱신을 정상 동작으로 만든다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안
> **✅ 종결 (2026-07-05):** 순서·원자성·중복정규화·부분 갱신은 이미 의도된 사양으로 닫혀 있었고(ADR-22·RFC-021·ADR-09·RFC-002), 남았던 유일 gap = **쓰기/소비 병목**이었다. 탈출구를 **Parallel Consumer(`KEY` ordering, key=aggregate_id) — V1 선례**로 확정: 파티션 내 key 병렬로 병렬 상한을 파티션 수에서 분리 → "파티션 수=순서 계약=one-way-door" 함정 소멸. 재전달은 기존 event_id inbox 멱등이 흡수(EOS 불채택). DESIGN-008 §4.4 채택·§268 종결, ADR-09 line 71 주석. **새 RFC 없이 Design으로**(V1-검증 메커니즘, 논의 아닌 채택). 단일 프라이머리 **DB 쓰기** 핫스팟만 별개 이월 축(무트래픽이라 MED). — 같은 메커니즘이 **C28도 무력화**(아래 참조).

**한 줄로:** 화면 데이터 한 줄을 두 개의 이벤트 흐름(예: 예약 + 식당)이 함께 채우는데, 한 번에 한 이벤트씩만 반영하는 규칙 때문에 "한쪽만 반영된 상태"가 잠깐 정상으로 보인다. 이 부분 갱신 자체는 의도된 사양으로 이미 정리됐지만, 프로젝션 쓰기가 서버 한 대에 몰리는 병목의 탈출구는 아직 못 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| read model | 읽기 전용으로 미리 만들어 둔 화면용 데이터 |
| 스트림 | 한 종류의 이벤트가 흐르는 줄기 |
| 한 이벤트=한 트랜잭션+오프셋 커밋 | 이벤트 하나를 처리·저장하고 "여기까지 읽었다"를 함께 기록하는 규칙 |
| 원자성 | 여러 갱신이 전부 되거나 전부 안 되거나 |
| 멱등 upsert / LWW | 같은 걸 여러 번 넣어도 결과가 같게 하는 저장 / 나중 값이 이김(Last-Write-Wins) |
| at-least-once | 최소 한 번 전달(중복 가능) |
| inbox / event_id 멱등 컨슈머 | 이미 처리한 event_id를 기억해 중복을 걸러내는 장치 |
| saga | 여러 애그리거트에 걸친 진짜 불변식을 순서대로 조율하는 절차 |
| competing consumers | 같은 그룹의 여러 컨슈머가 파티션을 나눠 병렬 소비 |
| 파티션 수 | 병렬 처리 상한. 순서 보장 단위이기도 함 |
| 프라이머리 / 레플리카 | 쓰기 담당 DB / 읽기 복제본 DB |

**뭐가 문제냐 (와 무엇이 이미 정해졌나):**
"두 스트림이 한 read model 행을 갱신할 때 한쪽만 반영된 부분 갱신이 정상이 되고, 합류 지점의 순서·중복을 누가 정규화하며, 어느 시점 스냅샷을 보여줄지가 침묵됐다"는 걱정이다. 핵심은 이미 결정됨:
- ADR-22(§56-60): 프로젝터 정확성은 애그리거트별 순서 + 멱등 upsert + 버전 가드로 확보하고, "교차-애그리거트 적용 순서는 정확성 요구가 아니다(멱등이 흡수)". 부분 갱신은 결국 수렴하는 정상 상태.
- RFC-021(§105·§111): 시점에 민감한 파생 값은 페이로드에 박제해 재구성을 없앰. 진짜 교차 불변식은 saga.
- ADR-09(§54-64): 파티션 키=aggregate_id로 애그리거트별 순서, at-least-once + event_id 멱등 컨슈머/inbox로 사실상 한 번 효과. 합류 중복 정규화 주체가 명확.
- RFC-002(§118-126): "방금 쓴 걸 바로 못 볼 수 있다"를 버그 아닌 기본 사양(최종 일관성)으로 못 박음.

**남은 진짜 문제 — 쓰기 병목:** 프로젝션 쓰기가 단일 프라이머리에 몰린다. 소비 확장은 레플리카로는 안 되고 competing consumers로만 되는데(DESIGN-008 §85-89), 그 병렬 상한이 파티션 수이고 "파티션 수=순서 계약"이라 나중에 늘리려면 무중단 토픽 마이그레이션(고비용)뿐이다. DESIGN-004 §188은 "인스턴스 분할 금지 + 단일 프라이머리 쓰기"가 탈출구를 미리 닫았다고, DESIGN-008 §268은 이를 "초기 파티션 추정 실수의 벌칙을 최대치로 키운 설계"라고 스스로 미해결 약점으로 표기했다. 또 "일반 교차-스트림 읽기에서 어느 시점 스냅샷을 보여줄지"는 명시 read 정책 대신 최종 일관성 수용으로 대체돼 있다.

**지금 상태:** 부분결정. 순서·원자성·중복정규화·부분 갱신은 의도된 사양으로 닫혔다. C08 문장 자체가 DESIGN-004 Weakness 절(§185)에서 그대로 온 것으로, 설계 문서가 쓰기 병목을 "후속 검토 대상" open item으로 명시 보류 중이다.

**그래서 뭘 해야 하나:** 새 RFC — **프로젝션 쓰기 처리량 확장: 파티션 계약과 단일 프라이머리 병목의 탈출구**. 파티션 초기 추정이 틀렸을 때의 증설 방법(고비용 토픽 마이그레이션 외 대안)과 단일 프라이머리 쓰기 병목의 해소책을 정한다. "어느 시점 스냅샷" gap은 대부분 최종 일관성 수용 + point-in-time 박제로 흡수되므로 이 RFC나 후속 관측 RFC에서 흡수 가능. 실트래픽이 없어 우선순위는 MED.

### C14 — read-your-writes를 Non-Goal로 미뤘으나 핵심 여정(202 취소·예약 직후 조회)이 이미 예외 후보
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안
> **🏷 RFC 착지 (2026-07-05, [[RFC-030-read-freshness-command-response-contract]]):** 순수 논의라 "논의=RFC"로 열어 계약화했다. 핵심 전환 — **RFC-012 "202 기본"을 동기 권위 응답(201/200 + 바디)으로 부분 supersede**: command는 커밋 시점에 권위 결과를 쥐므로("CQRS ≠ 비동기 쓰기") 202로 버릴 이유 없음. gap ① 예외 승격 = 여정별 **신선도 등급**(A 권위바디/B 낙관/C 토큰/D bounded)로; gap ② 202 결과 채널 = 사가·외부 게이트(결제·승인)로 **축소**(채널 구체는 결제/사가 RFC 이월); gap ③ 파이프라인 역제약 = 동기 프로젝션·write측 읽기 **봉인**(부분 V1 회귀라 최후 수단). read-after-write 토큰 = RFC-014 `sequence_no` 재사용(취소도 자동 해소). 정확성은 read gap과 무관(RFC-014 동기 불변식)임을 계약 전제로 못박음. **Design(DESIGN-013·004) 반영 + ADR 비준 대기.**

**한 줄로:** "내가 방금 쓴 걸 바로 보이게 할지"를 나중에 정하기로 미뤘는데, 정작 "예약 직후 내 예약 목록 보기"와 "취소 결과 확인"은 미룰 수 없는 핵심 화면이고, 결과를 어떻게 확인시켜 줄지(폴링/SSE 등)도 안 정해서 계약의 절반이 비어 있다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| read-your-writes | 방금 내가 쓴 변경을 바로 다시 읽었을 때 반영돼 보이는 성질 |
| Non-Goal | 이번 문서 범위 밖으로 밀어둔 항목 |
| 202 (Accepted) | "요청 접수함, 처리 결과는 아직"이라는 즉시 응답 |
| 최종 일관성 | 지금 당장은 아니어도 잠시 뒤엔 반영되는 성질 |
| 동기 프로젝션 / 버전 토큰 / command 직접 읽기 | read-your-writes를 특정 화면에만 예외로 보장하는 세 가지 수단 |
| 폴링 / SSE / 웹소켓 | 결과를 계속 물어보기 / 서버가 밀어주기 / 양방향 실시간 통신 |
| 프로젝션 파이프라인·트랜잭션 경계 | 화면 데이터를 만드는 처리 흐름과 그 처리 단위 |

**뭐가 문제냐:**
① **핵심 여정이 이미 예외 후보다.** "예약 확정 직후 내 예약 목록", "202로 접수된 취소의 결과 확인"은 부수 엣지가 아니라 사용자가 반드시 지나는 경로다. 그런데 read-your-writes를 "나중에 화면별로 증명되면 별도 ADR로 승격"으로 미뤄뒀다(DESIGN-004 §3, §4.7). RFC-002 line 126은 "예약 직후 목록처럼 명백한 후보가 있으면 RFC 단계에서 예외로 인정해도 된다"며 문만 열어두고 실제로 승격하지 않았고, 예고된 신규 ADR "읽기 신선도 예외 정책"은 21개 ADR 중 존재하지 않는다(RFC-INDEX line 23).
② **결과 조회 채널이 통째로 비었다.** RFC-012/DESIGN-013 §4.2가 "command 기본 응답 = 즉시 202"를 확정하면서, 202를 받은 클라이언트가 자기 쓰기 결과를 확인하는 채널(폴링/SSE/웹소켓)은 Non-goal로 미뤘다. 동기 응답을 버리는 되돌리기 어려운 결정은 확정했는데, 확인 방법은 열어둔 것이다. 나중에 결론이 "폴링만 실용적"으로 나면 취소 한 번마다 수백ms~수초 폴링 왕복이 UX 기본값이 된다(DESIGN-013 §Weakness line 192).
③ **선택이 거꾸로 파이프라인을 제약한다.** 예외 수단(동기 프로젝션/버전 토큰/command 직접 읽기)을 뒤늦게 고르면, 그 선택이 이미 굳은 프로젝션 파이프라인·트랜잭션 경계를 거꾸로 제약한다. "나중에 못 고를 것을 나중에 고르겠다고 선언한 셈"(DESIGN-004 §Weakness line 184).

**지금 상태:** 부분결정. 정책 골격(기본 202 + 기본 최종 일관성 + 예외는 증명된 화면만)은 섰지만, 핵심 여정에 대한 예외 승격과 202 결과 조회 채널은 결정 공백이다. 이 concern은 DESIGN-004 §184·DESIGN-013 §192에 거의 그대로 적힌 저자 자신의 Devil's-Advocate 노트로, 문서가 긴장을 인지·기록만 하고 해소하지 않았다. ADR-04 line 55도 "예외 화면 목록"을 명시 미결로 남겼다.

**그래서 뭘 해야 하나:** 새 RFC/ADR로 (1) "예약 직후 목록·202 취소 결과 확인"을 read-your-writes 예외 화면으로 지금 승격할지 결정하고 (2) 각 예외 화면에 어느 수단(동기 프로젝션/버전 토큰/command 직접 읽기)을 쓸지 정하며 (3) 202 결과 조회 채널(폴링/SSE/웹소켓)을 확정 — 특히 폴링만 남는 최악 케이스를 계약이 감당하는지 검증한다. 예고된 ADR "읽기 신선도 예외 정책"을 실제로 생성한다.

### C19 — 크립토 셰딩의 물리 잔존·백업 전파·at-rest 평문·DR 복구 완결성이 보장되지 않는다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안
> **✅ 종결 (2026-07-06) — 새 RFC 없이 DESIGN-016 확정:** 크립토 셰딩의 두 문제를 분리 — **삭제 가능성**(불변 로그에서 PII 지우기)은 per-subject 키 파기로 이미 해결됐고, **탈취 기밀성**만 열려 있었다. 확정 전략(사용자 결정): **① at-rest 평문(폭탄 돌리기) → 봉투 wrap 채택** — `key_material`을 **DB 밖 마스터 키 1개(K8s secret)로 감싸 저장**, DB 통째 유출돼도 마스터 없이 복호 불가(DESIGN-016 §4.1). overhead는 마스터 인메모리 + 언랩 캐시로 실질 0. 대안(평문 키·Vault·AAD split) 기각. **③ 백업 전파 → 키 테이블 짧은 보존**으로 셰딩 창 bounded(DESIGN-016 §4.1 분리 스키마). **AAD → 안 씀**(per-subject 키가 이미 스코프, §4.2). **② InnoDB 물리 잔존·binlog 포렌식 → 프로토타입 범위 밖**(실 PII 없음, "내부=신뢰"로는 안 적음). **④ 오주입 물리 제거 → case-by-case(ADR-18 §50)**, **⑤ blind index 누출 → 마이너 이월**. DR 시 PII 프로젝션 빈 값 = 의도된 결과(ADR-18 §34)로 이미 조정됨. 완전 KMS·자동 회전은 규제 실재 시 졸업.

**한 줄로:** 개인정보를 "키를 버려서 못 읽게 만드는" 방식으로 지우기로 했는데, 그 키가 디스크·백업·복제본에 진짜로 사라지는지, 그리고 그렇게 지운 뒤 재난 복구를 하면 데이터가 온전히 돌아오는지가 아직 확실히 정해지지 않았다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 크립토 셰딩 | 개인정보(PII)를 암호화해 두고, 지우고 싶을 때 원문 대신 "복호화 키"만 파기해 영구히 못 읽게 만드는 삭제 방식. |
| key_material | 그 복호화 키가 실제로 담긴 값. 이게 평문으로 노출되면 삭제 효과가 무너진다. |
| 봉투 암호화 | 데이터 키를 다시 상위 "마스터 키"로 한 번 더 감싸(래핑) 저장하는 방식. 키 테이블이 통째로 읽혀도 마스터 키 없이는 못 푼다. |
| at-rest 평문 | 저장된 상태(디스크)에서 암호화 없이 그대로 놓인 데이터. |
| InnoDB DELETE | MySQL의 삭제. 실제로는 즉시 물리 삭제가 아니라 논리 삭제라, undo 로그·데이터 페이지·SSD에 원본이 한동안 잔존한다. |
| binlog / PITR / standby | binlog=DB 변경 이력 로그, PITR=특정 시점 복원, standby=복제 대기 서버. 셋 다 "과거 데이터의 사본"을 품는다. |
| 프로젝션 | 이벤트로부터 조립해 두는 조회용 읽기 모델. PII에 의존하면 키가 파기된 뒤 재구축 시 빈 값이 된다. |
| blind index | 암호화된 값을 검색하려고 만든 HMAC 해시 색인. 값 자체 대신 "존재 여부"를 흘릴 수 있다. |

**뭐가 문제냐:** 키를 파기해도 그 파기가 모든 사본에 미치지 않으면 삭제가 무효가 된다. ① key_material을 봉투 암호화 없이 그냥 키 테이블에 두면, 그 테이블 하나가 읽히는 순간 전 개인정보가 복호된다(at-rest 평문). ② MySQL의 DELETE는 논리 삭제라 undo 로그·페이지·SSD에 평문 키가 남을 수 있다. ③ 방금 파기한 키가 어제 뜬 백업, binlog, PITR 재료, standby 복제본에는 여전히 살아 있는데, 이 사본들로 "파기를 소급 전파"하는 메커니즘이 설계에 없다. ④ 반대로 재난 복구를 하면 PII 프로젝션은 이미 키가 없어 빈 값으로 살아나는데, 이게 "완전 복구"라는 서사와 부딪힌다. ⑤ 실수로 잘못 넣은 PII를 물리적으로 제거할 경로도, blind index가 값의 존재를 누출하는 문제 대책도 없다.

**지금 상태:** 부분결정. 재난 복구 시 PII 프로젝션이 빈 값이 되는 것은 결함이 아니라 의도된 결과로 조정됨(ADR-18 §34: "1급 보호는 이벤트 스토어만, 파생물은 재구축", 복원은 이벤트 시계는 되돌리되 키 시계는 안 되돌림). 봉투 암호화 미도입은 ADR-11이 §99 미결(TBD)로 "규제 요구가 실재할 때 도입하는 졸업 경로"라며 의식적으로 유보하고 위협을 접근통제에 맡겼다. 반면 파기 키의 백업·binlog·standby 소급 전파는 RFC-005(논점4)·RFC-017(§56-57)이 "원칙은 정하되 실제 백업 도구로 구현 가능한지는 Design/운영에서 검증"으로 유보했고, InnoDB DELETE의 물리 잔존은 어느 문서도 다루지 않아 완전 open이다. 오주입 PII 물리 제거(ADR-18 §50 "사례별 판단")와 blind index 존재 누출(DESIGN-016 Weakness)도 문서가 스스로 남긴 미해결 숙제다.

**그래서 뭘 해야 하나:** 한 RFC로 (1) 파기한 키를 백업·binlog·PITR·standby 등 모든 사본에 소급 전파하는 구체 메커니즘, (2) InnoDB 논리 삭제 잔존(undo/페이지/SSD)을 실제로 없앨 방법 또는 봉투 암호화로 위협을 낮출지 여부, (3) 오주입 PII 물리 제거 경로, (4) blind index 존재 누출 완화 — 이 open 항목들을 확정한다.

### C22 — query 측 수평 권한상승·역할 게이트 단일지점 방어가 개발자 규율·엣지 단일점에만 의존
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안

**한 줄로:** "남의 데이터를 못 보게" 막는 장치가 지금은 개발자가 매번 조건을 손으로 붙이는 규율과 관문 한 곳에만 기대고 있어서, 새 코드 한 곳이 그 조건을 빠뜨리거나 관문을 우회하면 전량이 새어나간다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| query 측 | 데이터를 읽는(조회) 쪽. 반대로 command 측은 바꾸는 쪽. |
| 수평 권한상승 | 같은 등급의 다른 사용자 데이터에 손대는 것(예: 판매자 A가 판매자 B 예약을 봄). |
| WHERE owner_id 스코프 | 조회 SQL에 "내 것만" 거르는 조건(`WHERE owner_id = 나`)을 붙여 남의 것을 안 보이게 하는 방식. |
| RLS (Row-Level Security) | DB가 행 단위로 "누가 어떤 행을 볼 수 있나"를 강제하는 기능. 개발자가 조건을 빠뜨려도 DB가 막아준다. |
| 스코프 인터셉터 | 모든 쿼리에 스코프 조건을 자동으로 끼워 넣는 공통 장치(프레임워크 강제). |
| 역할 게이트 | 요청의 역할(USER/SELLER/ADMIN)을 검사하는 관문. "엣지"=게이트웨이 같은 입구 한 곳. |
| defense-in-depth | 방어를 한 겹이 아니라 여러 겹으로 두는 것(엣지에서 한 번, 앱에서 또 한 번). |
| NetworkPolicy / mTLS | "게이트웨이를 거친 트래픽만 앱에 닿게" 네트워크로 강제하는 장치. |

**뭐가 문제냐:** ① 조회 보호가 "각 핸들러가 `WHERE owner_id`를 꼭 붙인다"는 규율에만 기댄다. 새 핸들러를 만든 개발자 한 명이 이 조건을 빠뜨리면, 그 화면에서 전 사용자 데이터가 노출된다. DB가 강제하는 RLS나 조건을 자동 주입하는 인터셉터가 없어서 누락을 잡아줄 안전망이 없다. ② 역할 검사를 게이트웨이(엣지) 한 곳에만 두고 앱에서의 이중 검사를 후속으로 미룬 채 Accepted 상태다. 게이트웨이를 우회해 앱에 직접 닿는 경로가 하나라도 열리면, 역할이 검증되지 않은 요청이 그대로 처리된다.

**지금 상태:** 부분결정. 문제를 인지·논의는 했으나 프레임워크 강제 장치는 구현 사이클로 미뤄 열려 있다. ADR-17 Q-2는 "스코프가 쿼리의 구조적 일부라 빠뜨릴 자리가 없다"고 주장하지만 이는 핸들러별 명시 규율에 기댄 진술이고, RLS나 기본 스코프 인터셉터는 어디에도 결정되지 않았다. 유일하게 "강제"라 부른 것(프로젝터가 스코프 키 컬럼을 채움)조차 "ArchUnit/Konsist에 얹을지"로 ADR-17 미결(line 63)에 위임됐다. 역할 게이트 이중화(defense-in-depth)도 ADR-17 미결(line 60)이 명시적으로 구현 사이클로 미뤘다. 게이트웨이 우회는 RFC-020이 모델 A 의무로 "신원 헤더 strip + NetworkPolicy '게이트웨이만 앱 도달'"을 못박아 위험을 정면으로 다뤘으나, 그 강제 장치의 구체 구현은 RFC-020 Non-goal(line 74)로 09-deployment-runtime에 위임돼 아직 확정된 강제물이 아니다.

**그래서 뭘 해야 하나:** 한 RFC로 (1) 새 핸들러가 스코프 조건을 빠뜨려도 막을 프레임워크 강제(RLS 채택 여부 또는 기본 스코프 인터셉터)를 정하고, (2) 역할 게이트를 엣지 단일점에 둘지 앱에서 이중 검사(defense-in-depth)할지 결론내며, (3) 게이트웨이 우회 차단 강제물(헤더 strip 규칙·NetworkPolicy/mTLS)을 "의무"에서 "확정된 구현 결정"으로 끌어올린다.

### C23 — 소유권 판단의 결과적 일관성 창이 조회 유출과 command 인가 우회를 동시에 열고, 도메인에 역할 어휘가 샌다
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, 새 RFC 없음)**

> **✅ 종결 (2026-07-06) — 새 RFC 없이 구현 사이클 위임.**
> 세 소주제 모두 "지금 추상적으로 정할 결정"이 아니라 코드가 생길 때 정해지는 것이라 사전 RFC 고정은 과설계로 판단.
> - **③ 도메인 역할 어휘 누출** — 애그리거트가 `ROLE_ADMIN`을 직접 알지 vs 핸들러가 플래그로 넘겨 도메인은 자원 상태만 알지는 **핸들러를 실제 구현할 때 정할 코드 형태** 문제. 계층이 어떻게 변할지 모르는 상태에서 A/B 못 정함. (DESIGN-014 §6 "역할 어휘 경계" bullet에 기록됨)
> - **② stale 클레임 창** — 토큰 TTL 정책으로 창 이미 좁힘. 표준 관심사. (DESIGN-014 §Risks 행에 기록됨)
> - **① 양도 창 command 우회** — 유일하게 correctness 이빨 있으나, 이 시스템에서 식당 소유권 양도가 사실상 없는 플로우. command 측 재확인은 그 핸들러 존재 시 자원 민감도 분류로 값싸게 결정. (DESIGN-014 §6 "민감도 분류" bullet에 기록됨)
> 셋 다 DESIGN-014에 백로그/리스크로 **기록 완비** → 잊힘 방지 됨, 결정은 구현 사이클. 관련: RLS(저장소 계층 인가)는 ①에 걸쳤으나 스택 MySQL이라 미채택(DESIGN-014 §5 기록).

**한 줄로:** 식당 주인이 바뀌는 순간부터 시스템이 새 주인을 인식하기까지 짧은 시차가 있는데, 이 시차 동안 옛 주인이 "볼 수 있는" 것만 문서가 다뤘고 "취소·변경까지 실행할 수 있는" 문제는 안 다뤘다. 게다가 소유권 규칙이 도메인 코드에 보안 역할 이름을 끌고 들어와 계층 분리를 어긴다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 결과적 일관성(창) | 변경이 모든 곳에 즉시 반영되지 않고 잠깐 옛 상태가 남는 시간대. 그 시간대가 "일관성 창". |
| 조회 유출 | 그 창 동안 옛 주인이 남의 것을 잠깐 더 "보는" 문제. |
| command 인가 우회 | 그 창 동안 옛 주인이 취소·변경 같은 "행위"를 성사시키는 더 심각한 문제. |
| 클레임 스냅샷 | 토큰 발급 시점의 역할을 토큰 안에 박아둔 것. 발급 후 역할이 강등돼도 토큰 만료 전까지 옛 권한이 유효. |
| stale 창 | 위처럼 실제 권한과 토큰 속 권한이 어긋나 있는 시간대. |
| 소유권 불변식 | "이 자원은 주인 본인 OR 충분한 권한의 역할만 손댄다"는 규칙. |
| 역할=엣지 분리 | 보안 역할(ROLE_ADMIN 등)은 입구에서만 판단하고, 도메인 코드는 자원 상태만 알게 하는 계층 원칙. |

**뭐가 문제냐:** ① 식당 양도 후 새 주인 정보가 퍼지기 전 짧은 시차 동안, 문서 본문(§4.4)은 옛 주인이 잠깐 더 "보는" 조회 유출만 다뤘다. 그러나 소유권을 각 컨텍스트의 이벤트/상태로 판단하므로 command 측 소유권도 stale해서, 옛 주인이 그 창 동안 예약 취소·변경 command를 실제로 성사시킬 수 있다. ② 역할이 강등돼도 이미 발급된 토큰이 만료될 때까지는 옛 권한이 살아 있어, ADMIN 전역 강제 취소 같은 고위험 행위조차 그 stale 창에 노출된다. ③ "주인 본인 OR 충분권한 역할"이라는 불변식 때문에 애그리거트(도메인)가 ROLE_ADMIN 같은 보안 역할 어휘를 알아야 해서, "역할은 엣지에서만, 도메인은 자원 상태만"이라는 분리를 도메인 내부에서 위반한다.

**지금 상태:** 부분결정. 세 우려 모두 DESIGN-014에 이미 기록됐으나 결정이 아니라 미결/백로그 위임 상태다. command 측 stale 소유권은 본문이 아니라 §Weakness bullet 4(line 191)가 "옛 주인이 취소·변경 command를 성사시킬 수 있다"고 문서 스스로 지적했을 뿐 해소책이 없고, 민감도 분류·command 측 재확인은 §6과 ADR-17 미결로 넘어갔다. 클레임 stale 창은 §4.5/§7에서 인지했으나 완화를 인프라 백로그 T-13으로 위임했고, §Weakness bullet 3(line 189)이 이게 미착수임을 확인한다. 도메인 역할 어휘 누출은 §4.2에서 형태만 확정하고 "도메인이 보안 어휘를 알지 여부"는 §6·ADR-17에서 명시적으로 미결로 남겼다. ADR-17은 방향(역할=엣지/소유권=앱, 이벤트로 양도 모델링)은 정했으나 세 완화의 구체안은 구현 사이클/백로그(T-13·RFC-019)로 위임했다. RFC-015는 종결됐으나 이 세부 완화 결정을 담지 않고 실질 설계를 DESIGN-014로 이관했다.

**그래서 뭘 해야 하나:** 한 RFC로 (1) 양도 일관성 창 동안 command 측 소유권 재확인을 어느 자원에 요구할지(민감도 분류), (2) 클레임 stale 창 완화(토큰 정책·강제 취소 반영 방식)를 백로그에서 실제 결정으로, (3) 소유권 불변식에서 도메인이 보안 역할을 직접 알게 할지 vs 핸들러가 플래그로 넘겨 도메인은 자원 상태만 알게 할지의 경계 — 이 셋을 확정한다.

### C25 — 무상태 refresh·재사용 탐지·단일 refresh 컬럼·denylist 포기가 세션 보안 기본기를 훼손
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, 새 RFC 없음)**

> **✅ 종결 (2026-07-06) — 새 RFC 없이 DESIGN-017 스코프 결정 + ADR-20 정합화.**
> "훼손"은 과장 — 재사용 탐지(`current_refresh_jti`)는 이미 채택돼 있었고(RFC-019/020·DESIGN-017), 대부분은 스코프·값 문제였다.
> - **① access TTL 값** — 값 하나, DESIGN-014 stale 창과 함께 정하기로 이미 위임됨. 설계 구멍 아님. (그대로)
> - **② 디바이스 바인딩/지문** — 단일 세션 + 짧은 TTL이면 optional defense-in-depth. 필수 아님.
> - **③ 다기기 불가·로그아웃 폭탄** — **다기기 동시 세션은 애초 요구 아님** → 주체당 단일 활성 세션이 의도된 스코프임을 DESIGN-017 §4.3에 명문화. "기능 상실"이 아니라 명시적 스코프. 남는 건 같은 기기 병렬 탭 rotation 경합(§6 구현 사이클 위임).
> - **④ denylist 포기** — ADR-20 D-2 의도 채택(기결).
> - **⑤ ADR-20 vs DESIGN-017 "재사용 탐지" 모순** — 정합화 완료: ADR-20이 "재사용 탐지=서버 상태 필요=기각"으로 전제했으나, 재사용 탐지는 Redis must-not-evict가 아니라 쓰기 모델 단일 `jti` 컬럼이면 충분 → 기각 대상은 denylist/서버 사본에 한정, 재사용 탐지는 채택. ADR-20(Proposed) 결정절·트레이드오프·포기 대안·미결 항목에 정정 주석 반영.
> 편집: DESIGN-017 §4.3 스코프 노트 + Weakness ②③ 해소 주석 + Changelog / ADR-20 정합화 4곳.

**한 줄로:** 로그인 토큰을 서버에 사본 없이 발급하기로 해서, 토큰이 탈취되면 만료될 때까지 막을 길이 없는데 그 "막을 길 없는 시간"의 길이(access TTL)조차 이 문서에서 안 정했고, 한 사람이 여러 기기로 로그인하는 정상 상황을 지금 설계가 구조적으로 못 받는다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| access / refresh 토큰 | access=짧게 쓰는 출입증, refresh=그걸 새로 발급받는 재발급권. |
| 무상태 refresh | refresh 토큰의 사본을 서버 DB에 안 두는 방식. 서버가 개별 토큰을 무효화할 수단이 없다. |
| rotation | refresh를 쓸 때마다 새 refresh로 교체하는 것. 탈취돼도 계속 새로 돌려막을 수 있으면 위험. |
| access TTL | access 토큰의 유효 시간. 이게 곧 "탈취 후 통제 불가 노출 창"의 크기. |
| 재사용 탐지 | 이미 교체된 옛 refresh가 다시 제출되면 "탈취"로 보고 세션을 끊는 것. |
| current_refresh_jti | 주체당 유효한 refresh를 딱 하나만 기록하는 단일 컬럼. 불일치=탈취로 판단. |
| 디바이스 바인딩 | 토큰을 특정 기기·IP·UA에 묶어 다른 환경에서 못 쓰게 하는 보완책. |
| denylist | 무효화된 토큰 목록. 있으면 탈취 즉시 전역 무효화가 가능. |

**뭐가 문제냐:** ① 서버에 사본이 없으니 refresh가 탈취되면 만료까지 무제한 rotation이 가능한데, 그 노출 창 크기를 결정하는 access TTL 값이 이 문서에서 안 정해졌고 디바이스 바인딩 같은 보완책이 전무하다. ② `current_refresh_jti`를 "주체당 하나"로 두면, 병렬 탭·여러 기기로 동시에 로그인하는 정상 경합에서도 서로가 서로를 "탈취"로 오인해 전 세션이 끊기는 로그아웃 폭탄이 된다. ③ 같은 단일 컬럼 구조라 애초에 다중 디바이스 동시 세션을 구조적으로 지원하지 못한다. ④ denylist 포기를 "V1도 못 했으니"로 정당화하지만, 계정 탈취·강제 차단 대응에서 즉시 전역 무효화는 기본기다.

**지금 상태:** 부분결정. 결정된 것: denylist 즉시 폐기 포기는 ADR-20이 D-2로 의도 채택(V1 미구현+짧은 TTL 근거, 요구 입증 시 부활 예외경로)했고, "탈취 하나로 무제한 rotation" 트레이드오프도 ADR-20 트레이드오프절에서 명시 수용했다. 재사용 탐지·강제 로그아웃을 `current_refresh_jti` 단일 컬럼으로 푸는 메커니즘은 RFC-019(논점3·결정요약#4)·RFC-020에서 확정됐다. 미결로 남은 것(C25 지적과 정확히 겹침): (1) 노출 창 크기를 정하는 access TTL 구체 값은 RFC-019 Non-goal·ADR-20 미결·D-017 §6에서 모두 후속 design_doc으로 이관돼 여기서 안 정해짐, (2) 디바이스 바인딩·IP/UA 핀·토큰 지문 보완책은 세 문서 어디에도 언급 없음(전무), (3) 병렬 탭·다기기 정상 경합의 오탐 처리(유예·grace window·refresh 체이닝)와 병렬 /refresh 동시성은 D-017 §6·Risk표에서 "후속 사이클로 넘김", (4) 단일 jti가 다중 디바이스를 못 받는 문제는 D-017 Weakness §3이 "리스크로도 다루지 않았다"고 스스로 인정 — 어떤 ADR/RFC도 해소 안 함. (부수 관찰: ADR-20 결정절은 "재사용 탐지 유지=기각"이라 적었으나 RFC-019/020/D-017은 이를 채택 — 문서 간 모순이 존재하며 이는 concern 해소가 아님.)

**그래서 뭘 해야 하나:** 한 RFC로 (1) access TTL 구체 값을 확정해 노출 창 크기를 명시하고, (2) 디바이스 바인딩/토큰 지문 등 보완책 채택 여부를 정하며, (3) 병렬 탭·다기기 정상 경합에서 로그아웃 폭탄을 막을 오탐 처리(grace window·체이닝)와 병렬 /refresh 동시성 정책을 결정하고, (4) 단일 jti를 유지할지 다중 디바이스 세션을 지원할 구조(디바이스별 세션 레코드 등)로 갈지, 그리고 (5) ADR-20 결정절과 RFC-019/020 간 "재사용 탐지" 모순을 정합화한다.

### C27 — 솔로 운영자의 self-managed 인프라 운영 표면과 진실원천 HA·relay failover 미스매치
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, 새 RFC 없음 — 오버)**

> **✅ 종결 (2026-07-06) — 새 RFC 없이 DESIGN-010 스코프 확인.**
> C27이 잠그자는 네 항목(RPO 목표·failover SLI·PDB·리소스쿼터·브로커 규격)은 전부 **프로덕션 운영 수치**인데, 이 시스템은 무트래픽 학습 프로토타입이라 지킬 실트래픽·실데이터·사용자가 없다. "사고를 막을 하한선 없음" 프레임 자체가 존재하지 않는 프로덕션 stakes를 가정 → 오버.
> - **① 브로커 규격·PDB·디스크 / ④ 리소스쿼터** — 배포 시점 config 값(Strimzi 매니페스트 sane default). 사전 RFC 형식화는 과설계.
> - **③ relay failover SLI** — SLI는 측정할 트래픽이 있어야 의미. 무트래픽엔 잴 대상 없음.
> - **② event_store RPO** — 유일한 ES 학습 지점이나, *deliberate* ≠ *RPO=0 동기복제*. 비동기 binlog 꼬리 유실을 의식적으로 수용+기록한 ADR-018이 이미 학습으로서 올바른 처리. RPO=0은 프로덕션 비용이지 학습 요구 아님.
> 네 항목 다 D-010 §Weakness에 후속 검토 대상으로 기록돼 있고, §6에 "운영 수치 유예 = 무트래픽 학습 스코프의 의식적 결정" 명문화 + 프로덕션 전환 시 재검토 트리거로 못 박음. 편집: DESIGN-010 §6 스코프 노트 + Changelog.

**한 줄로:** 혼자 운영하는 사람이 직접 값을 정해야 하는 인프라 설정(카프카 브로커 규격, 디스크, 장애 복구 등)을 "나중에 재보고 정하자"로 미뤄뒀는데, 그 미뤄둔 것들이 하필 사고가 나면 진짜 데이터를 잃거나 시스템이 멈추는 지점들이다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| self-managed | 카프카를 클라우드 관리형(MSK 등)이 아니라 내가 직접 설치·운영. 학습 목적으로 일부러 고른 방식. |
| KRaft | 카프카가 자기 상태를 관리하는 신형 방식(구형 ZooKeeper 대체). |
| PDB (PodDisruptionBudget) | 쿠버네티스에서 "한 번에 몇 개까지 파드를 내려도 되는가" 한도. |
| 리밸런스 | 카프카가 파티션(작업 조각)을 노드들 사이에 다시 나누는 과정. 잘못되면 폭주. |
| 진실원천(event_store) | 모든 사실의 원본 저장소. 여기 데이터가 사라지면 복구 불가. |
| binlog standby | MySQL 원본(primary)의 변경 로그를 예비 서버에 비동기로 복사해 두는 이중화. |
| tail 유실 | primary가 죽는 순간, 예비 서버로 아직 복사 못 한 "마지막 꼬리" 데이터가 사라짐. |
| RPO | 사고 시 "얼마나 최근까지의 데이터는 지킨다"는 목표. RPO=0이면 한 건도 안 잃음. |
| relay | event_store의 이벤트를 읽어 밖으로 내보내는 중계기. |
| failover | 죽은 서버 대신 예비가 넘겨받는 전환. 그 사이 공백 시간이 생김. |
| 평탄 namespace | 앱과 DB·카프카 같은 상태저장(stateful) 컴포넌트를 한 칸에 몰아둔 배치. 하나가 터지면 옆도 휘말림(폭발 반경↑). |

**뭐가 문제냐:**
① 카프카를 직접 운영하기로 했는데(ADR-12), 브로커 수·복제 팩터·PDB·스토리지클래스·리소스 한도를 전부 "구현 사이클에서 정함"으로 미뤘다. 규격이 안 정해진 브로커가 디스크 풀(가득 참)이나 리밸런스 폭주를 내면, 학습이 아니라 실제 장애 대응이 된다. 위험은 D-010 Risks 표에 "Strimzi KRaft 운영 미숙"으로 적혀만 있고 정량적 완화책이 없다.
② event_store가 모든 사실의 원본인데, 그 이중화를 비동기 binlog로 뒀다(ADR-13). primary가 죽으면 아직 예비로 안 넘어간 마지막 꼬리 이벤트가 사라진다 = 진실원천이 소실된다. ADR-18은 "잃는 건 마지막 복제분 이후 꼬리뿐"이라며 이 유실을 명시적으로 수용하고, "진실원천의 RPO가 0이어야 하는가"라는 핵심 질문은 T-18 백로그로 미뤘다.
③ relay는 replicas:1(한 대)이라 죽으면 예비가 넘겨받을 때까지 프로젝션(읽기 모델 갱신)이 멈춘다. 그런데 DB HA에는 failover 소요시간 SLI가 있어도(§4.6) relay에는 없다 — relay 가용성 공백을 재는 지표가 어느 문서에도 없다.
④ 앱과 stateful을 한 namespace에 몰아둬(RFC-007 논점1) 하나가 자원을 잡아먹으면 옆이 휘말리는데, 리소스쿼터·PDB 경계가 정의돼 있지 않다.

**지금 상태:** 부분결정. 큰 방향은 ADR로 잠겼으나(self-managed 채택, binlog=HA 고정, 단일 namespace 기본), 우려가 지목한 구체 수치·규격·실패 모드는 의식적으로 측정/구현 사이클로 미뤄졌다. C27의 네 항목은 D-010 자체 "Weakness(Devil's Advocate)" 절(라인 248·249·252·253)을 거의 그대로 옮긴 것이고, 문서 스스로 "리뷰용 반박 정리이며 결정을 뒤집지 않는다. 각 항목은 후속 검토 대상"(라인 256)이라 적어 미해결임을 인정한다. relay failover SLI는 어느 ADR/RFC도 정의하지 않아 사실상 open이다.

**그래서 뭘 해야 하나:** 한 RFC로 다음을 확정한다. (1) 진실원천 event_store의 RPO 목표 — 꼬리 유실을 정말 수용하는가, 아니면 동기 복제가 필요한가. (2) relay 가용성 목표와 failover 소요시간 SLI. (3) 카프카 브로커 규격·PDB·디스크 임계의 최소 안전값(측정 전이라도 사고를 막을 가드레일). (4) 앱↔stateful 리소스쿼터·PDB 경계. 지금은 "재보고 정하자"만 있고 사고를 막을 하한선이 없다.

### C30 — 검증 환경이 게이트로 거는 다중브로커·HA 특유 위반을 재현할 수 없는 구성 모순
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, 새 RFC 없음 — 오버)**

> **✅ 종결 (2026-07-06) — 새 RFC 없이 DESIGN-012 §6.4b 스코프 확인.**
> 트리아지 스스로 인정했듯 "재현 못 하는 환경에 T-05를 CI 게이트로 건다"는 틀렸다 — 결정적 하위집합(멱등성·재생 등가·동시성)만 CI 필수고 HA 위반은 이미 카오스/비차단으로 연기. 남는 갭 둘도 오버:
> - **HA/다중브로커 위반 로컬 재현 불가** — 분산 장애 모드는 원리상 로컬에서 값싸게 재현 안 됨. 게다가 이 프로토타입은 다중브로커/failover를 **프로덕션으로 안 돌린다(C27)** → 걱정하는 실패 모드가 실제 배포에서 발생도 안 함. 학습은 그 주제 공부 시점의 타깃 카오스/수동 실험으로. 상설 다중브로커 CI 게이트는 과설계.
> - **결정적 CI 게이트는 옳고 유지** — 쓰기 모델 correctness 보호. 희석 금지.
> - **relay 경로 등가성(compose vs k3s)** — 유일한 구체 실item이나 "결정"이 아니라 k3s relay 실재 시 추가할 테스트 항목(구현 사이클).
> D-012 §Weakness(패리티 환상·경로 분기·단일 브로커 축)에 이미 기록됨 + §6.4b에 내재적·수용된 스코프로 명문화. 편집: DESIGN-012 §6.4b + Changelog.

**한 줄로:** 테스트 환경을 브로커 한 대·복제본 한 개·예비 없음으로 단순하게 꾸며놨는데, 정작 실제 사고는 브로커가 여러 대이고 이중화가 있을 때만 생긴다. 그래서 "운영 버그를 로컬에서 미리 잡자"는 목표가 가장 필요한 지점에서 성립하지 않는다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| effectively-once | "결과적으로 정확히 한 번" 처리된 것처럼 보이게 하는 보장. at-least-once(최소 한 번)에 멱등성(중복 무시)을 얹어 만든다. |
| effectively-once 위반 | 중복 소비·재전달로 그 보장이 깨지는 상황. |
| 리밸런스 중 중복 소비 | 카프카가 파티션을 재분배하는 순간 같은 메시지를 두 번 먹는 현상. |
| 리더 전환 재전달 | 파티션 리더(주 담당 브로커)가 바뀔 때 메시지가 다시 전달되는 현상. |
| 복제 지연 신선도 | 예비 DB로 데이터가 늦게 복사돼 읽기 모델이 오래된 값을 보는 문제. |
| Testcontainers / k3s | 테스트용 임시 인프라. k3s는 경량 쿠버네티스. |
| 패리티(parity) | 로컬 환경과 운영(EKS) 환경이 얼마나 똑같은지. |
| T-05 | "무손실·effectively-once 보장" 요건. |
| 결정적(deterministic) | 같은 입력이면 항상 같은 결과 — 그래서 CI에서 매번 안정적으로 돌릴 수 있는 것. |
| CI 필수(차단) 게이트 | 통과 못 하면 머지를 막는 관문. |
| 카오스 테스트 | 일부러 파드를 죽이거나 네트워크를 끊어 장애를 재현하는 실험. |
| relay 경로 등가성 | compose에서는 relay가 앱 안 스케줄러로 돌고, k3s에서는 별도 파드로 도는데 — 두 실행 방식의 동작이 같은지. |

**뭐가 문제냐:** 위에 적은 세 종류의 위반(리밸런스 중 중복 소비, 리더 전환 재전달, 복제 지연 신선도)은 전부 브로커가 여러 대이거나 이중화가 있을 때만 나타난다. 그런데 로컬 검증 환경(Testcontainers/k3s)은 브로커 1대·복제 1·standby 생략으로 확정돼 있어(§2.1) 이 위반들을 아예 만들어낼 수 없다. 또한 compose에서 인프로세스로 도는 relay와 k3s에서 별도 파드로 도는 leader relay는 동시성·트랜잭션·중복발행 경로가 다른데, 두 실행 모드가 같게 동작하는지 확인하는 테스트가 테스트 피라미드에 없다(§Weakness line 430).

단, 우려의 강한 표현 하나는 문서와 어긋난다. "위반을 못 만드는 환경에 T-05를 CI 필수로 건다"는 정확하지 않다 — 실제로는 멱등성·재생 등가·동시성 같은 결정적 하위집합만 CI 필수이고, HA/다중브로커 특유의 위반 검증은 카오스로 밀어 "정기/통합" 또는 비-차단으로 명시 연기했다(§5.7, §5.5). 그래도 남는 핵심 갭은 그대로다: 하필 사고가 나는 축(failover·리밸런스·ALB)을 로컬이 재현 못 하므로 "운영 버그를 로컬로 당긴다"가 가장 필요한 곳에서 안 통하고, relay 경로 등가성 테스트가 없다.

**지금 상태:** 부분결정. 관련 결정(패리티 축 단순화, 게이트 분류, 카오스 연기)은 내려졌으나 우려가 지적하는 갭 자체는 인지된 채 미해결이다. 세 축은 D-012 §Weakness(line 427·430·432)에 거의 축자적으로 적혀 있고, line 435에서 "결정을 뒤집지 않는 후속 검토 대상"으로 못박혀 있다. ADR(09/12/14)·RFC(003/009/017) 어디에도 이 재현불가 모순을 해소하는 결정은 없다.

**그래서 뭘 해야 하나:** 한 RFC로 정한다. (1) HA/다중브로커 특유 위반을 언제·어떤 환경에서 검증할 것인가 — 다중 브로커 로컬 구성을 둘지, 카오스 도입 시점을 언제로 못박을지. (2) compose relay와 k3s 파드 relay의 경로 등가성을 보장하는 테스트를 피라미드 어디에 넣을지. 지금은 "운영 버그 조기 검출"을 표방하면서 정작 그 버그가 나는 조건을 재현할 수단·시점이 비어 있다.

### C31 — 무거운 E2E 게이트·비-차단 관측·절대 SLO 부재로 게이트가 실효를 잃고 완만한 회귀가 누적
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, 새 RFC 없음 — laundering)**

> **✅ 종결 (2026-07-06) — laundering. 새 RFC 없이 D-012 미비준 태깅.**
> C31이 비판하는 대상(매 PR/머지 E2E 게이트·k6 매 실행·Chaos CI 편입)은 **사용자가 결정한 바 없는 AI 초안 케이던스**다. 사용자 명시: "E2E 한다고 한 적 없음, k6 매 CI 돈다 얘기 안 함, Chaos도." 확정된 건 차단성 *분류 원칙*(결정적=차단/무거운 분산=비-차단)뿐이고 실행 빈도·게이트 배치는 미결.

> - 절대 SLO·졸업 트리거도 케이던스가 정해져야 의미 → 테스트 인프라 실제 구축 시점(구현 사이클)에 함께 결정.
> D-012 §4.2 미비준 노트 + §5.3 태깅 + Changelog(1.2)로 초안임을 명문화. [[ai-draft-laundered-as-user-decision]] 계열. 이 laundering 이후 트리아지의 오버/미소유 전제는 사용자 위임(2026-07-06)으로 AI가 스스로 잡아 닫는다.

**한 줄로:** 매번 무거운 E2E 테스트를 돌리게 해놨더니 느리고 자꾸 실패해서 사람들이 건너뛰고 싶어지고, 성능 테스트는 "통과/실패 기준선" 없이 그냥 사람이 추세를 눈으로 보게 해서 조금씩 나빠지는 성능 저하가 매번 통과되며 쌓인다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| E2E | 처음부터 끝까지 전체를 실제로 돌려보는 통합 테스트. |
| ephemeral | 매번 새로 띄웠다 버리는 일회용 환경. |
| Awaitility 비동기 대기 | "결과가 나올 때까지 기다리는" 테스트 코드. 비동기라 느리고 타이밍에 민감(flaky). |
| flaky | 코드가 그대론데도 됐다 안 됐다 하는 불안정 테스트. |
| k6 | 부하(성능) 테스트 도구. |
| 비-차단(non-blocking) | 실패해도 머지를 막지 않는 관문. 참고용. |

**뭐가 문제냐:** ① 매 PR/머지마다 일회용 k3s + Strimzi + MySQL 2대를 띄우고 Awaitility 비동기 대기를 도는 E2E는 느리고 flaky하다 → 스킵·타임아웃 완화의 유혹을 부른다. ② k6(성능)와 Chaos를 비-차단으로 두고 절대 임계 없이 "추세를 사람이 읽는다"에 기대면, 매번 "지난번보다 아주 조금 나쁨"인 회귀가 계속 통과해 누적된다. 어제보다 5ms씩 느려지는 게 100번 쌓이면 500ms인데 각 PR은 다 통과한다. ③ 혼자 하는 환경에서 매번 추세 리포트를 읽는 규율이 유지된다는 보장이 없고, 언제 이걸 자동 차단 게이트로 "졸업"시킬지 시점 자체가 TBD다.

**지금 상태:** 부분결정. 잠근 부분: 게이트 차단성 분류 고정(Chaos/k6는 비-차단 관측, 대신 CI 아티팩트·추세 리포트로 매 실행 가시화 의무 — §4.2 line107), 커버리지는 후퇴 금지(ratchet) 고정(line108), E2E는 매 커밋이 아닌 PR/머지 시점에만 일회용 실행(§7 line198). 남은 갭이 정확히 C31이 짚는 것이다: (a) 절대 SLO는 "베이스라인 측정 후 결정"으로 명시 연기(line35, ADR-14 line60), (b) 자동 차단으로의 졸업 트리거 시점이 TBD(line107, Phase 5 line216), (c) 커버리지만 ratchet일 뿐 k6·Chaos 성능 회귀에는 절대 임계가 없음, (d) 솔로 추세 읽기 규율·E2E 게이트 완화가 충분한지 근거 없음 — 이 두 항목은 D-012 §Weakness 반박 3(line429)·5(line431)에 프로젝트 스스로 미해결 약점으로 등재했다. ADR-14는 아직 Proposed 상태다.

**그래서 뭘 해야 하나:** 한 RFC로 정한다. (1) k6·Chaos 성능 지표에 최소한의 절대 임계(또는 이전 대비 허용 하락폭 상한)를 걸어 완만한 회귀를 막을 것. (2) 비-차단 관측을 자동 차단 게이트로 졸업시키는 트리거를 구체 조건(베이스라인 N회 수집 후 등)으로 못박을 것. (3) 무거운 E2E를 매 머지에서 유지할지, 아니면 결정적 하위집합만 게이트로 남기고 전체 E2E는 릴리스 전으로 뺄지 — flaky·스킵 유혹을 줄이는 실질 대책. 지금은 "측정 후 결정"만 반복돼 결정 시점이 무한 연기되고 있다.

| 관측성(observability) | 시스템 안에서 무슨 일이 일어나는지 밖에서 들여다보는 능력(추적·메트릭·로그). |
| OTel Context | OpenTelemetry가 "이 요청은 어느 추적에 속한다"는 정보를 담아 코드 흐름을 따라 실어 나르는 통. |
| Context 전파 | 그 통을 비동기 경계(스케줄러·Kafka 리스너·@Async)를 넘겨 계속 이어주는 것. 안 이어지면 추적이 끊긴다. |
| taskDecorator / ContextSnapshot | 비동기 실행 시 Context를 복사해 넘겨주는 실제 수단. |
| traceparent | "이 이벤트가 어느 추적에 속하는가"를 나타내는 표준 ID 문자열. |
| 봉투(envelope) vs 페이로드 | 이벤트를 담는 겉봉투(헤더) 자리에 둘지, 내용물(본문)에 둘지. |
| event_store 영구 직렬화 | event_store의 이벤트는 한 번 저장하면 영원히 그 형태로 보관됨. |
| 업캐스팅(upcasting) | 과거에 저장된 옛 형식 이벤트를 최신 형식으로 읽어 올리는 변환. |
| correlationId / causationId | 같은 요청 묶음을 잇는 ID / "이 이벤트를 일으킨 원인 이벤트"를 가리키는 ID. |
| Tempo / Loki / Prometheus / Grafana | 각각 추적·로그·메트릭 저장·대시보드 도구(OSS 스택). |
| 배선(wiring) | 그 도구들을 실제로 배포하고 신호를 흘려보내 연결하는 작업. |
| 교차 조회 | 추적(Tempo)에서 관련 로그(Loki)로 건너뛰어 보는 것. 관측성의 핵심 효용. |

**뭐가 문제냐:** ① 규약은 "OTel Context가 전파 매체"라고 전제하는데, 그 Context가 스케줄러·Kafka 리스너·@Async executor 같은 비동기 경계에서 실제로 이어지는지는 "구현 사이클에서 검증"으로 미뤘다(§4.1). 하필 관측성이 가장 필요한 경계라, 안 이어지면 규약 전체가 종이 위에서만 성립한다. ② traceparent를 봉투 헤더에 둘지 페이로드에 둘지 미결이다(§4.3). 그런데 event_store는 이벤트를 영구 보관한다 — 나중에 위치를 바꾸면 과거 이벤트를 전부 재직렬화·업캐스팅해야 해서 되돌리기가 매우 비싸진다. 즉 지금 안 정하면 미래의 인질이 된다. ③ Tempo·Loki·Prometheus·Grafana의 배포·수집·대시보드 배선을 전면 보류했다(§3 Non-Goal, §4.7). 그래서 correlationId가 root span에 제대로 붙는지, Tempo→Loki 교차 조회가 실제로 되는지 같은 핵심 규약을 이 사이클 안에서 도구 위에서 확인할 방법이 없다.

**지금 상태:** 부분결정. 규약 층은 확정돼 있다 — 전파 매체=OTel Context/MDC(§4.1), correlationId/causationId/traceparent를 AbstractEvent 메타데이터로 의무화(§4.2·§4.3), correlationId를 root span 필수 attribute로 격상(§4.4), OSS 백엔드 스택 선택 고정(§4.7.7). 반면 C32가 짚는 세 항목은 문서가 의도적으로 미결/보류로 남겼고, C32는 사실상 DESIGN-011 자신의 Weakness(Devil's Advocate) 1·2·6번(line 232-237)을 재진술한 것이다. 이 미결을 해소하는 별도 ADR/RFC는 없다 — 관측성 전용 ADR이 없고, RFC-007은 SLI/배포 hook만 다루며 관측성 신호 정의는 RFC-008로 되넘긴다.

**그래서 뭘 해야 하나:** 한 RFC로 정한다. (1) traceparent를 봉투 헤더 vs 페이로드 어디 둘지 — 이건 event_store 영구성·업캐스팅과 얽혀 되돌리기 비싸므로 다른 것보다 먼저 못박아야 한다(DESIGN-003 스키마와 함께). (2) Context 전파를 각 비동기 경계(스케줄러·Kafka 리스너·@Async)에 실제로 잇는 구현과, 그것이 이어지는지 확인하는 최소 검증. (3) Tempo→Loki 교차 조회 같은 핵심 규약을 검증할 수 있을 만큼의 백엔드 배선을 언제 할지 시점을 못박기. 지금은 "규약은 정했으나 그것이 실제로 이어지는지·위치·검증"이 전부 열려 있다.

### C38 — 핫 슬롯 직렬화 구간이 사가 다단계 트랜잭션 길이가 되고 granularity 완화는 순환에 빠진다
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안  
> 🔴 **사용자 결정 대기 (GENUINE)** — 타임테이블 슬롯 애그리거트 granularity + 교차슬롯 불변식을 애그리거트 안 vs 사가로 (미세화→사가 순환 회피). 이벤트 스토밍

**한 줄로:** 인기 많은 예약 슬롯에 사람이 몰릴 때, 원래 우려는 "예약 확정 3단계 전체가 줄서서 느려진다"였는데 이건 이미 정해진 규칙이 반박한다. 다만 슬롯을 얼마나 잘게 쪼갤지, 그리고 그 비용이 실제로 얼마인지는 아직 아무도 안 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 핫 슬롯 | 같은 시간대·같은 자리를 여러 사람이 동시에 예약하려고 몰리는 인기 슬롯 |
| 락(lock) | 한 번에 한 명만 건드리게 문을 잠그는 것. 나머지는 줄 서서 기다림 |
| 직렬화 구간 | 락 때문에 한 줄로 세워져 순서대로만 처리되는 구간 |
| 애그리거트 | 함께 묶여 한 덩어리로 다뤄지는 도메인 단위(예: timetable 슬롯, payment, reservation 각각) |
| 사가(saga) | 여러 애그리거트에 걸친 일을 이벤트를 주고받으며 순차적으로 잇는 방식 |
| 즉시 일관성 vs 최종 일관성 | 즉시=그 자리서 딱 맞음(락으로 보장), 최종=조금 시차 두고 결국 맞음(사가로 흡수) |
| granularity | 애그리거트를 얼마나 잘게/굵게 나눌지의 크기 단위 |
| apply 리플레이 | 저장된 이벤트를 처음부터 다시 적용해 현재 상태를 재조립하는 것 |

**뭐가 문제냐:**
원래 우려는 "핫 슬롯에서 예약 확정의 timetable→payment→reservation 3단계 전부가 슬롯 락 뒤에 줄서서, 락이 잡고 있는 시간이 단순 저장 한 번이 아니라 3단계 분산 트랜잭션만큼 길어진다"였다. 그런데 정해진 락 규칙은 이렇다. 락이 감싸는 건 `lock(aggregate_id) → load(리플레이)=N개 → handle → append(N+1) → release` 딱 한 애그리거트의 append 하나뿐이다. payment·reservation으로 넘어가는 건 락 바깥에서 이벤트로 도는 사가(최종 일관성)라 줄서지 않는다. 즉 슬롯 락 뒤에 서는 건 timetable 슬롯의 SeatHeld append 하나이지 3단계가 아니다 — 이 헤드라인은 반박된다.

남는 두 갈래가 진짜 문제다. ① 슬롯을 더 잘게(예: 좌석 단위) 쪼개 경합을 줄이려 하면, "동시에 N석을 교차로 잡는" 불변식이 다시 사가로 넘어가 원래 피하려던 문제로 되돌아온다 — 순환. ② load 때마다 이벤트를 처음부터 다시 apply하는 리플레이 비용이 핫 스트림(경합 심한 슬롯)에서 얼마나 커지는지 숫자로 잰 적이 없다. 문서는 "학습 환경이니 명목상"이라고만 하고 절대 임계 숫자는 측정으로 미뤘다.

**지금 상태:** 부분결정. 락 경계·직렬화 메커니즘은 ADR-16·RFC-014에서 못박혀 헤드라인은 answered. 하지만 granularity 균형은 ADR-16 미결정 §의 "🌱 핫스팟 슬롯 granularity와 교차-슬롯 불변식의 사가 위임 균형"으로 이벤트 스토밍·05-aggregate-design에 위임됐고, RFC-014는 아예 non-goal(§75-76)로 뺐다. 리플레이×경합 정량화도 RFC-008 결정 6(§153-159)에서 측정 트리거로 미룸. 문서들이 스스로 남긴 숙제다.

**그래서 뭘 해야 하나:** 새 RFC로 (1) 슬롯 granularity를 어디까지 잘게 그을지와, 잘게 그었을 때 교차-슬롯 불변식을 사가로 넘길지의 균형을 확정, (2) 핫 스트림에서 리플레이 비용의 측정 방법·재검토 임계를 정한다. 락 경계 자체는 다시 열 필요 없다.

### C39 — 단일 Redis durability 등급 전제가 멱등 디듀프 must-not-evict 성격 및 미확정 상위 결정과 모순
`HIGH` · 판정 부분결정 · 처분안 새 RFC 제안  
> 🔴 **사용자 결정 대기 (GENUINE)** — 멱등 디듀프 상태를 어디에 — 자연 유니크 없는 생성 커맨드는 UNIQUE 백스톱이 없음. 손실허용 단일 Redis로 충분? 별도 durability/DB 백스톱?

**한 줄로:** 결제·예약 중복을 막는 "중복 방지 표식"을 Redis가 메모리 부족하면 그냥 지워버릴 수 있는데, 그러면 막으려던 중복이 다시 열린다. 이 표식은 "지워지면 안 되는" 성격인데도 "우리 Redis엔 지워져도 되는 것만 있다"고 단언해 정책이 자기모순이다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 멱등 디듀프 키 | 같은 요청이 두 번 와도 한 번만 처리하려고, 이미 처리했다고 표시해두는 Redis 표식 |
| durability 등급 | 데이터를 얼마나 끝까지 지켜줄지의 등급(지워져도 됨 vs 지워지면 안 됨) |
| eviction | Redis가 메모리 부족할 때 오래된 키를 자동으로 내다버리는 것 |
| allkeys-lru | 모든 키를 대상으로, 안 쓴 지 오래된 것부터 버리는 정책 |
| volatile-lru | TTL(만료시간)이 붙은 키만 골라 버리는 정책 |
| must-not-evict | 절대 버려지면 안 되는 성격 |
| UNIQUE 백스톱 | DB에 같은 값 두 번 못 넣게 막는 제약. 최후의 안전장치 |
| denylist | 즉시 로그아웃/차단 대상을 담아두는 목록 |
| DESIGN-017 | 인증 refresh 토큰 즉시 폐기를 들어내 must-not-evict 부담을 없앤 설계 |

**뭐가 문제냐:**
Redis 정책을 allkeys-lru 하나로 두면 메모리가 차는 순간 어떤 키든 버려질 수 있다. 그런데 멱등 디듀프 키는 그 짧은 윈도 동안 살아 있어야 중복 결제·예약을 막는다. 윈도 안에 evict되면 두 번째 요청이 "처음 보는 요청"으로 통과해 결제/예약이 이중으로 열린다. 즉 이 키는 준-must-not-evict인데, 결정 3은 "우리 Redis엔 손실 허용 상태뿐"이라 단언해 volatile-lru + 명시 TTL로 분리하지 않는다 — 자기모순.

락 키에는 방어가 있다. ADR-19는 "락은 liveness(경합 완화)일 뿐 safety가 아니고, 정확성은 (aggregate_id, sequence_no) UNIQUE가 최후로 막으니 락 키가 evict돼도 안전"이라 했다. 하지만 디듀프 키에는 그런 UNIQUE 백스톱이 없다 — 디듀프가 존재하는 이유 자체가 자연 유니크 불변식이 없는 생성 command를 지키려는 것이라서다. 게다가 이 단순화 전체가 "DESIGN-017이 즉시 폐기를 들어내 must-not-evict가 사라졌다"에 얹혀 있는데, DESIGN-017의 즉시 폐기 포기는 "요구가 입증되면 denylist 부활"이라는 조건을 달고 있다. 부활하면 must-not-evict 등급이 되살아나 단일 durability·단일 인스턴스 가정이 통째로 깨져 재설계가 필요하다.

**지금 상태:** 부분결정. 긴장은 여러 문서가 스스로 이름 붙였다 — DESIGN-018 §4.4(라인 119 ⚠ 경고)·§Weakness 5·6번(라인 261·263)이 이 우려와 거의 같은 문장으로 자기고발. 부활 경로도 §6.5(라인 170-172)에 확보. 하지만 디듀프 eviction 정책 확정과 volatile-lru+TTL 분리 여부는 DESIGN-018 §8 Phase 3, ADR-19 라인 59·61로, 부활 대응은 Phase 5·RFC-018 라인 130으로 후속에 열려 있다.

**그래서 뭘 해야 하나:** 새 RFC로 (1) 디듀프 키를 allkeys-lru에 그냥 태울지, volatile-lru + 명시 TTL로 분리할지 확정, (2) 디듀프 키 구성·윈도 길이 확정, (3) denylist 부활 시 durability·인스턴스·eviction 재설계 트리거와 대응을 미리 정한다.

### C46 — inbox 생략 자격·effectively-once가 검증 불가 전역 가정과 부분 보장에 기댄다
`HIGH` · 판정 부분결정 · ~~처분안 새 RFC 제안~~ → **✅ 종결 (2026-07-06, OVER)**: effectively-once 기결(ADR-09 D-A: at-least-once+멱등 inbox); inbox 균일 유지=안전 기본, skip 자격·파티션증설은 배포 위임, §6표 문구만

**한 줄로:** 어떤 소비자는 "중복 방지 장부(inbox)를 생략해도 된다"고 정했는데, 그 판단이 "메시지 순서가 절대 안 뒤집힌다"는 가정에만 기댄다. 이 가정은 운영 중 파티션을 늘리거나 재시도하면 국소적으로 깨지고, 컴파일러가 못 막는 사람 약속이라 조용히 read model이 오염된다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| inbox | 소비자 쪽에서 "이 메시지 이미 처리했나?"를 기록해 중복 처리를 막는 장부 |
| 멱등 upsert | 같은 걸 여러 번 넣어도 결과가 같아지는 저장(있으면 갱신, 없으면 삽입) |
| 순서 역전 | 나중 이벤트가 먼저 도착해 순서가 뒤바뀌는 것 |
| 파티션 키 | 메시지를 어느 줄(파티션)로 보낼지 정하는 기준. 같은 키는 같은 줄=순서 유지 |
| 리밸런싱 | 파티션을 소비자들에게 다시 나눠 배정하는 것 |
| relay 재시도 | 이벤트 중계기가 실패분을 다시 쏘는 것 |
| effectively-once | "결과 상태는 한 번 적용된 것과 같음". 배달 자체가 정확히 한 번이란 뜻은 아님 |
| 부수효과 | 외부 알림 발송처럼 상태 저장 밖에서 실제로 일어나는 일 |
| read model / 프로젝터 | 이벤트를 받아 조회용 화면 데이터를 만들어두는 것과 그걸 만드는 놈 |

**뭐가 문제냐:**
inbox 생략은 "순서 역전 없음 + 자연 멱등 upsert 동시 충족" 소비자만 자격이 있다고 정해졌다. 문제는 두 가지다.

① "순서 역전 없음"은 파티션 키가 같은 애그리거트를 같은 줄에 몰아넣어 순서를 지킨다는 가정에 전적으로 기댄다. 그런데 파티션을 증설하거나, 리밸런싱이 일어나거나, relay가 재시도하면 이 순서 보장이 국소적으로 깨진다. 게다가 "이 소비자는 순서 무풍지대다"라는 판단은 컴파일러가 강제 못 하는 사람 사이의 약속이라, 운영이 바뀌면 아무 에러 없이 read model이 조용히 틀어진다. write(append) 쪽엔 (aggregate_id, sequence_no) UNIQUE와 "더 과거로 덮지 마라" 순서 가드가 있지만, 이건 쓰기 측 보장이지 프로젝터 read model의 생략 안전성과는 연결돼 있지 않다.

② effectively-once는 upsert로 상태가 수렴하는 경우에만 성립하는 부분 보장이다. §4.8은 부수효과(외부 알림 등)가 두 번 발사될 수 있음을 인정하는데, §6 요약 표는 "프로젝터도 부수효과도 다 effectively-once"인 것처럼 균일하게 보여 오도한다. 부수효과의 1회성은 inbox/outbox로 감싸야 얻는 부채이지 전달 보장이 아니다.

**지금 상태:** 부분결정. 정책 뼈대는 ADR-09 §결정·RFC-003 논점1에서 확정. 하지만 "어떤 소비자가 실제로 순서 무풍지대인가의 판정 기준"은 ADR-09 §미결정(L98)에 TBD로 남았고, RFC-003 §85·§87은 〔근거 확인/보강 필요〕를 달고 컨슈머별 검증을 Design으로 위임. 순서 붕괴·사회적 규약 위험은 D-008 자신의 Weakness(§260-262)에 devil's-advocate로 자기고발돼 있을 뿐 어느 ADR/RFC도 해소하지 않았고, §6 표 오도와 "부수효과 보장=래핑 부채지 전달 보장 아님" 재프레이밍도 미결정.

**그래서 뭘 해야 하나:** 새 RFC로 (1) 어떤 소비자가 inbox 생략 자격이 있는지 컨슈머별 판정 기준을 명문화하고, 파티션 증설·리밸런싱·relay 재시도 하에서도 순서 가정이 유지되는지 검증 규율을 붙인다. (2) §6 요약 표를 프로젝터(상태 수렴)와 부수효과(별도 래핑 필요)로 분리해 보장 등급을 정확히 표기. (3) 비-멱등 부수효과의 inbox/outbox 귀속을 유형별로 확정한다.

### C15 — 9개 컨텍스트 수동 도메인↔JPA 매핑의 반복 비용과 데이터 정합성 결함 위험 과소평가
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 매핑 방식 기결(ADR-07·RFC-010) — 잔여는 라운드트립/필드커버 테스트 규율, 설계결정 아님

**한 줄로:** 도메인 객체와 DB 저장 객체를 손으로 하나하나 변환하기로 정했는데, 필드가 바뀌면 변환 코드도 사람이 같이 고쳐야 하고 빠뜨리면 런타임/테스트에서야 걸린다. 문서는 이걸 "생산성 비용"으로만 적고, 매핑 누락이 데이터가 틀어지는 정합성 결함으로 이어지는 위험은 안 다룬다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 도메인↔JPA 매핑 | 순수 도메인 객체와 DB 저장용 JPA 엔티티 사이를 서로 변환하는 코드 |
| MapStruct | 매핑 코드를 자동 생성해주는 라이브러리 |
| hexagonal 경계 | 도메인/응용/인프라 계층을 갈라놓는 선. 흐려지면 계층 규칙이 무너짐 |
| 보일러플레이트 | 비슷비슷하게 반복 작성해야 하는 뻔한 코드 |
| genesis/프로젝션 | (마이그레이션 맥락) 초기 상태 생성 매핑, 조회 모델 생성 매핑 |
| 정합성 결함 | 매핑 누락 등으로 저장/조회 데이터가 실제와 어긋나는 것 |
| 왕복(round-trip) 테스트 | 도메인→JPA→도메인으로 되돌려 원본과 같은지 확인하는 검증 |

**뭐가 문제냐:**
MapStruct류 코드젠은 Kotlin 스택과 마찰이 있어서, 공통 매퍼 추상은 hexagonal 경계를 흐려서 각각 기각하고, 컨텍스트별 손 매핑을 "분리의 정당한 대가"로 채택했다 — 여기까지는 결정이 문서와 정확히 일치한다. 문제는 그 대가를 "생산성/유지비"로만 프레이밍한다는 점이다.

구체적 실패 모드는 이렇다. 도메인 객체에 필드를 하나 추가하면 도메인→JPA, JPA→도메인 양쪽 변환 함수를 사람이 손으로 같이 고쳐야 한다. 하나를 빠뜨리면 컴파일은 통과하고, 그 필드는 저장이 안 되거나 조회 때 비어서 나온다 — 조용한 데이터 정합성 결함이다. 게다가 마이그레이션 맥락에선 8개+ 컨텍스트 × (커맨드 + 프로젝션 + genesis) 만큼 변환 코드가 반복되어, 이 반복 자체가 누락 버그의 상당한 원천이 된다. 그런데 Risk 표는 하방을 "변환 코드 발생/유지비"로만 적고, 매핑 누락 → 정합성 결함이라는 실패 모드나 그걸 잡을 왕복 테스트 같은 탐지 장치를 명시하지 않는다.

**지금 상태:** 부분결정. 매핑 방식 결정 자체는 ADR-07·RFC-010에서 닫혔다. 하지만 정합성-위험 갭은 열려 있다 — ADR-07 트레이드오프(49-51행)·미결정(58행), RFC-010 논점2(107-118행)·리스크 표(49-56행) 모두 하방을 "보일러플레이트/유지비"로만 프레이밍한다. ADR-14/RFC-009 테스트 전략에도 도메인↔JPA 왕복·누락 검증 규율이 없고, RFC-013의 "정합성"은 V1↔V2 병행창 동기 얘기지 매핑 누락과 무관하다. 결정이 스스로 남긴 숙제라기보다, 결정이 한 각도(생산성)만 봐서 다른 각도(정합성)가 안 걸린 갭이다.

**그래서 뭘 해야 하나:** 매핑 방식 결정을 다시 열 필요는 없으니 노트로 완화한다. (1) 테스트 전략(ADR-14/RFC-009)에 도메인↔JPA 왕복 테스트와 필드 커버리지 검증을 규율로 추가해, 매핑 누락이 런타임이 아니라 테스트에서 잡히게 한다. (2) ADR-07/RFC-010 리스크 표에 "매핑 누락 → 데이터 정합성 결함(조용한 누락)"을 별도 실패 모드로 명기하고 탐지 장치를 링크한다.

### C17 — event_store 무한 성장·스냅샷 재생성과 콜드 파티션 이관·업캐스팅 누적 비용의 충돌
`MED` · 판정 부분결정 · 처분안 노트 완화

**한 줄로:** 옛날 이벤트를 싼 창고(S3)로 옮기기로 이미 정했는데, 스키마가 바뀌어서 과거 상태를 처음부터 다시 계산해야 할 때 그 "이미 옮겨버린 옛 이벤트"를 다시 불러와야 하는 상황과, 매번 계산할 때마다 옛 포맷을 새 포맷으로 바꾸는 비용이 쌓이는 문제를 아직 안 정했다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| event_store | 일어난 사건을 지우지 않고 계속 덧붙여 쌓기만 하는(append-only) 저장소. 그래서 무한정 커진다. |
| 스냅샷 | 특정 시점의 상태를 통째로 저장해 둔 사진. 처음부터 다 계산하지 않고 사진 이후 것만 계산하면 되게 해 준다. |
| 리플레이 | 저장된 사건들을 처음부터 다시 적용해서 현재 상태를 재조립하는 것. |
| 파티셔닝 | 큰 테이블을 생성월 같은 기준으로 조각내어 관리하는 것. |
| 핫/콜드 | 핫 = 자주 쓰는 빠른 DB, 콜드 = 잘 안 쓰는 옛 데이터를 옮겨 두는 싼 창고(S3). |
| 업캐스팅 | 예전 포맷으로 저장된 옛 이벤트를 읽을 때 현재 코드가 이해하는 새 포맷으로 변환하는 것. |
| p99 가드레일 | 100번 중 99번은 이 시간 안에 끝나야 한다는 성능 기준선. 넘으면 조치. |

**뭐가 문제냐:**
① 스키마(데이터 구조)가 바뀌면 옛 스냅샷은 버리고 이벤트를 처음부터 다시 재생해 새로 만든다고 정했다(RFC-004 논점8). 그런데 오래 산 애그리거트는 그 옛 이벤트가 이미 콜드 창고(S3)로 빠져서 핫 DB에 없다. 결국 "핫에서만 쓴다"던 전제를 깨고 콜드에서 옛 이벤트를 강제로 다시 끌어와야 하는데, 이 상황을 어떻게 처리할지가 어느 결정 문서에도 없다.
② 이벤트를 읽을 때마다 옛 포맷을 새 포맷으로 바꾸는(업캐스팅) 비용이 든다. 수백만 개 이벤트를 재조립하면 그 변환이 그 수만큼 곱해진다. 그런데 "재조립 p99가 50ms를 넘으면 조정"이라는 성능 기준선은 스냅샷+증분만 계산에 넣었지, 이 업캐스팅 누적 비용은 계산에 안 넣었다.

**지금 상태:** 부분결정. 세 갈래 중 "무한 성장 대비 파티셔닝·아카이빙이 아예 없다"는 갈래는 사실이 아니다 — RFC-004 논점4/5/6이 생성월 기준 시간 파티셔닝 + 도메인 종결상태+90일 유예로 핫/콜드 경계 + S3 이관을 이미 결정했고 ADR-05·DESIGN-009 §4/§6이 반영한다(이 갈래는 기결). 나머지 두 갈래(재생성×콜드 강제 호출, 업캐스팅×p99 미계상)는 문서가 스스로 gap으로 인정했다: DESIGN-009 §Weakness 라인 318("이 상호작용이 문서에 없다"), 라인 320("업캐스팅 누적 비용을 재구축 경로에서 계산하지 않았다"), 그리고 라인 332에서 "본 절은 결정을 뒤집지 않는 후속 검토 대상"이라 명시. RFC-022는 업캐스터 카탈로그만 다루고 재구축 경로 누적 비용 가드레일은 안 정했다.

**그래서 뭘 해야 하나:** 노트로 완화하되, 두 질문을 후속 검토 항목으로 남긴다. (1) 스냅샷 폐기 후 재생성할 때 필요한 옛 이벤트가 콜드로 빠져 있으면 어떻게 불러올지(복원 경로). (2) 재조립 p99 가드레일에 업캐스팅 누적 비용을 포함시켜 다시 계산할지. 성장·아카이빙 축은 이미 닫혔으므로 새 RFC 없이 노트 수준으로 추적한다.

### C18 — 스냅샷 N값·reconciliation·업캐스팅 전략이 예약 도메인 실제 스트림 특성과 자기모순
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: §6.3은 핫패스 한정·reconciliation은 백그라운드라 자기모순은 오독; 짧은 스트림 스냅샷 희소=의도, N값은 측정 위임+재검토 트리거 有

**한 줄로:** "이벤트 100개마다 상태 사진을 한 장 찍는다"는 규칙을 정했는데, 예약은 사건이 몇 개 안 생겨서 사진이 거의 안 찍힌다 — 이게 헛돈인지 의도인지, 그리고 검증용 전체 재계산이 성능 규칙과 부딪히는지를 다시 짚은 것. 다만 이 긴장들은 대부분 이미 "의도된 결정"이거나 "수치는 운영에서 측정해 정한다"로 처리돼 있다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| N값 | 이벤트 몇 개마다 스냅샷(상태 사진)을 한 장 찍을지 정하는 주기. 기본 N=100. |
| 스트림 | 한 애그리거트에 쌓인 이벤트들의 흐름. "짧다" = 사건이 몇 개 안 된다. |
| seq 0 리플레이 | 맨 처음(순번 0)부터 전부 다시 재생해서 상태를 계산하는 것. |
| reconciliation | 스냅샷+증분으로 계산한 결과와 처음부터 전부 재생한 결과를 대조해 스냅샷이 맞는지 검증하는 것. |
| 표본률 | 전체 중 얼마를 뽑아 검증할지의 비율. |

**뭐가 문제냐:**
① N=100인데 예약은 사건이 짧아서 사진이 사실상 안 찍힌다. 그럼 스냅샷 인프라가 무용해 보인다 — 짧으면 어차피 처음부터 재계산해도 싸서 스냅샷이 불필요하고, 길게 만들면 파티션 경계 문제가 생기는 딜레마다.
② reconciliation은 "처음부터(seq 0) 전부 재생한 결과와 대조"로 정의되는데, §6.3 성능 규칙은 "핫 경로에서 seq 0 전체 리플레이가 일어나면 안 된다"고 금지한다. 정의와 금지가 겉보기엔 모순으로 보인다.
③ 검증 표본률·주기의 구체 숫자를 "운영 측정에 맡긴다"고만 해 얼버무린 것처럼 보인다.

**지금 상태:** 부분결정. 대부분은 이미 결정됐거나 의도적 위임이다. ①의 "짧은 스트림엔 사진이 거의 안 찍히는 게 단점이 아니라 의도"는 RFC-004 논점1(라인 86·88·90)에서 실제 채택된 결정이다. ②의 "자기모순"은 오독이다 — §6.3 금지는 핫 경로 한정이고, reconciliation은 배경/오프피크 배치로 층위가 분리돼 있다(DESIGN-009 §6.3 라인 216·217, §9.1 Glossary). ③의 표본률·N 절대값은 RFC-004 논점3·§9.2·NG1에서 의도적으로 운영 측정에 위임했고 재검토 트리거(p99>50ms→k6 스윕)까지 붙였다. 다만 핵심 긴장(스냅샷이 싼 곳엔 불필요/필요한 곳엔 위험, reconciliation 신뢰도-비용 상호잠식)은 DESIGN-009 §7 라인 252·253과 Weakness 라인 322·328에서 문서가 스스로 "후속 검토"로 남겨 완전 해소는 아니다.

**그래서 뭘 해야 하나:** 노트로 완화. 새 결정은 필요 없다 — 정책·메커니즘은 정해졌고 절대 수치는 운영 측정 위임이 명시적 의도다. 다만 (1) 예약처럼 짧은 스트림에서 스냅샷 인프라가 실효가 있는지, (2) reconciliation 검증 범위에 콜드를 포함할지(신뢰도 vs 비용)를 운영 측정 후 재검토 항목으로 추적한다.

### C20 — 콜드 이벤트의 핫 키 저장소 종속이 재해복구·키 수명주기·감사 요구와 충돌
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, OVER)**: 셰딩 무결성 기결(RFC-005/ADR-11/D-016); 키스토어 DR·다년 보존·감사 as-of는 프로덕션 운영 수치 위임

**한 줄로:** 옛 데이터를 싼 창고(S3)에 옮길 때 내용은 암호문만 두고 해독 열쇠는 빠른 DB에만 둔다 — 그래서 열쇠 DB가 사라지면 창고의 개인정보를 영원히 못 푼다. 수년 뒤 열쇠를 어떻게 계속 찾을지, 감사·규제 담당자가 어떻게 옛 상태를 조회할지가 아직 안 정해졌다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 셰딩(shredding) | 개인정보를 지우는 대신 그 사람 전용 암호 열쇠를 파기해 영원히 못 풀게 만드는 삭제 방식. |
| self-contained | 콜드 데이터 하나만으로 스스로 해독이 되는 상태. 지금은 열쇠가 핫에 따로 있어 아니다. |
| 키 저장소 | 암호 열쇠(key)를 보관하는 곳. 여기선 핫(빠른 DB)에 있다. |
| 미파기 주체 | 아직 삭제(셰딩)되지 않은 정상 활성 사용자. |
| key_id | 어떤 데이터를 어느 열쇠로 암호화했는지 가리키는 열쇠 식별자. |
| 로테이션 | 보안을 위해 열쇠를 주기적으로 새 것으로 교체하는 것. |
| as-of 조회 | "그 시점에 상태가 어땠나"를 되짚어 보는 과거 시점 조회(temporal). |
| PII | 개인식별정보(이름·연락처 등). |

**뭐가 문제냐:**
① 콜드(S3) 본문을 풀려면 항상 핫 키 저장소를 참조해야 한다. 그래서 콜드 데이터는 혼자서 못 풀고, 재해로 키 저장소가 통째로 유실되면 아직 삭제하지 않은 정상 사용자의 콜드 PII까지 영원히 복호 불능이 된다(가용성 리스크).
② 수년 뒤 옛 이벤트를 재생하려면, 그 사이 로테이션·마이그레이션을 거친 옛 key_id를 여전히 찾을 수 있어야 한다. 그런데 지금은 "열쇠를 무한 보존한다"는 가정만 있고 그 조회 보장 설계가 없다.
③ 과거 시점(as-of) 조회를 운영·디버깅 전용(개발자만, API 비노출)으로 정했는데, 감사·분쟁은 대개 CS·법무·규제 같은 비개발자가 "그 시점 상태"를 물어야 한다. ops 한정이면 매번 개발자 수동 조회에 의존하게 돼 규제 대응이 늦어질 소지가 있다.

**지금 상태:** 부분결정. 셰딩 정합성 자체(콜드엔 암호문만, 열쇠는 핫에 잔류, 열쇠 1회 파기로 핫·콜드 동시 셰딩)는 RFC-005 논점7·ADR-11·D-016 §4.4·D-009 §2.2에서 확정됐다. 그러나 C20의 세 갈래는 모두 결정이 아니라 명시적 유보다. (1) 재해복구: RFC-017 논점3이 "진짜 미결 논점"으로 못박고 Design 검증으로 위임, ADR-18 라인 51·63도 후속으로 위임 — 완화 방향은 "키 별도 백업"뿐이고 복원 경로 설계는 없다. (2) 키 수명주기: ADR-11이 로테이션 정책·콜드 키 셰딩 경로를 미해결로, RFC-005 논점4는 방향만 잡고 수치는 별도 ADR로 위임, D-009 §6.5는 TBD·NG5로 Non-Goal 처리. (3) as-of ops 한정과 감사 모순은 D-009 §Weakness 라인 326, D-016 §Weakness 라인 195에서 문서가 스스로 미해결로 지적했다.

**그래서 뭘 해야 하나:** 노트로 완화하되 세 질문을 추적. (1) 키 저장소 유실 시 미파기 주체 콜드 PII 복원 경로를 어떻게 설계할지(RFC-005 키 백업 스코프와 함께). (2) 수년 뒤 로테이션·마이그레이션을 거친 옛 key_id를 어떻게 계속 조회 보장할지. (3) 감사·규제(비개발자) 조회 요구를 as-of ops 한정 정책이 어떻게 감당할지. 셰딩 자체는 기결이므로 새 RFC 없이, 이미 열려 있는 위임 지점(RFC-005/RFC-017/ADR-18)으로 추적한다.

### C21 — YAGNI 비대칭·학습가치 정당화·트래픽 발생 시 재검토 경로 폐쇄
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 전환 트리거는 ADR-16/05가 명시 개방 — '재검토 경로 폐쇄' 반증; 학습 프레임은 승인된 프로젝트 전제

**한 줄로:** "지금 안 쓸 기능은 만들지 않는다(YAGNI)"며 인프라는 엄격히 자르면서, 정작 가장 어려운 스택(이벤트소싱+리플레이+스냅샷+분산락)은 미리 다 도입한 게 앞뒤가 안 맞아 보인다는 지적. 다만 이 비대칭은 문서가 이미 이름 붙여 논의했고, 재검토 경로도 실제로는 열려 있다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| YAGNI | "You Aren't Gonna Need It" — 지금 필요 없는 건 미리 만들지 않는다는 원칙. |
| 비대칭 | 인프라엔 YAGNI를 엄격히 적용하면서 최고난도 ES 스택엔 안 적용하는 불균형. |
| 낙관 락 / 비관 락 | 동시 수정 처리 방식. 낙관 = 일단 진행하고 충돌 시 재시도, 비관 = 미리 잠그고 진행. |
| build-vs-buy | 직접 만들지(build) 완성품을 사서 쓸지(buy)의 선택. |
| 전용 제품 | ES를 직접 구현하는 대신 쓸 수 있는 기성 이벤트스토어 제품/솔루션. |
| 구현 정확성 리스크 | 리플레이·업캐스팅·동시성을 직접 짜다가 틀리게 만들 위험(성능·규모 리스크와 별개). |

**뭐가 문제냐:**
① 프로토타입엔 실트래픽이 없다. 그러면 "낙관 락이 성능상 공짜로 이득"이라는 논변도 성립 안 하지만, 동시에 "비관 락이 안전해서 낫다"는 논변도 성립 안 한다(대칭 논변). 결국 비관 락을 정당화할 근거로 남는 건 "학습가치"뿐인데, 그게 충분한 방어인지 따지지 않았다.
② §7이 "낙관으로 회귀하지 않는다"고 못박아, 나중에 실트래픽이 생겨도 다시 저울질할 경로를 스스로 닫아버린 것처럼 보인다.
③ 전용 제품을 안 쓰고 리플레이·스냅샷·업캐스팅·동시성을 직접 재발명하는 리스크가 "규모(성능 한계)" 관점으로만 논증되고, "직접 짜다 틀릴 위험(구현 정확성)"은 build-vs-buy 저울에 안 올랐다.

**지금 상태:** 부분결정. (1) 비대칭 자체는 RFC-001 §맥락 라인 76이 명시적으로 이름 붙였고 RFC 전체를 비용 트레이드오프로 프레이밍하며 ADR-02가 ES에도 컷을 적용(선택적 ES: reservation·timetable·restaurant만, lookup 제외)한다. 다만 "ES 스택 자체를 왜 도입하나"의 방어는 RFC-001 §6 라인 171의 "학습가치" 단일 축에만 의존 — 이 지적은 맞다. (2) 그러나 "재검토 경로 폐쇄" 주장은 반증된다: ADR-16 라인 63 "실트래픽 시 재검토 트리거", ADR-05 라인 59 "트래픽 증가 시 전환 기준"이 경로를 명시적으로 열어두고, "낙관 회귀 안 함"(ADR-16 L1′ 라인 40)은 Redis 다운 시 폴백을 낙관이 아닌 DB 비관 락으로 고정한다는 뜻일 뿐 전면 봉쇄가 아니다 — concern의 과대 해석. (3) 구현 정확성 리스크는 ADR-05 라인 50-54가 규모/코드책임으로만 논증하고 정확성을 build-vs-buy 요인으로 저울질하지 않았다. ADR-14 Option B·RFC-009가 정확성을 테스트로 완화하나 이는 도입 결정 근거가 아닌 사후 안전망이다.

**그래서 뭘 해야 하나:** 노트로 완화. 재검토 경로가 열려 있다는 반증 때문에 concern의 핵심 전제 하나가 무너지므로 새 RFC는 불필요하다. 다만 두 가지를 노트로 남긴다: (1) ES 스택 도입의 상위 정당화가 "학습가치" 단일 축에 의존한다는 점을 명시적으로 인정할 것, (2) 직접 구현의 정확성 리스크를 (성능·규모뿐 아니라) 향후 전용 제품 전환 기준(ADR-05 라인 59)에 저울 요인으로 포함할 것.

### C26 — CSRF 방어를 SameSite Lax+body 비대칭에만 걸고 in-memory access 강제 UX·부하 비용 미계량
`MED` · 판정 부분결정 · 처분안 노트 완화

**한 줄로:** 로그인 세션을 지키는 방어 장치가 "다른 사이트에서 온 요청은 쿠키를 조심히 다룬다"는 브라우저 기본 규칙 하나에만 의존하고 있는데, 이 규칙만으로는 못 막는 공격 경로가 남아 있다. 게다가 접속 토큰을 메모리에만 두게 강제해서 새로고침·새 탭마다 서버를 다시 두드리게 만드는데 그 비용을 아무도 재보지 않았다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| CSRF | 공격자가 피해자 브라우저를 속여, 피해자 몰래 그 사이트로 요청을 보내게 하는 공격. |
| access / refresh 토큰 | access는 "지금 이 요청 해도 되는 사람"임을 증명하는 짧은 수명 표. refresh는 access가 만료되면 새로 발급받는 데 쓰는 긴 수명 표. |
| SameSite Lax / Strict | 브라우저가 "다른 사이트에서 넘어온 요청"에 쿠키를 붙일지 정하는 옵션. Lax는 주소창으로 직접 이동(top-level GET)엔 쿠키를 허용, Strict는 그것도 막음. |
| access=body 비대칭 | access는 쿠키가 아니라 응답 본문(body)으로 내려주고, refresh만 쿠키에 담는 방식. 공격자가 응답을 못 읽으니 CSRF에 유리하다는 주장. |
| rotation | /refresh를 호출하면 서버가 기존 refresh를 폐기하고 새 refresh로 갈아끼우는 것. |
| in-memory 강제 | access를 localStorage 같은 영구 저장소가 아니라 메모리(변수)에만 두게 강제 — 새로고침하면 사라짐. |

**뭐가 문제냐:**
① access를 body로 내려 CSRF에 면역이라고 하지만, 공격자가 피해자를 속여 /refresh를 호출시키면 응답을 못 읽더라도 서버는 rotation을 실행한다. 그러면 피해자가 쓰던 멀쩡한 refresh가 새 것으로 교체돼 무효화되고, 피해자는 세션이 끊긴다 — 즉 훔치는 게 아니라 세션을 파괴하는 DoS다.
② SameSite Lax는 주소창 이동 같은 top-level GET에는 쿠키를 붙여주므로, 메서드를 섞어 쓰면(GET으로 상태를 바꾸는 등) 뚫린다. 진짜 방어인 CSRF 토큰·Origin 검증·Strict 채택은 전부 뒤로 미뤄졌다.
③ access를 메모리에만 두게 강제하면 모든 리로드·새 탭·복귀마다 /refresh 왕복이 강제된다. 짧은 TTL과 겹치면 호출이 급증하고, refresh 재사용 탐지의 오탐(정상 사용자를 공격자로 오인)도 늘 수 있다. 이 운영 비용·UX 저하를 아무도 수치로 재지 않았다.

**지금 상태:** 부분결정. 메커니즘의 방향(transport=V1 계승+SameSite Lax, access=body 비대칭, in-memory 강제)은 ADR-20/RFC-019/DESIGN-017에서 정해졌다. 하지만 위 세 취약점은 결정으로 닫힌 게 아니라 DESIGN-017 스스로 §7 리뷰(line 153, 155)에서 자기 반박으로 적어둔 것이고, line 157에서 "이 절은 리뷰용 반박이며 결정을 뒤집지 않는다, 각 항목은 후속 검토 대상"이라 못박았다. 쿠키 속성(Lax vs Strict)·path·TTL은 §6(line 95)에서 후속 design_doc으로 위임됐고, ADR-20도 이들을 미결정으로 남겼다. RFC-020은 엣지 검증 위치·헤더 신뢰만 정하고 CSRF 토큰/Origin은 범위 밖이다. 즉 문서가 스스로 남긴 열린 숙제다.

**그래서 뭘 해야 하나:** 노트로 완화하되, 후속에서 (1) /refresh CSRF로 인한 rotation-DoS를 막을 방어(CSRF 토큰 또는 Origin/Referer 검증) 채택 여부, (2) SameSite Lax vs Strict 확정, (3) in-memory 강제의 /refresh 왕복 부하·오탐 비용을 실제로 계량할지를 정해야 한다.

### C28 — 파티션 수를 계약으로 못박고 HPA 상한=파티션 수로 두어 초기 추정 실패의 벌칙을 극대화
`MED` · 판정 부분결정 · 처분안 노트 완화
> **✅ 종결 (2026-07-05, C08과 동일 메커니즘):** "벌칙 극대화·순환 논리"의 뿌리는 "파티션 수 = 유일한 병렬 레버"라는 전제였다. **Parallel Consumer(`KEY` ordering)** 채택으로 파티션 내 key 병렬이라는 2번째 온라인-조절 레버가 생겨 이 전제가 깨진다 — 초기 파티션 추정이 빗나가도 HPA 상한(=파티션 수)에 막히지 않고 컨슈머 동시성으로 흡수. 초기값·증설 절차의 순환은 "정확할 필요 없음"으로 완화(추정 틀려도 탈출구가 저비용). DESIGN-008 §4.4 / ADR-09 line 71 참조.

**한 줄로:** 메시지를 나눠 담는 "칸(파티션)" 개수를 나중에 못 늘리게 못박고, 일꾼(프로젝터)을 늘릴 수 있는 최대치도 그 칸 수에 딱 맞춰 고정했다. 그래서 처음에 칸 수를 잘못 잡으면 일이 밀려도 일꾼을 더 못 붙이고, 유일한 해결책이 값비싼 무중단 이사(마이그레이션)뿐이 된다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 파티션 | Kafka 토픽을 나눈 병렬 처리 단위. 같은 aggregate_id는 같은 파티션으로 가서 순서가 보장된다. |
| 순서 계약 | "같은 대상의 이벤트는 들어온 순서대로 처리된다"는 약속. 이 약속이 파티션 수에 묶여 있다. |
| 컨슈머 그룹 / 프로젝터 | 파티션에서 이벤트를 읽어 처리하는 일꾼 무리. 한 파티션은 그룹 내 한 일꾼만 담당하므로, 일꾼 수의 최대치 = 파티션 수. |
| HPA 상한 | 부하에 따라 파드를 자동으로 몇 개까지 늘릴지의 최대치. 여기선 이 상한 = 파티션 수로 고정. |
| lag(적체) | 들어온 이벤트를 아직 처리 못 해 밀려 쌓인 양. |
| in-place 증설 | 기존 토픽의 파티션 수를 그 자리에서 늘리는 것. 여기선 금지 → 새 토픽 만들어 이사. |

**뭐가 문제냐:**
칸 수를 3개로 잡았는데 실제 처리량이 예상을 넘으면, 일꾼을 최대 3개까지밖에 못 붙인다(병렬 상한=파티션 수). 부하가 그 이상이면 프로젝터가 상한에 막혀 lag이 계속 쌓인다. 유일한 탈출구는 파티션이 더 많은 새 토픽을 만들어 데이터를 옮기는 무중단 마이그레이션 — 고비용에 위험하다. 게다가 "초기값은 보수적으로 잡는다"는 근거 자체가 처리량 추정치에 기대는데, 그 처리량 추정이 아직 TBD라서 논리가 순환한다(추정을 몰라서 보수적으로, 그런데 보수적 기준은 추정에 의존).

**지금 상태:** 부분결정. 설계 방향은 확정돼 있다 — ADR-09(line 57-59, 71)가 "파티션 수는 순서 계약의 일부, 넉넉히 잡고 고정, 증설은 드레인-정지 후"와 "병렬 상한=파티션 수"를 채택했고, RFC-003(논점 6·9)·DESIGN-008(§4.3/§4.4/§4.7)·DESIGN-010(§4.4, HPA캡=파티션수)이 이를 확정했다. 그러나 concern이 지적한 벌칙 극대화·순환 논리는 해소 안 됐다: ADR-09 Risks(line 86)는 벌칙을 인지만 하고 완화책이 없으며 초기값·증설 절차를 미결(line 97)로 남겼고, RFC-003 line 174에는 초기값 근거에 "〔근거 확인/보강 필요〕" 표식이 그대로 있다. DESIGN-008의 초기값은 TBD, ADR-12(line 64)도 숫자를 이벤트 스토밍·projector 스케일과 함께 정하라고 재위임했다.

**그래서 뭘 해야 하나:** 노트로 완화하되, 후속에서 (1) 초기 파티션 수를 처리량 추정 없이도 정할 산정 방법(순환 끊기), (2) 추정이 빗나갔을 때의 회복 경로 — 여유 파티션 사전 과다프로비저닝이나 컨슈머 다중그룹 샤딩 등 마이그레이션 외 대안, (3) 재추정·재파티셔닝 운영 절차를 정해야 한다.

### C29 — command/query 배포 합침이 독립 스케일·단일 이미지 격리 주장과 충돌
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, OVER)**: 독립 HPA·단일이미지 blast·분리 트리거는 프로덕션 배포 관심사 위임; relay 단일성(유일 안전축)은 SFU SKIP LOCKED로 기결(RFC-003)

**한 줄로:** 초기에는 쓰기(command)·읽기(query)·투영(projector)·발행(relay)을 한 배포·한 이미지로 같이 굴리기로 했는데, 이건 "각각 따로 확장하고 서로 격리한다"는 주장과 부딪힌다. 읽기가 폭증하면 쓰기 파드까지 같이 늘어나고, 한쪽의 취약점(CVE)이 나머지로 번지며, 언제 분리할지 판단할 지표마저 합쳐진 탓에 흐려진다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| command / query | 쓰기(상태 변경)를 담당하는 쪽과 읽기(조회)를 담당하는 쪽. CQRS에서 나뉜 두 경로. |
| projector / relay | projector는 이벤트를 읽어 읽기 모델을 갱신하는 일꾼. relay는 Outbox의 이벤트를 Kafka로 내보내는 발행기. |
| 독립 스케일 / HPA 축 | 부하 종류(읽기 vs 쓰기)에 따라 각각 파드 수를 따로 늘리는 것. |
| 단일 이미지 다중 프로파일 | 하나의 Docker 이미지를 만들고, 실행 시 프로파일(command/query/…)만 바꿔 역할을 지정하는 방식. |
| relay 단일성 | 같은 Outbox 행을 둘이 집어 중복 발행하지 않도록, relay가 사실상 하나처럼 동작해야 한다는 요구. |
| CVE / 폭발 반경 | 알려진 보안 취약점. 폭발 반경 = 하나가 뚫렸을 때 영향이 미치는 범위. |

**뭐가 문제냐:** 이 클러스터는 서로 다른 네 축을 묶고 있고, 결정 상태가 갈린다.
① relay가 프로파일 오설정 등으로 둘 뜨는 "단일성 위반" — 사실상 닫혀 있다. RFC-003 논점3(line 104-116)이 바로 그 상황을 전제로 `SELECT … FOR UPDATE SKIP LOCKED` 경쟁 소비를 채택해(leader election 미도입) DB가 직렬화하게 하고, at-least-once + projector 멱등성(Zero Payload, ADR-09)이 잔여 중복을 흡수한다. 즉 둘 떠도 읽기 모델이 오염되지 않게 데이터 안전성은 구조적으로 보장됨 — C29가 "안 다뤄진다"고 한 건 부정확하다.
② 한 파드에 command·query가 같이 있으면 읽기 폭증 시 쓰기 경로까지 함께 스케일되어, "읽기는 읽기 부하로, 쓰기는 쓰기 부하로 독립 스케일"(DESIGN-010 §4.6 line 180)이 성립하지 않는다. 방향(초기 단일 배포, 나중에 물리 분리)은 정해졌지만 이 충돌 자체의 해소책은 없다.
③ 분리 시점 판단 지표("읽기 스케일 한계 증명")를 합쳐진 배포에서 재면 오염돼, 언제 나눌지 판단 자체가 어렵다.
④ 단일 이미지에 모든 역할을 담으면 한 워크로드의 의존성·CVE 변경이 나머지로 번지는데, DESIGN-012 §4는 오히려 "빌드·취약점 스캔 표면을 하나로 유지"를 이점으로만 서술하고 전파 반경은 저울질하지 않는다.

**지금 상태:** 부분결정. ①은 결정(RFC-003 논점3 line 104-116·186, DESIGN-010 §4.4 line 153-158·Risks line 212). ②의 방향은 RFC-007 논점2(line 89)·DESIGN-010 §4.6이 정했으나 충돌 해소책은 없고 DESIGN-010 Weakness 절(line 250 부근)이 C29와 거의 같은 문장으로 자기 지적하며 "후속 검토 대상"으로 남긴다. ③도 같은 Weakness 절이 미해결로 인정, RFC-007 논점2는 "분리 신호 지표·임계는 Design"이라며 여지만 남겼다. ④는 DESIGN-012 §4(line 319-330)에서 어디서도 저울질 안 됨. ADR-01은 모듈 분리가 별도 파드를 강제하지 않는다는 근거로 RFC-007이 참조한다. 즉 relay만 결정, 나머지 셋은 문서가 남긴 열린 숙제다.

**그래서 뭘 해야 하나:** 노트로 완화하되, 후속에서 (1) 합쳐진 배포에서 read/write 독립 HPA가 불가한 점을 어떻게 다룰지(초기엔 독립 스케일 포기임을 명시할지), (2) 분리 트리거를 판단할 지표를 오염 없이 관측할 방법, (3) 단일 이미지의 CVE·의존성 전파 반경을 감수할지 이미지 분리를 검토할지를 정해야 한다. relay 단일성은 이미 닫혔으니 재론 불필요.

### C36 — 클라이언트 Idempotency-Key 거부·422/409 경계·cursor 안정성 전제가 재시도·경합에서 취약
`MED` · 판정 부분결정 · 처분안 노트 완화  
> ✅ **종결 (2026-07-07, 트리아지 C36)** — ① 서버 디듀프: 클라 키 미도입 확정, 생성별 자연 유니크 존재 확인은 *구현 사이클* 열거 항목(유니크 없는 생성이 나오면 그것만 서버 디듀프; C37과 연결) / ② ~~'락 후 자리없음'=422 vs 409~~ → **✅ 확정**: 판별축 = 도메인 상태가 실제 커밋되어 바뀌었나. 선점=`422`, 순수 락 경합=`409`. DESIGN-013 §4.4·ADR-16·RFC-014 정합화 / ③ ~~cursor 단조·유일성~~ → **✅ 확정**: 정렬 키 = 시간순 UUID PK(유일·단조·재처리 불변 구조 보장), 비-기본정렬=`(필드,UUID)` 복합. DESIGN-013 §4.6

**한 줄로:** "우리 클라이언트는 믿을 만하다"는 이유로 중복 방지 키를 안 받기로 했지만, 네트워크 끊김 재시도는 믿음과 무관하게 서버가 "재시도인지 새 요청인지" 구분 못 하게 만든다. 또 "자리 없음" 응답을 422로 줄지 409로 줄지 경계가 흔들리고, 다음 페이지를 가리키는 커서(cursor)가 안정적이라는 전제도 재처리 상황에서 깨진다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| Idempotency-Key(멱등 키) | 같은 요청이 여러 번 와도 한 번만 처리되게, 클라이언트가 요청에 붙이는 고유 식별자. |
| 생성 계열 command | 새 리소스를 만드는 요청(예약 생성 등). 자연스러운 유니크 불변식이 없으면 재시도와 새 요청 구분이 어렵다. |
| 422 vs 409 | 422 = 도메인 규칙상 확정 거절("이건 안 됨"). 409 = 경합으로 인한 충돌("지금 겹쳐서 안 됨, 다시 시도 가능"). 클라이언트는 이 둘로 다르게 분기한다. |
| 낙관 락 | "충돌 나면 그때 실패시키자"는 동시성 제어. 자연 멱등과 함께 상태전이 중복을 흡수. |
| cursor 페이징 | 다음 페이지를 오프셋이 아니라 "마지막 항목의 정렬 키" 기준으로 이어 읽는 방식. |
| 단조(monotonic)·유일성 | 정렬 키가 항상 증가하고(역행 없음) 값이 겹치지 않음. cursor가 항목을 건너뛰거나 반복하지 않으려면 필요. |

**뭐가 문제냐:**
① 멱등 키 거부: 네트워크 타임아웃으로 클라이언트가 같은 생성 요청을 재전송하면, 서버는 이게 "아까 그 요청의 재시도"인지 "새 의도"인지 구분할 수단이 없다. 유니크 불변식이 없는 생성 계열은 사실상 멱등 키가 필요하다.
② 422/409 경계: "락을 잡고 다시 확인하니 자리가 없더라"는 상황이 확정 거절(422)인지 경합(409)인지 규칙 문구에서조차 병기돼 흔들린다. 동시 예약 2건 중 하나가 거절될 때 클라이언트가 422로 볼지 409로 볼지 오분기한다.
③ cursor 단조성: 유일한 완화책이 "정렬 키가 존재하는지" 검증뿐인데, 이건 키의 존재만 볼 뿐 단조·유일성은 못 본다. 재처리로 timestamp가 역행하면 항목을 건너뛰거나 반복해도 못 잡는다.

**지금 상태:** 부분결정. 세 논점 모두 방향은 RFC-012에서 잠겼으나 구체적 실패 모드는 미해결이다. ① RFC-012(논점3, line 100-120·155)가 "멱등=서버 책임, 클라이언트 키 미도입"을 확정하되 "유니크 불변식 없는 생성 command는 서버 디듀프의 잔여 케이스"로 구현에 위임했고, DESIGN-013 §4.3 각주·Weakness 3(line 79, 196)이 "생성 계열은 사실상 필요가 정직한 결론"이라 자인. ② RFC-014(논점3, line 106-112·129)·ADR-16(line 47)이 "재판단 시 결과 뒤집힘=409, 도메인 거절=422" 규칙을 주지만 "자리 없음"을 422/409로 병기해 경계가 흔들리고, DESIGN-013 §4.4·Weakness 4(line 93, 151, 198)가 @ControllerAdvice 매핑을 구현 사이클로 넘기며 오분기를 자인. ③ RFC-012(논점6, line 139-145·158)는 cursor를 확정하되 정렬 키의 단조·유일성은 논하지 않고, RFC-002는 read-your-writes만 다루며 이를 전혀 언급 안 함(concern이 종속 대상으로 지목했으나 보장 없음), DESIGN-013 §4.6·Weakness 5(line 110, 150, 200)가 존재 검증의 불충분함을 인정. 즉 문서가 건드렸으나 스스로 미해결로 남긴 숙제다.

**그래서 뭘 해야 하나:** 노트로 완화하되, 후속에서 (1) 유니크 불변식 없는 생성 계열에 서버 측 디듀프(또는 멱등 키)를 어떻게 붙일지, (2) "락 후 자리 없음"을 422와 409 중 무엇으로 확정하고 @ControllerAdvice 매핑 표를 명시할지, (3) cursor 정렬 키의 단조·유일성을 어떻게 보장할지(존재 검증을 넘어)를 정해야 한다.

### C37 — 생성 도메인 유니크와 동시성 UNIQUE가 물리적으로 같은 제약이면 재시도 storm을 분리 못 한다
`MED` · 판정 부분결정 · 처분안 노트 완화  
> ✅ **종결 (2026-07-07, 트리아지 C37 — GENUINE 오분류 정정)** — 결정 포크가 아니라 **구현 사이클 가드레일**이다. ① C37은 "중복키를 무조건 동시성으로 보고 재시도"를 기정사실로 깔았으나 그 재시도 메커니즘은 사용자가 커밋한 적 없는 AI 초안 — [[ai-draft-laundered-as-user-decision]]. ② "분리 전제가 깨지면?"은 아직 만들지도 않은 설계의 우발 규약(가정 위 가정). ③ 원칙 자체(업무 중복 거절 ≠ 동시성 재시도)는 이미 C36 ②에서 `422`(도메인 판단·락+reload)로 DesignDoc에 정리됨. → 가드레일: **업무 중복 거절은 자연키 UNIQUE 위반으로 재시도 경로에 얹지 말고 도메인 판단에서 `422`로 거른다; 부득이 자연키 UNIQUE를 두면 `(aggregate_id, sequence_no)` 백스톱과 물리적으로 분리해 재시도 대상에서 뺀다.** 이미 DESIGN-006 §Weakness가 후속 검토로 자인 — 신규 결정 불요.

**한 줄로:** "같은 자리를 두 번 예약"(사람이 잘못 요청 → 재시도해도 소용없음)과 "동시에 두 요청이 부딪힘"(잠깐 기다렸다 다시 하면 됨)이 데이터베이스에서 똑같은 "중복" 오류로 튀어나오면, 시스템이 둘을 구별 못 하고 안 될 요청을 계속 재시도해서 부하가 폭발할 수 있다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 채번(시퀀스 채번) | 이벤트마다 붙는 순번을 한 곳에서 발급하는 것. |
| UNIQUE 제약 | DB가 "이 값은 중복 못 넣어"라고 막는 규칙. 어기면 중복키 오류. |
| append 시점 | 이벤트를 저장(추가)하는 순간. |
| 도메인 유니크 | 업무 규칙상 중복이면 안 되는 것(예: 같은 시각·같은 슬롯 중복 예약). |
| 동시성 충돌 | 두 요청이 같은 대상을 동시에 건드려 순번이 겹친 것. 재시도로 대개 풀림. |
| 바운디드 재시도 | 정해진 횟수만큼만 다시 시도. |
| 낙관/비관 락 | 충돌을 사후 감지(낙관)하느냐, 미리 잠가서 막느냐(비관). |
| 422/409 | HTTP 응답 코드. 422=업무 규칙 위반, 409=충돌. |

**뭐가 문제냐:** 설계는 순번을 한 곳에서 발급하고, 저장할 때 중복키 오류가 나면 무조건 "동시성 충돌"로 해석해 재시도한다(ADR-22 line 77). 그런데 "같은 시각 중복 예약" 같은 업무상 거절도, 만약 그걸 DB의 자연키 UNIQUE로 막게 만들면 똑같이 저장 시점 중복키 오류로 나타난다. 이 경우 재시도해도 영원히 거절되는데(사람이 진짜 중복 요청을 보낸 거라) 시스템은 "동시성이겠지" 하고 정해진 횟수만큼 계속 재시도한다 → 막으려던 재시도 storm이 오히려 발생. 두 제약이 물리적으로 같은 UNIQUE 인덱스를 공유하면 발급 계층에서 "이건 업무 거절, 저건 동시성"을 가를 방법이 없다.

**지금 상태:** 부분결정. 방향은 정해졌다 — 업무 거절은 락 잡고 reload 후 도메인 판단으로 확정적 422/409로 거르고(DESIGN-013 §4.3 line 74-75), (aggregate_id, sequence_no) UNIQUE는 락이 새는 극단 상황의 백스톱으로만 쓴다. 즉 두 제약을 물리적으로 분리한다는 전제. 하지만 "그 전제가 깨져서 도메인 유니크가 자연키 UNIQUE로 저장 경로에 얹히는 경우의 분리 규약"은 어디에도 확정 안 됨. DESIGN-006 §Weakness line 279가 이 시나리오를 거의 똑같은 문장으로 스스로 제기하고, line 282에서 "후속 검토 대상, 결정을 뒤집지 않음"으로 이월했다. DESIGN-013 §Risks line 149도 유니크 불변식 없는 생성의 디듀프를 구현 사이클로 미뤘다. 문서가 스스로 남긴 숙제다.

**그래서 뭘 해야 하나:** 노트로 남겨 못박을 것 — (1) 업무상 중복 거절은 절대 자연키 UNIQUE에 얹지 말고 도메인 판단 계층에서만 거른다는 규칙, 혹은 (2) 부득이 UNIQUE로 얹어야 한다면 그 인덱스를 동시성 백스톱 UNIQUE와 물리적으로 분리하고 오류를 구분해 재시도 대상에서 빼는 규약. 재시도 storm을 막으려면 "재시도해도 안 풀리는 거절"을 저장 계층이 식별할 수 있어야 한다.

### C41 — read model 캐시 거부→전용 프로젝션 방침의 영구 운영·조합 폭증 비용이 저울질되지 않았다
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, OVER)**: 캐시거부→전용투영 정책 기결(ADR-19/RFC-018/D-004); break-even 측정은 무트래픽 불가, 배포/운영 위임

**한 줄로:** 화면이 빨리 떠야 하는 조회를 "캐시 한 겹"으로 안 풀고 "화면 전용 데이터 사본(프로젝션)을 새로 만들어" 푸는 방침인데, 그 사본은 한 번 만들면 영구히 관리해야 하는 짐이 되고 조회 조건이 많으면(식당×날짜) 사본 종류가 폭발한다. 이게 캐시보다 정말 이득인지 재본 적이 없다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| read model | 조회 전용으로 미리 가공해 둔 데이터 형태. |
| 프로젝션 | 이벤트를 흘려 넣어 만드는 조회용 데이터 사본. 새로 추가하면 계속 유지·갱신해야 함. |
| 캐시(Redis 한 겹) | 원본 앞에 임시로 답을 저장해 두는 층. 문제되면 배포로 그냥 끄면 됨. |
| 백필 | 과거 데이터를 새 프로젝션에 채워 넣는 작업. |
| staleness | 데이터가 살짝 낡아 원본과 어긋난 상태. |
| 손익분기 | 캐시 vs 프로젝션 중 어느 쪽이 싸지는 갈림 지점. |

**뭐가 문제냐:** 캐시는 두 겹으로 낡을 위험(원본 낡음 + 캐시 낡음)이 있어 이를 피하려고 "핫 쿼리는 전용 프로젝션 추가"를 1차 수단으로 정했다. 그런데 프로젝션 하나를 새로 만들면 백필·재구축·여러 소스로부터의 갱신·구독·스키마가 전부 영구히 따라온다. 캐시는 문제 생기면 배포로 롤백하면 끝이지만, 프로젝션은 되돌리기 어려운 영구 부채다. 게다가 파라미터가 많은 조회(식당 × 날짜 × …)는 조합마다 프로젝션이 필요해 수가 폭발한다. 결국 "캐시 낡음 두 겹을 피하는 이득"이 "프로젝션 N개의 운영·정합성 비용 N배"를 정당화하는지 측정이 없다.

**지금 상태:** 부분결정. 방침 자체(캐시 거부 → 핫 쿼리는 전용 프로젝션 1차, 캐시는 측정된 예외에만)는 ADR-19·RFC-018·DESIGN-004/018에서 확정됐고, 두 비용 축도 문서가 인지한다(ADR-19 line 47-48, DESIGN-004 §Weakness line 187이 C41을 거의 그대로 재진술). 하지만 정작 그 저울질(측정·손익분기 임계·전환 트리거)은 ADR-19 미결정(line 57)·RFC-018 Non-goal(line 68)에서 Design/운영으로 명시 위임됐고, DESIGN-004 line 191이 "후속 검토 대상"으로 스스로 표시했다. 조합 폭증의 정량 평가, 영구 부채 대 롤백 가능 비대칭의 실제 비교는 어디에도 없다.

**그래서 뭘 해야 하나:** 노트로 남길 것 — 실제 읽기 분포를 측정해 (1) 어떤 패턴이 프로젝션으로는 비싸고 캐시가 싼지 식별하는 트리거, (2) 캐시로 갈아탈 손익분기 임계, (3) 조합 폭증하는 파라미터 쿼리는 프로젝션 대상에서 뺄 기준을 정할 것. 지금은 "측정 후 결정"이라 위임만 돼 있으니, 그 측정을 누가 언제 어떤 지표로 하는지를 구현/운영 항목으로 못박아야 방침이 검증 가능해진다.

### C42 — 컨텍스트 경계가 잠정값인데 하위 설계가 이미 결합됐고 수직 분산이 미래 분할을 막는다
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 분할 난이도는 ADR-01/RFC-001서 명명·선택('불가'는 과장), 스키마는 의도적 잠정+genesis 재작성 경로 — 지금 결정 아님

**한 줄로:** schedule·menu가 어느 그룹에 속할지 "잠정"이라면서 이미 그룹별로 저장 방식을 확정해 버려서, 나중에 그룹이 바뀌면 데이터를 통째로 다시 쓰는 값비싼 되돌림이 생기는데 그 비용을 아무도 계산 안 했다. 또 한 컨텍스트가 코드상 4곳에 흩어져 있어 나중에 서비스로 쪼개기가 비싸진다(문서는 이걸 알고 택했지만).

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 컨텍스트(경계) | 예약·메뉴·시간표처럼 업무 단위로 나눈 영역. |
| 이벤트 스토어(ES) | 상태 대신 "일어난 사건"들을 쌓아 저장하는 방식. |
| 상태+Outbox / 현행 | ES 아닌 저장 방식들. 현재 상태를 테이블에 두는 전통 방식. |
| 이벤트 스토밍 | 관계자가 모여 사건 흐름을 그려 경계를 정하는 워크숍. |
| 수직 분산 | 한 컨텍스트가 core/application/adapter/infrastructure 네 계층에 걸쳐 흩어진 것. |
| genesis 이벤트 | 기존 상태를 "최초 사건" 하나로 만들어 ES로 옮기는 변환. |
| Option B/C | B=CQRS(읽기/쓰기)를 최상위 축으로; C=컨텍스트를 최상위 축으로. |

**뭐가 문제냐:** 두 주장이 묶여 있다.
① **되돌림 비용 (공백):** ADR-02·DESIGN-001 §4.4는 schedule·menu의 그룹 분류를 "스토밍 재실시 후 재검토"라 잠정 처리했다. 그런데 DESIGN-003 §4.1~4.3은 벌써 세 그룹으로 저장 방식을 확정했다 — reservation·timetable·restaurant=이벤트스토어, schedule·user·authenticate=상태+Outbox, menu·category·company=현행. 잠정이던 menu·schedule이 나중에 ES로 옮겨지면, 이미 만든 상태 테이블을 이벤트 스토어로 재작성해야 한다. 변환 경로 자체는 RFC-013(genesis)에 있지만, "잠정 경계가 뒤집힐 때의 재작성 비용"을 계상하거나 "스토밍 전에 저장 방식을 지금 확정하는 게 조숙한가"를 그 비용과 교차 검토한 문서는 없다. DESIGN-003 Weakness 마지막 항목은 Payment의 ES 승격을 "재분류 항목으로 올릴 것"이라 남겨 재분류가 실제 가능함을 시사하면서도 비용은 공백.
② **분할 용이성 반납 (이미 해결):** 이 주장은 ADR-01이 정면으로 이미 다뤘다. ADR-01은 컨텍스트를 최상위로 두는 Option C(도메인별 분할이 가장 쉬움)를 검토·기각하고 Option B를 택하면서, "최상위 축이 CQRS라 한 도메인이 두 트리에 걸쳐 도메인별 서비스 분할이 비싸진다"는 대가를 이름 붙여 자인하고 완화책(깨끗한 패키지 유지)까지 명문화했다(RFC-001 line 127-129,141 동일). 즉 "반납"은 몰라서 잃은 게 아니라 알고 택한 트레이드오프. 다만 ADR-01은 "비싸짐"이라 했지 C42처럼 "사실상 불가능"이라 하진 않아 강도 차가 있다.

**지금 상태:** 부분결정. ②는 ADR-01/RFC-001에서 이미 결정·해명(다만 강도 표현 과장). ①은 touched-but-gap — 잠정 라벨과 세 갈래 분류 비용은 인정됐고 전환 경로도 RFC-013에 있으나, 재분류·재작성 비용의 회계는 어느 문서에도 없다.

**그래서 뭘 해야 하나:** ②는 새 결정 불필요 — C42의 "불가능/반납" 프레이밍을 "ADR-01이 알고 택한 비용"으로 정정하면 닫힌다. ①만 노트로 남길 것 — 잠정 경계(schedule·menu)가 ES로 뒤집힐 때 상태 테이블→이벤트 스토어 재작성에 드는 비용을 명시하고, "스토밍 전에 저장 방식을 지금 확정하는 것"과 "재분류 시 되돌림 비용" 중 어느 쪽이 큰지 교차 검토할 것.

### C43 — 컴파일 의존성 우위 원칙이 정작 컨텍스트 간 격리에는 적용되지 않는 자기모순
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 컴파일 의존 vs 정적분석은 의식적 스코프 트레이드오프(ADR-01 이중강제·D-002 §5.3 YAGNI) — 잔여는 ArchUnit/Konsist 구현 TODO

**한 줄로:** "규칙 위반은 코드가 컴파일 단계에서 물리적으로 막는 게 검사 도구보다 낫다"고 원칙을 세워놓고, 정작 실무에서 제일 자주 어길 "컨텍스트끼리 직접 갖다 쓰지 마" 경계는 그 열등하다는 검사 도구로만 막는다. 원칙과 가장 중요한 경계 강제 수단이 서로 어긋난다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 컴파일 의존성 강제 | 모듈을 물리적으로 분리해 "쓸 수 없으면 아예 컴파일이 안 되게" 막는 방식. |
| 정적분석(ArchUnit/Konsist) | 코드를 훑어 규칙 위반이면 빌드를 실패시키는 검사 도구. 물리적 차단은 아님. |
| 서브모듈 | Gradle에서 물리적으로 나뉜 빌드 단위. |
| 컨텍스트 간 직접 참조 | 예약 컨텍스트가 메뉴 컨텍스트 코드를 곧장 import 하는 것. |
| 도메인 순수성 | core 계층에 JPA·Spring 같은 바깥 기술이 안 섞인 상태. |
| YAGNI | "아직 필요 없으니 지금 만들지 마." |

**뭐가 문제냐:** 문서는 "컴파일 의존성 > 정적분석"을 논리축으로 삼는다(D-002 §4.4). 그런데 9개 컨텍스트가 서로를 직접 참조하지 못하게 막는 경계는 서브모듈(물리적 차단)이 아니라 ArchUnit/Konsist(검사 도구)로만 강제한다(§4.5). 즉 실무에서 가장 자주 위반될 경계가, 문서 스스로 "열등하다"고 규정한 수단에 의존한다. 원칙이 가장 중요한 곳에서 뒤집힌 꼴.

**지금 상태:** 부분결정. 이 선택 자체는 의식적으로 내려졌다 — ADR-01은 모듈 경계=Gradle 물리 강제, 컨텍스트 간 경계=ArchUnit/Konsist로 강제를 명시 이원화했고, D-002 §5.3은 "컨텍스트 격리까지 컴파일 타임 보장"하는 C안을 검토 후 "YAGNI, 9개 규모에 모듈 수 폭발, ArchUnit으로 충분"으로 기각했다. 즉 원칙을 "도메인 순수성 강제용"으로 한정한 스코프드 트레이드오프. 하지만 세 가지가 남았다 — (1) "이 원칙은 계층 순수성에만 적용되고 컨텍스트 격리엔 적용 안 한다"는 적용범위를 정면으로 선언하지 않아 우회만 함(D-002 §5.1·리뷰 §5 line 302에 자기모순 인정 문구가 그대로 남음). (2) 감사 문서 analysis/04 line 145에 따르면 ArchUnit/Konsist 규칙이 아직 이름만 있고 미작성(어느 툴·테스트모듈 위치도 미정) — 열등하다는 그 수단조차 구현 공백. (3) ADR-01은 ArchUnit vs Konsist 도구 선택도 미결.

**그래서 뭘 해야 하나:** 노트로 정합화할 것 — (1) "컴파일 의존성 우위 원칙은 계층 순수성에만 적용되며, 컨텍스트 간 격리는 비용 대비 효용(YAGNI)으로 정적분석에 맡긴다"고 원칙의 적용범위를 명시 선언해 자기모순 문구를 해소. (2) ArchUnit/Konsist 중 도구를 정하고, 규칙을 실제로 작성(어느 테스트모듈에 둘지 포함)해 현재 공백인 격리 강제를 채울 것. 지금은 강제장치 자체가 TODO라 원칙 논쟁 이전에 경계가 아예 강제되지 않는 상태다.

### C44 — 신규 기능 게이팅이 사업 우선순위와 교착하며 실행 가능한 답이 없다
`MED` · 판정 부분결정 · 처분안 노트 완화  
> ✅ **종결 (2026-07-07, 트리아지 C44 — GENUINE 오분류 정정)** — 지금 결정거리가 아니라 **아직 안 온 상황의 선결정**이다. 기본 정책(신규=신구조 네이티브·레퍼런스 검증 후 투입)은 이미 RFC-010 §5·ADR-06에 있다. 두 공백 모두 선결정 불요 — ① "사업 우선순위가 순서를 뒤집으면 어디 지을래"는 사용자가 **확정한 적 없는 가정 시나리오**("신규 기능 확장은 하면 좋다지 한다고 확정 안 함") → 실제 그 압력이 오면 그때 결정. ② genesis 합성이력 예외(b) 판단 기준은 "전환 사이클에서 데이터 보고 판단"으로 이미 정당하게 미뤄둔 것 — 데이터 보기 전 기준·상한 선결정은 오버. 신규 결정 불요.

**한 줄로:** 새 기능(리뷰·포인트·신고 같은 것)을 지금 만들려는데, 구조를 갈아엎는 이사(마이그레이션)가 진행 중이라 "낡은 집(V1)에 지을지, 아직 짓다 만 새 집에 지을지"를 아무도 정해두지 않았다. 그래서 급한 기능이 생기면 개발자가 매번 도박을 해야 한다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 게이팅 | "이 조건을 통과해야만 다음 걸 해도 된다"는 문지기 규칙. 여기선 "패턴을 다 검증하기 전엔 새 기능 금지". |
| 레퍼런스 (전환/사이클) | 새 구조를 가장 먼저 적용해 본보기로 삼는 컨텍스트, 그리고 그 작업을 도는 한 회차. 여기가 검증되면 나머지가 따라 한다. |
| command 컨텍스트 | 쓰기(명령) 담당 새 구조. 신규 기능은 이 신구조 네이티브로 짓자는 게 기본 방침. |
| 합성 이력 (genesis) | 과거 데이터를 이벤트 방식으로 옮길 때, 옛날 기록을 "가짜로 지어낸 시작 이벤트"로 채워 넣는 것. (a)는 시작점 하나만 만드는 기본안, (b)는 컨텍스트별로 더 만드는 예외안. |

**뭐가 문제냐:**
기본 방침은 정해져 있다 — 신규 기능은 새 구조로 짓고, 레퍼런스 검증이 끝난 뒤에 투입한다(RFC-010 §5, 결정요약 #5, 라인 153·165). 문제는 예외 상황이다. "사업 우선순위가 마이그레이션보다 높으면 순서가 뒤집힐 수 있다"고만 적어두고(라인 17), 정작 뒤집혔을 때 그 기능을 낡은 V1 구조에 지을지 미완성 신구조에 지을지 규칙이 없다. 이건 완화가 아니라 문제를 다시 말한 것뿐이다. ADR-06도 "신규 기능 투입 시점"을 대놓고 미결로 남겼다(라인 62).
두 번째로, 합성 이력 예외 (b)를 "적용할지 말지는 나중에 전환 사이클에서 데이터 보고 판단"(RFC-013 라인 102·104·159)이라고 미뤘다. 판단 기준도, 얼마나 만들지 상한도 없다. 그래서 예를 들어 reservation이 과거 이력 복원을 요구하면 첫 레퍼런스 사이클이 예상보다 훨씬 커지고, 본보기로 삼아 나머지에 복붙하려던 계획이 흔들린다(DESIGN-005 §4.4 리뷰, 라인 177).

**지금 상태:** 부분결정. 기본 정책(순서·신구조 네이티브)은 RFC/ADR에 있으나, 순서가 뒤집힐 때의 실행 규칙과 합성 이력 예외의 판단 기준이라는 공백은 안 닫혔다. DESIGN-005 §4.4 리뷰(라인 177)와 ADR-06(라인 62)이 스스로 미결 숙제로 적어둔 것.

**그래서 뭘 해야 하나:** 노트로 완화. 두 가지를 명문화하면 된다. (1) 순서가 뒤집힐 때 새 기능을 어느 구조에 짓는지 기본값 한 줄, (2) 합성 이력 예외 (b)를 켤 판단 기준과 범위 상한. 첫 레퍼런스 사이클을 열기 전에 이 둘을 노트로 못 박아 사이클 규모가 미지의 데이터에 휘둘리지 않게 한다.

### C47 — CDC 전환 트리거가 전부 주관적이라 폴링 부채를 발화 못 시킨다
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, OVER)**: 폴링 시작+3트리거 방향 기결(RFC-003·D-008); CDC 전환 정량 임계는 실측 위임(RFC-007·ADR-05)

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 폴링 (relay) | DB를 주기적으로 훑어 바뀐 걸 퍼가는 방식. 만들기 쉽지만 지연·부하가 있는 임시방편. |
| CDC | Change Data Capture. DB 변경 로그를 직접 읽어 실시간으로 흘려보내는 정공법. Debezium/Kafka Connect로 돌린다. |
| 듀얼 라이트 | 같은 데이터를 두 군데(예: DB와 메시지)에 동시에 쓰는 것. 어긋날 위험이 있어 없애고 싶어 하는 대상. |

| TBD | To Be Determined, 아직 안 정함. |

**뭐가 문제냐:**
전환 트리거 세 개 모두 발화 숫자가 비어 있다. (1) "폴링 지연이 SLI를 위협하면" — 그런데 그 SLI 절대값을 RFC-008이 RFC-007에 떠넘기고, RFC-007은 다시 "운영 실측 후 확정"이라며 도로 미룬다(라인 15-18). 즉 어느 문서에도 발화선 숫자가 없다. (2) "듀얼 라이트 제거 요구" — 정성적 서술뿐. (3) "Connect 성숙도" — ADR-12가 "도입 시"라고만 해서 자기평가에 의존, 임계 없음(라인 19-20). 게다가 방향을 잠근 RFC-003 결정에도 〔근거 확인/보강 필요〕가 달려 확정이 덜 됐다(라인 14). 결과적으로 세 조건 모두 주관적이라 아무도 "지금이다"라고 못 하고, 문서가 스스로 경고한 "트리거 없으면 폴링이 부채로 굳는다"가 그대로 실현된다.

**지금 상태:** 부분결정. "폴링으로 시작하고 세 트리거를 둔다"는 방향은 RFC-003 논점4에서 결정됐고 D-008 §4.9와 일치한다. 하지만 발화 가능한 정량 임계는 어디에도 없고, ADR-05도 CDC 전환 "기준"을 후속 과제로 열어뒀다(라인 21).

**그래서 뭘 해야 하나:** 노트로 완화. 세 트리거 중 최소한 (1) 폴링 지연에 대해 "이 값을 이만큼 기간 넘으면 CDC 착수"라는 잠정 숫자 한 줄이라도 박고, (3) Connect 성숙도는 자기평가 대신 체크 가능한 조건(예: 운영 담당·롤백 절차 존재)으로 바꾼다. 운영 실측 전이라 확정이 어렵다면, 실측 후 이 숫자를 채우기로 하는 후속 시점 자체를 노트에 못 박아 무기한 미룸을 막는다.

| ES / 비-ES | ES(이벤트 소싱)는 상태를 이벤트 쌓기로 관리하는 컨텍스트, 비-ES는 그냥 테이블에 현재값을 두는 컨텍스트. |
| 리플레이 지연 | 쌓인 이벤트를 되감아 현재 상태를 재조립하는 데 걸리는 시간. |
| 스냅샷 신선도 | 중간 저장본이 얼마나 최신인지. 오래됐으면 되감을 게 많아 느려진다. |
| 분산 락 (Redisson) | 여러 서버가 같은 자원을 동시에 못 건드리게 거는 잠금. 대기하다 타임아웃이 날 수 있다. |
| 추상화 누수 | "안 보이게 숨겼다"던 내부 차이가 바깥 동작(속도·실패 방식)으로 새어 나오는 것. |
| hexagonal / layered | 두 가지 코드 구조. 쓰기(command)는 hexagonal(포트·어댑터), 읽기(query)는 layered(얇게 DB→DTO)로 다르게 짓기로 함. |
| projector / read model | 이벤트를 받아 조회용 테이블(read model)을 만들어 채우는 놈. 여러 이벤트를 합치고 중복을 걸러 넣는다. |
| SLA / p99 | 응답 시간 약속치. p99는 "느린 순 상위 1% 빼고 이 안에 답한다"는 지연 지표. |

**뭐가 문제냐:**
이 우려는 두 갈래인데, 대부분은 이미 닫혔다.
갈래 A(읽기 쪽 복잡도 과소평가): projector가 여러 이벤트를 조인·집계·중복제거해 read model을 만드는 게 얇지 않다는 걱정 — RFC-011이 프로젝션 재구축·따라잡기(catch-up)·백필·멱등 병합(키 upsert + sequence_no 버전 가드 + 오프셋 추적 + blue-green 무중단 교체)을 정면으로 상세히 확정해 이 복잡도를 명시적으로 떠안았다(라인 24-26). RFC-002 §6과 ADR-03은 "갱신은 projection, 조회는 service"로 책임을 갈라, projector 로직이 얇은 조회 코드를 오염시킬 걱정을 구조로 분리했다. → 해소됨.
갈래 B의 쓰기 쪽(리플레이·분산 락에서 오는 실패·타임아웃): ADR-16/RFC-014가 lock-wait 타임아웃→409/503, 도메인 거절→422/409, UNIQUE 백스톱으로 확정(라인 17). → 해소됨.
남은 진짜 갭: 읽기 쪽 SLA·신선도가 컨텍스트 종류로 갈리는 부분이다. ES 컨텍스트 조회는 리플레이 지연·스냅샷 신선도 때문에 비-ES 조회와 응답 특성·장애 모드가 다를 수 있는데, RFC-002는 모든 읽기 경로에 "기본은 최종 일관성"이라는 단일 기준만 깔고 p99 절대값과 신선도 예외는 측정·후속으로 미뤘을 뿐(라인 19, 34), ES vs 비-ES별 차등화는 다루지 않는다.

**지금 상태:** 부분결정. 재구축·백필 복잡도(RFC-011)와 쓰기 측 장애 모드(ADR-16)는 결정됨. 읽기 경로의 컨텍스트별 SLA/신선도 누수만 미결. D-001 §4.3 직후 Weakness 절이 이 항목을 스스로 "후속 검토 대상"으로 자인(라인 36-38).

**그래서 뭘 해야 하나:** 노트로 완화. ES 컨텍스트 조회 유스케이스에 대해 "리플레이·스냅샷 때문에 읽기 신선도/타임아웃 기준을 비-ES와 다르게 둘 것인지"를 후속 검토 항목으로 명시하고, 필요 시 신규 ADR로 컨텍스트별 read SLA를 분리 결정하도록 트리거를 남긴다.

### C50 — 비-ES가 ES 데이터를 조인하는 문제가 첫 레퍼런스(예약 상세)에서 바로 터진다
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 비동기 로컬사본 패턴 기결(RFC-002 L111·D-004 §4.5·D-003 §4.3) — '두 나쁜 선택' 전제 반증, item 소유표는 03-read-model 구현 위임

**한 줄로:** "이벤트 안 쓰는 컨텍스트가 이벤트 쓰는 컨텍스트 데이터를 같이 봐야 하는 상황은 나중에 압력이 생기면 정하자"고 미뤘는데, 예약 상세 화면이 예약(ES)과 메뉴/카테고리(비-ES)를 함께 보여주는 건 거의 확실히 첫 본보기에서 일어난다. 다만 이걸 해결할 방법 자체는 이미 정해져 있어서, 걱정만큼 나쁜 선택으로 몰리진 않는다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 조인 | 두 테이블 데이터를 즉석에서 합쳐 읽는 것. |
| lookup 컨텍스트 | 메뉴·카테고리·업체처럼 남들이 참조하는 기준 데이터 컨텍스트. |
| QueryDSL | 여기선 비-ES가 "자기 DB 테이블만" 타입 안전하게 조회하는 도구. 남의 컨텍스트를 직접 조인하지 않는다. |
| 비정규화 | 조회를 빠르게 하려고 남의 데이터 사본을 자기 read model 칼럼에 미리 복사해 두는 것. |
| projection / published-subscription | read model에 외부 데이터를 채우는 두 방식. projection은 이벤트 구독해 갱신, published-subscription은 발행자가 내보낸 걸 받아 로컬에 적재. |
| Outbox | 상태 변경과 함께 "이 변경을 이벤트로 내보내라"를 같은 트랜잭션에 적어두는 발행 장치. 비-ES도 이걸로 발행할 수 있다. |
| 통일 압력 | "비-ES도 그냥 ES로 통일하자"고 몰리는 힘. |

**뭐가 문제냐:**
걱정의 프레이밍은 "예약이 메뉴를 같이 보여줘야 하는데 비-ES는 자기 테이블만 읽으니, ① 예약 프로젝션이 메뉴까지 비정규화하거나 ② 비-ES를 억지로 ES화하거나 둘 다 나쁜 선택으로 수렴한다"는 것이다. 그런데 이 두 선택지는 문서 결정으로 반박된다. RFC-002 결정1 + DESIGN-004 §4.5 + DESIGN-003 §4.3이 정한 정식 패턴은 이렇다 — (1) 예약(ES) 조회 측 프로젝션이 외부 데이터를 비정규화해 자기 칼럼에 담는 건 안티패턴이 아니라 채택된 방식이다(식당명 예시가 메뉴명에 그대로 적용됨, DESIGN-004 라인 99-104). (2) 메뉴 같은 비-ES lookup은 "누가 구독해야 할 때만 Outbox로 이벤트를 발행"해 published-subscription 소스가 되므로, 조회 시점에 조인하지도 억지로 ES화하지도 않는다(DESIGN-003 라인 21-22, ADR-04 라인 23-24). 즉 예약 query 측이 메뉴 변경을 구독해 로컬에 적재하고, 예약 조회는 조인 없이 읽는다.
남는 진짜 갭은 셋이다: (a) 메뉴·카테고리·업체의 실제 소유권과 "이건 projection, 저건 published"라는 항목별 귀속표가 구현 사이클로 명시 위임됨(DESIGN-004 §4.2(나) 라인 68, §7 리스크 표), (b) "비-ES를 ES로 통일할지"라는 통일 압력은 RFC-002 논점5에서 Design 검증 항목으로만 열려 있음(라인 25-26), (c) DESIGN-004 §7 리스크 표가 예약 상세 케이스를 "그때 결정"으로 미룸.

**지금 상태:** 부분결정. 교차 컨텍스트 읽기의 메커니즘(비동기 로컬 카피)은 RFC-002/DESIGN-004/DESIGN-003/ADR-04로 확정돼 "두 나쁜 선택" 프레이밍은 반박됨. 다만 항목별 귀속표와 통일 압력 트리거는 미결. DESIGN-004 자신의 Weakness 절(라인 189)이 C50과 같은 반박("예약 상세에서 바로 터진다")을 적어두고도 후속 검토로 둠.

**그래서 뭘 해야 하나:** 노트로 완화. 첫 레퍼런스가 예약이라는 점을 근거로, 예약 상세가 요구하는 메뉴·카테고리 항목들의 소유권과 projection/published 귀속을 그 구현 사이클에서 우선 확정하도록 명시한다. 아울러 "비-ES가 ES 데이터를 조인해야 하는 경우가 실제로 나오면 통일 압력 검토를 발화한다"는 트리거 조건을 노트에 남겨 Design 검증 항목이 표류하지 않게 한다.

### C51 — 깨진 크로스레퍼런스가 CI 필수 게이트 강제력을 미확정 상류에 인질로 잡는다
`MED` · 판정 부분결정 · 처분안 노트 완화

**한 줄로:** 어떤 테스트를 "이거 통과 못하면 배포 못 함"으로 강제할지는 이미 다른 문서에서 확실히 정해졌다. 문제는 이 결정을 가리키는 D-012 문서의 링크·번호가 서로 안 맞아서, 독자가 근거를 따라가다 길을 잃는 편집상 오류만 남았다는 것이다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| CI 필수 게이트 | 코드가 합쳐지기 전 반드시 통과해야 하는 자동 검사. 실패하면 배포·머지가 막힌다. |
| 동적 분산 행위 | 여러 서버가 메시지를 주고받으며 실행 중에만 드러나는 동작(재생·동시성 등). 정적 코드 검사로는 안 잡힌다. |
| 크로스레퍼런스 | 문서가 다른 문서/절을 "여기 근거 있음"이라고 가리키는 상호 참조. |
| 상류(上流) | 이 문서가 근거로 삼는, 먼저 결정됐어야 할 다른 문서. |
| 인질로 잡힌다 | 근거 문서가 아직 안 정해졌으면 이 문서의 결정도 공중에 뜬다는 비유. |

**뭐가 문제냐:** C51은 원래 두 가지를 한데 묶었는데, 하나는 오해이고 하나는 진짜다.
① (오해) "게이트를 CI 필수로 걸겠다는 핵심 결정이 아직 안 정해진 상류에 매여 있다" — 사실이 아니다. 이 결정의 실제 주인은 RFC-009이고, 이미 '합의(2026-06-23)' 상태로 잠겨 있다. RFC-009는 6가지 동적 분산 행위를 나눠 "결정적인 것(멱등성·재생/스냅샷 등가·동시성)=CI 필수, 무거운 통합(재구축·사가·종단)=정기 실행"으로 못박았다(논점4 표 L102-111, 결정요약#4 L151). §5.7이 인용하는 상류 RFC(003/004/006/011/012/013)도 전부 합의 또는 종결 상태라 "미확정 상류" 전제 자체가 틀렸다.
② (진짜) D-012 상단의 '관련 RFC' 목록(004/005/012/013/015/022/002)과 본문 §5.7·§5.5의 인용 번호(002~006/011/012)가 서로 안 맞는다. 독자가 "게이트 근거가 어느 RFC냐"를 따라가면 번호가 어긋나 근거가 공중에 뜬다. D-012가 Weakness 절(L433)에서 스스로 "깨진 크로스레퍼런스가 게이트 근거를 공중에 띄운다"고 자인한 그대로다.

**지금 상태:** 부분결정. 게이트 강제력이라는 실체 결정은 이미 닫혔다(RFC-009). 하지만 참조 번호 불일치는 어떤 ADR/RFC도 고쳐주지 않는 순수 편집 결함이라 미해소로 남았다. 덧붙여 ADR-14(테스트 전략)는 아직 'Proposed(2026-06-14)'라 RFC-009가 예고한 최종 비준(Proposed→Accepted) 고리도 안 닫혔다.

**그래서 뭘 해야 하나:** 새 결정은 필요 없다. (1) D-012 상단 관련문서 목록과 §5.7·§5.5 본문 인용 번호를 실제 근거인 RFC-009로 일치시키는 편집 수정. (2) 그 김에 ADR-14를 Proposed→Accepted로 비준. 둘 다 노트성 정합 작업이다.

### C04 — L1 분산 락이 append와 원자적이지 않아 정확성은 사실상 L0 UNIQUE에만 의존한다
`HIGH` · 판정 기결 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: 정확성은 분산락 아닌 UNIQUE 불변식(ADR-16·RFC-014) — 전제 무효, D-006 문구정합만 잔여

**한 줄로:** "Redis 락이 정확성을 지킨다"고 오해할까 봐 걱정한 문제인데, 결정 문서들은 이미 "락은 속도용일 뿐 정확성은 DB의 UNIQUE 제약이 지킨다"고 정확히 반대로 못박아 놨다. 남은 건 개별 설계 문서 문장이 그 표현을 흐릿하게 쓴 것뿐이다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| append INSERT | 이벤트 저장소(event_store)에 새 이벤트 한 줄을 덧붙여 쓰는 것. |
| 분산 락(Redis/Redisson) | 여러 서버 중 하나만 특정 작업을 하도록 잠그는 장치. Redis에 산다. |
| 리스 만료 / watchdog | 락은 일정 시간 뒤 자동 풀린다(리스 만료). watchdog은 작업이 아직 진행 중이면 락을 연장해 주는 감시견인데, 이게 못 미치는 순간 창(틈)이 생긴다. |
| L0 UNIQUE | DB의 유일성 제약. `(aggregate_id, sequence_no)`가 중복이면 두 번째 INSERT를 거절한다. 최종 안전장치. |
| L1 / L1′ | 1차 경합 완화(Redisson 락) / 폴백 경합 완화(DB의 SELECT ... FOR UPDATE). |
| liveness vs safety | liveness=일이 진행되게 함(속도·경합완화). safety=틀린 결과가 안 나오게 함(정확성). 둘은 다른 목표. |
| split-brain | 페일오버 등으로 락 관리자가 갈라져 둘 다 자기가 락 주인이라 믿는 상태. |

**뭐가 문제냐:** 락 획득(Redis)과 append INSERT(MySQL)는 서로 다른 시스템의 다른 트랜잭션이다. 리스가 만료됐는데 watchdog이 아직 연장 못 한 창, 또는 split-brain 창에서 두 번째 라이터가 동시에 진입할 수 있다. 이때 정확성을 실제로 지키는 건 락이 아니라 L0 UNIQUE다(두 번째 append가 UNIQUE 위반으로 거절됨). 그렇다면 "락이 정확성을 보장한다"는 서술은 정직하지 않고, L1은 정확성 계층이 아니라 가속/경합완화 계층으로 재분류돼야 한다 — 이것이 C04의 요구다.

**지금 상태:** 기결. C04가 요구한 결론이 이미 정본으로 확정돼 있다. ADR-16은 제목부터 "비관 락 + UNIQUE 백스톱"이고, "분산 락은 liveness지 safety가 아니다... UNIQUE를 정확성 불변식으로 유지(L0)"(L30), "정확성은 `(aggregate_id, sequence_no)` UNIQUE가, 경합 완화는 분산 락이 맡는다 — 락이 정확성을 대체하지 않는다"(L34)라고 명시한다. 3층 방어(L38-40)에서 L1/L1′은 명시적으로 '경합 직렬화'로만 라벨링된다. 리스 만료·watchdog·split-brain 창의 둘째 라이터를 L0가 흡수한다고 L46·L55·L65가 못박는다. RFC-014도 "잠그되 믿지 않는다 — UNIQUE가 최종 심판"(합의 2026-06-29)으로 같은 입장이다. 즉 결정 층위에는 자기모순이 없고 오히려 C04 편이다.

**그래서 뭘 해야 하나:** 확정된 ADR을 다시 여는 새 RFC는 topical-RFC 규율 위반이라 불필요하다. 남은 일은 개별 설계 문서(D-006/D-003/D-013/D-018) 본문에서 "비관 락=정확성 의존" 뉘앙스로 읽히는 문장을 "락=경합 완화, 정확성은 L0 UNIQUE"로 맞추는 문구 정합 검증(노트)뿐이다.

### C06 — event_store와 Outbox의 트랜잭션 경계 공유 조건이 명시되지 않아 '원자적' 주장이 취약
`HIGH` · 판정 기결 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: ES append=기존 MySQL 단일 트랜잭션(ADR-05) — 이중 데이터소스 전제 무효, D-003 §4.2 불변식 노트만

**한 줄로:** "이벤트 저장과 발행 예약을 한 번에 성공하거나 한 번에 실패하게(원자적) 만든다"는 주장은, 둘이 같은 DB의 같은 트랜잭션일 때만 참이다. 결정 문서는 이미 그렇게 되도록 단일 MySQL을 골랐다. 다만 그 전제를 "이래야 원자적이다"라는 한 줄 규칙으로 못박은 문장이 없어 보강이 필요할 뿐이다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| event_store | 발생한 이벤트를 append-only로 쌓는 테이블. |
| Outbox | 대외(Kafka)로 내보낼 이벤트를 같은 DB에 먼저 적어두는 발행 대기함. 나중에 별도 발행기가 읽어 Kafka로 보낸다. |
| 원자성(atomicity) | 여러 쓰기가 전부 성공하거나 전부 실패하는 성질. 중간에 하나만 되는 일이 없음. |
| 트랜잭션 경계 | 원자성이 보장되는 묶음의 범위. 같은 트랜잭션 안이면 함께 커밋/롤백된다. |
| datasource | DB 연결. 같은 datasource여야 한 트랜잭션으로 묶을 수 있다. |
| BEFORE_COMMIT | 커밋 직전 같은 트랜잭션 안에서 Outbox 기록을 끼워 넣는 시점. |
| ES 엔진 | 이벤트 저장소를 다루는 엔진. 별도 제품이면 독립 트랜잭션·별도 datasource가 된다. |

**뭐가 문제냐:** 상태(또는 event_store) 저장과 Outbox 기록이 원자적이려면 둘이 같은 트랜잭션·같은 datasource여야 한다. 만약 ES를 별도 전용 제품으로 두고 그 엔진이 독립 트랜잭션으로 append하면, 이벤트는 저장됐는데 Outbox 기록이 실패하는 경우가 생긴다 → 이벤트는 남지만 대외 발행은 영영 유실된다. D-003 §4.2가 "상태(or 이벤트스토어) + Outbox 원자적"(L84)이라 주장하면서 "동일 datasource"라는 전제를 한 줄로 명문화하진 않았다는 지적이다.

**지금 상태:** 기결. 우려가 상정한 실패모드(ES가 독립 트랜잭션으로 append)는 ADR-05가 정면으로 기각한 대안이다. ADR-05는 전용 ES 제품(Option A, 독립 트랜잭션·이중 datasource)을 빼고 "기존 MySQL의 append-only 이벤트 테이블로 직접 구현"(합의 2026-06-12)하기로 확정했고, 그 근거가 바로 "기존 MySQL/Outbox 자산 재사용 → 한 트랜잭션 원자성"(L39/L44)이다. RFC-001("같은 트랜잭션 안에서 Outbox에도 적는다", L23)과 RFC-003("command DB(이벤트 스토어+Outbox)에 같은 트랜잭션으로 적는다", L20)도 반복 명시하며, RFC-003 다이어그램은 event_store와 Outbox를 하나의 command DB 노드로 묶어 동일 datasource임을 구조적으로 표현한다. D-003 §4.2 자체도 ADR-05를 근거로 BEFORE_COMMIT 같은 트랜잭션을 인용한다. 다만 "동일 datasource·동일 트랜잭션"이 명명된 불변식 한 줄로 못박히지 않고 단일 테이블 결정의 함의로만 도출된다.

**그래서 뭘 해야 하나:** 새 RFC나 결정 재개는 불필요하다. D-003 §A(또는 §공통 발행 경로)에 "원자성은 event_store와 Outbox가 동일 MySQL·동일 트랜잭션(BEFORE_COMMIT)일 때 성립한다"를 명시적 invariant 한 줄로 추가하는 문서 보강(노트)이면 충분하다.

### C12 — 혼합 패러다임(ES/비-ES) 사가와 보상 인터리빙이 원자성·순서를 훨씬 어렵게 하나 표시되지 않는다
`MED` · 판정 부분결정 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: Zero Payload 폐기(RFC-029)+버전가드+Parallel Consumer KEY — 전제 무효, RFC-006 문구노트만

**한 줄로:** 실패한 예약을 되돌리는 "보상" 작업이, 이벤트로 상태를 쌓는 컨텍스트와 테이블로 상태를 들고 있는 컨텍스트를 동시에 조율할 때 더 어려워진다. 기술적 위험(순서 뒤집힘)은 이미 여러 문서가 처리선을 그어놨지만, "혼합이라서 더 어렵다"는 사실 자체를 어디에도 명시적으로 적어두지 않았다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| ES / 비-ES | ES=상태를 이벤트로 쌓음(reservation·timetable·restaurant). 비-ES=상태를 테이블로 들고 있음(schedule·user). |
| 진실원(source of truth) | 그 데이터의 최종 정답이 어디 있느냐. ES는 이벤트 스트림, 비-ES는 상태 테이블. |
| 사가(saga) | 여러 컨텍스트에 걸친 작업을 단계별로 진행하고, 중간에 실패하면 앞 단계를 되돌리는(보상) 분산 트랜잭션 패턴. |
| 보상(compensation) | 이미 한 일을 취소하는 역동작(예: 좌석 해제 SeatReleased, 결제 환불 PaymentRefunded). |
| 멱등(idempotent) | 같은 걸 여러 번 해도 결과가 한 번 한 것과 같음. 중복 이벤트에 안전. |
| 인터리빙 / 순서 역전 | 서로 다른 두 보상이 뒤섞여 도착 순서가 뒤집히는 것. 멱등은 중복은 막지만 이건 못 막는다. |
| Zero Payload 재조회 | 이벤트에 값 대신 id만 싣고, 받는 쪽이 필요한 값을 다시 조회하는 방식. |
| PoisonMessage | 처리에 계속 실패해 격리하는 문제 메시지. |

**뭐가 문제냐:** ES 예약이 비-ES schedule·ES restaurant와 얽히면, 사가는 이벤트 스트림 진실원과 상태 테이블 진실원을 동시에 조율해야 한다. 멱등 보상 + Zero Payload 재조회는 같은 이벤트가 중복 도착하는 데는 안전하지만, 서로 다른 보상이 순서 뒤바뀌어 도착하는 인터리빙에는 안전하지 않다(오래된 값으로 새 값을 덮어쓰는 사고). 게다가 부분 보상 상태 — 예를 들어 좌석 해제(SeatReleased)는 성공했는데 환불(PaymentRefunded)은 실패한 상태 — 를 어떻게 다룰지가 미정이다. C12는 문서가 "혼합 패러다임 사가가 더 어렵다"는 점 자체를 표시하지 않고 하위 문서로 미룬다고 지적한다.

**지금 상태:** 부분결정. 두 갈래로 나뉜다.
(1) 기술적 실체 — "멱등만으로 순서 역전을 못 막는다"는 이미 정면 처리돼 있다. RFC-003(논점 L83, 결정요약 L184)은 Zero Payload upsert의 inbox 생략을 "순서 역전이 없을 때뿐"으로 못박고 "역전 가능하면 오래된 값 덮어쓰기 사고"라 명시한다. RFC-011(L129)은 중복 제거(event_id inbox)와 순서 가드(sequence_no 버전 가드)를 분리하고, 교차-애그리거트 증분 갱신은 per-aggregate 가드로 멱등이 안 됨을 밝힌다. RFC-021(논점2 L105)은 시점 의존 파생 사실을 유일 예외로 카빙해 "생산 시점 페이로드 박제"로 해소하고 "진짜 교차 불변식 강제는 사가 몫"으로 귀속한다.
(2) 프레이밍 — 여기에 gap이 남는다. ADR-02·ADR-07·RFC-001은 ES/비-ES를 "저장 방식 차이일 뿐 대외 발행 경로는 동일"로 균질화하고, ADR-08·RFC-006은 보상을 패러다임 구분 없이 "각 컨텍스트가 자기 aggregate 상태로 자기 보상 판단"으로 일원 처리한다 — 진실원이 스트림이냐 테이블이냐가 보상 난이도를 바꾼다는 서술이 없다. 특히 RFC-006 §논점4(L125)는 부분 보상 상태를 PoisonMessage가 담을 수 있는지 TBD로 하위 사이클에 넘긴다 — C12가 지적한 "하위 문서로 넘긴다"가 실제 확인된다.

**그래서 뭘 해야 하나:** 기술적 핵심은 이미 처리선이 그어져 새 RFC(accept-new-rfc)는 과잉이다. 순수 프레이밍 gap만 노트로 메운다. RFC-006에 (1) "혼합 패러다임 사가는 두 진실원(스트림·테이블)을 동시 조율하므로 보상 난이도가 다르다"는 한 줄 표지를 추가하고, (2) 부분 보상 상태(SeatReleased 성공 + PaymentRefunded 실패)의 PoisonMessage 수용 여부 TBD가 바로 이 난이도의 발현임을 명시하면 충분하다.

### C48 — core에서 Spring 배제가 흔한 도메인 헬퍼(Bean Validation·로깅)까지 배제한다
`LOW` · 판정 부분결정 · 처분안 노트 완화

**한 줄로:** "도메인 코드는 스프링 같은 바깥 라이브러리를 절대 못 쓴다"는 규칙 때문에, 값이 올바른지 검사하는 흔한 도구(Bean Validation)까지 못 쓰게 됐다. 로깅 쪽 걱정은 이미 다른 방식으로 풀렸지만, 검증을 어떻게 대신할지는 아직 정식으로 못 박히지 않았다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| core | 순수 도메인 로직만 담는 모듈. 바깥 라이브러리(스프링, JPA 등) 의존을 컴파일 단계에서 아예 금지한다. |
| Bean Validation (jakarta.validation) | "이 값은 비어있으면 안 됨" 같은 규칙을 애노테이션(@NotNull 등)으로 선언해 자동 검사해 주는 표준 도구. |
| 불변식 검증 | 애그리거트가 항상 지켜야 하는 규칙(예: 예약 시작시각 < 종료시각)을 어겼는지 확인하는 것. |
| require(...) | 코틀린 기본 문법. 조건이 거짓이면 예외를 던진다. 바깥 라이브러리 없이 순수하게 검증할 수 있다. |
| SLF4J / MDC | 로깅 도구와, 로그에 추적용 키를 실어 나르는 저장소. |
| 리치 도메인 | 데이터만 담는 껍데기가 아니라, 검증·행동을 스스로 하는 도메인 객체. 이 프로젝트의 목표. |

**뭐가 문제냐:** core가 바깥 의존을 못 쓰니 값 검증을 오직 순수 코틀린 `require(...)`로만 짜야 한다. 그러면 세 갈래로 샌다. ① 검증 로직을 shared 모듈에 다시 구현하거나, ② 검증을 application 계층으로 끌어올려서 하게 되는데, 이건 "도메인이 스스로 검증한다"는 리치 도메인 목표와 정면충돌한다(빈혈 도메인으로 회귀). 로깅도 비슷한 우려가 있었지만 이쪽은 이미 해소됐다 — 도메인 메서드 안에 로그를 손으로 뿌리지 않고, 도메인 경계에서 AOP가 자동으로 추적 키를 주입하기로 정했으므로 core에 SLF4J가 필요하다는 전제 자체가 성립하지 않는다.

**지금 상태:** 부분결정. 뿌리 결정(core = 물리적 별도 모듈, 순수성 강제)은 ADR-07(합의됨)·RFC-010(합의)에서 확정됐지만, 이 두 문서는 JPA 매핑 비용만 "정당한 대가"로 다루고 Bean Validation 배제 문제는 언급하지 않는다. 로깅 갈래는 RFC-008 §5(도메인 경계 AOP + OTel Baggage → MDC)로 실질 해소됐다. 반면 검증 갈래는 "애그리거트 안에서 순수 require로 검증한다"는 패턴이 DESIGN-006 §4.2·DESIGN-003에만 있고(디자인 문서일 뿐 ADR/RFC 아님), Bean Validation 배제 딜레마를 결론지은 ADR/RFC는 없다. D-002 §6.1(라인 23–24)에 여전히 열린 반박 포인트로 문서가 스스로 남겨둔 숙제다.

**그래서 뭘 해야 하나:** 심각도 LOW이고 메커니즘(순수 require 검증)의 방향은 이미 디자인 문서에 잡혀 있으므로, 새 RFC까지는 불필요하다. "core의 불변식 검증은 순수 코틀린 require로 하고 Bean Validation/shared 재구현/application 상향 우회는 쓰지 않는다"는 원칙을 결정 문서(또는 D-002 §6.1)에 못 박아, 디자인 문서에만 떠 있는 패턴을 정식 결정으로 승격시키는 노트만 남기면 충분하다.

### C05 — 분산 락의 안전성·토폴로지 가정(Redlock·단일 인스턴스 SPOF·상시 왕복 비용)이 검증되지 않았다
`HIGH` · 판정 기결 · ~~처분안 기각~~ → **✅ 종결 (2026-07-06, VOID)**: 3층 락(ADR-16)·UNIQUE 백스톱·SFU 폴백·lock-free 기각(RFC-014) 모두 기결; 락 왕복비용만 무트래픽 유예

**한 줄로:** "Redis 락에 GC 멈춤이나 장애 대비 안전장치가 없고, Redis 한 대가 죽으면 전체가 멈추며, 매 쓰기마다 락 왕복 비용이 든다"는 걱정인데 — 설계는 이 셋을 모두 이미 다뤘다. 핵심은 "락은 걸되 락을 믿지 않는다"이고, 정확성은 락이 아니라 DB의 UNIQUE 제약이 최종 보증한다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| 분산 락 | 여러 서버가 같은 자원을 동시에 못 건드리게 막는 잠금. 여기선 Redis(Redisson)로 구현. |
| Redlock | Redis로 분산 락을 구현하는 대표 알고리즘. 안전성 논쟁이 유명하다. |
| fencing token | 락이 잘못 풀려도 오래된 작업자가 뒤늦게 쓰기 못 하게 막는 순번표. Redlock 안전성 보강책으로 자주 거론됨. |
| SPOF | 단일 장애점. 그것 하나가 죽으면 전체가 멈추는 지점. |
| split-brain | 노드들이 서로를 못 보고 각자 "내가 락 주인"이라 믿어 이중 쓰기가 나는 상황. |
| liveness / safety | liveness=일이 진행되게(경합 완화), safety=틀린 결과가 안 나오게(정확성). 이 설계는 락을 liveness 용도로만 쓴다. |
| L0 UNIQUE | `(aggregate_id, sequence_no)`에 건 DB 유일성 제약. 같은 애그리거트에 같은 순번을 두 번 못 쓰게 막는 최종 심판. |
| L1' (DB 폴백) | Redis가 죽으면 대신 쓰는 `SELECT … FOR UPDATE` DB 비관 락. |
| 낙관/락프리 | 락 없이 진행하고 충돌 나면 재시도하는 방식. |

**뭐가 문제냐 (그리고 왜 이미 닫혔나):** 걱정한 세 축이 각각 이렇게 대체·수용됐다.
① 안전성 — GC 정지·네트워크 지연·watchdog 실패·락 키 evict로 락이 풀려도, 락과 독립한 L0 UNIQUE가 두 번째 append를 구조적으로 거절한다. 즉 fencing token은 "빠뜨린" 게 아니라 UNIQUE 백스톱으로 아키텍처적으로 대체됐다.
② 가용성 — Redis 단일 인스턴스가 죽으면 DB 비관 락(L1', `SELECT … FOR UPDATE`)으로 폴백해 쓰기를 유지한다. 폴백 전환 창에 일부 노드는 Redisson·일부는 DB 락을 쥐는 split-brain이 나도, 둘째 append는 역시 L0 UNIQUE가 거절해 정확성이 유지된다.
③ 성능 — 경합이 없는 쓰기에도 락 왕복 비용이 상시 붙는 점은 트레이드오프로 자인했고, 락프리(낙관) 대안은 핫 스트림에서 retry storm·라이브락이 난다는 근거로 명시 기각했다.

**지금 상태:** 기결. ADR-16(비관 락, L0/L1/L1' 3층 구조)·RFC-014(3층 동시성 제어, 낙관 대안 명시 기각)·ADR-19(Redis = 조정·휘발성 상태 전용, 정확성과 분리)가 세 축을 모두 명시적으로 결정했다. 다만 성능 축만은 정량 비교 없이 "트래픽 없는 학습 환경에서 명목상 비용"으로 판단하고 "실트래픽 시 재검토"로 위임한 정성적 결정이다. 그래도 채택 근거와 재검토 조건이 다 내려져 있어 "미검증 가정 위에 열려 있다"는 우려의 전제는 사실과 다르다.

**그래서 뭘 해야 하나:** 기각. 새로 열 미결 사항이 아니다. fencing token은 L0 UNIQUE로, SPOF는 DB FOR UPDATE 폴백으로, 락프리 대안은 retry storm 근거로 이미 처리됐다. 유일하게 정성적인 성능 축(락 왕복 비용 정량 비교)도 무트래픽 환경에서의 의도적 유예이자 "실트래픽 시 재검토 트리거"로 위임된 결정이므로, 지금 RFC로 열 이유가 없다. (재검토 트리거는 실트래픽이 생길 때 발동.)

### C07 — UUIDv7 커서가 '순서 정확성 아님'인데 전역 재구축이 이 부정확성에 노출된다
`LOW` · 판정 기결 · ~~처분안 노트 완화~~ → **✅ 종결 (2026-07-06, VOID)**: event_id=진행/열거용, 순서권위 아님(ADR-22·RFC-021) — 전제 무효, D-003 §4.1 stale 정렬문구만

**한 줄로:** 이벤트 ID(UUIDv7)는 밀리초 단위라 같은 밀리초에 여러 개가 들어오면 누가 먼저인지 못 가린다. 이걸로 전체 데이터를 다시 훑어 재구축할 때 순서가 뒤바뀔까 걱정했지만 — 정확성은 ID 순서가 아니라 별도의 순번(sequence_no)이 책임지므로 뒤바뀌어도 결과는 멀쩡하다. 이미 닫힌 문제다.

**먼저 용어:**

| 말 | 뜻 |
|---|---|
| UUIDv7 | 앞부분에 시각(밀리초)이 들어가 대략 시간순으로 정렬되는 ID. 단 같은 밀리초 안에서는 순서를 보장 못 함. |
| keyset 커서 | "지난번 마지막 ID 다음부터" 이어서 읽는 페이지 넘김 방식. `WHERE event_id > :last ORDER BY event_id`. |
| projection 재구축 | 저장된 이벤트를 처음부터 다시 훑어 조회용 화면 데이터(읽기 모델)를 재조립하는 것. |
| aggregate 단위 재구축 | 한 애그리거트의 이벤트만 sequence_no 순으로 재조립. 순서가 안전하다. |
| 전역 재구축 | 애그리거트 구분 없이 event_store 전체를 PK(event_id)로 훑는 것. 여기서 동일 ms 문제가 걸린다. |
| sequence_no | 애그리거트마다 매기는 순번. 진짜 순서 정확성은 이게 책임진다. |
| 멱등 upsert | 같은 걸 두 번 적용해도 결과가 안 바뀌게 넣는 것. |
| 버전 가드 | 애그리거트별 순번(sequence_no)으로 이미 반영한 이벤트를 다시 반영하지 않게 막는 것. |

**뭐가 문제냐 (그리고 왜 이미 닫혔나):** 우려는 "전역 재구축이 `WHERE event_id > :last ORDER BY event_id` PK 스캔에 의존하는데, UUIDv7이 밀리초 해상도라 동일 ms 다중 삽입의 시간순을 보장 못 한다 → keyset 커서와 순서 정확성을 한 컬럼(event_id)이 겸하게 해서 경계가 흐리다"는 것이다. 설계는 이 전제 자체를 깬다. event_id(keyset)는 "어디까지 읽었나"라는 진행/열거만 나르고, 프로젝터의 정확성은 스캔 순서가 아니라 per-aggregate 순서(파티션 키=aggregate_id) + 멱등 upsert + sequence_no 버전 가드가 진다. 그래서 같은 ms 타이로 스캔 순서가 뒤바뀌어도 결과 정확성에 영향이 없다.

**지금 상태:** 기결. 이 우려는 D-003(=DESIGN-003) §4.1 자기 리뷰(라인 197–199)에서 문서가 스스로 제기했고, 리뷰어가 귀속처를 DESIGN-009·DESIGN-004·ADR-22로 지정했으며 그 문서들이 실제로 불변식을 못 박아 닫았다. ADR-22(§정확성 불변식, 정정 노트)는 "global_seq/event_id는 진행·열거를 나르지 순서 정확성을 나르지 않는다"를 명시하고, DESIGN-009 §6.3(라인 217–218)은 전역 재구축·projection 재빌드 경로에 동일 가드레일을 적용하며, RFC-011은 dedup(event_id inbox)과 순서 가드(sequence_no)를 명시 분리하고, RFC-021은 UUIDv7 확정·global_seq 불채택을 못 박았다. 남은 gap 없음.

**그래서 뭘 해야 하나:** 노트 완화. 새 설계 결정은 없으므로 신규 RFC는 불필요하다. 다만 DESIGN-003 §4.1 자기리뷰의 정정 문구가 실제로는 채택되지 않은 해법(`(occurred_at, event_id)` 정렬)을 가리켜 하류 문서와 어긋난다. 그 한 줄을 "정확성은 스캔 순서가 아니라 sequence_no 버전 가드가 진다"로 바로잡는 정정 노트만 남기면 충분하다.
