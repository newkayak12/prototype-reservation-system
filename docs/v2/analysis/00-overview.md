# V2 Analysis — 00. Overview

> 상태: **분석(Analysis) 단계** — 현재 시스템(V1)을 사실 기반으로 진단한다.
> 설계 결정(무엇을 ES로, R/W 모델은 어떻게)은 이 분석 위에서 별도 `docs/v2/design_doc/` · `docs/v2/adr/` 로 이어진다.
> 작성 근거: `core-module` / `application-module` / `adapter-module` / `infrastructure-module` / `shared-module` 코드 직접 분석 (2026-06-12).

## 1. V2가 하려는 것

V1 → V2 전환의 목표는 세 가지다.

1. **Read / Write 모델·DB 분리 (CQRS)** — 명령(쓰기)과 조회(읽기)를 모델·저장소 수준에서 분리.
2. **이벤트 소싱 (Event Sourcing)** — 상태 변화를 이벤트 스트림으로 기록하고, 그 이벤트로부터 상태를 재구성.
3. **이벤트 드리븐 (Event-Driven)** — 컨텍스트 간 통합을 이벤트(메시지) 기반 비동기로.

세 목표는 **독립적이며 적용 강도가 컨텍스트마다 다를 수 있다.** (예: 핵심 예약 플로우만 진짜 ES, 나머지는 CQRS + Outbox 이벤트.) 그 갈래를 정하는 것이 설계 단계의 핵심 결정이며, 본 분석은 그 결정을 위한 사실 기반을 제공한다.

## 3. 한 줄 결론

> 도메인은 **빈약(anemic)**하고 이벤트 인프라는 **timetable 한 컨텍스트에만** 있다. 그러나 헥사고날 구조와 **검증된 Transactional Outbox 패턴**이 이미 있어, V2는 백지가 아니라 "**timetable이 먼저 깐 패턴을 일반화 + 애그리거트를 행위 중심으로 재설계**"하는 작업이다.
