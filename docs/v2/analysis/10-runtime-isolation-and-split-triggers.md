# 런타임 격리 — 개념 정리와 C1·C2 해소 노트

> 성격: 개념 정리. devils-advocate가 제기한 C1(물리 분리 트리거 부재)·C2(namespace를 격리로 오인)는 [[ADR-026-workload-runtime-placement]]으로 **해소**됐다. 이 노트는 그 해소 근거와 격리 개념을 남긴다.
> 최종 갱신: 2026-07-21

## 1. 두 지적과 그 해소 (문제 한 장)

원래 문서 체인은 "처음엔 command와 query를 한 덩어리로 띄우고, 읽기 부하가 커지면 그때 물리적으로 쪼갠다"고 읽혔고, 워크로드를 `app-ns`/`data-ns` namespace로 나눠 "격리했다"고 했다. 여기서 두 질문이 안 풀렸다:

1. **언제 쪼개나?** — "부하가 커지면"의 숫자·오너가 없다. (C1)
2. **namespace 나누면 진짜 격리인가?** — namespace가 장애 벽이 맞는지 검증이 없다. (C2)

**둘 다 ADR-026으로 닫혔다:**

- **C1 해소** — "한 덩어리로 시작"은 틀린 전제였다. command/query를 포함한 **모든 앱 워크로드는 처음부터 별도 배포 + 노드 분리**다(ADR-026). 나중에 "물리적으로 쪼갤" 일이 없으니 트리거 자체가 불필요. "모듈 분리 비용만 선불, 런타임 이득은 미수령"이라는 구도도 성립 안 한다 — 물리 분리를 처음부터 같이 지불한다.
- **C2 충족** — namespace를 격리 수단으로 쓰지 않는다. **단일 평탄 NS**. 격리는 **노드 분리**에서 온다. 즉 C2가 옳다고 한 방향("격리는 노드/노드풀에서 나오지 namespace가 아니다")을 그대로 채택했다.

## 2. 기초 개념 (용어 풀이)

| 용어 | 뜻 | 격리에 기여? |
|---|---|---|
| **module (모듈)** | 코드 경계(컴파일 단위) | ❌ 런타임과 무관 |
| **workload (워크로드)** | 런타임에 실제로 뜨는 프로세스 묶음(예: projector) | 배치의 단위 |
| **Pod** | 컨테이너 실행 최소 단위 | — |
| **Deployment** | 같은 Pod를 N개 굴리는 K8s 리소스 | — |
| **node (노드)** | Pod가 올라가는 실제 서버(VM) | 자원 경계의 실체 |
| **node pool / node group** | 용도별로 묶은 노드 집합 | ✅ 자원·스케줄 격리 |
| **namespace** | 클러스터 안의 **논리 구획**(이름·권한·쿼터) | ⚠️ **기본은 격리 아님** |
| **cluster** | 노드+컨트롤플레인 전체 한 벌 | 최상위 경계 |
| **failure domain (장애 도메인)** | "여기 하나 죽으면 같이 죽는 범위" | 격리의 진짜 기준 |
| **AZ (availability zone)** | 물리적으로 분리된 데이터센터 구역 | ✅ 가용성 격리 |
| **NetworkPolicy** | Pod 간 통신을 막고 허용하는 방화벽 규칙 | ✅ 네트워크 구획 (CNI가 지원해야 강제됨) |
| **taint / toleration** | 특정 노드에 특정 Pod만 오게 하는 배치 규칙 | ✅ node pool 격리 도구 |
| **requests / limits** | Pod가 예약·사용할 CPU·메모리 하한/상한 | ✅ noisy-neighbor 1차 방어 |
| **control plane / CNI / cluster-autoscaler** | 클러스터 전체가 공유하는 핵심 부품 | ❌ **공유 SPOF** |

### 한 문장 요약

**namespace는 "이름표·권한·쿼터"지 "장애 벽"이 아니다.** 진짜 장애 벽은 node pool·AZ·NetworkPolicy 같은 **물리/네트워크 설정**에서 나온다. — 그래서 우리는 격리를 namespace가 아니라 **노드 분리**에 둔다.

## 3. 격리 사다리와 우리 위치

| 단계 | 설정 | 막아주는 장애 | 비용 |
|---|---|---|---|
| 0 | namespace만 | (거의 없음 — 이름/권한뿐) | 무료 |
| 1 | **requests/limits** | 한 워크로드 폭주가 옆 워크로드 CPU·메모리 잡아먹기 | 무료(설정) |
| 2 | **NetworkPolicy** (deny-by-default) | 워크로드 간 불필요한 통신·측면 이동 | 낮음 |
| 3 | **별도 node pool + taint/toleration** | 노드 단위 자원 경합, 특정 워크로드가 노드 통째 점유 | 중(노드 추가) |
| 4 | **multi-AZ + topologySpread** | AZ 하나 다운 | 중~높음 |
| 5 | **별도 클러스터** | 컨트롤플레인·CNI 등 공유 SPOF | 높음 |

**우리 위치(ADR-026):** 격리를 **노드 분리(3단계 근처)** 에 둔다 — 각 앱 워크로드가 서로 다른 노드에 놓인다. **0단계(namespace 분리)는 쓰지 않는다**(단일 평탄 NS). 노드를 나누는 구체 방식(전용 node pool + taint/toleration vs anti-affinity)과 pool 수·규격은 [[08-k6-load-test-strategy]] 측정 후 확정할 **학습 변수**다 — 지금은 작업가설이지 블로커가 아니다.

## 4. C1이 "없는 문제"가 된 이유

유예된 트리거("부하가 요구하면 분리")는 오너도 숫자도 없으면 영원히 발동 안 한다 — 그게 원래 C1의 지적이었다. ADR-026은 이 문제를 **트리거를 채워서**가 아니라 **처음부터 분리해서** 없앤다. command/query는 시작부터 별도 배포 + 별 노드이므로 "나중에 쪼갤 시점"이라는 개념 자체가 사라진다.

projector·relay가 처음부터 별 워크로드인 논리는 그대로다 — 요청-응답이 아니라 컨슈머 루프라 동시성·스케일·장애 특성이 근본적으로 다르다. ADR-026은 이 "처음부터 분리" 원칙을 **모든 앱 워크로드로 확장**한 것이다.
