---

## 1. Background

### V1 취약점 — 빈약한 애그리거트 + 흩어진 도메인 로직

V1은 상태 변경 로직의 ~95%를 **16개 이상의 `*DomainService`** 에 두고, 애그리거트는 `var` + setter 데이터 홀더로 만들었다. 그 결과 "어떤 이벤트가 언제 발생하는가"의 권위가 애그리거트에 없어, 이벤트 소싱으로 가는 데 가장 큰 장애가 된다.

핵심 진단: V1의 `*DomainService` **대부분은 진짜 도메인 서비스가 아니라 애플리케이션 오케스트레이션**이다(`validate → 객체 생성 → save → snapshot`). 도메인 로직과 절차가 한 곳에 뭉쳐 있다.

---

## 2. Goal

- **리치 애그리거트 원칙 확립**: 애그리거트가 자신의 불변식과 상태 전이를 스스로 책임지도록 설계 기준을 정의한다.
- **로직 배치 규칙 정의**: V1의 `*DomainService` 에 흩어진 로직을 애그리거트 / 애플리케이션 서비스 / 얇은 도메인 서비스로 재배치하는 triage 기준을 제시한다.
- **동시성 제어 메커니즘 확립**: ES 컨텍스트에서 행 잠금이 사라진 자리를 메울 비관 락 + UNIQUE 백스톱 3층 구조를 정의한다.

---

## 3. Non-Goal

- **컨텍스트별 구체 애그리거트·이벤트 목록**: 이벤트 스토밍 재실시 후 확정한다. 기존 보드는 참고용으로만 사용한다.
- **사가 상세 설계**: 크로스-애그리거트 일관성을 위한 사가 패턴의 구체 구현은 [[DESIGN-007]]에서 다룬다.
- **낙관 락 전략**: RFC-014에서 낙관 → 비관 락으로 방향이 확정되었다. 낙관 락으로 회귀하지 않는다.

---

## 4. Proposed Solution

### 4.1 High-Level Architecture

V2의 애그리거트 설계는 `handle/apply` 패턴을 핵심으로 한다.

- **handle**: 명령을 받아 불변식을 검증하고, 발생할 이벤트 목록을 반환한다.
- **apply**: 이벤트를 상태에 적용한다. 리플레이와 신규 발생 모두에서 공용으로 사용한다.

동시성 제어는 3층으로 구성된다.

```
[L1] Redisson 분산 락 (Redis 정상 시)
  └→ [L1'] DB 비관 락 (Redis 불가 시 폴백)
       └→ [L0] (aggregate_id, sequence_no) UNIQUE — 최종 안전망 (항상 존재)
```

### 4.2 Key Design Decisions

#### 리치 애그리거트 원칙

애그리거트는 자신의 불변식과 상태 전이를 **스스로** 책임진다.

```kotlin
// 개념 예시 — 시그니처는 구현 사이클에서 확정
class Reservation private constructor(/* state */) {
    // 1) 명령을 받아 불변식 검증 후 발생할 이벤트를 반환
    fun handle(command: CancelReservation): List<DomainEvent> {
        require(canCancel(command.now)) { "취소 가능 기한(방문 3일 전) 초과" }
        return listOf(ReservationCancelled(id, command.reason, command.now))
    }
    // 2) 이벤트를 상태에 적용 (불변 전이) — 리플레이·신규 발생 공용
    fun apply(event: ReservationCancelled): Reservation { /* ... */ }
}
```

- 불변식 검증은 **애그리거트 안**에서 수행한다 (V1처럼 서비스에서 하지 않는다).
- 상태 변경은 **이벤트를 통해** 표현(ES) 또는 이벤트와 함께 발행(비-ES).

#### 로직 배치 규칙 (triage)

V1의 `*DomainService` 에 있던 로직을 다음 기준으로 재배치한다.

| 로직 성격 | V2 행선지 | 위치 |
|-----------|-----------|------|
| 단일 애그리거트의 불변식·상태 전이 | **애그리거트** | `command.<ctx>.domain` |
| 적재 → 애그리거트 호출 → 저장 → 이벤트 발행 (절차) | **애플리케이션 서비스(유스케이스)** | `command.<ctx>.application.service` |
| 진짜 여러 애그리거트에 걸친 도메인 규칙 / 순수 도메인 계산 | **얇은 도메인 서비스** (소수만) | `command.<ctx>.domain` |

> 결과: V1의 16개 서비스 대부분이 **애그리거트 + 유스케이스**로 흡수되고, 도메인 서비스는 몇 개만 남는다. "도메인 서비스가 많다 = 빈약 도메인 신호"로 본다.

#### 애그리거트 설계 5원칙

1. **불변식 경계로 식별** — "항상 함께 일관성이 지켜져야 하는 것"이 한 애그리거트.
2. **작게 유지** — 큰 애그리거트는 경합·잠금 범위를 키운다. 의심되면 쪼갠다.
3. **애그리거트 간은 ID 참조** — 객체 직접 참조 금지 (예: `Reservation` 은 `restaurantId` 만 안다).
4. **부수효과는 이벤트로** — 다른 애그리거트/컨텍스트 변경은 직접 호출이 아니라 이벤트 발행으로 ([[DESIGN-003]]).
5. **불변(immutable) 전이 선호** — `apply` 는 새 상태를 반환 (ES 리플레이 안전성).

#### 경계를 넘는 일관성은 전역 락이 아니라 사가

이 제어는 *한 애그리거트* 안의 직렬화만 보장한다 (락 범위 = 단일 `aggregate_id`). 여러 애그리거트에 걸친 불변식("결제와 예약 확정이 함께 성립", "식당 정원 초과 금지")은 사정권 밖이고, 이를 **전역 락으로 풀지 않는다** — 전역 락은 여러 애그리거트를 한꺼번에 잠가 작게 유지 원칙(가이드 2)을 정면으로 깬다.

- 즉시 일관성(한 애그리거트) = **비관 락 + UNIQUE 백스톱**.
- 최종 일관성(여러 애그리거트) = **사가** ([[DESIGN-007]] · RFC-006-saga-process-manager).
- 둘의 경계가 곧 애그리거트 경계다.

예약 라이프사이클이 그 모양이다 — 점유(`timetable`)·결제(`payment`)·확정(`reservation`)이 각자 자기 애그리거트 락 안에서 쓰고, 단계 간 어긋남은 PM이 `SeatReleased`·`PaymentRefunded` 보상으로 되감는다.

### 4.3 Interface / Contract

ES 컨텍스트의 append 경로:

1. 애플리케이션 서비스가 L1/L1' 락 획득
2. 이벤트 스토어에서 애그리거트 로드 (리플레이)
3. `aggregate.handle(command)` 호출 → 이벤트 목록 반환
4. `(aggregate_id, expected_version + 1)` 으로 INSERT (L0 UNIQUE 검증)
5. 락 해제

비-ES 컨텍스트도 동일한 리치 애그리거트 원칙을 따르되, 상태 테이블에 저장 + Outbox 발행한다 ([[DESIGN-003]]).

### 4.4 Data Model

동시성 제어의 핵심 데이터 구조:

- **이벤트 스토어**: `(aggregate_id, sequence_no)` UNIQUE 제약 — [[05.event-store-mysql-table]] 참조.
- **DB 폴백 lock-row**: per-aggregate lock-row (`SELECT … FOR UPDATE`). 상세 스키마는 구현에서 확정.
- **스냅샷 연동**: 스냅샷이 낀 로드의 expected-version은 **스냅샷 버전 + 이후 이벤트 수**로 계산 ([[DESIGN-009]] 스냅샷 전략과 정합).

## 5. Alternatives Considered

### 낙관 락 (Optimistic Locking)

RFC-014에서 검토 후 기각되었다. 학습 프로토타입에서 실 트래픽이 없어 낙관의 "평소 공짜" 이득이 실재하지 않고, 분산 락을 직접 운영하는 학습 가치가 더 크다. 상세 전환 경위는 RFC-014-aggregate-concurrency-control 참조.

### 전역 락

여러 애그리거트에 걸친 불변식을 전역 락으로 풀면 작게 유지 원칙(가이드 2)을 정면으로 깨고, 전체 처리량이 단일 락 경합 지점에 수렴한다. 사가로 대체한다.

## 6. Details

### 6.1 Error Handling

#### 충돌 처리 — 락이 대부분 소거, 잔여 표면 셋

락 보유로 동시 충돌이 **대부분 소거**되므로, 클라이언트가 보는 충돌 표면은 셋으로 좁혀진다.

| 충돌 종류 | 처리 | 예 |
|-----------|------|-----|
| **lock-wait 타임아웃** | 호출자에 재시도 신호 — **409/503 + retry-after** | 앞 라이터가 락 점유 중, 한도 내 미획득 |
| **도메인 거절** | **422/409로 확정** — 재시도 storm 없이 | 락 잡고 reload하니 "자리 없음": 7시 자리 경합에서 먼저 든 쪽이 점유하면 둘째는 판단이 뒤집힘 |
| **잔여 UNIQUE 위반** | **동시성 충돌로 흡수** — 바운디드 재시도/409 | 락 유실·split-brain edge에서 L0가 발동 (드물지만 경로는 반드시 존재) |

핵심 경계는 **재시도하면 풀릴 수 있느냐**다. lock-wait 타임아웃·잔여 UNIQUE 위반은 재시도로 풀리는 일시 경합이지만, 도메인 거절(자리 없음)은 무한정 재시도해도 자리가 안 생기므로 **확정적으로 거절**한다 — 둘을 같은 409로 뭉뚱그리지 않는다.

[[DESIGN-013]]의 "락 충돌 409 = 재시도 신호"와 맞물리되, 그 409는 "락 경합/락 유실이라 최신을 다시 읽고 재시도하라"는 의미로 좁혀지고, 도메인 거절은 422/409로 분리된다. lock-wait 한도·백오프, 잔여 UNIQUE 충돌 매핑(`DuplicateKeyException`→충돌), 그리고 이 처리가 202 비동기 응답 모델 안에서 노출되는 시점은 구현에서 확정한다.

#### 헷갈리기 쉬운 세 층 — 동시성 ≠ 요청 멱등 ≠ 전달 멱등

같은 409·중복 언저리지만 *다른 문제, 각자 따로* 필요하다. 한 예약이 셋을 차례로 다 통과한다.

| 층 | 무엇이 막나 | 막는 대상 | 위치 |
|----|-------------|-----------|------|
| **동시성 충돌** (본 문서) | 비관 락(Redisson/DB) 직렬화 + UNIQUE 백스톱 | 쓰기 *경합* (이중 점유) | append 시점 · command DB |
| **요청 멱등** ([[DESIGN-013]]) | 상태 전이 = 자연 멱등 + 버전 가드 / 생성 = 도메인 유니크 | 같은 의도의 *중복 제출* (더블클릭) | 요청 진입 · HTTP |
| **전달 멱등** ([[DESIGN-008]]) | inbox / Zero Payload upsert | *중복 전달* → 프로젝션 오염 | append 이후 · 메시징 |

### 6.2 Security Considerations

- 락 키는 `{aggregate_type}:{aggregate_id}` 단위로 구성한다. 서로 다른 애그리거트는 서로를 막지 않는다.
- **전역 락 금지**: 락 범위 = 단일 `aggregate_id`만. 이를 어기면 애그리거트 경계 밖의 데이터에 대한 암묵적 의존이 생긴다.

### 6.3 Performance & Scalability

#### 핫 애그리거트 — 직렬화는 버그가 아니라 정확성의 근거

인기 슬롯 하나가 곧 핫 스트림 하나라, 그 슬롯을 노리는 모든 시도가 같은 애그리거트 락에서 직렬화된다 (한 번에 하나만 락을 잡고 N+1을 적는다). **이 직렬화는 받아들인다** — 한 자리에 대한 결정이 한 줄로 서야 이중 점유가 안 난다. 완화는 정확성을 깨지 않는 선, 곧 **스트림 granularity를 잘게** 잡는 것까지다.

- "식당 하루 전체 타임테이블"이 한 애그리거트 → 그 식당의 모든 예약이 직렬화
- "슬롯(시각×테이블)"이 한 애그리거트 → 다른 슬롯은 다른 스트림이라 동시에 진행

단, 너무 잘게 쪼개면 "한 식당에서 동시에 N석까지" 같은 **교차-슬롯 불변식**을 한 애그리거트로 못 지켜 사가로 떠넘겨야 한다. granularity는 *경합 완화*와 *교차 불변식* 사이의 트레이드오프다 — 경계를 긋는 일은 위 가이드 1·2 (불변식 경계로 식별·작게 유지)와 **이벤트 스토밍 재실시**에서 확정한다. 동시성 RFC는 요구사항만 넘긴다: "핫스팟이 예상되는 경계(슬롯·좌석)는 경합 범위를 줄이는 방향으로 식별하라."

#### 학습 프로토타입에서의 락 비용 수용

평소 락 획득 비용은 학습 프로토타입에서 수용한다 (측정할 실트래픽이 없어 낙관의 "평소 공짜" 이득이 실재하지 않고, 분산 락을 직접 운영하는 학습가치가 더 크다). [[DESIGN-008]]이 파티션 키를 `aggregate_id`로 잡아 전달 순서를 애그리거트별로 보장한 것과 같은 결 — 동시성도 순서도 애그리거트 경계 안에서 푼다.

### 6.4 Observability

- append 경로의 시퀀스 채번은 **한 곳으로 모아**, 이 자리의 UNIQUE 위반이 *항상* 동시성 충돌로만 해석되게 한다 (프로그래밍 버그의 중복 키와 구분).
- lock-wait 타임아웃 빈도, L0 UNIQUE 발동 빈도를 메트릭으로 노출해 핫 애그리거트를 조기 감지한다.

### 6.5 Migration / Rollback

- V1의 `*DomainService` 로직 재배치는 컨텍스트별 이벤트 스토밍 재실시 이후 단계적으로 진행한다.
- ES 컨텍스트는 `handle/apply` 가 이벤트 스토어와 직접 맞물린다.
- 비-ES 컨텍스트도 동일한 리치 애그리거트 원칙을 따르되, 상태 테이블에 저장 + Outbox 발행한다 ([[DESIGN-003]]).

## 7. Risks & Mitigations

| 리스크 | 완화 |
|--------|------|
| Redis 장애 시 L1 락 불가 | L1' DB 비관 락으로 폴백. 낙관 락으로 회귀하지 않는다. |
| 단일 Redis·`allkeys-lru` 에서 락 키 evict | L0 UNIQUE가 최종 안전망으로 흡수. split-brain은 *비효율*(일시 재시도)일 뿐 *부정확*이 아니다. |
| 페일오버·리스 만료·전환 창의 dual-provider split-brain | 두 라이터가 같은 N+1을 적으려 할 때 L0 UNIQUE가 두 번째 INSERT를 거절 |
| 애그리거트 granularity 오판 (너무 크거나 작음) | 이벤트 스토밍 재실시로 경계 확정. 변경은 사가 범위에 영향을 준다. |
| 도메인 서비스 증가 = 빈약 도메인 회귀 | "도메인 서비스가 많다 = 빈약 도메인 신호" 원칙을 코드리뷰 기준으로 삼는다. |

## 9. Appendix

### 9.1 Glossary

| 용어 | 설명 |
|------|------|
| **리치 애그리거트** | 불변식 검증과 상태 전이 로직을 스스로 보유한 애그리거트. 빈약한 애그리거트(anemic aggregate)의 반대. |
| **handle/apply 패턴** | `handle`은 명령을 받아 이벤트를 생성, `apply`는 이벤트를 상태에 적용. ES 리플레이와 신규 발행을 동일 경로로 처리한다. |
| **L0 안전 불변식** | `(aggregate_id, sequence_no)` UNIQUE 제약. 락이 어떻게 되든 제거하지 않는 최종 안전망. |
| **L1 경합 직렬화** | Redisson 분산 락으로 같은 애그리거트를 향하는 라이터를 큐로 세우는 1차 제어. |
| **L1' 폴백** | Redis 불가 시 DB 비관 락으로 강등. 낙관 락으로 회귀하지 않는다. |
| **핫 애그리거트** | 경합이 집중되는 애그리거트. 직렬화는 정확성의 근거이므로 granularity 조정으로 완화한다. |
| **빈약 도메인 신호** | 도메인 서비스가 많을수록 로직이 애그리거트 밖으로 흘러나온 증거. V1의 주요 문제. |
