## 1. Background

V1은 동기 CRUD였다 — `POST` 직후 `GET`이 방금 쓴 것을 돌려준다. 한 트랜잭션·한 DB라 당연했다. V2는 ES 위에서 쓰기를 받으면 **이벤트는 즉시 커밋되지만 그 이벤트로 read model 프로젝션이 갱신되는 것은 비동기**다(DESIGN-003-write-model · DESIGN-004-read-model). 즉 "쓰고 바로 그 결과를 읽을 수 없다"가 V2의 기본값이다.

계약은 이 사실을 숨기지 말고 표면에 새겨야 한다 — 숨기면 클라이언트는 경합에서 산발적으로 실패하고, 그 실패는 재현이 어렵다. 안쪽에서 command 핸들러와 read model을 나눈 것(DESIGN-004-command-hexagonal-query-layered)과, 그걸 HTTP로 어떻게 노출하느냐는 별개의 문제다. 클라이언트가 보는 것은 엔드포인트와 응답 바디뿐이라, 그 표면이 CQRS의 성질을 정직하게 드러내지 못하면 안쪽을 아무리 잘 갈라도 클라이언트는 V1과 같은 가정을 하고 깨진다.

> 본 문서는 **목표 계약**이다. 현재(V1)는 동기 CRUD + `@ControllerAdvice` 글로벌 예외 처리로 돈다(DESIGN-002-current-state). 아래 task-based·202·cursor 규약은 V2의 도착점이며, 컨텍스트 전환(DESIGN-005-migration) 순서대로 단계적으로 도입한다.

---

## 2. Goal

command/query 외부 인터페이스 규약을 확정한다. 구체적으로 아래 여섯 규약을 확립한다.

1. command는 task-based로 받는다
2. 비동기 응답은 202가 기본이다
3. 멱등은 서버(도메인)가 떠안는다
4. 실패는 셋으로 갈라 알린다
5. 클라이언트에게는 한 표면으로 보인다
6. query는 cursor 페이징으로 조회한다

---

## 3. Non-Goal

- 구체 엔드포인트 목록·행위 명명 규약 (구현 사이클에서 도메인 이벤트 카탈로그와 함께 확정)
- API 버저닝 방식 (경로 prefix vs 헤더 — 구현 사이클에서 확정)
- 202 결과 조회 메커니즘의 구체 (폴링/SSE/웹소켓 — DESIGN-004-read-model read-your-writes 결론에 종속)

---

## 4. Proposed Solution

### 4.1 command는 task-based로 받는다

자원 CRUD(`PUT /reservations/{id}`)가 아니라 행위 단위(`POST /reservations/{id}/cancel`)로 받는다. 안쪽이 이미 그 모양이기 때문이다 — 쓰기를 도메인 이벤트로 적재하는데(DESIGN-003-write-model), 이벤트는 본질적으로 "무슨 일이 일어났다"는 행위 기록이다. `PUT`으로 자원 전체를 덮어쓰면 그 diff를 역산해 `Cancelled`인지 `Rescheduled`인지를 추측해야 한다 — 손실이 크고 깨지기 쉽다. command가 의도(`cancel`·`reschedule`)를 들고 들어오면 그 의도가 그대로 이벤트가 되어, API 표면과 이벤트 저장소가 한 줄로 정렬된다.

- 단순 메타데이터 수정처럼 행위로 명명할 가치가 옅은 것까지 task-based로 강제하지 않는다.
- 행위로 떨어지는 것과 아닌 것의 경계는 **도메인 이벤트 카탈로그**와 함께 긋는다(구현 사이클).

### 4.2 비동기 응답은 202가 기본

command를 받았을 때 **이벤트만 커밋하고 즉시 `202 Accepted`** 를 돌려준 뒤, 결과는 별도 조회로 확인하게 한다. 프로젝션 완료를 동기로 기다려 200을 돌려주는 방식은 쓰기·읽기를 가른 이유 자체를 무력화한다 — 두 경로의 결합도가 다시 올라가고, 프로젝션이 느리거나 막히면 쓰기까지 같이 멈춘다.

```
POST /reservations/{id}/cancel
→ 202 Accepted   { "위치 토큰": "...", ... }   # 이벤트는 받아 적었다, 반영은 곧 따라온다
```

- 202를 받은 클라이언트가 **자기 쓰기를 확인**하는 길은 DESIGN-004-read-model의 read-your-writes 메커니즘을 그대로 빌려 쓴다(이벤트 위치 토큰을 들고 폴링하든, 그 토큰까지 따라잡은 read를 보장받든).
- **결과 조회 방식의 구체(폴링/SSE/웹소켓)는 DESIGN-004-read-model의 read-your-writes 결론에 종속**시켜 함께 본다.
- **모든 것이 202는 아니다.** 입력 검증 실패처럼 이벤트를 적기도 전에 동기로 거절할 수 있는 것은 즉시 4xx다(§4.4). 동기 거절과 202의 경계는 구현 사이클에서 긋는다.

### 4.3 멱등은 서버가 떠안는다 — 클라이언트 키를 받지 않는다

202를 기본으로 두는 순간 중복 제출이 현실이 된다 — 202만 받은 클라이언트는 불안하면 다시 누른다(더블클릭·타임아웃 재시도). 같은 의도가 두 번 들어와 이벤트가 둘 쌓이면 예약이 두 번 취소·생성된다.

결제 API류가 쓰는 **클라이언트 발급 `Idempotency-Key` 패턴은 채택하지 않는다.** 그 패턴은 서버가 자기 상태만으로 "재시도인지 의도된 두 번째 요청인지" 구분할 수 없을 때 클라이언트가 키로 그 구분을 선언하게 하는 장치다. 하지만 클라이언트를 우리가 만들고 도메인 불변식을 우리가 쥐고 있어 그 구분을 클라이언트에 떠넘길 필요가 없다. 대신 도메인이 떠안는다.

| command 종류 | 멱등 흡수 방식 |
|--------------|----------------|
| **상태 전이**(`cancel`·`reschedule` — 기존 애그리거트에 가하는 행위) | *자연 멱등 + 비관 락 직렬화*. 비관 락이 같은 애그리거트의 쓰기를 한 줄로 세워 재시도를 락 안에서 재로드·재판단하므로, 이미 취소된 걸 다시 취소하면 no-op으로 흡수된다. 락 유실 edge의 잔여 충돌은 `(aggregate_id, sequence_no)` UNIQUE 백스톱이 잡아 바운디드 재시도/409로 처리(DESIGN-006-aggregate-design) |
| **생성**(자연 멱등이 약함) | *도메인 유니크 불변식*. "같은 사용자가 같은 슬롯을 두 번 예약 불가" 같은 규칙이 있으면 더블클릭의 두 번째 요청이 도메인 충돌(409)로 거절됨 |

- 핵심은 재시도/의도된 중복의 구분을 *클라이언트가 키로 선언*하는 대신 *도메인이 떠안게* 하는 것 — 멱등이 API 계약이 아니라 도메인 규칙으로 내려가 클라이언트 표면이 가벼워진다.
- 이 **요청-단 멱등**은 DESIGN-008-messaging-topology의 *전달 멱등*과 다른 층이다. 요청을 도메인이 한 번만 받아들였어도 그로 인해 적힌 이벤트는 컨슈머에게 두 번 전달될 수 있으므로, 전달 멱등은 여전히 따로 필요하다.
- **잔여 케이스**: 자연 유니크 불변식이 없는 생성 command는 도메인만으로 재시도/의도된 중복을 못 가른다. 이 경우에 한해 *짧은 윈도의 서버 측 디듀프* 또는 *서버 발급 토큰*을 검토한다. 클라이언트 발급 키는 외부·비신뢰 클라이언트가 붙는 그림이 생기면 다시 테이블에 오른다.

### 4.4 실패는 셋으로 갈라 알린다

command가 거절되는 경로는 셋이고 클라이언트의 대응이 제각각이라, 한 덩어리 500이나 막연한 400으로 뭉뚱그리면 클라이언트는 구분할 수 없다.

| 실패 | HTTP | 클라이언트 대응 |
|------|------|------------------|
| 입력 검증 실패(형식 오류) | `400` | 요청을 고쳐 재전송 |
| 도메인 규칙 위반(영업시간 밖 예약, 락 잡고 reload하니 자리 없음 등) | `422`(또는 409 계열) | 보통 고쳐도 안 됨 — 확정적 거절 |
| 쓰기 경합 잔여 충돌(lock-wait 타임아웃 / 락 유실 edge의 UNIQUE 위반) | `409`(또는 `503` + `Retry-After`) | 최신 상태 재조회 후 재시도하면 풀림 |

- 바디에는 **기계가 분기할 에러 코드 + 사람이 읽을 메시지**를 함께 싣는다.
- 동시성은 비관 락으로 직렬화하므로 **동시 충돌은 대부분 락 안에서 소거**된다 — 클라이언트가 보는 쓰기 경합은 잔여 표면뿐이다. lock-wait 타임아웃은 `409`/`503`(+`Retry-After`)로 재시도를 신호하고, 락 유실 edge의 UNIQUE 위반은 서버가 바운디드 재시도로 흡수하다 못 풀면 `409`로 올린다.
- 특히 이 잔여 충돌의 `409`/`503`은 "재시도하면 풀릴 수 있다"는 신호이므로 **영구 실패와 반드시 구분**한다. 락을 잡고 reload한 뒤 도메인 판단이 뒤집힌 거절(자리 없음 등)은 재시도로 풀리지 않는 확정적 거절이라 `422`/`409` 쪽이다.
- V1의 `@ControllerAdvice` 글로벌 예외 처리(도메인 예외 계층 → HTTP 응답 매핑을 한 곳에 모으는 발상)는 그대로 계승한다.
- 쓰기 경합 잔여 충돌을 `409`/`503`으로 즉시 노출할지, 202 모델 안에서 결과 조회 시점에 알릴지는 §4.2 비동기 응답 모델과 엮여 있어 DESIGN-004-read-model read-your-writes 결론·구현 사이클에서 함께 본다.

### 4.5 클라이언트에게는 한 표면으로 보인다

> 전제: 모든 트래픽 앞단에 게이트웨이·인증 서버가 선다는 것은 본 문서가 다투는 사안이 아니라 주어진 토대다(토폴로지·배치는 DESIGN-010-deployment-runtime · RFC-007-deployment-infra-ops의 몫).

내부에서 command/query를 나눈 분리를 **클라이언트에게 한 표면으로 노출한다.** 게이트웨이 뒤 한 표면으로 통합하되, command는 행위 `POST`에 202·도메인 멱등 규약이, query는 조회 `GET`에 cursor 페이징 규약이 붙는 식으로 **규약의 차이가 곧 성격 구분**이 되게 한다. 클라이언트는 한 호스트만 알면 되고, 어떤 호출에 비동기·멱등 규약이 적용되는지는 메서드·경로 모양으로 자명해진다.

- command/query를 **별도 백엔드로 실제 라우팅**하는 분리는 다른 층의 문제다 — 모듈을 물리 분리·배포하는 시점에 DESIGN-010-deployment-runtime(RFC-007-deployment-infra-ops)이 정한다. 지금은 "클라이언트가 보는 표면은 하나, 라우팅 분리는 배포 토폴로지가 익으면".
- **버저닝**: 깨는 변경을 흡수할 통로가 필요하므로 처음부터 정책을 박아둔다(경로 prefix vs 헤더 — 구체는 구현 사이클). 표면 분리는 모듈 물리 분리 시점에 재검토.

### 4.6 query는 cursor 페이징으로 조회한다

페이지네이션·필터·정렬을 표준화하되, 핵심은 **cursor 페이징**이다. offset은 read model이 계속 갱신되는 V2에서 위험하다 — 페이지를 넘기는 사이 새 프로젝션이 끼어들면 offset 기준이 밀려 항목이 중복·누락된다. read model은 정의상 비동기로 흘러드는 데이터라 "고정된 0~N번"이라는 offset의 전제가 성립하지 않는다. cursor는 위치를 절대 인덱스가 아니라 정렬 키 기준점으로 잡으므로 그 사이 데이터가 끼어들어도 안정적이다.

- cursor가 안정적이려면 **정렬 키가 read model 프로젝션에 안정적으로 채워져** 있어야 한다 — 이 규약은 read model 투영 형태와 맞물린다(DESIGN-004-read-model).
- 임의 정렬·복합 필터의 cursor 일반화는 까다롭고 일부 관리용 조회는 offset이 실용적일 수 있다 — 표준은 cursor, 예외 범위는 구현 사이클에서 한정.

## 5. Alternatives Considered

### 클라이언트 발급 Idempotency-Key 패턴

결제 API류에서 널리 쓰이는 방식이다. 서버가 자기 상태만으로 "재시도인지 의도된 두 번째 요청인지" 구분할 수 없을 때 클라이언트가 키로 선언하게 한다. 클라이언트를 우리가 만들고 도메인 불변식을 우리가 쥐고 있는 현 구조에서는 필요하지 않다 — 도메인이 직접 멱등을 흡수하는 쪽이 클라이언트 표면을 단순하게 유지한다. 외부·비신뢰 클라이언트가 붙는 그림이 생기면 다시 테이블에 오른다.

### 동기 200 응답 (프로젝션 완료 대기)

command 처리 후 프로젝션 완료를 기다려 200을 돌려주는 방식은 V1 경험과 가장 가깝다. 그러나 쓰기·읽기를 가른 이유 자체를 무력화한다 — 두 경로의 결합도가 다시 올라가고, 프로젝션이 느리거나 막히면 쓰기까지 같이 멈춘다. 채택하지 않는다.

### offset 페이징

구현이 단순하다. 그러나 read model이 비동기로 갱신되는 V2에서는 페이지를 넘기는 사이 항목이 중복·누락될 수 있어 위험하다. 관리용 조회 등 예외 범위를 한정해 허용할 수 있으나, 표준은 cursor로 확정한다.

## 6. Details

### 구현 사이클로 넘기는 것

- command 엔드포인트 목록·행위 명명 규약 — task-based 경계, 도메인 이벤트 카탈로그와 함께.
- 202 결과 조회 메커니즘(폴링/SSE/웹소켓)·동기 거절 vs 202 경계 — DESIGN-004-read-model read-your-writes 결론에 종속.
- 서버 측 멱등 잔여 케이스(유니크 불변식 없는 생성) — 짧은 윈도 디듀프 vs 서버 발급 토큰.
- 에러 분류 HTTP 상태·코드 표와 `@ControllerAdvice` 매핑 범위; 쓰기 경합 잔여 충돌(lock-wait 타임아웃·UNIQUE 위반) 노출 시점·`Retry-After` 정책.
- API 버저닝 방식(경로 prefix vs 헤더)·표면/라우팅 분리 재검토 시점(DESIGN-010-deployment-runtime 토폴로지 확정 시).
- cursor 인코딩·정렬 키 규약과 offset 예외 허용 범위.

## 7. Risks & Mitigations

| 위험 | 완화 |
|------|------|
| 클라이언트가 202를 이해하지 못하고 동기 응답을 가정 | API 문서에 202 규약 명시; read-your-writes 토큰 기반 확인 경로 제공 |
| 도메인 멱등 흡수가 누락된 생성 command에서 이중 생성 | 유니크 불변식 없는 생성 command는 구현 사이클에서 별도 디듀프 메커니즘 적용 |
| cursor 정렬 키가 프로젝션에 누락돼 페이징 깨짐 | 프로젝터 단위 테스트에서 정렬 키 존재 검증 강제 |
| 실패 3분류 경계 모호 → 클라이언트 오분기 | `@ControllerAdvice` 매핑 표를 구현 사이클에서 명시적으로 확정 |
