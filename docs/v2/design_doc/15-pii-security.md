# V2 Design Doc — 15. PII Security (크립토 셰딩)

- **상위 결정**: [[11.es-pii-crypto-shredding]] · [[RFC-005-pii-security]]
- **개요**: [[00-design-overview]] · **이벤트 스토어**: [[08-event-store-lifecycle]]
- **인접**: [[03-read-model]] (프로젝션 정정) · [[14.testing-strategy]] (셰딩 누락 가드)

> [[08-event-store-lifecycle]]가 정리한 "append-only의 대가" 중 하나는 보존이나 스냅샷처럼 마냥 운영으로 미룰 수 없다 — 한 번 추가된 이벤트는 물리적으로 지울 수 없는데(그게 append-only의 정의다), 운영하다 보면 *어떤 사람의 데이터는 진짜로 없애야 하는* 순간(탈퇴·삭제 요청·유출 blast radius 축소)이 오기 때문이다. "지울 수 없는 저장소"와 "지워야 하는 현실"이 정면으로 부딪친다 — 규제 이전의 엔지니어링 긴장이고, 실유저가 붙으면 GDPR·개인정보보호법이 이를 비-옵션으로 굳힌다. 본 문서는 그 충돌을 **크립토 셰딩**으로 푸는 메커니즘을 *어떻게 짓는가* 수준에서 확정한다. *왜* 이 전략인지의 근거는 [[11.es-pii-crypto-shredding]]에 있다.

## 0. 출발점: 크립토 셰딩이란

이벤트 본문에는 PII를 평문이 아니라 **암호문**으로 적고, 복호 키는 **정보주체별로 따로** 보관한다. 삭제 요청이 오면 이벤트는 그대로 둔 채 **그 주체의 키만 파기**한다. 키가 사라지면 암호문은 영구히 풀 수 없는 바이트 덩어리가 되니, 사실상 삭제와 같다. 여기에 더해 애초에 저장하는 PII를 최소화한다(Zero Payload 정신, [[02-write-model]] 계승).

세 가지 불변식이 이 전략을 떠받친다. 이 셋이 깨지면 셰딩은 성립하지 않는다.

1. **PII는 그 주체의 키 아래 암호문으로만 존재한다.** 평문으로 새는 PII는 키를 지워도 그대로 남아 셰딩을 무력화한다.
2. **키 저장소는 이벤트와 분리된다.** 한 백업·복원이 이벤트와 키를 함께 되살리면 셰딩이 통째로 무효가 된다.
3. **삭제는 완전하다.** 백업·인덱스·콜드 스토리지를 가리지 않고, 키 한 번의 파기가 전 경로의 셰딩을 성립시켜야 한다.

## 1. 키 저장소 — 별도 테이블·새 스키마

셰딩 키는 **정보주체(data subject)당 하나**다. 한 사람 = 키 하나여서 삭제 요청 단위와 셰딩 단위가 정확히 일치한다. 그 키로 그 주체의 PII를 암호화해 이벤트에 싣고, 삭제 요청이 오면 그 키 하나를 즉시·완전히 파기한다.

키는 **전용 테이블을 새 스키마로 따로 파서** 둔다. 매체 후보(전용 KMS·외부 시크릿 스토어)는 검토했으나 비채택이다 — 키 저장소에 필요한 네 요건과 가장 곧게 맞는 것이 분리 스키마의 테이블이기 때문이다.

| 요건 | 연산 | 별도 테이블이 곧게 맞는 이유 |
|------|------|------------------------------|
| 주체 생성 시 **동적 생성** | INSERT | 미래 주체를 미리 알 수 없으니 사전 등록이 아니라 런타임 생성 |
| 재생·조회 시 **조회** | SELECT | 키 머티리얼을 읽어 복호 |
| 삭제 요청 시 **즉시 완전 셰딩** | DELETE | KMS CMK식 7~30일 예약 삭제 지연이 없다 — 즉시 하드 삭제 |
| 이벤트와 **분리** | 새 스키마 | 애플리케이션 데이터와 갈라 백업을 따로 스코프(불변식 #2) |

```
-- 이벤트 데이터와 분리된 별도 스키마
key_store.subject_key(
  subject_id,            -- 데이터 주체(예: userId), 주체당 1행
  key_id,
  key_material,          -- 주체 생성 시 동적 생성된 키
  status,                -- ACTIVE | SHREDDED
  created_at, shredded_at
)
```

> 키 라이프사이클(생성·조회·삭제)은 **한 포트 뒤에 캡슐화**한다. 크립토 셰딩의 신뢰성은 매체가 무엇이냐보다 *키를 정말 지웠는가*에 달렸고, 그 보장은 라이프사이클을 한 군데 모았느냐에서 나오기 때문이다. 매체를 갈아끼우더라도 이 경계는 유지한다.

⚠️ **(이의 여지)** 테이블의 키는 그 스키마 접근통제만큼만 안전하다 — 테이블이 읽히면 전 PII가 복호 가능하다. 그래서 키 스키마는 별도 자격/역할로 접근을 좁힌다. 키 자체를 상위 마스터 키로 감싸는 **봉투 암호화(envelope encryption)는 격리·규제 요구가 실재할 때 도입하는 졸업 경로**로 남긴다 — 마스터 키의 거처라는 또 다른 질문을 끌고 오므로, 지금은 분리 스키마 + 접근통제를 경계로 삼는다.

## 2. 페이로드 — PII만 암호화 봉투

```
event_store.payload(JSON) = {
  ...비-PII 필드(평문)...,                                  -- 리플레이·정합성에 필요
  "_encrypted": { "key_id": "...", "subject_id": "...", "cipher": "..." }  -- PII만 암호화 봉투
}
```

- **쓰기**: PII 필드는 주체 키로 암호화한 봉투로 페이로드에 넣는다. 비-PII(예약 시각·상태·식당 식별자)는 평문 — 리플레이·정합성에 필요하다.
- **읽기/리플레이**: `apply` 시 키가 `ACTIVE`면 복호해 PII를 채운다. `SHREDDED`(키 행이 삭제돼 조회 불가)면 PII 자리는 **익명 토큰**으로 두고 나머지 상태는 정상 복원한다. 복호 실패는 예외가 아니라 *정상 경로*다.
- **삭제 요청**: 해당 `subject_id` 키를 즉시 하드 삭제한다. 이벤트는 건드리지 않는다 → append-only 유지.
- **스냅샷도 동일**: 스냅샷([[08-event-store-lifecycle]] §1)도 PII를 담을 수 있으므로 같은 봉투를 적용한다. 키 폐기 시 스냅샷 PII도 복호 불능.

셰딩 표현은 **익명 토큰으로 통일**한다 — `null`은 "값 없음"과 "셰딩됨"을 구분 못 하고, `"[redacted]"`는 문자열 자리에만 맞다. 익명 토큰은 "여기 셰딩된 PII가 있었다"는 사실을 타입과 무관하게 표현한다. 이미 그 PII로 만들어져 떠 있는 **다운스트림 프로젝션은 셰딩을 하나의 이벤트로 취급해 그 '셰딩 이벤트'에 반응해 자기 투영을 정정**한다 — 재생 시 복호 실패 처리와 같은 규칙을 쓰니 일관된다. 인덱스·캐시에 비정규화된 PII까지 한 번에 정정되는지는 프로젝션별로 따진다([[03-read-model]]).

## 3. 검색 — PII는 쿼리 키가 아니다

암호문은 그 자체로 동등·부분·범위 검색이 막힌다. 그래서 **기본적으로 PII를 쿼리 키로 쓰지 않는다.** read model은 불투명 식별자(`userId`·`reservationId`)로 조회하고, PII(이름·이메일·전화)는 그 위에 *표시용* 암호문으로 따라붙는다 — 조회는 식별자로, 복호는 표시 시점에만. 대부분의 화면이 이 모양으로 떨어지고, PII로 자유 검색이 되는 read model 자체가 위험 표면이라 프라이버시 관점에서도 이쪽이 옳다.

진짜 PII *동등* 검색이 필요한 좁은 경우(관리자 조회·로그인 식별)에는 **blind index** — PII의 keyed-HMAC를 암호문 옆에 저장해 동등 일치만 가능하게 — 를 쓴다. 결정적인 것은 이 인덱스가 반드시 **주체별 셰딩 키에서 파생**돼야 한다는 점이다.

> 전역 키로 만든 인덱스는 키를 지워도 남아 "이 값과 같다 / 그 사람이 있었다"를 여전히 확인시켜주는 **셰딩 누수**가 된다. 주체 키로 파생하면 키 삭제가 인덱스도 함께 무효화하니, 핫/콜드를 가리지 않는 셰딩 원리와 결이 같다.

⚠️ blind index는 동등 일치만 지원한다. 부분·범위·정렬을 PII에 요구하는 요구사항이 나오면 그건 암호화를 푸는 신호가 아니라 **요구사항을 재검토할 신호**다.

## 4. 콜드 스토리지의 셰딩 경로

[[RFC-004-event-store-schema-evolution]]에서 오래된 이벤트를 S3 콜드 스토리지로 이관하기로 한 결정이 여기 그림자를 드리운다 — 콜드로 빠진 이벤트도 키 삭제 한 번으로 같이 셰딩돼야 한다(불변식 #3). 다행히 크립토 셰딩의 구조가 답을 준다: 셰딩은 본문을 건드리는 게 아니라 키를 지우는 행위다. 그러니 **콜드(S3) 본문은 이관하되 셰딩 키는 핫 키 저장소에 영속하고 콜드로 함께 이관하지 않는다.** 키는 핫 경로의 키 저장소에 남고, 콜드엔 풀 수 없는 암호문만 간다. 키 저장소에서 키를 지우는 한 번의 동작이 핫·콜드를 가리지 않고 셰딩을 성립시킨다. 이 규칙은 [[08-event-store-lifecycle]] §2.2와 동일하다.

- **콜드 이벤트 재생 시 핫 키 저장소를 참조해 복호한다.** 본문이 콜드로 빠져도 복호 키의 출처는 항상 핫 키 저장소 하나다 — 키가 `ACTIVE`면 복호, `SHREDDED`면 §2와 같은 정상 경로(익명 토큰)를 탄다.
- **키 백업은 셰딩 의미론을 깨지 않는다.** 셰딩된 키는 백업에서도 함께 무효화되거나 애초에 백업 대상에서 제외돼, 백업·복원 한 번이 셰딩을 부활시키지 못한다(불변식 #2, [[08-event-store-lifecycle]] §4.3과 동일). blind index도 주체 키 파생이라 키와 함께 무효화된다.

## 5. 셰딩 누락 방지 — 빌드 타임 강제

PII 필드가 암호화 경로를 우회해 평문으로 저장되면 셰딩은 처음부터 불가능하다(불변식 #1 위반). 키를 지워봐야 평문이 그대로 남는다. 이건 리뷰에 기대선 안 되는 종류의 실수다 — 리뷰는 반드시 빠뜨린다.

- **모든 필드는 PII 여부를 명시적으로 선언한다.** 미분류 필드가 조용히 평문으로 새는 것을 디폴트로 막는다.
- **ArchUnit/Konsist 규칙으로 빌드 타임에 강제한다.** PII로 선언된 필드가 암호화 래퍼를 거치지 않고 이벤트 페이로드에 실리면 빌드를 깬다. 선언이 있어야 규칙이 검사할 대상이 생긴다. [[14.testing-strategy]]의 ArchUnit 레이어에 얹는다.

⚠️ 정적 규칙이 잡는 건 "선언과 경로의 불일치"까지다. "이 필드가 사실 PII인데 비-PII로 선언됐다"는 오분류는 못 잡는다 — 그건 분류 정책(§아래 🌱)의 몫이다.

## 구현 사이클로 넘기는 것

- 키 테이블 스키마 상세(주체 키 1행, 동적 생성·즉시 하드 삭제)와 분리 경계 포트 인터페이스, 키 스키마 접근통제·백업 분리 스코프 구현. 봉투 암호화(마스터 키 래핑) 졸업 경로.
- blind index의 HMAC 구성과 주체키 파생, 동등 검색이 실제 필요한 필드 식별(분류와 함께).
- 익명 토큰의 직렬화 표현, 프로젝션별 정정 경로 — 셰딩을 하나의 이벤트로 취급해 다운스트림이 자기 투영을 정정하게 하되, 인덱스·캐시에 비정규화된 PII까지 한 번에 정정되는지는 프로젝션별로 따진다([[03-read-model]]).
- ArchUnit/Konsist 규칙의 정확한 술어(선언 어노테이션 ↔ 암호화 래퍼 경로 매칭).
- 키 로테이션 주기·백업 보존·접근통제 운영 수치 — 별도 ADR + 운영 측정.
- 콜드 스토리지 복호 시 핫 키 저장소 참조 결합도와 S3 이관 설계 정합([[RFC-004-event-store-schema-evolution]]).
- 🌱 **PII 필드 분류표** — 암호화·셰딩 대상 필드 집합은 이벤트 카탈로그가 먼저 서야 확정된다. 이벤트 스토밍/도메인 작업 완료 후 별도 ADR("PII 분류 정책")로 비준한다.
