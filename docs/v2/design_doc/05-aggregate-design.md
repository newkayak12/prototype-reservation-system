# V2 Design Doc — 05. Aggregate Design (도메인 로직 배치)

- **개요**: [[00-design-overview]] · **근거**: [[02-domain-limitations]]
- **관련 결정**: [[03.command-hexagonal-query-layered]] · [[02-write-model]] · [[RFC-014-aggregate-concurrency-control]]

> 이 문서는 command 측 **애그리거트를 어떻게 설계하고, 로직을 어디에 둘지**의 참고 기준이다. 구현 사이클에서 컨텍스트별 애그리거트를 설계할 때 이 규칙을 따른다.

## 다루는 취약점 (V1)

> **취약점 W-1 — 빈약한 애그리거트 + 흩어진 도메인 로직**
> V1은 상태 변경 로직의 ~95%를 **16개 이상의 `*DomainService`** 에 두고, 애그리거트는 `var` + setter 데이터 홀더로 만들었다([[02-domain-limitations]] #1). 그 결과 "어떤 이벤트가 언제 발생하는가"의 권위가 애그리거트에 없어, 이벤트 소싱으로 가는 데 가장 큰 장애가 된다.

핵심 진단: V1의 `*DomainService` **대부분은 진짜 도메인 서비스가 아니라 애플리케이션 오케스트레이션**이다(`validate → 객체 생성 → save → snapshot`). 도메인 로직과 절차가 한 곳에 뭉쳐 있다.

## V2 원칙 — 리치 애그리거트

애그리거트는 자신의 불변식과 상태 전이를 **스스로** 책임진다.

```kotlin
// 개념 예시 — 시그니처는 구현 사이클에서 확정
class Reservation private constructor(/* state */) {
    // 1) 명령을 받아 불변식 검증 후 발생할 이벤트를 반환
    fun handle(command: CancelReservation): List<DomainEvent> {
        require(canCancel(command.now)) { "취소 가능 기한(방문 3일 전) 초과" }
        return listOf(ReservationCancelled(id, command.reason, command.now))
    }
    // 2) 이벤트를 상태에 적용 (불변 전이) — 리플레이·신규 발생 공용
    fun apply(event: ReservationCancelled): Reservation { /* ... */ }
}
```

- 불변식 검증은 **애그리거트 안**에서 (V1처럼 서비스에서 하지 않는다).
- 상태 변경은 **이벤트를 통해** 표현(ES) 또는 이벤트와 함께 발행(비-ES).

## 로직 배치 규칙 (triage)

V1의 `*DomainService` 에 있던 로직을 다음 기준으로 재배치한다.

| 로직 성격 | V2 행선지 | 위치 |
|-----------|-----------|------|
| 단일 애그리거트의 불변식·상태 전이 | **애그리거트** | `command.<ctx>.domain` |
| 적재 → 애그리거트 호출 → 저장 → 이벤트 발행 (절차) | **애플리케이션 서비스(유스케이스)** | `command.<ctx>.application.service` |
| 진짜 여러 애그리거트에 걸친 도메인 규칙 / 순수 도메인 계산 | **얇은 도메인 서비스** (소수만) | `command.<ctx>.domain` |

> 결과: V1의 16개 서비스 대부분이 **애그리거트 + 유스케이스**로 흡수되고, 도메인 서비스는 몇 개만 남는다. "도메인 서비스가 많다 = 빈약 도메인 신호"로 본다.

## 애그리거트 설계 가이드

1. **불변식 경계로 식별** — "항상 함께 일관성이 지켜져야 하는 것"이 한 애그리거트.
2. **작게 유지** — 큰 애그리거트는 경합·잠금 범위를 키운다. 의심되면 쪼갠다.
3. **애그리거트 간은 ID 참조** — 객체 직접 참조 금지(예: `Reservation` 은 `restaurantId` 만 안다).
4. **부수효과는 이벤트로** — 다른 애그리거트/컨텍스트 변경은 직접 호출이 아니라 이벤트 발행으로([[02-write-model]]).
5. **불변(immutable) 전이 선호** — `apply` 는 새 상태를 반환(ES 리플레이 안전성).

## 동시성·쓰기 경합 제어 (비관 락 + UNIQUE 백스톱)

> 애그리거트는 곧 **동시성 직렬화 단위**다. 위 가이드 2번("작게 유지 — 경합·잠금 범위")이 왜 중요한지가 여기서 드러난다. 근거·전환 경위(원안 낙관 → 비관 락 supersede)는 [[RFC-014-aggregate-concurrency-control]].

V1에서는 행 잠금과 유니크 제약이 경합을 막아 줬다 — 두 손님이 같은 7시 테이블을 노려도, 한쪽이 행을 잡은 동안 다른 쪽은 기다리고 유니크 제약이 두 번째를 거절했다. V2의 ES 컨텍스트에는 그 잠글 행이 없다. 현재 상태는 이벤트 스트림을 리플레이한 결과고([[02-write-model]]), 쓰기는 상태 갱신이 아니라 스트림 끝에 이벤트를 *append*하는 것뿐이다. 갱신할 행이 없으니 잠글 행도 없다 — 그래서 경합 직렬화를 **명시적으로 다시 세운다**.

### 3층 — 잠그되 믿지 않는다

같은 7시 테이블을 두 손님이 동시에 노릴 때, V1의 행 잠금이 사라진 자리를 **비관 락이 메우고 `(aggregate_id, sequence_no)` UNIQUE가 최종 심판**한다. 락은 경합을 *완화*(liveness)하는 도구지 정확성(safety)을 보장하는 도구가 아니므로 — 락이 풀려도 이중 점유를 막을 안전망을 따로 둔다.

| 층 | 무엇 | 역할 |
|----|------|------|
| **L0 안전(불변)** | `(aggregate_id, sequence_no)` UNIQUE([[05.event-store-mysql-table]]) | append-only 스토어의 **진짜 정확성 불변식**. 어떤 락을 얹어도 **절대 제거하지 않는다** — split-brain·락 유실의 백스톱. |
| **L1 경합 직렬화(1차)** | 단일 `aggregate_id`에 대한 **Redisson 분산 락** | Redis 정상 시 같은 애그리거트로 향하는 라이터를 큐로 세운다. |
| **L1′ 폴백** | Redis 불가 시 **DB 비관 락**(per-aggregate lock-row `SELECT … FOR UPDATE`) | 락 제공자만 Redis→DB로 강등. **낙관으로 회귀하지 않는다.** command DB는 이벤트 append에 어차피 필수라 새 하드 의존이 0이다. |

- 애그리거트를 버전 N에서 로드했다면 다음 이벤트의 `sequence_no`는 N+1이다. append는 `(aggregate_id, N+1)`로 INSERT한다.
- L1/L1′ 락이 같은 애그리거트의 라이터를 한 줄로 세우므로 동시 충돌이 **대부분 소거**된다. 그래도 락 키 evict(단일 Redis·`allkeys-lru`)·페일오버·리스 만료·전환 창의 dual-provider split-brain으로 두 라이터가 같은 N+1을 적으려 할 수 있다 — 그 잔여 경합을 **L0 UNIQUE가 두 번째 INSERT를 거절**해 흡수한다. split-brain은 *비효율*(일시 재시도)일 뿐 *부정확*이 아니다.
- 평소 락 획득 비용은 학습 프로토타입에서 수용한다(측정할 실트래픽이 없어 낙관의 "평소 공짜" 이득이 실재하지 않고, 분산 락을 직접 운영하는 학습가치가 더 크다). [[07-messaging-topology]]가 파티션 키를 `aggregate_id`로 잡아 전달 순서를 애그리거트별로 보장한 것과 같은 결 — 동시성도 순서도 애그리거트 경계 안에서 푼다.

> **락 범위 = 단일 `aggregate_id`만. 전역 락 금지.** 락 키는 `{aggregate_type}:{aggregate_id}` 단위로, 서로 다른 애그리거트는 서로를 막지 않는다.

> 구현 위임 — Redisson 락 키 포맷·리스 TTL·watchdog 자동 연장, DB 폴백 lock-row 스키마·트랜잭션 스코프, Redis up/down 판정(서킷 브레이커)과 폴백 전환 창의 split-brain UNIQUE 흡수 검증은 구현에서 못박는다. append 경로의 시퀀스 채번은 **한 곳으로 모아**, 이 자리의 UNIQUE 위반이 *항상* 동시성 충돌로만 해석되게 한다(프로그래밍 버그의 중복 키와 구분). 스냅샷이 낀 로드의 expected-version은 **스냅샷 버전 + 이후 이벤트 수**로 계산한다([[08-event-store-lifecycle]] 스냅샷 전략과 정합).

### 충돌 처리 — 락이 대부분 소거, 잔여 표면 셋

락 보유로 동시 충돌이 **대부분 소거**되므로, 클라이언트가 보는 충돌 표면은 셋으로 좁혀진다.

| 충돌 종류 | 처리 | 예 |
|-----------|------|-----|
| **lock-wait 타임아웃** | 호출자에 재시도 신호 — **409/503 + retry-after** | 앞 라이터가 락 점유 중, 한도 내 미획득 |
| **도메인 거절** | **422/409로 확정** — 재시도 storm 없이 | 락 잡고 reload하니 "자리 없음": 7시 자리 경합에서 먼저 든 쪽이 점유하면 둘째는 판단이 뒤집힘 |
| **잔여 UNIQUE 위반** | **동시성 충돌로 흡수** — 바운디드 재시도/409 | 락 유실·split-brain edge에서 L0가 발동(드물지만 경로는 반드시 존재) |

핵심 경계는 **재시도하면 풀릴 수 있느냐**다. lock-wait 타임아웃·잔여 UNIQUE 위반은 재시도로 풀리는 일시 경합이지만, 도메인 거절(자리 없음)은 무한정 재시도해도 자리가 안 생기므로 **확정적으로 거절**한다 — 둘을 같은 409로 뭉뚱그리지 않는다. [[12-api-contract]]의 "락 충돌 409 = 재시도 신호"와 맞물리되, 그 409는 "락 경합/락 유실이라 최신을 다시 읽고 재시도하라"는 의미로 좁혀지고, 도메인 거절은 422/409로 분리된다. lock-wait 한도·백오프, 잔여 UNIQUE 충돌 매핑(`DuplicateKeyException`→충돌), 그리고 이 처리가 202 비동기 응답 모델 안에서 노출되는 시점은 구현에서 못박는다.

### 핫 애그리거트 — 직렬화는 버그가 아니라 정확성의 근거

인기 슬롯 하나가 곧 핫 스트림 하나라, 그 슬롯을 노리는 모든 시도가 같은 애그리거트 락에서 직렬화된다(한 번에 하나만 락을 잡고 N+1을 적는다). **이 직렬화는 받아들인다** — 한 자리에 대한 결정이 한 줄로 서야 이중 점유가 안 난다. 완화는 정확성을 깨지 않는 선, 곧 **스트림 granularity를 잘게** 잡는 것까지다: "식당 하루 전체 타임테이블"이 한 애그리거트면 그 식당의 모든 예약이 직렬화되지만, "슬롯(시각×테이블)"이 한 애그리거트면 다른 슬롯은 다른 스트림이라 동시에 진행된다.

> 🌱 단, 너무 잘게 쪼개면 "한 식당에서 동시에 N석까지" 같은 **교차-슬롯 불변식**을 한 애그리거트로 못 지켜 사가로 떠넘겨야 한다. granularity는 *경합 완화*와 *교차 불변식* 사이의 트레이드오프다 — 경계를 긋는 일은 위 가이드 1·2(불변식 경계로 식별·작게 유지)와 **이벤트 스토밍 재실시**에서 확정한다. 동시성 RFC는 요구사항만 넘긴다: "핫스팟이 예상되는 경계(슬롯·좌석)는 경합 범위를 줄이는 방향으로 식별하라."

### 경계를 넘는 일관성은 전역 락이 아니라 사가

이 제어는 *한 애그리거트* 안의 직렬화만 보장한다(락 범위 = 단일 `aggregate_id`). 여러 애그리거트에 걸친 불변식("결제와 예약 확정이 함께 성립", "식당 정원 초과 금지")은 사정권 밖이고, 이를 **전역 락으로 풀지 않는다** — 전역 락은 여러 애그리거트를 한꺼번에 잠가 작게 유지 원칙(가이드 2)을 정면으로 깬다.

- 즉시 일관성(한 애그리거트) = **비관 락 + UNIQUE 백스톱**.
- 최종 일관성(여러 애그리거트) = **사가**([[06-consistency-and-sagas]] · [[RFC-006-saga-process-manager]]).
- 둘의 경계가 곧 애그리거트 경계다.

예약 라이프사이클이 그 모양이다 — 점유(`timetable`)·결제(`payment`)·확정(`reservation`)이 각자 자기 애그리거트 락 안에서 쓰고, 단계 간 어긋남은 PM이 `SeatReleased`·`PaymentRefunded` 보상으로 되감는다.

### 헷갈리기 쉬운 세 층 — 동시성 ≠ 요청 멱등 ≠ 전달 멱등

같은 409·중복 언저리지만 *다른 문제, 각자 따로* 필요하다. 한 예약이 셋을 차례로 다 통과한다.

| 층 | 무엇이 막나 | 막는 대상 | 위치 |
|----|-------------|-----------|------|
| **동시성 충돌**(본 절) | 비관 락(Redisson/DB) 직렬화 + UNIQUE 백스톱 | 쓰기 *경합*(이중 점유) | append 시점 · command DB |
| **요청 멱등**([[12-api-contract]]) | 상태 전이 = 자연 멱등 + 버전 가드 / 생성 = 도메인 유니크 | 같은 의도의 *중복 제출*(더블클릭) | 요청 진입 · HTTP |
| **전달 멱등**([[07-messaging-topology]]) | inbox / Zero Payload upsert | *중복 전달* → 프로젝션 오염 | append 이후 · 메시징 |

## 적용 메모

- 컨텍스트별 구체 애그리거트·이벤트 목록은 **이벤트 스토밍 재실시 후** 확정(기존 보드는 참고용).
- ES 컨텍스트는 `handle/apply` 가 이벤트 스토어와 직접 맞물린다. 비-ES도 동일한 리치 애그리거트 원칙을 따르되, 상태 테이블에 저장 + Outbox 발행한다([[02-write-model]]).
