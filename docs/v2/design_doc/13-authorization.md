# V2 Design Doc — 13. Authorization (인가 모델)

- **상위 결정**: [[RFC-015-authorization-model]]
- **개요**: [[00-design-overview]] · **API**: [[12-api-contract]] · **읽기**: [[03-read-model]] · **쓰기**: [[02-write-model]]
- **관련 결정**: [[03.command-hexagonal-query-layered]]

> 이 문서는 V2에서 **"검증된 주체가, 이 자원에, 이 행위를 해도 되는가"**(인가)를 *어디에 어떻게 거는가*를 확정한다. 호출자가 누구인지(인증)는 전제다 — 게이트웨이·인증 서버가 토큰을 검증해 신원·역할 클레임을 확정한 뒤라야 이 문서가 시작한다(그 인증 경계 자체는 [[RFC-020-authentication-boundary-gateway]] · [[09-deployment-runtime]]).

> ⚠️ 본 문서는 **목표 아키텍처**다. 현재(V1)는 `SecurityConfig`가 경로 prefix에 역할을 박고(`requestMatchers(...).hasRole(...)`), 컨트롤러가 호출자 신원으로 자기 테이블을 읽어 "내 것만"이 자연히 걸렸다([[01-current-state]]). V2의 분리된 인가 배치는 [[04-migration]] 순서대로 컨텍스트 전환에 맞춰 깐다.

## 0. 출발점: V1에서 "녹아 있던" 인가가 V2에서 갈 곳을 잃는다

V1 인가는 데이터 접근 경로에 녹아 있었다. 경로-prefix 역할 게이트가 "이 URL은 ADMIN만"까지 거르고, 그 뒤는 컨트롤러가 **호출자 신원으로 자기 DB를 읽으니 자연히 자기 것만 나왔다**. "이 예약이 이 USER 것인가"를 따로 검사한 적이 없다 — 같은 트랜잭션·같은 테이블이 그걸 대신했다.

V2는 쓰기(ES/Outbox command 경로 — [[02-write-model]])와 읽기(별도 프로젝션 조회 — [[03-read-model]])를 찢는다([[03.command-hexagonal-query-layered]]). 둘은 더는 같은 테이블을 공유하지 않으므로 "자연히 걸리던" 층이 사라진다. 그래서 V2 인가는 **두 종류**로 쪼개 명시적으로 박는다.

| 종류 | 묻는 것 | 자원 상태를 보나 | 거는 위치 |
|------|---------|------------------|-----------|
| **역할 기반** | 이 *행위*를 이 역할이 할 수 있나 (자원 무관) | 아니오 | **게이트웨이/엣지** |
| **소유권/스코프 기반** | 이 *특정 자원*이 이 주체 것인가 | 예 (도메인 지식) | **애플리케이션 안** |

역할은 자원을 몰라도 판단되니 엣지에서 거칠게 거른다(V1 경로-prefix 발상 계승). 소유권은 자원의 상태를 봐야 알므로 도메인 지식이고, 엣지에 떠넘기면 게이트웨이가 도메인에 결합된다 — 안티패턴이다.

## 1. 역할 체계 (V1 계승)

```
Role            SecurityRole       비고
ROOT          → ROLE_ADMIN
RESTAURANT_OWNER → ROLE_MANAGER     ("SELLER" = RESTAURANT_OWNER = ROLE_MANAGER)
USER          → ROLE_USER
```

V2 1단계는 이 3역할을 그대로 잇는다. 역할을 권한(permission) 집합으로 분해하는 것은 멀티테넌트·세분 권한 요구가 실제로 나온 뒤의 일이다(아래 🌱).

## 2. command 측 — 소유권을 애그리거트 불변식으로

USER가 예약 취소 command를 보낸다. 소유권 검사("예약은 그 주인만 취소할 수 있다")는 **애그리거트의 불변식**으로, 도메인 안에 둔다. 이건 보안 규칙이 아니라 *도메인 규칙* — 취소라는 상태 전이의 정당성 조건의 일부다. 핸들러에 두면 도메인이 "누구나 취소 가능"한 빈약 모델로 새고, V2가 탈피하려는 빈약 도메인([[02-write-model]] "애그리거트 책임")으로 되돌아간다.

```
게이트웨이/인증 → 검증된 주체 클레임 확정
   → command 핸들러: 클레임의 신원을 command 메타로 애그리거트에 전달
      → 애그리거트: 자기 상태(주인 userId)와 대조 → 전이 허용/거부
         → 거부 = 도메인 예외 → [[12-api-contract]] 에러 분류에 매핑
```

**결정적 원칙 — 신원은 검증된 클레임만 믿는다.** 핸들러가 애그리거트에 넘기는 신원은 *클라이언트가 보낸 페이로드가 아니라 토큰에서 나온 검증된 값*이어야 한다. command 바디의 자칭 신원("내 userId는 X")은 무시하거나, 검증된 클레임과의 일치를 강제한다. 그렇지 않으면 누구나 남의 자원에 대한 command를 위조한다.

역할만으로 충분한 행위(예: ADMIN의 전역 강제 취소)는 소유권 검사를 우회해야 한다. 그래서 애그리거트의 소유권 불변식은 **"주인 본인 OR 충분 권한 역할"** 형태가 된다(둘 중 어느 표현을 도메인에 들일지는 §Design).

## 3. query 측 — 스코프를 쿼리 조건으로

SELLER가 자기 식당 예약 목록을 연다. 조회는 command를 거치지 않고 프로젝션을 직접 읽으므로([[03-read-model]] "읽기는 항상 query 측") 애그리거트 불변식이 작동하지 않는다 — 조회엔 애그리거트가 없다.

스코프는 **쿼리 자체에 주체 조건으로 박는다**(`WHERE owner_id = :subject`). 사후 필터링(받아온 목록에서 남의 것 빼기)은 두 가지로 위험하다.

- **페이징이 깨진다** — 남의 것 100건을 받아 90건을 버리면 페이지 크기가 망가진다.
- **전량 유출 위험** — 사후 필터 한 줄을 빠뜨리면 막을 자리가 없다.

쿼리 조건이면 "내 것만"이 쿼리의 구조적 일부라 빠뜨릴 자리가 없고 페이징도 자연히 맞는다. 스코프 키(SELLER의 식당 식별자·ownerId)는 query 측 application 레이어가 **검증된 클레임에서** 받아 조건으로 내린다 — 여기서도 클라이언트 파라미터(`?ownerId=남`)가 아니라 클레임에서 나온다.

## 4. 프로젝션이 스코프 키를 1급 컬럼으로 들어야 한다

§3의 `WHERE owner_id = :subject`가 성립하려면 **프로젝션이 스코프 키를 컬럼으로 들고 있어야** 한다. `reservation` 목록 프로젝션이 `owner_id`(예약자)·`restaurant_owner_id`(식당 주인) 같은 키가 없으면 거를 게 없다. 그래서 인가는 조회 시점에서 끝나지 않고 **프로젝션 설계로 거슬러 올라간다** — 프로젝터가 이벤트를 투영할 때 인가용 스코프 키를 함께 비정규화해 심는다.

이는 [[03-read-model]]의 비정규화 원칙(식당명을 예약 프로젝션에 박기)과 같은 결이되, 비정규화 대상이 표시용 데이터가 아니라 *인가용 스코프 키*다. 인가에 쓰이는 키는 프로젝터가 **반드시** 채우도록 강제한다([[14.testing-strategy]] 레이어에 얹을지는 §Design).

**소유권이 바뀌는 경우(예: 식당 양도)** 는 [[RFC-002-read-model-consistency]]의 결과적 일관성과 부딪친다. 소유권 이전을 **도메인 이벤트로 모델링**하고, 그 이벤트가 프로젝션 스코프 키를 갱신하게 한다 — 소유권 변경은 보안 패치가 아니라 도메인 사실이니 이벤트로 흐르는 게 맞다. 양도 직후의 좁은 일관성 창("옛 주인이 잠깐 더 본다")을 어느 자원까지 허용하는지는 자원 민감도별 분류에 따른다(§Design).

## 5. 신원·역할의 전파 — 컨텍스트 횡단 동기 조회를 만들지 않는다

`user`·`authenticate`는 ES가 아니라 **상태 테이블 + Outbox**다([[02-write-model]]). 즉 "이 주체가 누구·무슨 역할인가"의 진실은 이벤트 스트림이 아니라 상태 테이블에 있다. 그런데 인가는 `reservation` 같은 다른 컨텍스트의 핸들러·프로젝터에서 필요하다. 매번 `user` 테이블을 동기 조회하면 컨텍스트 간 동기 결합 — V2가 피하려는 모놀리식 결합으로 되돌아간다.

그래서 분담을 못 박는다.

- **역할(누구냐의 속성) = 클레임으로 전파(컨텍스트 횡단).** 게이트웨이/인증이 토큰에서 확정한 신원·역할이 command 메타에 실리고, [[02-write-model]] 공통 발행 경로에서 추적 메타(`correlationId` 등)를 채우는 바로 그 자리에서 봉투에 함께 직렬화된다. 다운스트림은 `user` 컨텍스트를 호출하지 않고 봉투에서 읽는다.
- **소유권 = 자기 컨텍스트의 이벤트/상태에서(컨텍스트 내부).** "이 예약의 주인"은 `reservation` 생성 이벤트에 박혀 있으니 애그리거트도 프로젝션도 자기 안에서 안다. 소유권은 컨텍스트를 건너오지 않는다.

클레임의 역할은 **토큰 발급 시점의 스냅샷**으로 둔다 — 발급 후 권한이 강등되면 한 토큰 수명만큼 stale할 수 있다. 그 즉시성 요구가 실제로 빡빡하면 인증 토큰 정책(인프라 백로그 T-13)의 문제로 넘어간다.

## Design / 후속으로 넘기는 것

- 역할 게이트(엣지)와 소유권 검사(앱)의 **이중화(defense-in-depth)** 여부 및 엣지 역할 술어의 경로 매핑 — 배포 토폴로지([[09-deployment-runtime]]) 확정과 함께.
- 애그리거트 소유권 불변식 **"주인 본인 OR 충분 권한 역할"** 에서 도메인이 보안 역할 어휘를 직접 알지, 핸들러가 권한 우회를 판정해 플래그로 넘길지의 경계.
- query 측 스코프 술어가 역할별로 갈리는 방식 — 쿼리 빌더의 역할 분기 vs 역할별 분리 쿼리 핸들러; USER/SELLER/ADMIN 스코프 폭 정의.
- 컨텍스트별 프로젝션 **스코프 키 컬럼 목록**과 프로젝터가 빠짐없이 채우게 강제하는 규칙([[14.testing-strategy]] ArchUnit/Konsist 레이어).
- 소유권 변경 이벤트 모델링 + 프로젝션 스코프 키 갱신 경로, 일관성 창에서 옛 주인 노출의 자원별 허용 범위([[RFC-002-read-model-consistency]] 종속).
- 어떤 자원이 query 측 프로젝션 인가로 충분하고, 어떤 자원이 command 측 권위 상태 재확인을 요구하는지의 **민감도 분류**.
- command/이벤트 봉투의 인가 클레임 직렬화 표현 + 검증된 클레임 ↔ 자칭 신원 불일치 처리 규칙.
- 🌱 V2 역할 체계 재검토 — {ROOT, RESTAURANT_OWNER, USER} 3역할 유지 vs permission 집합 분해. 도메인·제품 요구가 잡힌 뒤 ADR로 비준.
